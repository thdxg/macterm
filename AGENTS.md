# Macterm Codebase Guide

A macOS terminal emulator built with SwiftUI and libghostty: a project-based sidebar, split panes, persistent zmx sessions, remote (ssh) projects, a quick-terminal overlay, desktop widgets, a control CLI, and — since #353 — any number of windows onto one shared model.

This file is the map: what exists, how it fits together, and the rules that were earned the hard way. Each rule is stated without its backstory; the reasoning lives in the doc comment on the symbol named, the PR that introduced it, and this file's own git history (the pre-2026-09 revision carried the full narratives). When you change a rule, change its doc comment too.

## Build & Run

```bash
mise install          # Install tools (gh, swiftformat, swiftlint, xcodegen, xcbeautify)
mise run setup        # Download pre-built GhosttyKit.xcframework + ghostty resources + zmx
mise run run          # Build and launch (debug)
mise run logs         # Stream live logs from the debug app (--release for release app)
mise run format       # Auto-fix formatting with swiftformat
mise run lint         # swiftlint
mise run test         # Run the unit test suite
mise run e2e          # Debug build + end-to-end suite against the real app
mise run bench        # Release build + resource benchmark
mise run build        # Release build + DMG
mise run install      # Copy the built app to /Applications
```

`format`, `lint`, `test`, `e2e` and `bench` show a spinner and print output only on failure. **Always pass `--verbose`** (`mise run test --verbose`) to stream the raw output.

Requires macOS 14+, Swift 6.0+. Liquid glass and some chrome refinements are macOS 26 (Tahoe) features gated behind `#available` / `WindowAppearance.glassSupported`.

### The terminal core

- **"libghostty" here means `ghostty-internal`**, which upstream marks "not for external use". `libghostty-vt` (the public library) has no surface API, so it is not a fallback. Treat every `ghostty_*` symbol as able to change without notice: pin, probe, and diff rather than assume.
- `GhosttyKit.xcframework`, `Macterm/Resources/{ghostty,terminfo}` and the bundled `zmx` are gitignored artifacts from the `thdxg/ghostty` and `thdxg/zmx` forks. **Every fresh checkout — including a git worktree — must run `mise run setup`.** Never symlink them from another checkout; setup's presence check would then never refresh them.
- Both fork releases are **pinned** (`GHOSTTYKIT_TAG`, `ZMX_TAG` in `scripts/setup.sh`) and recorded in gitignored `.ghosttykit-tag` / `.zmx-tag` stamps. Bumping a pin is its own reviewable commit; a weekly auto-PR (`.github/workflows/bump-ghosttykit.yml`, needs the `GH_PAT` secret so CI runs on it) does it for GhosttyKit and attaches an API review from `scripts/ghosttykit-api-diff.sh` — read the "renumbered enum constants" section of that report, since Swift imports enum constants by name and a mid-enum insert compiles silently. `.github/workflows/bump-zmx.yml` does the same for zmx, with the downstream patches that changed in place of an API review; nothing compiles against zmx, so End-to-end is that PR's real gate.
- A pinned tag is **not immutable**: the fork has re-uploaded assets under the same tag. When a build behaves differently from an identical commit, compare `GhosttyKit.xcframework/*/Headers/ghostty.h` sizes before suspecting your own change. CI's DerivedData caches key on that header's hash for the same reason — don't collapse the restore/save split in `test.yml` or add a framework-agnostic `restore-keys` fallback.
- Setup requires the `GHOSTTY_ACTION_OUTPUT_ACTIVITY` ABI (the tab-activity heartbeat). Bisecting to before that requirement means installing a contemporary GhosttyKit by hand, not running setup.
- A stale-looking tree (stamp disagrees with reality) is cured with `rm -rf GhosttyKit.xcframework Macterm/Resources/terminfo && mise run setup`.

## Architecture

```
MactermApp (SwiftUI @main)
  └─ WindowGroup                       one scene, N windows (#353)
       └─ MainWindow  ── WindowState   per window: project, tab per project, sidebar, sheets
            ├─ SidebarContent          List with native selection
            └─ WorkspaceView
                 └─ SplitTreeView      recursive
                      └─ TerminalPane
                           └─ TerminalSurface (NSViewRepresentable)
                                └─ GhosttyTerminalNSView   owned by Pane, not SwiftUI
```

### Pane-owned NSView

`GhosttyTerminalNSView` is owned by its `Pane`. `TerminalSurface.makeNSView` returns `pane.ensureNSView()`, a cached instance living as long as the `Pane`; `dismantleNSView` is a no-op and the view dies only via `pane.destroySurface()`. Ghostty surfaces are welded to their `NSView` + `CAMetalLayer`, so a SwiftUI recreation on a tree reshape or tab switch would kill the surface. `SurfaceIncubator` is a permanently invisible window that gives off-screen panes a sized window so `createSurface()` can succeed early.

### State

- **`AppState`** — the single `@Observable` root, passed via `.environment()`. Every workspace/tab/pane/window mutation goes through it. `WorkspaceStore` is injectable for tests.
- **`ProjectStore`** — the project list (`projects.json`), persisted independently.
- **`Workspace`** — per-project tab collection, `AppState.workspaces[projectID]`. The pinned tabs are a sentinel workspace (see Pinned Tabs).
- **`TerminalTab`** — a `SplitNode` tree plus focused/zoomed pane IDs. **`SplitNode`** is `.pane(Pane)` or `.split(SplitBranch)`.
- **`WindowState`** (`Macterm/App/WindowState.swift`) — one per window: the project it shows, its tab per project (`activeTabIDs`), sidebar width/visibility, palette and sheet flags. Persisted as `WindowSnapshot`.
- **`Preferences`** — observable UserDefaults wrapper. Never touch `UserDefaults.standard` in app code; `Preferences.defaults` resolves to a wiped side suite under tests.

### Windows (#345, #353)

The rules that make multiple windows work over one model:

- **Registry keyed by `NSWindow`** (`AppState.windows`, a weak-keyed `NSMapTable`). SwiftUI instantiates a view and its `@State` more than once per real window, so the view cannot own identity; the first `WindowState` proposed for an `NSWindow` wins (`canonicalWindowState`). Register at NSWindow attachment, never in `onAppear`. Never stamp the SwiftUI window identifier.
- **One teardown entry**: `AppState.windowDidClose` clears every per-window table. A new per-window table must hang off it and be weak-keyed by the window (never by `ObjectIdentifier`, whose address gets reused).
- **App-wide values mirror the key window.** `AppState.activeProjectID`, `Workspace.activeTabID`, `sidebarVisible`, `isCommandPaletteVisible` etc. are pushed from/into the key window's `WindowState` by `noteKeyWindow`. Anything *rendered* per window must read `WindowState`, never the mirror. Something that happens *to* a project (notification click, CLI `pane focus`) goes through `revealProject`, which fronts a window already showing it.
- **A tab's real panes render in one window; other windows on that tab render a mirror.** `tabOwners` is sticky (settled by `reconcileWindowViews`); a non-owner gets a *shadow* tab of `Pane(mirroring:)` panes attached to the same zmx sessions, rebuilt when the real tab's `shapeSignature` changes. `WorkspaceView` maps a mirror's focus/zoom/split/click onto the real tab by tree position (`counterpartPaneID`). The pinned workspace has **no per-window tab selection** — every path that consults `activeTabIDs` skips the sentinel.
- **Session leadership.** Only one zmx client is leader (its size drives the pty); others render dimmed. `AppState.sessionLeaders` tracks it and an APC claim (`ZmxLeadership.claimSequence`, a wire contract with the zmx fork) tells zmx. Leadership follows the key window's tab whole (`claimLeadershipForKeyWindow`); records are re-asserted, never trusted; the claim is sent only when leadership moves, synchronously, recorded only if delivered, and never on focus for remote panes. A non-key window whose tab is entirely non-leader renders `MirroredTabNotice` instead of panes; the key window always renders its panes. First-responder restore after that goes through `FocusRestoration.restoreFocusWhenAttached`, which resolves the window from the pane's own view.
- **Closing and quitting.** Only the **last visible** terminal window hides on close (`AppDelegate.hidesInsteadOfClosing`); every other window really closes. Quit freezes the window list (`unregisterWindow` is a no-op under `AppTerminationState.isTerminating`), or each closing window would re-save a snapshot with one window fewer. `restoreWindows` gives the scene's own window the first saved entry and opens the rest via `applicationOpenUntitledFile`, fronting the saved key window last.
- **"Is this the terminal window?" is `AppDelegate.isTerminalWindowCandidate`**, not `!(window is NSPanel)`. It excludes marker subclasses (`QuickTerminalPanel`, `SurfaceIncubatorWindow`). Route any new auxiliary window through it; it is a heuristic used only before `didBecomeMain` has cached the real pointer.
- **A window opened from the quick terminal while the app is inactive gets activated for** (`QuickTerminalService.panelDidResignKey` → `AppDelegate.activateForKeyHandoff`). The non-activating panel takes keys while another app is frontmost, so ⌘, or ⌘N typed into it makes Settings or a new window key inside an inactive app: dimmed and untypable. The handoff is watched for one run-loop turn (the new window becomes key synchronously as the panel resigns), forced with `ignoringOtherApps: true`, and that one activation skips `reopenIfNeeded`, or a hidden terminal window is re-fronted over the window the keystroke asked for.
- **A launch that doesn't front the app builds no window (#241)** — how macOS relaunches apps at login. `AppDelegate.repairMissingWindow` polls ~3s and, only if no candidate window exists, calls `applicationOpenUntitledFile` (activation alone does nothing). Gated on "no window at all" and debounced via `requestInitialWindow`, or one launch opens two windows.
- `AppDelegate.reopenIfNeeded` (Dock-click re-front) uses an `NSWorkspace.didActivateApplicationNotification` observer, since `applicationShouldHandleReopen` is unreliable through `@NSApplicationDelegateAdaptor`. Observers installed in `didFinishLaunching` miss launch-time window notifications — `didBecomeMain` can fire before it on Dock/Finder launches.
- **Full screen is native, and fn+F belongs to AppKit.** ghostty's `toggle_fullscreen` (⌃⌘F and ⌘↩ by default) toggles the pane's own window through `toggleFullScreen(_:)` (`GhosttyCallbacks`), the same path as AppKit's automatic Enter Full Screen menu item, which is what carries macOS's fn+F. Leave that item alone — don't set `NSFullScreenMenuItemEverywhere` to false or change its shortcut: Ghostty.app lost fn+F by rewriting its full-screen item's shortcut (ghostty-org/ghostty#1389). `macos-non-native-fullscreen` isn't honored, and the quick terminal's panel can't go full screen.

### Hotkeys

`HotkeyAction` + `HotkeyRegistry` hold the bindings (defaults in `Hotkeys.swift`, overrides at `macterm.hotkey.<action_id>`). `KeyRouter` installs one `NSEvent.addLocalMonitorForEvents` and dispatches through the ordered `KeyResponder` chain in `Responders.swift`; `isAppShortcut` in `GhosttyTerminalNSView` lets registered shortcuts pass the terminal.

**Passthrough (#209)**: a per-action opt-in (`.passthrough` suffix) hands the chord to the program in the focused pane when that program's name is in `Preferences.passthroughPrograms`. `KeybindPassthrough` owns the policy; both key paths (the responders *and* `isAppShortcut`) consult it; remote panes never yield. Inferring the condition (tty raw mode, "not a shell") was tried twice and failed — see the type's doc comment before re-attempting.

**Global keybinds**: a per-action opt-in (`.global` suffix, a Settings → Keymaps column beside passthrough) registers the chord as a Carbon `RegisterEventHotKey`, so it fires while another app is frontmost — Ghostty's `global:` prefix. `GlobalHotkeys` owns every registration in the process, the quick terminal's included (`HotkeyAction.isAlwaysGlobal`); `sync` reconciles it after each rebind and flag change, leaving an unchanged chord alone. Carbon, not a CGEvent tap: no Accessibility grant, and the system reports a chord it won't give us (`eventHotKeyExistsErr` → the row says so, rather than a chord that silently does nothing anywhere). **One owner:** Carbon consumes a registered hot key, so the local monitor never sees that keyDown — `KeyRouter` yields exactly the chords Carbon *holds* (`yieldsToCarbon`), which both states the no-double-fire rule and leaves a *refused* chord working as a plain local keybind. Consequences, both deliberate: a global chord always runs its app-level `AppCommand` (so it no longer reaches the quick-terminal responder's own splits), and global + passthrough on one action is refused rather than silently defeating passthrough. A fired chord fronts a window first (`AppDelegate.showWindow`) unless it is the quick-terminal toggle, whose panel is non-activating.

**Non-Latin layouts**: a ⌘ chord on a key that types no ASCII (Cyrillic, Greek, Hebrew, Arabic…) is named by the layout's Command key map — `HotkeyRegistry.commandKeyCharacter`, the QWERTY Latin letter those layouts type under ⌘ — and that one name serves all three matchers: Macterm's bindings (`eventToken`), `isAppShortcut`'s system-key carve-out (⌘Q/⌘H/⌘M/⌘,), and libghostty, which `performKeyEquivalent` hands it as the key's text. libghostty resolves a unicode binding like `super+c` from the text before the unshifted codepoint, which under a Cyrillic layout is `с`, so without the text ⌘C/⌘V matched nothing. The three must agree, or ghostty's raw default bindings (`super+q=quit`, `super+w=close_surface`) take chords Macterm or the menu bar owns. A key that types ASCII keeps its own character — Dvorak, AZERTY and every other Latin layout are untouched.

### Tab naming and activity

- A tab's auto-title is the foreground process name (`ProcessInspector.runningProcessName`, kernel `comm`), falling back to the login shell (from `getpwuid`), overridden by `customTitle`. There is no switch for this (`macterm.tabs.autoName` is a retired key); polling also serves busy-close and execution tracking.
- `AppState` polls adaptively (`PollCadence` + `refreshAllForegroundProcesses`): 250ms burst after any `.terminalPollEvent`, 1s active-idle, 2s inactive, stopped when nothing is on screen.
- **The `GHOSTTY_ACTION_OUTPUT_ACTIVITY` heartbeat is the sole activity source** (it fires while occluded; the render-path scrollbar action does not). Completion edges (OSC 133;D, foreground transitions) rebase the row baseline so a fast command's late heartbeat never restarts it as activity. `TerminalExecutionTracker` holds the rules for when non-growing output counts as work (AI-agent foregrounds after a real Return).
- **An OSC 9;4 progress ERROR ends the run as a failure**, and the tab's done dot turns red (`MactermTheme.failure`, palette 1; tooltip "Failed"). The outcome is `Pane.completionFailed`, a flag that means something only while `.done`: it is cleared in `executionState`'s `didSet` whenever the state leaves `.done`, so every acknowledgement path clears red exactly as it clears green, and it is set *before* `.done` publishes, because the poll that publish wakes synchronously can save or acknowledge on the spot. Never a fourth `TerminalExecutionState` — the tracker's guards compare against `.done`. REMOVE and PAUSE end a run as a success, and a report that finds the pane not `.running` is dropped, which is why SET → ERROR → REMOVE stays red. Within a tab, running > failed > done. It persists as `PaneSnapshot.completionFailed` beside `needsAttention`, never in place of it. The CLI's `state` stays `done`, and the percentage is never shown.
- OSC 0/2 titles are **provenance-gated** (`Pane.receiveReportedTitle`): adopted as `programTitle` only while the foreground is a real program, pinned to that pid, expired when it loses the foreground. Prompt-time titles (nushell, Starship) are discarded. Titles are never persisted.
- **A title report is throttled before it costs anything** (`TitleReportThrottle`, one per pane, pure and tested). The provenance lookup plus the foreground refresh a title triggers are ~100µs of syscalls (`KERN_PROCARGS2` ×3, `open` + `tcgetattr` on the tty), and a zmx session replaying prompt-heavy scrollback at launch reports one title per prompt — 150k of them froze the main thread for 14s with the control socket unanswered. The first title after a quiet window (`PollCadence.fastInterval`, 250ms) is evaluated at once; the rest of the window's titles are held, newest wins, and flushed once at the window's end — nothing dropped, at most 250ms late, judged against the foreground holding the pane then, which is what the poll's next tick would have seen anyway. `receiveReportedTitle(_:programPID:)` is the unthrottled core the tests drive; `destroySurface` cancels a pending flush and resets the window.
- **Remote panes** have no local pid. Their name comes from OSC titles (`Pane.receiveRemoteReportedTitle`) plus `RemoteForegroundResolver` — one BatchMode ssh per host per ~3s (frontmost project, plus any pane with a boundary request or a title awaiting confirmation) running the POSIX probe in `RemoteSpawn.foregroundProbeScript`, which also returns the host's own idle and shell (`/etc/shells`) verdicts and the foreground command line (the agent logo's argv fallback, as `KERN_PROCARGS2` is locally, and the name of a version-named `comm`). A title that arrives while the pane is running (OSC 133, activity, progress) is shown at once; one at a prompt OSC 133;D announced is discarded; **any other title is held until a probe sent after it sees a program in front** (`RemoteTitleConfirmation`), which is how an agent idling between turns keeps its title. The probe's sample lags the host by a round trip, so never trust the sample alone: when an agent quits, the shell's prompt title arrives while it still says the agent. A run's title that outlives the run stays up, unconfirmed, until the probe the run end requests (no flicker between turns), whatever the last sample said; OSC 133;D, a shell answer, an unanswerable probe (unreachable, auth refused, session missing, Background SSH off) or teardown takes it down. The revision recorded at dispatch (`consumeRemoteProbeRequest`), not a timestamp, decides which answers count: `ForegroundSample.sampledAt` is first-seen. Every new held title voids the probe in flight — never let a second one skip that, or a probe sent while the program ran vouches for the shell title that replaced it. A waiting title re-wakes the poll (`Pane.defaultRemoteTitleRetryDelay`, bounded), since with every window hidden the poll is paused. Both pipelines publish one value, `Pane.foregroundSample`; policies like `ForegroundPolicy.needsConfirmClose` are pure functions over it. Every busy-close guard reads `Pane.needsConfirmClose`, never libghostty's `needsConfirmQuit` directly (for a remote pane that only sees the `ssh` client).
- The whole remote probe pipeline sits behind `Preferences.backgroundSSHConnections` (Settings → General → Remote Projects), the kill switch for Touch ID-gated hosts (#272). An auth-refused probe suspends that host's probes for the run.
- **`bell-features = attention` has two halves.** `GHOSTTY_ACTION_RING_BELL` handles the app-level ones (beep, `bell-audio-path`, `NSApp.requestUserAttention`) in `GhosttyCallbacks.ringBell` and additionally flags the ringing pane (`Pane.ringBell`); `title`/`border` are per-tab UI Macterm doesn't implement. The Dock badge is the second half: `BellBadge.label` is the pure count → label rule (nil without `attention` or with nothing ringing, capped `99+`) and `BellBadge.apply` is the one AppKit write, glued by `AppState.syncDockBadge`. It counts **tabs**, not ghostty's windows — a tab is what the user goes and looks at — and is DERIVED, never written from the ring, which is what lets a config reload dropping `attention` clear a badge already up with no code path that knows about clearing. Acknowledgment follows Macterm's existing "looking at the active tab" verdict rather than ghostty's next-keypress rule, so the badge can't disagree with the sidebar: a bell in the active tab of the active app is seen the instant it rings, and everything else clears the way the completion dot does (tab selection, pane focus or interaction, the app coming forward, surface teardown). Each flag flip posts `.terminalBellStateDidChange`, so clearing re-derives for free.

### Password prompts (Settings → Passwords)

A pane asking for a password gets a native `NSPopover` at the cursor (`PasswordBubble`): **Autofill** when a password is saved for that prompt, **Save Password?** once one the user typed has worked. All of it is `PasswordPromptMonitor` (`Macterm/App/`); the pure rules are in `Macterm/Model/PasswordPrompt.swift`.

- **Detection is the tty, not the screen**: canonical mode with echo off (`ProcessInspector.terminalIsReadingPassword`) — ghostty's and iTerm2's rule. It reads the **zmx session's** tty (`ZmxForegroundResolver.daemonTTYPath`), because libghostty's own check sees the `zmx attach` client's pty, which `cfmakeraw` keeps raw forever: under zmx `GHOSTTY_ACTION_SECURE_INPUT` never fires. The same reading now drives `macos-auto-secure-input` (`GhosttyTerminalNSView.detectedPasswordInput`, OR'd with libghostty's `passwordInput`); its per-pane lock badge is off by default (`macos-secure-input-indication = false` in the defaults layer) because the bubble marks the prompt. Read on the pane's output heartbeat (`viewDidOutput` — a prompt is output), on every key typed into the pane (`viewDidType`, reported by `keyDown` **at the send point, as the text the tty receives** — the IME's committed text, nothing during a composition, nothing legible for an option-as-alt chord, and never a chord `isAppShortcut` or the ⌃\ swallow ate — so a program on the surface's own pty, a remote project's ssh, has already ended its read when the Return is reported, and a line end is credited to the prompt that was up when it went out), and on a timer: 1s with tolerance for the focused pane while idle, 150ms only while some pane is in a *timed* phase (`sighted`, `verifying`); a pane parked at a prompt or an unanswered offer costs the slow cadence only. `pane run`/`pane key` feed the same capture (`viewDidSendText`/`viewDidSendKey`), which is how the e2e suite answers prompts; the monitor's own autofill typing is fenced off (`isInjecting`). Everything the monitor reads or drives goes through `PasswordPromptMonitor.Probes`, so `PasswordPromptMonitorStateTests` runs the whole machine without a surface. A sighting must hold 200ms (a script dropping echo to read a terminal reply is not a prompt) unless the user types at it. Prompts on a remote host *inside* ssh are invisible (the local ssh client is raw) — a remote project's own ssh login is not, since its surface pty is where ssh asks.
- **Identity is command + prompt line** (`PasswordEntryID`): the foreground command named by its **executable's real path** (`ProcessInspector.passwordAsker`: `proc_pidpath` + argv minus argv[0]) plus the last non-empty viewport line. Never argv[0] — a process sets that for itself, and `exec -a ssh ./fake prod` would collect the password saved for the real ssh. `runningCommand` (layout `run:` capture) stays argv-based and untouched. The prompt line is what separates `ssh -J bastion prod`'s two passwords. Exceptions: `sudo …` files under `sudo` (one login password), key passphrases under the prompt alone, a remote project's pane under `ssh user@host`. **Those two shared entries answer only a program the user can't have replaced** (`PasswordAsker.isProtected`, `ProcessInspector.isProtectedExecutable`: the executable and every directory above it root-owned and not writable by us — true of `/usr/bin`, false of Homebrew and `~`). Anything else named `sudo` files under its own full command, and a passphrase asked by a replaceable program under that program's path; otherwise a `~/bin/sudo` earlier on PATH printing `Password:` would be autofilled with the login password. A shell *running a script* is a program to `passwordAsker` (`isIdleShellInvocation`), so a prompt inside `./deploy.sh` is filed under `/bin/sh ./deploy.sh`; the idle shell itself (`read -s`) is `.shell`, filed by prompt alone; an unreadable foreground is `.unknown`, never `.shell` — the prompt stays `sighted` and is retried, and a key typed meanwhile taints the capture (`confirmTyping`). Display shortens a resolved program path to its name and drops the options Macterm's own ssh wrapper injected (`SSHWrapper.userArguments`) — except a `sudo`-named program, which keeps its path so it can't pass for the real one; matching never shortens. The Details editor files through `declaredEntryID`, which trusts what the user typed. **`Preferences.passwordManagerEnabled` is the master switch** (stored under the old "Offer to save" key, so an old off stays off): off, `step` drops the pane to idle with its offers every observation — nothing captured, offered or autofilled — while `detectedPasswordInput` still follows the tty.
- **Save is offered only on evidence** (`PasswordSubmissionJudge`): a failure line within `failureWindow` (3) lines of the prompt fails; a prompt up again past the settle window, an OSC 133 exit of **any** code, non-failure output, or the tty leaving line mode (`ICANON` off — all a remote project's login ever shows, since zmx then repaints the screen from the top and nothing is drawn below the prompt) succeeds; silence past 12s saves nothing. Two things are deliberately not rejections: the exit code (it judges the command — `sudo grep -q` exits 1 with the password accepted) and the identical prompt again without a failure line (git over HTTPS asks once per connection). Typed keys go through `PasswordLineCapture` (DEL/⌃H, ⌃U, ⌃W; arrows/escape taint it), fed from `keyDown` before libghostty and from `surfaceDidPasteText`. Offers queue (`ssh -J` yields two), show one at a time once no prompt is up, expire after `offerLifetime` (15 min), and are dropped only by a command *the pane's own shell* runs (`foregroundProcessIsShell`; a bare Return keeps them, and so does anything typed into ssh's remote shell). A keychain write that fails keeps the offer up with the error (`Offer.problem`) instead of losing the secret. A keystroke at a prompt while a submission is still `verifying` settles the verdict on the spot (`settle`), so a fast retype after a rejection isn't captured minus its first characters. Failure lines count only within `failureWindow` (3) lines of the prompt — a MOTD saying "denied" is a successful login. Prompts for one-time codes (`isOneTimeCode`) are never offered.
- **Storage is the login keychain** (`KeychainPasswordStore`, service `<bundle id>.passwords`, metadata as JSON in `kSecAttrGeneric`): the data-protection keychain needs a provisioning-profile entitlement a self-signed app can't have, so Touch ID is the app's gate (`PasswordAuthenticator`, `.deviceOwnerAuthentication`; once per app launch by default — also ended by a screen lock, sleep or user switch, and never persisted, since a lock while Macterm is quit leaves no reliable trace — or every time). Ad-hoc debug builds get a keychain dialog on read. Tests, `MACTERM_BENCHMARK=1` and any `MACTERM_BENCHMARK_DATA_DIR` launch use `InMemoryPasswordStore` (`PasswordVault.isHermetic`), and a **debug** build under that condition skips Touch ID — the only passwords such a run holds are ones it captured itself, and the e2e suite autofills with nobody at the keyboard.
- **Autofill types, never pastes** (`GhosttyTerminalNSView.sendSecret`: the text path minus command-submission evidence, then Return), re-checks the tty after authentication, and clears a half-typed line with ⌃U first. A refused autofill turns the next sighting into "Saved Password Didn't Work", and a typed password that then works is offered as an update.
- **The bubble never keeps key**: `.applicationDefined` behavior, and every button hands key back to the terminal's window (`PasswordBubble.returnKey` — only when the popover or nothing holds key, never from another window of ours). Anchor is `cursorCellRect()` (libghostty's IME point). **Return is the primary button and Escape dismisses, through the terminal's key path** (`viewWillSendKey` consumes them) and only while nothing has been typed since the bubble appeared (`Tracker.typedSinceBubble`, reset when `PasswordBubble.show` reports new *content*, not a re-anchor after the cursor scrolled away and back) — the first character hands both keys back, so a password or command typed under the bubble submits normally. No key hints are drawn. A parked AeroSpace window (off-screen) makes AppKit push the popover onto the visible screen — not an anchoring bug.
- **On demand (`PasswordPaletteScope`, the palette's Password Manager)** types any saved entry the user picks into the active tab's focused pane (`PasswordPromptMonitor.fillOnDemand`), no prompt match and **no confirmation** — the pick is the authorization (Touch ID still gates the read). The tty decides only Return (`OnDemandPasswordFill` over `TerminalLineMode`): a verified read (canonical, echo off) gets ⌃U first and Return and is judged as an autofill, its `Submission.id` the *picked* entry so a rejection marks that entry and nothing typed is offered for saving; anywhere else — ssh or tmux relaying a remote prompt (remote `sudo`, the reason this exists), a shell's line editor, an echoing line — the password is typed with no Return, so a wrong pick never runs or reaches a history and the user submits or deletes it. A verified read gone after authentication types nothing. **An entry with an empty prompt is on-demand only** (`PasswordEntryID.isOnDemandOnly`): detection never reads an empty prompt line, so nothing ever autofills it; its keychain account is `<command> — on demand`. Entries are added from Settings' `+` or the palette's Add rows, both through `PasswordEditorSheet` (shared with Details…; the palette's copy is presented by `MainWindow` from `WindowState.passwordEditor`), which **requires a command**: prompt-only entries are detection's alone (key passphrases, `read -s`), editable as they are but never created or made by hand.
- **`pane password` (DEBUG only)** reads a pane's phase/prompt/command/bubble — never a secret — and `--answer accept|dismiss|autofill` presses the bubble's buttons; `e2e/test_passwords.py` drives the whole flow with it against a `stty -echo; read` script.
- **Never** a CLI verb, App Intent or log line that carries a secret — any process in a pane can call `macterm`. Autofill Password is an `AppCommand` (default ⌥⌘F) whose action is nil unless the focused pane is at a saved prompt; like every nil-action chord, `isAppShortcut` then swallows it in `keyDown`, so it does nothing rather than reaching libghostty (which has no default on `super+alt+f`).

### Tab switcher previews (#344)

Holding the Recent Tab chord shows `TabSwitcherOverlay`: one card per tab in the cycle (`AppState.tabCycleOrder`, bounded by `Preferences.recentTabCandidates`), each a mosaic of `PanePreview`s. Cards are **live**: `beginLivePreviews` sets `GhosttyTerminalNSView.rendersForPreview` so `syncOcclusion` reports the pane visible and libghostty wakes its renderer; sampled at 5 Hz until `commitTabCycle` runs `endLivePreviews` (every exit from a cycle goes through it, so no renderer stays awake). `PanePreview.frameID` skips re-sampling a pane whose IOSurface hasn't changed and the thumbnail is drawn through a no-copy provider — that is what keeps a hold at ~7% CPU instead of 30%. Hover never scrolls the rows (`HoverSelectionTracker`, shared with the palette). Don't reintroduce a foreground copy-poll or a text stand-in renderer; both were removed once off-screen panes could be sampled.

### Remote Projects (#104)

A project whose `path` is an scp-style `[user@]host:dir` (parsed by `ProjectPath`). Each pane is a persistent zmx session **on the host**: the surface command is `ssh -t host 'sh -c '\''…'\'''` (`RemoteSpawn.paneCommand`), no local zmx wrapper. Quit detaches; relaunch reattaches by persisted `sessionName`. The pane's ssh is interactive (prompts render in the pane); background ops use `BatchMode=yes -o ConnectTimeout=5`, exec PATH-resolved `ssh` via `/usr/bin/env` (same client as the pane), and kill through `ZmxClient.killRemoteSession`.

Rules for the spawn script, each earned against a real host:

- **Depend only on inputs Macterm controls** — never source `/etc/profile` or `~/.profile` in any form (a `~/.profile` ending in `exec zsh` hijacked the pane three different ways). The user's environment takes effect inside the zmx session, where their login shell starts normally. `remote_scripts_never_source_profiles` enforces this.
- Ship as `sh -c '<single-quote-free script>'` — `sh -c`, not `sh -lc` (dash rejects `-l`). Append a fallback PATH (`~/bin`, `~/.local/bin`, `~/.cargo/bin`, `/usr/local/bin`, `/opt/homebrew/bin`); `Project.zmxPath` bypasses PATH entirely.
- On failure (no zmx, `cd` fails) print a `macterm:` diagnostic and drop to `${SHELL:-/bin/sh}` — a bare exit fires `closeSurface` and the pane vanishes without a clue.
- **TERM is settled host-side and a resolvable TERM is never touched**, including one the user pinned coarser via `SetEnv`. Only an unresolvable TERM is replaced (`xterm-ghostty` if the host has it, else `xterm-256color`). The script exports `COLORTERM=truecolor`, `TERM_PROGRAM=ghostty` and libghostty's `TERM_PROGRAM_VERSION` itself because TERM is the only variable ssh carries by a channel a server can't refuse — and programs gate on them: Claude Code sends OSC 9;4 progress (an agent's status dot) only to Ghostty ≥ 1.2.0.
- `RemoteTerminfo` installs our bundled `xterm-ghostty` entry (`infocmp -x | ssh … tic -x -`) off the critical path, gated on the user's own ghostty `ssh-terminfo` flag (default off upstream), never cached to disk, stderr logged on failure only.

**Dropped connections self-heal (#281).** `AppState.reconnectDroppedRemotePanes` respawns a dropped pane's surface in place (`destroySurface` then `requestSurfaceReattach`, never `killPersistentSession`). `AppState.handleProcessExit` classifies a remote exit by asking the host whether the session survived — **never by exit code** (always 0 on macOS). Triggers only (wake, activation, project selection) with `RemoteReconnectPolicy` backoff; no timer, no user-facing reconnect verb. `Pane.ensureNSView` passes `command` only on the first surface build so a respawn never retypes a layout `run:`.

**Remote orphans are reaped by ownership stamp.** `AppState.sweepOrphanSessions` (throttled per host) stamps `macterm.owner=<installationID>` on sessions our panes claim, lists, and kills only zero-client `macterm-*` sessions carrying **our** stamp (`ZmxReaper.orphans`). zmx labels are in-memory and settable only on live sessions, so a session orphaned before stamping is spared forever. `zmx ls --where` is silently unimplemented — never filter host-side. Both reapers skip entirely when `WorkspaceStore.loadFailed`.

### Session daemons and macOS attribution (#419)

macOS attributes privacy-gated work — Local Network, TCC — to a process's *responsible process*, a value fixed at spawn and inherited from the parent. A pane's whole tree was therefore attributed to the Macterm that created its session, and to nothing once that Macterm quit: every survivor becomes responsible for itself, and a relaunch reattaching over the zmx socket never re-attributes it (reattach is a connect, not a fork). From then on each pane program was judged on its own identity, which for anything not Apple-signed meant `EHOSTUNREACH` on the local subnet with no prompt. The fix lives in the zmx fork (downstream patch 0004, `daemonize.zig`): on macOS the session daemon re-execs itself with `POSIX_SPAWN_SETEXEC` + `responsibility_spawnattrs_setdisclaim`, so it is its own responsible process from the first instant and every program in the session is attributed to **it** for the session's whole life, whatever happens to the app.

- **The daemon is signed as the app itself** (`scripts/embed-zmx.sh`: the app's certificate — release cert in CI, ad-hoc locally — *and* the app's bundle identifier). macOS identifies a responsible process by its code signature's identifier, so with Macterm's the daemon resolves to Macterm's name, usage descriptions and existing Local Network / TCC grants: one grant covers the app and every pane. Any other identifier — the release download's linker-signed `zmx`, or a separate "Macterm Sessions" (tried; the prompt just said "zmx", since a bare binary has no LaunchServices record to take a name from) — names a second thing and needs a second grant. Xcode never re-signs a Mach-O it copies into `Resources/`, and an ad-hoc daemon would be a new identity every update. `build.sh` refuses a release bundle whose zmx is ad-hoc or not `com.thdxg.macterm`; `BundledResourcesTests` pins the identifier on the built bundle's zmx so a build-phase edit can't silently turn every pane prompt into one for "zmx".
- Full Disk Access follows the same attribution, so the daemon's programs satisfy the app's own TCC requirement (identifier + certificate) and inherit its FDA grant, consistently, instead of only until the first relaunch.
- Responsibility cannot be changed after the fact (`responsibility_set_*` needs a private entitlement) and the disclaim exists only as a spawn attribute, hence exec-in-place rather than a flag on the fork. The responsible root must *stay* a zmx process: a trampoline that exec'd the shell would keep the pid but the evaluated identity would become the shell's.
- A session created by an older build keeps its old attribution until recreated; the fix takes effect per session.
- Measure with `responsibility_get_pid_responsible_for_pid` (a ten-line C probe). An *unanswered* Local Network prompt denies everything under that responsible process, platform binaries included, so a subnet that looks dead may be a pending dialog.

### Pinned Tabs

Tabs belonging to no project, shown above the projects. They are a **sentinel workspace** (`workspaces[PinnedTabs.projectID]`, a fixed UUID that is not a `ProjectStore` row, so project iteration never sees it). Each is a `PinnedTabRecord`: a durable declaration (`LayoutTab`) plus, while loaded, a live `TerminalTab`. All the logic is in `AppState+PinnedTabs.swift`.

- Pin/Unpin are `moveTab`s, never kills. A tab born in the pinned workspace is pinned by `syncPinnedRecordsWithWorkspace`.
- **Closing a pinned tab is an unload**, never a removal: sessions end, the record stays as a dimmed row, relaunch eager-starts it again. Unpin is the removal path. The same unload happens when a tab's own sessions die (`paneProcessExited`). `unloadProject` uses the same dimmed-row treatment via `AppState.unloadedProjectIDs` (in-memory only; cleared in `activeProjectID`'s `didSet`).
- Persistence is two layers: live state in `workspaces_v3.json`'s `pinned` section, and the declaration in `~/.config/macterm/pinned.yaml` (beside `widgets.yaml`; `ProjectFileStore.configDirectoryURL`, which a test's custom store keeps inside its own directory) — a `ProjectFile` whose reserved `path: <pinned>` is the marker, with no per-entry ids (matched back by name → exact layout → position, `PinnedLayoutMatcher`). `AppState` tracks its own last write and absorbs external edits before every write; an unparseable file suspends auto-writes with an alert. An absent/empty file means "no input", never "remove everything".
- **`pinned.yaml` moved up from `projects/`, and the old place still works.** Launch moves an existing `projects/pinned.yaml` up (`PinnedLayoutStore.migrateLegacyFile`); if it can't be moved, or nothing has moved it yet, every read and write uses it in place (`PinnedLayoutStore.fileURL`), and with both present the new one wins. The project listing still skips the reserved name in `projects/`. Retiring the old location — dropping `legacyDirectoryURL` and the fallback — is #446; until then don't remove either.
- At launch every record materializes (`materializeRestoredPinnedTabs` asks `zmx ls` which sessions survived; dead ones respawn from the declaration). The declaration refreshes at pin time, on pinned foreground changes (debounced), and at quit — never at unload.
- Sidebar drag: pinned rows and tab lists share one ForEach-level `.dropDestination` that drives the native insertion line; rows carry no destinations of their own (a row-level target kills the line and swallows clicks). `PinTabDropZone` above the List is what makes the first pin possible by drag. `--project pinned` addresses the workspace over the CLI.
- **No project may be named `Pinned`** (any case, padding ignored): `ControlHandler.resolveProject` reads it as this workspace before any project, so such a project is unreachable by name. `PinnedTabs.reservesName` is the one test every naming path applies — a typed name is refused where it was typed (CLI `project create --name`/`project rename`, the sidebar rename's notice, the New Project intent, the remote sheet), and a name nobody chose (a folder's own) becomes `Pinned 2` in `ProjectStore.create`; `ProjectStore.rename` refuses it outright. Projects named before the rule keep their names.

### Desktop widgets

Terminals on the desktop (`DesktopWidget`, `AppState+DesktopWidgets.swift`, `DesktopWidgetWindows`, Settings → Widgets): each is one pane whose zmx session persists like a pinned tab's, drawn by a panel of our own shaped like a system widget. User grammar in `website/docs/pages/45-desktop-widgets.md`.

- **Not WidgetKit, and it can't be.** A WidgetKit widget is an archived SwiftUI snapshot rendered by another process: no NSView, no text input, a refresh budget of minutes. And chronod purges the descriptors of any widget extension signed without an Apple team (`Requested to add extension, but purging instead because we shouldn't cache it`), measured with ad-hoc and self-signed builds against a Team-ID control. So widgets never appear in the desktop's Edit Widgets gallery; they are created from Macterm (File menu, palette, Settings' `+`, `widget new`).
- **The metrics are measured, not guessed** (`DesktopWidgetMetrics`, `DesktopWidgetGrid`): chronod logs the host's `CHSWidgetMetricsSpecification` (`log show --predicate 'process == "chronod"'`, entries with `cornerRadius`) — 164/344/704pt edges, a 27.88pt continuous corner. Those edges are all spans of one module (164pt cells, 16pt gaps, a 180pt pitch), so a widget's size is a `DesktopWidgetSpan` — no presets: a new widget is `DesktopWidgetSpan.initial` (3×3), placed at the screen's exact middle (`DesktopWidgetGrid.centered`; off the lattice until its first move or resize, since the lattice cell nearest the middle is up to half a pitch off, and the nearest free default-lattice cell when the middle is taken). **There is no screen-wide grid:** Notification Center stores its widgets as groups, each with its own origin (it logs `Writing desktop widget placement storage to disk: … groups: [{origin: (18.0, 25.0), items: [<col, row, size>…]}]`), so every move and resize ends in `DesktopWidgetGrid.snap` onto the lattice of the nearest widget within a pitch — the system's own included, read from the window list (`NativeDesktopWidgets`: a widget's window is the widget plus 8pt of shadow; the placement file itself is in a protected container). Read EVERY window, not only on-screen ones — Notification Center reports its widgets off screen whenever windows cover the desktop — and accept only real widget windows: the host's, at desktop-icon level + 2, visible alpha, whole cells each way. Notification Center also keeps an untitled alpha-0 window a level below (seen at 464×824 after dragging widgets around); reading it as a widget blocked empty cells and pulled Macterm's widgets onto its lattice — else the screen's default lattice at the corner inset macOS uses (26, 33). Nearest cell and span, kept on screen, moved to the nearest free cell rather than overlapping; system widgets count as occupied. `widgets.yaml`'s `column`/`row` are on the default lattice, and the re-snap after it's applied pulls a widget back onto its neighbour's. Re-measure there when a macOS release looks different.
- **Locked by default; one widget edited at a time.** `AppState.editingDesktopWidgetID` is the single edit slot, in memory only, so every launch comes up locked. Locked, it behaves like a system widget: `canBecomeKey` is false, `DesktopWidgetShieldView` takes every mouse event (the wheel too — over mouse reporting or alternate scroll it is input) and turns a press into a widget drag, and the terminal is handed no focused pane (`focusedPaneID: nil`) — a widget's one pane is always its tab's focused pane, and passing that through showed a solid cursor in every locked widget. Editing: the widget's own edge resize (`DesktopWidgetResize`: the margin's outer 7pt band, 20pt corners, cursors from an `.activeAlways` tracking area) — not AppKit's `.resizable`, whose borderless resize area is a sliver and whose hover cursor never showed — the accent outline and a Done button, and a drag from the margin only — inside the terminal a drag selects. Every drag waits out a 4pt threshold (a click jitter must not move a widget) before `performDrag`, then the release is polled for and the widget snapped. The CLI can still type into a locked widget.
- **An edited widget has no shadow**: a KEY window's shadow and rim are drawn from the window's rectangle, not its alpha, which put a dark square behind the rounded corners (A/B: gone with `hasShadow = false`, unmoved by the style mask or `invalidateShadow`).
- **The panel lives where system widgets do**: level `desktopIconWindow + 1`, `.canJoinAllSpaces`/`.stationary`/`.ignoresCycle`, borderless and `.nonactivatingPanel` (typing into a widget leaves the frontmost app in front; the quick terminal's key handoff is shared via `panelDidResignKey`). It's an `NSPanel`, so `isTerminalWindowCandidate` already excludes it; AeroSpace doesn't manage it. A modal raised from a widget (`DesktopWidgetRemoval`) must activate the app first (`AppDelegate.activateWithoutReopen`) — in an inactive app it never comes forward and blocks unseen.
- **Appearance is `WindowAppearance.syncDesktopWidget`**: never an opaque window (the rounded backdrop is the shape), glass/tint at the widget's corner. **The window's shape is `DesktopWidgetPanel`'s `_cornerMask`**, the widget's continuous corner as a nine-part image: left to derive it from the alpha, the window server made a coarse, jagged, wider-cornered region, and with glass off the CGS blur filled it — blurred desktop around every corner, the radius visibly lost (glass hid it by drawing its material inside the curve). A/B against a flat backdrop: halo and rim gone with the mask.
- **Two persistence layers, as for pinned tabs.** The snapshot (`WorkspacesFile.desktopWidgets`, schema v7) carries session identity. `~/.config/macterm/widgets.yaml` (`WidgetLayoutStore`, schema `assets/widgets.schema.json` — keep in sync) is the declaration: `name`, `size`, grid `column`/`row`, `display` (screen name — always written, since which display is primary changes with what is plugged in; absent in a hand-written entry means the primary one), and the respawn recipe `cwd`/`run`, captured from the live pane with the pinned rule that an idle capture never erases `run:`. It follows `pinned.yaml`'s rules: rewritten after every change and at quit, external edits absorbed first (exact-text baseline), no ids (`WidgetLayoutMatcher`: name → content → position), authoritative for membership at launch, an absent file is no input, an unparseable one suspends writes behind an alert, and a running widget's removal is honored at launch only — but its entry stays out of every write from then on (`unlistedDesktopWidgetIDs`, judged against the widgets our last write listed so a widget created since isn't taken for a removal), or the next write put it straight back. The launch reconcile adopts an entry's size and cell only where they DIFFER from the widget's own declaration: the file's cell is on the default lattice and can't express a widget that joined a neighbour's, so re-deriving an untouched entry moved it off its neighbour every launch. It saves no snapshot either (it runs before any window registers; `windows` would be written absent). The recipe capture (`refreshDesktopWidgetRecipes`) drops a foreground seen while `Pane.isShellAtPrompt` — that is a prompt hook, and it was being typed into the next fresh shell. Restored widgets are drawn only after `materializeRestoredDesktopWidgets` asks zmx which sessions survived; a dead one respawns from its recipe (a surface attaching first would get zmx's empty upserted shell).
- **Widgets follow the displays, Notification Center's way** (`DesktopWidgetPlacement`, measured from its logs going from a 3008×1692 display to a 1920×1243 one). It keeps the system widgets' layout per display *and* per resolution, and on a display it has no layout for it PROJECTS the latest one — the same offsets from the visible top-left — and saves nothing. So a widget's `placements` record where the user put it (creation, a settle, a declaration; keyed by display name + whole-frame resolution, so the Dock doesn't make a new one), `topLeft` is where it is now, and a projection is never recorded. `desktopScreensDidChange` (from `DesktopWidgetWindows`, 1s after the screen-parameters notification stops firing — a connect posts it several times, and Notification Center is moving its own widgets meanwhile) and the launch restore both go through `placeForCurrentScreens`: the display last put on, else the primary one; exact placements first, then projections clamped onto the screen, any that would land on another widget moved to a free cell. The span is never shrunk to fit — that would lose its size for the big display. `widgets.yaml` declares the latest *placement*, not `topLeft`, or quitting on the laptop wrote the laptop's cell and the next launch on the external display adopted it. Unverified live: what Notification Center does with widgets that don't fit, and whether it anchors any to the right edge — ours clamp.
- **Widget panes live outside every workspace**, like the quick terminal's. Their sessions are reaper claims (`desktopWidgetSessionNames`), bound in `session list`, rows in the no-persistence quit prompt, and addressed by the pane verbs through a bare `--session` (`ControlHandler.widgetTarget`). A widget's shell exiting starts it over in a fresh session (`desktopWidgetShellExited`) rather than closing it.

### First-run seed

`FirstRunSeed` (pure) + `AppState.seedFirstRunIfNeeded` seed a fresh install with one project (the home directory) and one pinned "Welcome" tab, each running `macterm tutor <topic>` as its `run:`. It runs after `restoreSelection`; `Preferences.hasSeededFirstRun` is written on the first launch that can answer, seeded or not, except `.postpone` on `WorkspaceStore.loadFailed`. Off (postponed, not skipped) under `MACTERM_BENCHMARK=1`, because the harnesses look like fresh installs and do not isolate the defaults domain. The seeded `run:` is bare words so it tokenizes identically in every login shell.

### Project color tags

`Project.colorName` tints glyphs the row already draws (project icon, tab-row icons, including agent logos and status glyphs). **No stripes; no glyph means no tag; no titlebar indicator** — each alternative was tried and rejected. Colors are fixed system colors (`MactermTheme.color(for:)`), deliberately not derived from the ghostty palette. The picker is `.pickerStyle(.palette)` (`ProjectColorMenu`) — the only menu form that renders. Stored as a String so an unknown value degrades to untagged. `iconStyle` wraps both arms in `AnyShapeStyle`, because `tagColor ?? .secondary` silently coerces to `Color.secondary` and restyles every untagged row. `Preferences.autoAssignProjectColors` (default off) is read at creation only, via an injectable closure on `ProjectStore`.

### Finder Services

**Services → New Macterm Project Here** is an `NSServices` plist entry plus `FinderServiceProvider` (`Macterm/App/FinderServices.swift`). The plist `NSMessage` and the `@objc` selector are an unchecked runtime contract — `FinderServicesTests` reads the plist back. A request can arrive before the app has restored state, so the provider queues until `attach` and then defers through `AppState.performWhenRestored` — the hook any launch-time external request should use.

**Opening a folder or a file WITH Macterm** — Finder's Open With, a Dock-icon drop, `open -a Macterm <path>` — arrives at `AppDelegate.application(_:open:)`, which splits it with `DocumentOpenRequest` (`Macterm/App/OpenFolder.swift`): folders go to `FinderServiceProvider.open(paths:)` (always a **new** project, never a tab), files to `FinderServiceProvider.openTextFiles` (see Text files below) — so a cold launch reuses the queue-and-defer above for both. `CFBundleDocumentTypes` has three entries, **all `LSHandlerRank: Alternate`** so Macterm is never a default opener until the user picks it with Get Info → Change All: `public.directory` (Ghostty's entry), `public.text`, and an extension list for text macOS doesn't type as text (`go`, `rs`, `ts` — which it takes for video — Zed's Info.plist makes the same split). Unlike Ghostty, scripts and executables are not declared: a script opened with Macterm is edited, not run. `OpenFolderTests` reads the plist back for this contract.

**Text files (Settings → General → Text Files)** open in the user's terminal editor (`AppState+TextFiles.swift`). Ghostty has no equivalent — upstream declined `file:line` detection and a configurable `link` (discussions #11378, #9546), so this is Macterm's own:

- **A ⌘-click goes to the pane first** (`GhosttyTerminalNSView.onOpenLink`, only for the link regex's `.unknown` kind — never OSC 8 or keybind opens). `FileLink` splits `:line[:col]` off (libghostty's regex keeps it, and `foo.swift:42` even parses as a URL scheme) and resolves the path against the real pane's cwd; anything that isn't an existing local file, and every remote pane, falls through to the system opener unchanged. An existing file goes to its **default app with the line dropped** — no other app can be told one — unless that app is Macterm (`TextFileOpening.isDefaultApp`, by bundle id), in which case the editor opens directly and keeps the line. A mirror's click acts on the real pane (`editorAnchor`), a quick-terminal click splits the panel, a desktop widget's goes the Finder route.
- **The editor is `$VISUAL`, else `$EDITOR`, else `vi`** — git's order, and deliberately no setting of Macterm's own: the variable is where a user already names their editor. **It is typed, not spawned** (`TextFileEditor`): the variable and the editor's PATH live in the user's shell rc, which no process outside it can read. The typed line is a fixed ` exec sh -c '…'` that parses identically in nu, fish, zsh and bash (no `'` or `\` inside); the file and line ride in the new pane's environment (`MACTERM_EDITOR_FILE`/`_LINE`), so no path is ever escaped into shell grammar. `exec` makes quitting the editor close the pane; a missing editor waits for Return instead. The line is passed as `+N`, the one syntax every terminal editor shares.
- **Placement** is `Preferences.textFilePlacement`: a split (auto axis, `SplitDirection.auto`) beside the clicked pane or the project's focused pane, or a new tab — except in the pinned workspace, which always splits (a tab born there would be pinned, and quitting the editor would leave a dimmed row). A Finder file lands in `TextFileProject.project`: the deepest local project containing it, else the active local one, else the first local one, else a new project for its folder; never a remote project.

**A folder dropped on the sidebar** opens the same way (`SidebarFolderDropTarget`, `Macterm/Views/SidebarFolderDrop.swift`, through `AppState.openProjects`, which the Finder service shares), selected in the window it was dropped on. It is an AppKit view over the whole sidebar registered for `.fileURL` only and transparent to `hitTest`: AppKit picks a drag destination by registered type without consulting `hitTest`, so clicks, scrolls and the in-app tab/project/pane drags (none carries a file URL) still reach the outline beneath, where no SwiftUI destination could have caught a Finder drag. Feedback is the cursor's `+` alone. A drop on a pane is still `GhosttyTerminalNSView`'s path paste.

**SwiftUI answers that same event by opening a second window, and the scene's `handlesExternalEvents(matching:)` is what stops it.** Left alone, an open-documents event gets a new `WindowGroup` window on top of the project the delegate just selected — two windows on one tab, a dimmed mirror in front and `MirroredTabNotice` behind — and it happens with our delegate method removed too, so it is SwiftUI's handling, not ours. Macterm emits no external events of its own (no URL scheme, no Handoff), so the group declares a condition nothing ever matches. The set must be **non-empty**: `[]` means "handles no external events at all" and also silences `applicationOpenUntitledFile`, which is the only call that reliably builds a `WindowGroup` window — New Window, `window new` and #241's repair were all measured dead under `[]` and alive under a never-matching condition.

### Dock menu

Right-clicking the Dock tile offers **New Window**, **New Tab**, **New Project…**, **Toggle Quick Terminal** — Ghostty's set, built by `AppDelegate.applicationDockMenu` (`Macterm/App/DockMenu.swift`; `@NSApplicationDelegateAdaptor` does forward this one, verified live). Items are `AppCommand`s run through `AppCommand.action(in:)`, so the Dock is a fourth renderer of that list rather than a second set of handlers; the menu is rebuilt per right-click with `autoenablesItems` off (enabled ⇔ non-nil action), and is nil until `MainWindow` hands the delegate its state objects. What the Dock adds is `DockMenu.Preparation`: a pick arrives from outside the app and does not activate it, so New Tab / New Project… call `showWindow()` first (the hidden last window, or the #241 no-window state), New Window activates and lets the command make its own, and Toggle Quick Terminal prepares **nothing** — the panel is non-activating by design. The action is resolved *after* preparing, since fronting a window is what makes `activeProjectID` the right project. `DockMenu.Preparation` is now the shared **"invoked from outside the app"** table — App Intents run through the same `AppDelegate.performExternalCommand` rather than deciding again, which is why it carries `.toggleCommandPalette` (unreachable from the Dock menu itself).

### App Intents (Shortcuts, Spotlight)

Thirteen intents in `Macterm/Intents/`, mirroring Ghostty's surface (`macos/Sources/Features/App Intents/`) in Macterm's model: **New Project**, **New Tab**, **Run Command in Pane**, **Send Key**, **Get Pane Contents**, **Get Pane Details**, **Focus Project/Tab/Pane**, **Close Tab**, **Toggle Quick Terminal**, **Open Command Palette**, **Invoke Keybind**. User-facing grammar in `website/docs/pages/85-shortcuts.md`. `AppIntents.framework` is an SDK dependency in `project.yml`; the build's `appintentsmetadataprocessor` writes `Contents/Resources/Metadata.appintents/extract.actionsdata`.

- **Translate-and-delegate only**, exactly like `ControlHandler`: resolve what an entity names, then call the same `AppState`/`ProjectStore` methods the UI calls. `ControlHandler`'s own resolution is deliberately *not* shared — it speaks selector strings (name / 1-based index / UUID) while an entity's identity is exact, so `IntentTargets` does UUID/session lookups and the CLI is untouched.
- **`MactermIntentHost`** is the only way an intent reaches the app (the system instantiates intents, so nothing can be handed in). `AppDelegate.installResponders` attaches it, and readiness waits on `AppState.performWhenRestored` — running a shortcut is what *launches* the app, so `perform()` can arrive before the restore. The wait is a bounded sleep-poll (`readinessTimeout`), because a launch that fronts no window may never install responders (#241) and a hang would wedge the shortcut with no error.
- **Entities are tokens, not handles.** `MactermPaneEntity.id` is the zmx **session name**, not `Pane.id`: pane UUIDs are fresh on every restore, so a saved shortcut keyed on one would break at the first relaunch *silently* (the pane it names is visibly still there). Tab and project ids are persisted, so those are fine. Every lookup can answer `.notFound`.
- **The user's ghostty `macos-shortcuts`** (`ask`/`allow`/`deny`, default `ask`) gates every `perform()`, via `IntentPermissionGate` in front of the readiness wait. It is read live off the loaded config (`GhosttyApp.shortcutsAccess` → `ShortcutsAccess.resolve`, the `MacosHidden` shape; the raw values are ghostty's tag names) and has no Settings UI. `ask` remembers the answer for the run only (`.allow` is the standing grant; Ghostty instead persists an Allow forever under one UserDefaults key and remembers a Deny not at all). Under `MACTERM_BENCHMARK=1` it resolves to allow without a modal — the harnesses drive the app with nobody at the keyboard, the same reason the notification prompt is skipped — while an explicit `deny` still denies.
- **`MactermKeybind` restates `HotkeyAction`'s cases and titles by necessity**: `appintentsmetadataprocessor` reads `caseDisplayRepresentations` out of the source and rejects a computed dictionary ("must be a dictionary"). `MactermIntentsTests` pins the case set against `HotkeyAction.allCases` and every label against its `AppCommand.title`, so a new keybind fails a test rather than quietly missing from the picker. Same constraint applies to any future `AppEnum`.
- **Statics must be `let`** under `SWIFT_STRICT_CONCURRENCY: complete` (`title`, `description`, `defaultQuery`, `supportedModes`), and `supportedModes` is `#if compiler(>=6.2)`-gated like Ghostty's. `IntentFile`'s `supportedContentTypes:` is macOS 15 only — use `supportedTypeIdentifiers:` rather than gating an intent away from the 14 floor.
- **`linkd` indexes an app's intents only after it has been launched from a stable location.** A bundle in `/private/tmp` fails registration outright (`Could not create application record … -10814`); one copied to `~/Applications` but never run logs `is not trusted for binding, skipping`. Launch it once and the audit proceeds (`Checking … extract.actionsdata` → `Collating specified bundles`). Not a signing problem — reproduced identically ad-hoc and with a release-shaped self-signed cert. Verify with `log show --predicate 'process == "linkd"'`.

### Control CLI (`macterm`)

A bundled CLI (target `MactermCLI`, `PRODUCT_MODULE_NAME` must stay `MactermCLI`) controls the app over `<App Support>/control.sock`. It is copied to `Contents/Resources/bin/macterm`; every pane gets it on `PATH` plus `MACTERM_SOCKET` and `MACTERM_SESSION`. Full grammar in `website/docs/pages/80-cli.md`. Verbs: `status`; `project list/create/select/rename/remove`; `tab list/new/select/move/rename/close/merge`; `pane list/inspect/dump/split/focus/close/run/key/zoom/resize-split/mirror`; `grid RxC`; `session list/info/kill`; `window list/new/focus/close`; `widget list/new/set/edit/done/remove`; `layout apply/save`; `tutor`; `ssh` (offline — ghostty's `+ssh` natively via `SSHWrapper`); `skills` (offline — the agent skills below).

- **Wire protocol** (`ControlProtocol.swift`, compiled into both targets): one newline-terminated JSON request per connection, `{v, id, command, args}` with `noun.verb` commands; responses `{ok, data}` or `{ok:false, error:{code, message, action?}}` with snake_case codes (`not_found`, `busy`, `no_surface`, `starting`, `ambiguous`).
- **Server** (`ControlSocketServer`): dedicated thread polling a non-blocking listen fd; per-connection dispatch hops to `@MainActor`; starts in `applicationDidFinishLaunching`, handler attaches in `installResponders` (early requests get `starting`). 0600 socket in a 0700 dir, same-user only.
- **Handler** (`ControlHandler`): translate-and-delegate only — resolve selectors (name/UUID/1-based index), call the same `AppState`/`ProjectStore`/`ZmxClient` methods the UI uses. Close verbs return a typed `busy` error rather than staging dialogs. A session selector with no `--project` resolves in whichever project holds it (`MACTERM_SESSION` arrives the same way), so a background pane can still reach itself while the user looks at another project.
- **Client**: discovery `--socket` → `MACTERM_SOCKET` (hint, falls through when stale) → per-flavor App Support paths. stdout only on success; exit 0 ok / 1 app error / 2 unreachable. **Targeting trap**: an unpinned `--socket` from a debug harness can hit the developer's live app, where an untargeted `pane run` types into their focused pane. `pane run` therefore types verbatim only what follows `--`; before it its own flags parse wherever they are, plain words are typed, and any other dash-word fails validation with nothing sent. Its text is one `.allUnrecognized` array split at the `--` by hand (a second, `.postTerminator` array fails ArgumentParser's debug-build validation). `ssh` keeps `.captureForPassthrough`, mirroring ssh's own argv, and answers a leading `-h`/`--help` itself (`startsWithHelpFlag`).
- **Agent skills** (`macterm skills`): three Agent Skills (`SKILL.md`, the agentskills.io format) teaching coding agents this CLI, compiled into the binary from `Macterm/Control/AgentSkills/` (shared with the CLI target, like `ControlProtocol`) and printed offline — every skill after an install header, or one verbatim, since agents install them themselves. Agents load one skill at a time, so each embeds `AgentSkills.groundRules`. Every example was run against a hermetic instance before it shipped; keep it that way. `AgentSkillsTests` runs every `macterm …` line in them against the bundled CLI's `--experimental-dump-help` tree, so renaming a verb or flag fails a test until the skills follow.
- `pane run` types via the paste path (`sendText`; `--no-submit` withholds the newline and keeps submission evidence armed). `pane key <chord>` rides the key-encoding path (`sendKey`) and **bypasses `keyDown`**, so `keyDown` interceptions don't apply; a bare printable must carry `.text` or it encodes to nothing. `pane resize` is `#if DEBUG` only.

### Ghostty config pipeline

Automatic mode delegates the user layer to `ghostty_config_load_default_files`; Settings can append custom files. `GhosttyApp.loadConfig` loads `macterm-defaults.conf → user files → macterm-overrides.conf` (last wins), regenerating both private files (`MactermConfig.regenerate()`) before every load because the overrides depend on the user's content. `GhosttyConfigSource` is the raw-text seam for keys the C API can't expose.

**Ghostty keys Macterm applies to its own behavior** have no Settings UI: `macos-shortcuts` (App Intents), `tab-inherit-working-directory` / `split-inherit-working-directory` (`false` = the project directory — ghostty's "default working directory" in a project-based terminal; `AppState.newTabInheritsWorkingDirectory` is the injectable read), `macos-hidden`, `macos-icon`, `focus-follows-mouse` (read live on each pointer move; it moves focus only away from another pane). **Where Macterm's default departs from ghostty's, the departure is a line in `macterm-defaults.conf`** (`MactermConfig.defaultsBody`, pinned by `MactermConfigTests`: `tab-inherit-working-directory = false`, `macos-secure-input-indication = false`), never a `Preferences` fallback — so the user overrides it the way they override any other key. **Wheel scrolling is libghostty's on every path**: `GhosttyTerminalNSView.scrollWheel` forwards events exactly as Ghostty.app does (2× precise deltas, momentum phase) and `SurfaceScrollView` only draws the scroller and turns scroller drags into `scroll_to_row` plus, under smooth scrolling, the sub-row remainder (see Animations). The iTerm2-style row accumulator from #102 (with its Scroll speed slider) was removed so `mouse-scroll-multiplier` means the same thing here as in Ghostty; don't reintroduce a Macterm-side wheel path.

Overrides Macterm must lock (plus the `smooth-scroll`/`smooth-cursor`/`cursor-trail` lines from `MactermConfig.Animations`, see Animations): `background-default-transparent = true` (fork patch — the renderer skips the default background so `WindowAppearance` composites translucency itself), `background-opacity = <Preferences.windowOpacity>` (the real value, so the user's `background-opacity-cells` works), `background-blur = 0` (Macterm calls the CGS blur SPI), `env = GHOSTTY_BIN_DIR=<bundle>/Contents/Resources/ssh-bridge` (holds our `ghostty` shim relaying `+ssh` to `macterm ssh`; kept out of any dir on the pane PATH), and `shell-integration-features` re-emitted with the user's flags plus `no-path` (`ShellIntegrationFeatures.overrideValue`, #75 — the key can't be written bare). Macterm UI state lives in `Preferences` and never touches this pipeline.

**Custom app icon**: `macos-icon = custom` + `macos-custom-icon` is honored with Ghostty's semantics. `GhosttyApp.applyAppIcon` runs after every load and reload, reads both keys off the *loaded* config (so a `config-file` include counts) through `configCString` — libghostty's C getter hands enums back as their tag name and `?[:0]const u8` as a bare C string, not a `ghostty_string_s`, which is why that getter is distinct from `configString` — and passes them to the pure `GhosttyAppIcon.resolve` (`.bundled` / `.custom(URL)`; no path means Ghostty's `~/.config/ghostty/Ghostty.icns`, a path still relative after `~` expansion is invalid since a GUI app's cwd is unpredictable). The one AppKit write is `AppIconPresenter.apply`, which sets `NSApp.applicationIconImage` and assigns nil — that is what restores the bundle icon — for a missing, unreadable or undecodable file. Every other `macos-icon` value is Ghostty-brand artwork we don't ship; Ghostty's Dock-tile plugin is deliberately not mirrored. Hermetic caveat: `loadConfig` disables the user layer under `MACTERM_BENCHMARK=1`, so verify with a throwaway `HOME`/`XDG_CONFIG_HOME`/`ZMX_DIR` plus `MACTERM_BENCHMARK_DATA_DIR` and **no** `MACTERM_BENCHMARK`.
**`macos-hidden`**: ghostty's `never`/`always` maps to `.regular`/`.accessory` through `MacosHidden` (a pure, tested function; the raw values are ghostty's own tag names, so renaming a case is a wire break). `AppDelegate.applyActivationPolicy` applies it after `GhosttyApp.shared` at launch and again on `.mactermConfigDidChange`, skipping AppKit when the policy already agrees — that is what makes the over-firing observer safe. Read it as an **enum** (`configEnum`, a bare `[*:0]const u8`), never through `configString`, whose `ghostty_string_s` leaves `len` at 0 — the reason `GhosttyColorSpace` went to raw text. Accessory mode is deliberately narrower than Ghostty.app's, which builds no window: Macterm still builds one, because `MainWindow.onAppear` installs the responders and attaches the control handler. Every explicit window request (`window new`/`window focus`, `revealProject`) calls `MacosHidden.activateForWindowRequest`, which forces activation with `ignoringOtherApps: true` — plain `activate()` and a cross-process activate were both measured **refused** by cooperative activation, silently. An accessory app has no menu bar, so Settings, Quit, About and Check for Updates lose their only route; keybindings are unaffected (`KeyRouter`, not the menu bar).

**Process locale (#370)**: `ghostty_init` calls `setlocale(LC_ALL, "")`, and under any comma-decimal locale SwiftUI's toolbar glyph rendering asserts inside CoreUI on macOS 27 (SIGTRAP, nothing on stderr). `ProcessLocale.pinNumericToC()` runs right after `ghostty_init` and touches only `LC_NUMERIC`. Reproduce with `LANG` unset (a Dock launch); `OS_ACTIVITY_DT_MODE=enable ACTIVITY_LOG_STDERR=1` surfaces the assertion text.

### Bundled ghostty resources

The bundle mirrors Ghostty.app: `Contents/Resources/ghostty/{themes,shell-integration}` with the compiled terminfo at the **sibling** `Contents/Resources/terminfo/`. `GhosttyApp.resolveResources()` sets `GHOSTTY_RESOURCES_DIR` from our own candidates, ignoring any inherited value. **Never set `TERMINFO` ourselves** — libghostty overwrites it with `dirname(GHOSTTY_RESOURCES_DIR)/terminfo`, so terminfo must be a sibling of `ghostty/` (#39/#40). The tree uses the macOS hashed layout (`terminfo/78/xterm-ghostty`). `BundledResourcesTests` asserts all of this and skips before setup has run.

### Animations (Settings → Animations)

The motion pane, directly under Appearance in the Settings sidebar. Five toggles: **Smooth scrolling** and **Animate splits** ship **on**; **Snap to whole row** and the two cursor effects are opt-in. It was Settings → Experimental until the first two graduated; anything still settling in belongs here too, off by default, until it does.

- **Smooth scrolling** is fork patch 0005 (`.github/downstream/0005-smooth-scroll.patch`) behind the fork key `smooth-scroll`, which the toggle writes into the overrides via `MactermConfig.Animations` (`Preferences.smoothScrolling`, default on; the ghostty key's own default stays off). libghostty's `scrollCallback` already accumulates precise trackpad deltas in pixels and commits whole rows; with the key on, the patch keeps the sub-row remainder on `Screen.viewport_pixel_offset`, captures the rows being revealed as upstream's `RenderState` overscan (ghostty-org/ghostty#14400, the first step of upstream's own smooth scrolling; the fork's `beginShiftedUpdate` sets the request, `overscan.above` rows at the top or one below, fork PR 16) and shifts the grid by a `scroll_offset` uniform, clipping to the visible grid sized from `grid_size × cell_size` — **never from `grid_padding`'s bottom/right**, which hold the leftover measured at the last resize and go stale after the incubator→pane growth. Any row-level viewport move goes through `Screen.scroll`, which zeroes the remainder. Macterm has no part in the routing of a *wheel* event (every one reaches libghostty untouched, #393), which is exactly why the gate is a ghostty key and not a `Preferences` read. The alternate screen has no scrollback, so there the key animates a program scrolling a region of its screen by rows instead (DECSTBM/DECSLRM with SU/SD, or IND/RI at the margin, which is what `less` does): the renderer draws the region's new content shifted by the scrolled distance and eases it home in about a quarter second, with the rows that scrolled out sliding away as ghost rows (fork PR 11, carried in 0005 since fork PR 14 after a sync dropped it). A program that repaints every row still moves by rows.
  **A resize moves the viewport by pixels too** (fork PR 9): a grid only comes in whole rows, so the leftover height of a viewport grows as a pane is resized until it is a full row and the viewport takes one — and at that instant everything on screen jumps a cell, because the row it gains is pulled in from scrollback at the top. With the key on, the renderer hands the render state that leftover (`RenderState.Geometry`), which adds to whatever remainder a gesture left, and the grid is drawn that much lower with the row above partly revealed. So a divider drag and every split animation slide the content instead of stepping it, at the cost of a partial row at the top of any pane whose height isn't a whole number of cells — a scrollback row, so after a clear it is the old prompt line. That row selects like any other (`RenderState.Shift.rowsAboveAt`, fork PR 17): selection resolves the pointer to a pin, because a viewport coordinate cannot go above the viewport's first row and clamped a press there to the row below. The two offsets adding is why more than one row can be revealed above and `scroll_offset` carries the leftover in `.z` — the shifted grid draws onto it, so the clip extends by it.
  **A scroller drag is the one exception**, because `scroll_to_row` lands on whole rows and `Screen.scroll` zeroes the remainder on the way: `SurfaceScrollView` sends the row, then hands the sub-row leftover to the core as a synthetic precision scroll (`GhosttyTerminalNSView.applySubRowScrollOffset`). It can aim because `ScrollAccumulator` mirrors `Surface.mouse.pending_scroll_y` — unreadable over the C API, but `scrollCallback` is its only producer and Macterm is the only caller of `ghostty_surface_mouse_scroll`, so mirroring every delta we send reproduces it. The nudge is sized to land the accumulator exactly on the wanted remainder, which is under a cell and so commits no row of its own; being wrong costs at most a row of offset until the next drag update. The multiplier it divides out is the user's `mouse-scroll-multiplier`, read from raw config text (`MouseScrollMultiplier`) because the key is a Zig struct with no C shape. Skipped with the toggle off or with no scrollback to drag through.
  **Two rules the render state enforces, each found by measuring frames** (see `RenderState.resolveShift` in the fork). The gesture's remainder is validated *on its own* before the resize leftover is added: a remainder with no row to reveal is dropped and the leftover still shifts the grid. Validating the sum instead made a scroll pinned at the bottom bob the content by up to the leftover's height on every event, since the remainder cycles through a cell as row after row fails to commit. And the leftover is measured *by the render state against the terminal's row count* (`Geometry.terminal_height`), never by the renderer against its own grid: the renderer's size and the terminal's rows change on different threads, and a frame caught between them drew the grid a whole cell off — every divider drag showed it as a slide-then-snap-back.
  **Anything that turns a pixel into a row takes the shift from the render state** (`RenderState.resolveShift`, fork PR 13): the surface's hit test (selection, clicks, links), mouse reports and the IME point subtract exactly the shift a frame draws, validation and all. A copy of the arithmetic in `Surface.posToViewport` skipped those checks and put the pointer a row off wherever they drop the shift: below it at the bottom of scrollback after a scroll, above it in a pane without scrollback, on the alternate screen and at the top of history (#433). A region-scroll animation's offsets are per-region renderer state, so the renderer publishes them (`RenderState.RegionShifts`, fork PR 15) and the same three undo them: the offsets of the frame the layer is showing (its contents change on the main thread, where hit tests run, so neither drawing nor presenting a frame decides), with every region scroll the terminal has done since that frame was drawn folded in. A click during the quarter-second ease, or mid-momentum, lands on the row drawn under the pointer; one on a row the region has scrolled out of resolves to the region's edge row.
  **Upstream's overscan leaves the cursor out of revealed rows** (`cursor.viewport` is null there, and `renderer/cursor.zig` draws no cursor without it), so the prompt's cursor vanished from the row a scroll reveals at the bottom until the fork added `cursor.captured`, which the renderer and the style gate read instead. Links still come back in viewport rows. Both were found only by diffing rendered frames against the previous build; the unit tests passed.
- **Snap to whole row** is fork patch 0011 (`.github/downstream/0011-smooth-scroll-rows.patch`) behind the fork key `smooth-scroll-rows`, a mode of `smooth-scroll` that `MactermConfig.Animations` writes only alongside it (`Preferences.snapScrollToRow`, default off; the toggle is indented under Smooth scrolling and disabled without it). Scrolling moves the viewport by whole rows and each move slides into place, the way `less`'s region scrolls already animate, so the viewport never rests between rows. Input accumulates as it does without smooth scrolling and its sub-row remainder is never drawn; each row the viewport actually moves is drawn from where it was (`Surface.rowScrollOffset` puts the distance in `Screen.viewport_pixel_offset`) and the renderer decays it on the region animation's 45 ms time constant (`decayViewportScroll`, under the terminal lock on update wakes). Because the motion is the terminal's own offset, the hit test, selection, cursor and IME point follow it with no copy. Scrolling back draws content rows up, so `resolveShift` reveals as many rows below as the offset spans (`scroll_offset.w` tells the shaders' clip). At rest the leftover height stays padding — the geometry gets no terminal height — so only whole rows show, and a resize steps a row at a time as it does in `less`. It is the fork's because every wheel event reaches libghostty untouched (#393): a Swift settle after the gesture was tried first and missed phaseless smooth-wheel input (Logi Options+ posts precise deltas with no gesture phases). `SurfaceScrollView` sends no sub-row offset for a scroller drag in this mode.
- **Animate splits** (`Preferences.animatedSplits`, default on) swaps the recursive `SplitTreeView` for `AnimatedSplitView`, which renders the tab's tree **flat**: `SplitLayout` (pure, tested) resolves every pane and divider to an absolute rect, and one ZStack keyed by pane ID lays them out, so any tree change is frames moving on stable identities and SwiftUI animates it — the recursive view can't, because re-nesting a leaf changes its structural identity. `SplitRootView` is the switch; both call sites (`WorkspaceView`, the quick terminal) go through it. Rules, each verified live: **a platform view moves only by frame** (`.scaleEffect` and the `.scale`/`.move` transitions leave an NSView where it is), so a new pane grows out of its split's seam from a zero-length frame, edge-locked to the shrinking sibling; **nothing crosses another pane** (backgrounds are transparent, so overlap is text through text, and an empty new pane is invisible anyway); **a closing pane is a ghost** — `Pane.destroySurface` snapshots the last frame (`Pane.closingSnapshot`, only while the toggle is on) *without* a background fill, because an opaque ghost flashed to full opacity in a translucent window — clipped to the strip the sibling has not yet reclaimed; direction is the pane's **own outer edge** of the split (right/bottom pane slides right/down, left/top pane left/up); **what the strip closes onto is read off the new layout, never the old tree** (`SplitLayout.closingSeam`) — with one sibling reclaiming it that is the branch's own edge, but auto-tiling's rebalance moves *both* neighbours of a middle pane, and collapsing to the branch edge then dragged the dead divider back across the pane above it; **a divider outliving its branch travels to that same seam** (`AnimatedSplitView.MergingDivider`) instead of blinking out, so the two dividers either side of a closed pane cover the same distance from opposite sides and merge, which is the close read backwards from a split (where the new divider is born on the seam it peels off); **the unfocused-split dim is a value, not a branch** (`SplitLeafView.isSplitDimmed` drives an opacity, always mounted) — a view that comes and goes cannot cross-fade with the slide, and it popped a shade darker the instant a pane arrived; the animation is keyed to structure plus zoom plus `TerminalTab.animatedResizeGeneration`, never to ratios themselves, so a divider drag and the CLI's `pane resize-split` land immediately while Resize Split Left/Right/Up/Down (which bumps the generation with its ratio change) slides; each arriving or ghost animation starts from its own `onAppear`, the same frame as the sibling's, since a one-turn deferral visibly desynchronised the seam. Zoom keeps the hidden tiles mounted at opacity 0 (`GhosttyTerminalNSView.hiddenInLayout` sleeps their renderers) but removes the dividers, whose grab bands are NSViews that would catch drags through the zoomed pane. Every animation frame resizes the moving surfaces, the same path a divider drag takes; Reduce Motion disables the animation. **The curve is a spring, defined by its settling time** (`SplitAnimation.curve`): SwiftUI drives a spring itself, frame by frame, so each frame reaches the surfaces as a resize, whereas a timing curve (`easeOut`) is bridged to Core Animation for a representable's frame — the view is sized once, the layer is stretched, and the program sees two SIGWINCHs per split. A spring named by perceptual duration (`.smooth`) kept settling ~250 ms past it, a pixel per frame, each one a pty resize and a full redraw. libghostty applies those resizes behind its own coalesce timer (upstream: a fixed 25 ms; fork patch 0010 tracks frames), so the grid steps at that cadence, not SwiftUI's.
- **Smooth cursor** is fork patch 0008 (`.github/downstream/0008-smooth-cursor.patch`) behind the fork key `smooth-cursor`, written into the overrides by `MactermConfig.Animations` (`Preferences.smoothCursor`, default off). The renderer owns the motion (`CursorGlide` in the fork's `generic.zig`): the focused block, bar or underline cursor's sprite is still added, at alpha 0, so the custom-shader uniforms keep naming its cell; the rect itself is eased (140 ms, ease-out cubic, retargeted mid-glide from where it is drawn) into the cell uniforms every drawn frame and the **cell background shader fills it by exact box coverage**, under the text, while the **text shader colors each glyph pixel as cursor text by that same coverage** (`cursor_glide_text`, in place of the vertex shader's whole-cell recolor under `cursor_pos`, which is then left unset). That is what makes a glyph the cursor is halfway across two-toned and lets a highlighted cell's own background show through the uncovered part — the two things a custom shader could not do, since it sees one composited frame in which ghostty has already painted the destination glyph in cursor-text and cannot tell a glyph from a cell background. The rect is in grid pixels, so it rides a smooth scroll with the rows and takes the shift of a region-scroll animation its cell is in. Draws come from the vsync display link (the 8 ms animation timer is skipped on macOS whenever a display link exists), which `animationWake` keeps running while the glide is in flight and stops when it lands; `smooth cursor landed after N frames` in the debug log is the measured frame rate. A grid reshape, a font change or toggling the key snaps the cursor to its cell. Programs that paint their own cursor cell (Helix's `ui.cursor` theme style, its secondary cursors) still move that paint by cells under the gliding terminal cursor. The previous implementation was a custom shader gliding a block over the composited frame plus a `cursor-opacity = 0` override; both are gone.
- **Cursor trail** is fork patch 0009 (`.github/downstream/0009-cursor-trail.patch`) behind the fork key `cursor-trail`, written by `MactermConfig.Animations` (`Preferences.cursorTrail`, default off). It is the same `CursorGlide` motion: the glide is tracked whenever either key is on, and under the trail the streak (`CursorGlide.trail`: an axis-aligned box of the drawn rect's size swept from a tail that sets out halfway through the move to the head where the cursor is drawn, fading as the move completes; moves under 1.5 cell heights leave nothing, so typing doesn't streak) goes into the uniforms beside the rect and the background shader paints it in the cursor color under the text, beneath the cursor's own fill. With the trail alone the sprite stays the cursor and only the streak is drawn. It replaced the last bundled custom shader, which is why `AnimationShaders`, `Resources/shaders/` and the encoding-header install are gone: libghostty animates any loaded custom shader continuously while the pane is focused (a draw wake every 8 ms, the display link never pausing, the whole frame re-rendered and post-processed at the display's refresh at an idle prompt), so the trail's cost was permanent; the renderer's version costs the ~140 ms after a move and nothing otherwise, and its head is the glide's drawn rect rather than the cursor's cell. Macterm ships no custom shader now; the user's own `custom-shader` lines are untouched.

### Adaptive terminal background

`AdaptiveTerminalBackground` infers a TUI's background from libghostty's BGRA8 IOSurface (fails closed if the format changes) or takes OSC 11 directly. **A report is presented over inference, never written into it** (`AdaptiveTerminalChrome.reportedCandidate`): libghostty reports an OSC 111 reset as a change *to the configured color*, and a report that reset the stabilizer left the stale sampled color as the fallback — Helix's `:theme` then quit put a tint hole over the bare shell until a new surface's config reload. The report carries the alpha the renderer paints cells at (`reportedPaintAlpha`: the window opacity under `background-opacity-cells`, else opaque), never a bare 1. Rules: the alpha floor derives from the window opacity (`minimumPaintedAlpha`) because painted cells arrive premultiplied at `background-opacity`; a translucent color gets no pane fill and has the window tint **cut out from under its whole pane and its margin refilled in its own color** (`TintCutout`, a `TerminalPaintRegion` per pane: the paint edge-walked by alpha via `paintedUnitBounds` stays bare, the unpainted `window-padding` around it gets the pane's color at the window opacity on a sibling layer — in a split the window keeps the configured theme, and cutting only the paint framed every TUI in that theme), so the tint lives in a maskable view, never `NSWindow.backgroundColor` or `NSGlassEffectView.tintColor`; the tint does not depend on key status; colors are read in the renderer's color space (`GhosttyColorSpace`). `AdaptiveTerminalInferenceGate` freezes inference while `ghostty_surface_has_selection` is true and protects a confirmed color from repaints with no output heartbeat within 1.5s (adoption only, never clearing). The winning color must also span 0.80 of the sampled grid **per axis** (`minimumBackgroundExtent`), which is what keeps a slide or image from retinting the window. **A region follows the pane's visibility, not its frame** (`AdaptiveTerminalChrome.paintRegion`): a pane zoomed away keeps its frame, color and sampled paint at opacity 0, and its hole showed the bare material inside the zoomed pane — `hiddenInLayout` drops it at once and restores it only after the split animation has faded the pane back in (`layoutVisibilityDidChange`). The quick terminal is outside the window-wide tint.

## Tests

### Unit (`MactermTests/`)

One `XxxTests.swift` per production type, mirroring the source path; `@testable import Macterm`, `@MainActor`. Swift Testing suites run in parallel — anything touching shared state (preferences, stores) is injected: tests needing `AppState`/`WorkspaceStore` inject a tempdir file. Helpers in `Support/`: `TreeBuilder` DSL (`H(pane("a"), V(pane("b"), pane("c")))`), `TreeRenderer`, `LayoutFixture`. Coverage targets model, persistence, palette/hotkey logic and pure helpers; SwiftUI views and libghostty bindings are not unit-tested. Poll-until-condition waits must sleep, not `Task.yield()` in a fixed loop.

### End-to-end (`e2e/`)

Launches the real Debug app hermetically via `MactermHarness` (throwaway `$HOME`, `MACTERM_BENCHMARK_DATA_DIR`, `ZMX_DIR` — the zmx socket dir is per-user, so without the override a hermetic instance shares sessions with the developer's real Macterm) and asserts through the CLI (`pane dump` etc. read libghostty's live state). Conventions: one app instance per session, kept the **active app** before every test (`_active_app` in `conftest.py`: `lsappinfo front`, re-taken through the bench `activate` hook, which forces activation because the cooperative request is refused once another app holds the front) — the password monitor watches only the key window's focused pane and runs no timer while the app is inactive, and a test that launches an instance of its own (`open -n` fronts it) leaves the shared one behind Finder when it kills it, which is what timed out both `test_passwords.py` tests on CI; take the `fresh_tab` fixture, never mutate the initial pane; every wait is a deadline poll; type commands as `/bin/sh -c "…"` with no single quotes (CI's login shell is bash 3.2); target panes explicitly; prove execution with runtime-assembled markers (`printf started-%s <nonce>`), since no idle/running signal is environment-independent. CI runs it as `Test / End-to-end`; failures upload `e2e-diagnostics`.

### Benchmarks

`mise run bench` / `.github/workflows/benchmark.yml` measure CPU-time delta, RSS and wakeups across `focused`, `workload-focused`, `workload-unfocused`, driven by Darwin notifications (`BenchmarkControl`, `MACTERM_BENCHMARK=1`, which also skips the notification prompt, Sparkle and the first-run seed). PR runs compare against a pooled median of the last 10 main runs; a cell is flagged only past ±25% and a noise floor, and the `benchmark:regression`/`improvement` label needs ≥2 corroborating cells with one under a workload state (`should_label`). The label/comment writes live in `benchmark-report.yml` (a fork PR's token is read-only).

### Demo recordings

`scripts/record-demos/record-demos.sh` records the ten clips the landing page plays, driving the **installed** app with synthetic keystrokes and, for demos 8–9, the pointer — so it needs Accessibility and Screen Recording for whatever runs it, plus ffmpeg, plus podman for demos 5 and 10 (it starts the podman machine itself). Masters land in `$MACTERM_DEMOS_OUT` (default `~/Desktop/macterm-demos`); only `record-demos.sh web` writes into the repo, re-encoding the finished clips to 1400×792 CRF 26 with a first-frame poster in `assets/demo/`, which `website/public/assets` serves as `/assets/demo/…`.

The rules it encodes, each earned against the real app:

- **You place the window; it refuses to record until the rect matches** (1600×870 at 1330,411, captured with a 40pt margin). The spot keeps the frame clear of the desktop widgets in the top-left columns and the desktop icons in the top-right corner, and every clip then lines up. The quick terminal's panel is placed to the same frame by `quick-prefs` — the panel's frame is recomputed from prefs on each show, so an AX move never sticks — so moving the window means re-running `quick-prefs` and relaunching.
- **Wait for a prompt, never a delay.** Every typed command polls `pane dump` until the pane is showing one. A remote pane starts up blank — the shell printed its prompt before zmx had a client — so the wait nudges it with Ctrl-L until one appears. Never nudge a pane at a password prompt: the Ctrl-L becomes part of the password.
- **The tab switcher needs a HELD modifier**: the overlay lives exactly as long as the recent-tab chord's modifier is down (`commitTabCycle` fires on the flags-changed event when it drops), and System Events cannot hold one across statements. `hold.js` posts the key events at CGEvent level from osascript. The chord is read from `macterm.hotkey.recent_tab` at run time rather than assumed.
- **The quick terminal is recorded with the window parked off-screen, not closed.** The panel is non-activating: with no window at all Macterm cannot be the frontmost app, and every keystroke meant for the panel lands in whatever app is. `qt_ready` refuses to type unless the panel is up *and* Macterm is frontmost — Finder renames files with stray keystrokes.
- **`guard_repo` restores only the files a demo opens** (`AGENTS.md`), in the macterm *project's* checkout (`shown_repo`) — the one its panes open files in, which need not be the one the script runs from. Helix auto-saves on focus loss, so a keystroke that lands in an editor pane is written to disk; a blanket list reverts unrelated work in passing.
- **Cleanup matches by path, never by name.** Demo 3 opens `~/dev/macterm/website/docs` and removes only the project and layout file pointing there — removing "the project named website" nearly took the developer's own.
- **Programs that interrupt themselves are told not to**: opencode (demos 2 and 6) runs with `OPENCODE_DISABLE_AUTOUPDATE=1`, or an update dialog lands over the TUI mid-take.
- **Demos 5 and 10 build their own host**: a podman container with sshd, vim and zmx (compiled from source — the fork ships macOS binaries only), published on 127.0.0.1:2222 with a marked `Host demo-box` block prepended to `~/.ssh/config` (`HostName localhost`, which is what ssh's password prompt names). It takes a key and a password; the block decides which the pane uses, and the recorder's own checks always force the key (`rssh`). It refuses to record unless the alias answers with the image's own marker, so a name collision can never point a recording at a real machine, and teardown removes project, container and config block.
- **Desktop demos check the frame is empty** (`region_clear`, over `windows.swift`'s window list) and record the cursor (`CAPTURE_CURSOR=1`, moved by `mouse.js` on an eased arc — a pointer that jumps reads as fake). Finder state they change comes back through an EXIT trap, however the run ends.
- **Demo 8 drops a dummy `~/Desktop/starfield` on the Dock tile.** `dockdrop` aims for the tile's x while the auto-hidden Dock is still below the screen, wiggles on the edge until it slides up, then re-reads the tile under magnification. A desktop with Stacks or a sort order ignores the folder's position, so the take switches both off in Finder's `DesktopViewSettings` (Finder restarts to read them).
- **Demo 9 records the desktop's widgets as they are** — nothing created or moved for the take — full height below the menu bar with the desktop icons hidden (`CreateDesktop`). The btop widget is reset to a shell, edited from its right-click menu, and dragged out and back. btop needs ≥80×24 cells, so at a 16pt font a widget running it needs 4×4 cells or more.
- **Demo 10 is `ssh demo-box` from a local shell.** The password is typed with `pane key` (`pane run` pastes, and ssh reads the bracketed-paste markers as password). Macterm's ssh-terminfo wrapper would open a second, off-screen password prompt, so the recorder installs the entry over the key and lists the host in `~/Library/Caches/macterm/ssh-terminfo` for the take. Autofill wants Touch ID once per unlock, so `pw_rehearse` spends it off camera on a local script's prompt — someone has to be at the keyboard. Macterm keeps its saved-password list in memory, so a retake first opens Settings → Passwords (`vault_reload`), which re-reads the keychain; the demo's keychain entries are deleted afterwards.

## Releasing

Auto-updates via Sparkle (`SUFeedURL` = `https://macterm.thdxg.dev/appcast.xml`, served by `website/Caddyfile` straight off the `gh-pages` branch — a store, not a site). Tag-pushed builds release via `release.yml`; secrets: `SPARKLE_ED_PUBLIC_KEY`/`SPARKLE_ED_PRIVATE_KEY`, `HOMEBREW_TAP_PAT`, `MACTERM_SIGNING_CERT_P12`+`_PASSWORD` (a stable self-signed cert so TCC grants survive updates; **back up the private key and the cert** — losing either strands users). Release notes come from GitHub's generator (`.github/release.yml`); the version number is chosen by hand. The `/release` skill walks the ceremony; the cert recipe is in this file's history.

- **Three Sparkle channels, one feed**: a prerelease item carries `<sparkle:channel>beta|tip</sparkle:channel>`; Settings → Updates → Channel (`Preferences.updateChannel`, raw values are the wire names) opts in. A channel on a non-prerelease is a hard error in `publish-appcast.sh`. Homebrew stays stable-only.
- **Read the prerelease flag live** (`flag` job via `gh release view`), never from `github.event.release.prerelease` — the payload is frozen at dispatch and editing doesn't re-fire. Job outputs are strings: compare `== 'false'`.
- **Version ordering** (`sparkle_comparison_version` in `_lib.sh`): `0.9.0-beta.1` → `0.9.0.1`, stable `1.8.0` → `1.8.0.9999`, tip `1.24.2-tip.7` → `1.24.2.9999.7`. `build.sh` and `publish-appcast.sh` must both use it. `macterm_tip_version` filters tags to `^v[0-9]+\.[0-9]+\.[0-9]+$` because the rolling `tip` tag breaks `git describe`.
- **Tip channel** (`release-tip.yml`): every main commit with CI *passed* (Test success + Checks polled) publishes to ONE permanent prerelease edited in place, rolling `tip` tag moved **last** as the commit point, single-flight concurrency with `cancel-in-progress: false`, one tip item in the appcast, newest 3 DMGs kept. The staleness check asks whether the `tip` tag is an ancestor of the built commit — never compares against main's HEAD. **A version already in the appcast is never rebuilt**: a run whose tag push failed has shipped everything else, and a same-commit re-run would `--clobber` the DMG with new bytes while `publish-appcast.sh` keeps the old signature for the equal version, so the build job reads `appcast.xml` off the gh-pages branch first and, on a match, only moves the tag. `build.sh` bakes `MactermUpdateChannel` into `Info.plist` so a hand-installed tip build defaults to the tip channel; beta stamps `stable`.
- `release.yml` skips itself for `ref_name == 'tip'`. Keep GitHub Pages enabled on `gh-pages` until installs pinned to the old `thdxg.github.io` feed have moved.

## Conventions

### Code style

- SwiftFormat + SwiftLint enforced; run `mise run format`, `lint`, `test` before committing. swiftformat owns trailing commas; never write `static weak var` (the two tools fight).
- `@MainActor @Observable` on all state classes. No `@Published`/`ObservableObject`; inject via `@Environment(AppState.self)`.
- `os.Logger` only, one `private let logger = Logger(subsystem: appBundleID, category: "TypeName")` per file, **every interpolation `.public`**. View with `mise run logs`.

### Commits and PRs

- **Never add a `Co-Authored-By: Claude` trailer or any AI sign-off.**
- Subject lines say why. Split independent changes into separate commits.
- **PRs merge via squash only** — the PR title is the squash subject. On conflict, merge `main` into the branch; never rebase.
- Edit `AGENTS.md`; `CLAUDE.md` is a symlink to it.

### UI principles

- **Native SwiftUI/AppKit components only.** Accept a native limitation rather than mimic the behavior.
- All colors come from `MactermTheme`. Fixed system colors are allowed only for identity labels (`ProjectColor`, `AgentIcon.brandColor`).
- Gate Tahoe-only APIs behind `#available(macOS 26.0, *)` and, for controls, `WindowAppearance.glassSupported`.
- Settings copy: section headers Title Case, controls sentence case, buttons Title Case, descriptions via `.settingsCaption()`. `AppCommand` titles are Title Case.
- **Hover-revealed row controls change values, not view structure, and never use `.onHover`.** `SidebarProjectHeader`'s new-tab button is one `isRevealed` Bool driving padding/opacity/hit-testing; an `if/else` in a `List` row's label tears the row down and corrupts `NSTableView` reuse. Hover comes from an `NSTrackingArea` (`RowHoverTracker`, `.activeInActiveApp`) — `.onHover` has been retired three times for lag and leaked exits.
- Stacked `.dropDestination`s: only the first applied wins.
- The sidebar's `.contextMenu(forSelectionType:)` closure runs once per menu open, never on a row redraw (measured), so a cheap read like `GitWorktrees.list` belongs there. Inside it, `.disabled` on a `Menu` is dropped — the item renders enabled over an empty submenu — so a disabled submenu is a disabled `Button` (`SidebarContent.worktreesMenu`).
- **Anything taking mouse input over a pane needs an AppKit view.** `GhosttyTerminalNSView` wins hit testing, so SwiftUI gestures over a pane never see the press (`PaneDragSource`, `ResizeDragBand` are `NSViewRepresentable`s that forward what they don't own to `viewBeneath`). `NSHostingView` swallows hit tests even with `allowsHitTesting(false)`; override `hitTest`.

### Terminal surface rules

- Never tear down the NSView from a SwiftUI path.
- `pane.destroySurface()` kills the shell — only when a pane is permanently closed (or a remote reattach, which never kills the session).
- `createSurface()` needs a non-zero frame and a window; `TerminalSurface` defers until attached. `Pane.command`/`shell`/`env` map to libghostty's `initial_input`/`command`/`env_vars`, passed on the first build only.
- The `closeSurface` callback is asynchronous — guard double-close.
- First-responder handoff goes through `FocusRestoration` — a bare `makeFirstResponder` races window attachment.
- Any encoded key counts as typing to libghostty (clears selection, scrolls to bottom) — don't send control sequences on focus.
- **Every surface resize goes through `GhosttyTerminalNSView.applySurfaceSize`, gated by `SurfaceSizeGate`.** A grid under 8×2 cells is refused and the surface keeps its last size: libghostty reflows scrollback into whatever grid it is given, and a two-column grid (a split animation's first frame, a window shrunk to the sidebar's width, a container collapsing mid tab switch) shreds every line and leaves the content above the viewport when the pane grows back. Ghostty.app never meets this because its window can't get that small.

### Persistence

- Workspaces → `~/Library/Application Support/<display name>/workspaces_v3.json` (schema v6, written as v7 only while desktop widgets exist), projects → `projects.json`, wrapper configs beside them. Debug builds use `Macterm Debug/`, and the Debug bundle is `Macterm Debug.app` (`PRODUCT_MODULE_NAME` stays `Macterm`; spell the space wherever the bundle is named by path).
- `Pane` IDs are fresh on every restore; session identity (`sessionID`/`sessionName`, stored verbatim) is what reattaches. A declared layout is applied only by an explicit Apply Layout (palette, menu, Settings row, `layout apply`); selecting a project or relaunching never reads it — the snapshot is what restores, and a project without one gets the default workspace.
- **A directory is not an identity**: `ProjectStore.create` always appends a new project; `findOrCreate` exists only for idempotent callers (the benchmark).
- Project declarations are YAML in `~/.config/macterm/projects/` (shared across build flavors, `$HOME`-env-first via `ProjectPath.currentHome`): `name:` (display only), `path:` (identity, scp-style, `~`-contracted on write), optional `tabs:`. Schema at `assets/project.schema.json` — keep in sync. Files are written only by explicit Save Layout and the user's editor; deleted only by Settings → Projects → Layouts → Remove. Matching is by canonical `path:` with the project's name-slug as tiebreaker when one directory backs several projects (`ProjectSlug.owns`). Duplicates are surfaced, never deleted.
- `save` records `run:` as the live foreground command (`ProcessInspector.runningCommand`, remote via the probe cache), `shell:` only for a non-default shell; `apply` (`LayoutReconciler`) matches by the same `(run, cwd)`. Unparseable files surface `LayoutFileError`; empty `tabs:` is a bare declaration.
- The in-repo `.macterm/layout.yaml` was removed in v1.22.0; `LayoutFile` has no on-disk form — don't add load/serialize helpers to it.
- **The quick terminal's tab persists too** (`WorkspacesFile.quickTerminal`, an optional section with deliberately no schema bump — see its doc comment). `AppState` adopts `QuickTerminalService.shared.splitState` once (`adoptQuickTerminal`, injectable at init for tests), snapshots it in every `saveWorkspaces`, hands the tab back in `restoreSelection` before the orphan sweep, and counts its sessions as reaper claims — the panes attach only when the panel is first shown, so until then they sit at zero clients. `QuickTerminalSplitState` reports its own splits/closes through `onStructureChange` since it owns no `AppState`; a restore is refused once the panel has been shown this run. Consequences: quit kills nothing and confirms nothing while zmx is bundled (the confirmation returns, quick terminal included, only when zmx is unavailable), and closing a pane in the panel is still the one permanent kill.
- Settings → Projects duplicates the layout/unload/remove alerts; keep them gated on `AppState.DialogHost` so a confirmation raised from the palette doesn't also open Settings.

### Adding a new feature

**A feature request starts with "does ghostty already do this?", and the answer goes to the user before any code is written.** libghostty's config surface is large, and a Macterm-side implementation of something a ghostty key already expresses is a second, disagreeing answer the user has to discover — #393 deleted the scroll-speed slider and Macterm's entire wheel path once `mouse-scroll-multiplier` was actually tried, along with two Settings controls that `tab-inherit-working-directory` and `macos-shortcuts` had answered all along. Read ghostty's config reference and `ghostty.h` first, then:

- **A ghostty key covers it** → read the key live off the loaded config (see the config pipeline) and add **no Settings UI**. Where Macterm's default must differ from ghostty's, that departure is a line in `MactermConfig.defaultsBody`, never a `Preferences` fallback. Naming the key may be the whole answer — say so instead of building.
- **Ghostty can express it as a custom shader or a fork patch** → prefer that to a Swift reimplementation, and land it in Settings → Animations (off by default) first.
- **It is Macterm's own concept** (projects, per-project tabs, the sidebar, layouts, windows, the CLI, sessions) → build it here and follow *Adding a new setting*.

### Adding a new action

1. Add an `AppCommand` case (Title Case title, category, linked `HotkeyAction` if rebindable). The palette, menus and Settings pick it up.
2. If bindable, add the `HotkeyAction` to `Hotkeys.swift` with its default, **and the matching `MactermKeybind` case + label** — the App Intents picker restates them and `MactermIntentsTests` fails until it matches.
3. Handle it in the right `KeyResponder` in `Responders.swift`.
4. Add a `HotkeysTests` case for new parse/display behavior.

### Adding a new setting

Macterm-side settings go through `Preferences`; ghostty-shaped settings (theme, font, palette) belong in the user's ghostty config — don't add UI for them.

1. Add a `Preferences` property with a `didSet` writing UserDefaults.
2. Only if libghostty must be forced: `notifyConfigChanged()` in `didSet` and a line in `MactermConfig.regenerate()`.
3. Add UI to the matching `Macterm/Settings/` pane (a new pane also needs a `SettingsPane` case and a `SettingsView.detail` line).

### Windows and sidebars, AppKit reach-throughs

- **Settings window**: the sidebar is locked by `PinnedSidebar` (sets the `NSSplitViewItem`'s min == max thickness, `canCollapse = false`) *and* a `DividerShield` over the divider — SwiftUI resets the column metrics on events with no hook, so both layers are load-bearing. Replacing the split view's delegate crashes. The empty `NSToolbar` (`.unified`) is what gives it the roomier titlebar.
- **Main-window sidebar width** is persisted per window (`WindowSnapshot.sidebarWidth`, default `Preferences.defaultSidebarWidth`) and restored by `WindowAppearance.restoreSidebarWidth` via `NSSplitView.setPosition`, retried across run-loop ticks until the split view exists, because SwiftUI's autosave key embeds a runtime address (never readable back) and `navigationSplitViewColumnWidth(ideal:)` is ignored. `pinSidebarAutosaveName` gives the split view a stable name; `pruneChurnedAutosaveKeys` sweeps the old keys (matched on the `(unknown context at $` marker, skipped under tests). A collapsed sidebar is left alone. `forgetSidebarWidthRestore` clears a closed window's slot.
- **Main-window frame** is persisted per window too (`WindowSnapshot.frame`, AppKit's `frameDescriptor` string, recorded on every move/resize outside full screen) and restored by `WindowAppearance.restoreFrame` through `setFrame(from:)` (#496). SwiftUI's `WindowGroup` frame autosave is keyed by the scene's content type, which prints a private type (`AppColorScheme`) as `(unknown context at $ADDR)`, so it wrote a fresh `NSWindow Frame …` key every launch and never read one back. A stable name is not the fix: measured with `AppColorScheme` internal, every window of the group writes the one `AppWindow-1` key, so SwiftUI keeps a single frame per group (the last window moved) and other restored windows open at the default size — and the key still changes whenever the scene closure's modifiers do. `disownFrameAutosave` clears the window's autosave name at attach (one owner), and `pruneChurnedAutosaveKeys` sweeps both families of stale keys. A restored frame with under 60pt on any screen (a window manager's hidden-workspace corner) is centered on the main screen at its saved size.
- **Never leave persistent window state to a SwiftUI autosave.** Every one we have measured (sidebar column, window frame) keys on a runtime address and so silently resets on every launch and update; a stable key in `WindowSnapshot` is the rule.
- Overlay-sidebar spacing and blur are separate layers: the transparent `safeAreaBar` reserves titlebar space; `SidebarTopBlurBar` stays above rows and non-interactive.

## Known Limitations

- **Local sessions don't survive reboot**; remote ones do. Every pane — workspace, pinned, quick terminal — persists via zmx and reattaches after a quit.
- **Remote projects need zmx preinstalled on the host**; set `zmxPath` if PATH resolution fails. No install flow yet.
- **Remote orphan reaping only reaches sessions this installation stamped.**
- **A second window on the same tab shows a mirror**, dimmed where the pty is sized for the other view; `pane mirror` panes are not declarable in layouts, so Save/Apply Layout splits one into two sessions.
- **Adaptive background inference depends on ghostty's private renderer layout** (BGRA8 IOSurface) and fails closed; program-rendered selections (helix, vim under mouse capture) remain a residual gap.
- **Not Developer ID-signed**: first launch needs `xattr -cr /Applications/Macterm.app` or Homebrew. The stable self-signed cert keeps TCC grants across updates.
- **`macos-hidden = always` costs the menu bar**, so Settings, Quit, About and Check for Updates have no route while it is on; set Macterm's own preferences before switching it on.
- **Pane IDs are not stable across restarts.**
- **Desktop widgets aren't in the system's widget gallery** (see Desktop widgets), and don't take the system's monochrome look while an app is in front.
- **Password prompts are detected only where Macterm can read the prompting tty**: local panes and a remote project's own ssh login. `sudo` on a remote host, or anything behind a manually typed `ssh`, isn't seen; nor are raw-mode prompts that draw their own `*` mask.
