# Macterm Codebase Guide

A macOS terminal emulator built with SwiftUI and libghostty. It has a project-based sidebar, split panes, persistent zmx sessions, remote (ssh) projects, a quick-terminal overlay, desktop widgets and a control CLI. Since #353, it also has any number of windows on one shared model.

This file is the map. It says what exists, how the parts fit together, and which rules we learned the hard way. Each rule has no backstory. The reason for a rule is in three places. The first is the doc comment on the symbol that the rule names. The second is the PR that introduced the rule. The third is the git history of this file (the revision from before 2026-09 has the full narratives). When you change a rule, change its doc comment too.

## Build & Run

```bash
mise install          # Install tools (gh, swiftformat, swiftlint, xcodegen, xcbeautify)
mise run setup        # Download pre-built GhosttyKit.xcframework + ghostty resources + zmx
mise run run          # Build and launch (debug)
mise run logs         # Stream live logs from the debug app (--release for release app)
mise run format       # Auto-fix formatting with swiftformat
mise run lint         # swiftlint
mise run test         # Run the unit test suite
mise run e2e          # Debug build + end-to-end suite against the real app
mise run build        # Release build + DMG
mise run install      # Copy the built app to /Applications
```

`format`, `lint`, `test` and `e2e` show a spinner. They print output only when they fail. **Always pass `--verbose`** (`mise run test --verbose`) to stream the raw output.

**The Debug app signs ad-hoc, unless `Configs/Local.xcconfig` names an identity.** An ad-hoc designated requirement is the cdhash, and the cdhash changes at each build. TCC (Screen Recording, Accessibility, Full Disk Access, Local Network) therefore refuses each new `Macterm Debug.app`. Git ignores `Configs/Local.xcconfig`. A line `CODE_SIGN_IDENTITY = <name>` in it gives every Debug target a stable requirement. `Configs/Debug.xcconfig` includes it with `#include?`. `scripts/embed-zmx.sh` signs the bundled zmx with the same identity. The recipe for the self-signed certificate is in CONTRIBUTING.md ("Keeping macOS permissions across Debug builds").

- Keep `CODE_SIGN_IDENTITY` out of `settings.base` in `project.yml`. Project settings override the project xcconfig, so a value there hides the local identity. Release sets it in `settings.configs.Release`.
- A Release build takes its identity from `MACTERM_CODESIGN_IDENTITY` (`scripts/build.sh`, the release certificate in CI). The local file does not change it.
- The local identity must be a separate development certificate, never the release certificate. With it, every Debug build from any branch or worktree is the same app to TCC and gets the grants with no request.
- `codesign` reads the private key at each build. A headless build (an agent, `ssh`) cannot answer the keychain dialog, and a locked login keychain fails with `errSecInternalComponent`. A worktree with no `Configs/Local.xcconfig` signs ad-hoc. A file that names an identity that is not in the keychain stops the build at the start (`No certificate matching …`). It never falls back to ad-hoc, because a silent fallback removes the grants.

Macterm needs macOS 14 or later and Swift 6.0 or later. Liquid glass and some chrome refinements are macOS 26 (Tahoe) features. They are behind `#available` and `WindowAppearance.glassSupported`.

### The terminal core

- **"libghostty" here means `ghostty-internal`**. Upstream marks it "not for external use". `libghostty-vt` (the public library) has no surface API, so it is not a fallback. Treat every `ghostty_*` symbol as a symbol that can change without notice. Pin it, probe it and diff it. Do not assume it.
- `GhosttyKit.xcframework` and `Macterm/Resources/{ghostty,terminfo}` are artifacts of the `macterm/ghostty` fork. The bundled `zmx` is the build of `server/` at the same commit. Git ignores them. **Run `mise run setup` in every new checkout, including a git worktree**. Never make a symlink to them from another checkout. The presence check of setup would then never refresh them.
- The GhosttyKit release is **pinned** (`GHOSTTYKIT_TAG` in `scripts/setup.sh`). Setup records it in the stamp `.ghosttykit-tag`, which git ignores. A change of a pin is its own commit that a reviewer can check.
- **The server has no pin.** `scripts/build-server.sh` builds it for macOS universal and Linux x86_64 and aarch64 (static musl, stripped). That script holds the Zig version and the flags.
  - The build key is the git tree hash of `server/`, `protocol/` and that script, from the working tree. `zmx version` reports `1.0.1+thdxg.<key>`.
  - Setup installs the build for the key and records the key in `.server-key`. It takes, in order: `build/server` (CI puts its own build there); a Zig build when those folders have changes that are not committed; the prebuilt `macterm-<key>-<target>.tar.gz` from the `server-prebuilt` release; a Zig build. Every tarball is checked against its `.sha256`.
  - `.github/workflows/server-build.yml` builds on `macos-15`, because zig cannot link with Xcode 26.4 or later (zig#31658). It takes the prebuilt when it exists. It uploads a new build on `main` and on pull requests from this repository, and never replaces an asset. It removes assets older than 90 days, except the build of main's key.
  - The release workflows build from the commit, never from a prebuilt.
  - `build.sh` refuses a bundle whose server is not the build of the tree.
  - **The app carries a gzip build for every host target** for an install on a host, with no download: `Contents/Resources/server/macterm-<key>-<target>.gz` for `universal-macos`, `x86_64-linux` and `aarch64-linux`. The app reads the build key from the name of the macOS file (`ServerBuilds.bundledKey`); `embed-zmx.sh` names the files with the key of `.server-key`. `setup.sh` makes the Linux files next to `zmx`; `embed-zmx.sh` makes the macOS file from the signed `zmx`, so it has the app's identifier. The app's signature seals all three. `build.sh` refuses a bundle without them or with a macOS file that is not the bundled `zmx`. `build.sh` and `BundledResourcesTests` also check that each Linux file is an ELF binary for its machine.
  - A weekly auto-PR changes the GhosttyKit pin (`.github/workflows/bump-ghosttykit.yml`). It opens the PR with a token of the org's `macterm-ci` GitHub App (org variable `MACTERM_APP_CLIENT_ID`, org secret `MACTERM_APP_PRIVATE_KEY`), so that CI runs on it. It attaches an API review from `scripts/ghosttykit-api-diff.sh`. Read the section "renumbered enum constants" in that report. Swift imports enum constants by name, so a new constant in the middle of an enum compiles with no error.
- **The zmx fork is upstream v1.0.1 and no longer syncs.** The `DOWNSTREAM.md` on its main names each change by its old patch number (0003 is the leadership claim, 0004 the disclaim, 0010 the foreground report). zmx 1.0 changed the IPC header, so it cannot talk to a session daemon from before 1.0. We measured the 1.0.1 build against a 0.8.1 daemon: `zmx attach` hangs with a blank screen, `zmx kill` hangs, `zmx set` fails, and `zmx ls` lists the session as `err=Unexpected status=unreachable`. A pane whose session an older build started therefore opens blank. Closing the pane does not end that session: the kill hangs and Macterm stops it after 5 s, and the reaper skips an `err=` line. The old daemon and its programs keep running. Remote panes do not use the zmx of a host since 0057: they are sessions of the host's v2 server, and v1 sessions there keep running.
- **The header is under `#pragma clang assume_nonnull` since `build-2026-11-06`.** A pointer that the header does not mark `GHOSTTY_NULLABLE` imports into Swift non-optional, and a NULL there is undefined behavior, not nil. A fork field that can be NULL must carry the macro in its patch (`command` of `command_finished`, macterm/ghostty#41). `ghostty_runtime_config_s` has no zero initializer any more: every callback is given in its memberwise init, in `GhosttyApp.makeRuntimeConfig`, which is `nonisolated` on purpose. A closure literal made inside the `@MainActor` init is inferred main-actor-isolated, and libghostty calls the wakeup and the clipboard callbacks from its own threads: the test host died with SIGTRAP in `dispatch_assert_queue` at the first wakeup. The closures name `GhosttyApp.sharedCallbacks`, a nonisolated static, for the same reason. `GhosttyCallbacks.reportedCommand` reads the one field that a build imported non-null through its offset, as a nullable pointer, so that a NULL is nil under either header.
- A pinned tag is **not immutable**. The fork has uploaded assets again under the same tag. If a build behaves differently from an identical commit, compare the sizes of `GhosttyKit.xcframework/*/Headers/ghostty.h` before you suspect your own change. For the same reason, the DerivedData caches of CI have a key that includes the hash of that header. Do not merge the restore step and the save step in `test.yml`. Do not add a `restore-keys` fallback that does not depend on the framework.
- Setup needs the `GHOSTTY_ACTION_OUTPUT_ACTIVITY` ABI (the heartbeat for tab activity). To bisect to a commit from before that requirement, install a GhosttyKit of the same time by hand. Do not run setup.
- If a tree looks stale (a stamp does not match reality), run `rm -rf GhosttyKit.xcframework Macterm/Resources/terminfo && mise run setup`.

## Architecture

```
MactermApp (SwiftUI @main)
  └─ WindowGroup                       one scene, N windows (#353)
       └─ MainWindow  ── WindowState   per window: project, tab per project, sidebar, sheets
            ├─ SidebarContent          List with native selection
            └─ WorkspaceView
                 └─ SplitTreeView      recursive
                      └─ TerminalPane
                           └─ TerminalSurface (NSViewRepresentable)
                                └─ GhosttyTerminalNSView   owned by Pane, not SwiftUI
```

### Pane-owned NSView

A `Pane` owns its `GhosttyTerminalNSView`. `TerminalSurface.makeNSView` returns `pane.ensureNSView()`. This is a cached instance that lives as long as the `Pane`. `dismantleNSView` does nothing. The view dies only through `pane.destroySurface()`. A Ghostty surface is welded to its `NSView` and `CAMetalLayer`. If SwiftUI made the view again when the tree changes shape or you switch tabs, the surface would die. `SurfaceIncubator` is a window that is always invisible. It gives a pane that is off screen a window with a size, so that `createSurface()` can succeed early.

**The pane connects the callbacks of its view when it makes the view** (`Pane.connectViewCallbacks`, from `ensureNSView`): execution tracking, titles, search, bells, notifications and project memory. A pane that no window drew (a `tab new --no-focus` tab, a background tab that a launch warmed) therefore records its submissions and output, and `pane list` follows its runs. `TerminalSurface.configure` sets only the callbacks that need the window that draws the pane: focus, splits, zoom, process exit, tab titles, links, the adaptive background, and `onRunEnded` (the acknowledgement of a run that the user looks at). The poll pauses while the app is inactive and no window is visible (`PollCadence`), so the output heartbeat can be the only signal of a run in such a pane.

### State

- **`AppState`** is the single `@Observable` root. It is passed with `.environment()`. Every change to a workspace, tab, pane or window goes through it. You can inject `WorkspaceStore` for tests.
- **`ProjectStore`** is the project list (`projects.json`). It is saved on its own.
- **`Workspace`** is the collection of tabs of one project, `AppState.workspaces[projectID]`. The pinned tabs are a sentinel workspace (see Pinned Tabs).
- **`TerminalTab`** is a `SplitNode` tree plus the IDs of the focused pane and the zoomed pane. **`SplitNode`** is `.pane(Pane)` or `.split(SplitBranch)`.
- **`WindowState`** (`Macterm/App/WindowState.swift`) exists once for each window. It holds the project that the window shows and its tab for each project (`activeTabIDs`). It also holds the width and visibility of the sidebar, and the flags of the palette and sheets. Macterm saves it as `WindowSnapshot`.
- **`Preferences`** is an observable wrapper for UserDefaults. Never touch `UserDefaults.standard` in app code. Under tests, `Preferences.defaults` resolves to a side suite that Macterm wipes.

### Windows (#345, #353)

These rules make many windows work over one model:

- **The registry is keyed by `NSWindow`** (`AppState.windows`, a weak-keyed `NSMapTable`). SwiftUI makes a view and its `@State` more than one time for each real window, so the view cannot own the identity. The first `WindowState` that someone proposes for an `NSWindow` wins (`canonicalWindowState`). Register when the window attaches to the `NSWindow`. Never register in `onAppear`. Never stamp the SwiftUI window identifier.
- **A window registers when AppKit attaches its `WindowStyler` view** (`WindowAttachmentView.viewDidMoveToWindow`). Never poll `view.window` with a limit on main-queue turns. SwiftUI can make the view before its window exists, and an idle main queue runs 30 turns in a few milliseconds. A window that `window new` opened during launch then never registered: it showed its sidebar and no terminal, and `window list` did not show it.
- **There is one teardown entry**. `AppState.windowDidClose` clears every table that is for one window. A new table for one window must hang off it. Key it weakly by the window. Never key it by `ObjectIdentifier`, because Swift uses an address again.
- **App-wide values mirror the key window**. `noteKeyWindow` pushes `AppState.activeProjectID`, `Workspace.activeTabID`, `sidebarVisible`, `isCommandPaletteVisible` and similar values from the `WindowState` of the key window, and into it. Anything that you *render* for one window must read `WindowState`. It must never read the mirror. Something that happens *to* a project (a click on a notification, CLI `pane focus`) goes through `revealProject`. That function brings forward a window that already shows the project.
- **The real panes of a tab render in one window. Other windows on that tab render a mirror**. `tabOwners` is sticky (`reconcileWindowViews` settles it). A window that is not the owner gets a *shadow* tab of `Pane(mirroring:)` panes. They are connected to the same zmx sessions. Macterm builds the shadow tab again when the `shapeSignature` of the real tab changes. `WorkspaceView` maps the focus, zoom, split and click of a mirror onto the real tab by the position in the tree (`counterpartPaneID`). The pinned workspace has **no tab selection for each window**. Every path that reads `activeTabIDs` skips the sentinel.
- **Only `reconcileWindowViews` builds a shadow. `viewTab(for:in:)` is a pure read**. It returns the real tab for the owner, the shadow in `WindowState.shadowTabs` for any other window, and nil when there is none. It never allocates. The reconcile builds or refreshes the shadow of every window in `AppState.renderingWindows` that selects a tab it does not own, and it drops the rest. It runs inside every mutation that changes what a window shows: register, unregister, key window change, a project or tab selection in a window, `restoreWindows`, and `saveWorkspaces`, which follows every structural mutation (a split, a closed pane, a merge, a layout, `pane mirror`). It is cheap and idempotent, so add a call where a new mutation changes a tab's shape or a window's selection. Zoom changes no shape. Before this rule, `viewTab` built the shadow as a side effect of rendering. Every window that asked got a fresh tab of mirror panes, each one a zmx client, and no reconcile dropped it. Each stray client that we found (#353, #359, #366, #557, #657) was one more caller that nobody had guarded.
- **`renderingWindows` is the one set of windows that can own a tab and that can get a shadow**. It is the registered windows, plus the scene's own window from the moment `restoreWindows` adopts it, before it registers (`windowAdoptedBeforeRegistration`). A window outside the set renders nothing: a closed window whose SwiftUI view lives on, or a window that has not registered yet. It gets no shadow, however often its view renders. `registerWindow` lists a window before it applies the saved frame, and the reconcile at the end of registration gives it its tab.
- **Session leadership**. Only one client of a session is the leader. Its size sets the size of the pty. The other clients render dimmed. `AppState.sessionLeaders` tracks the leader. The claim is a `claim` message on the pane's channel (`PaneSession.claim`; a claim before the first attach waits for it). Leadership follows the tab of the key window as a whole (`claimLeadershipForKeyWindow`). Macterm asserts the records again. It never trusts them. It sends the claim only when leadership moves, synchronously. It records the claim only if the pane has a channel. It never sends the claim on focus for remote panes. **A pane in the key window's tab claims when its surface has a size, also when the model counts one client** (`surfaceDidGetSize`, `assertSessionLeadership`). `isMirrored` counts only the clients that Macterm knows of. A client from outside the model attaches first and leads, and the session then drops the control keys of the visible pane. The claim is a no-op for a client that already leads. A window that is not the key window and whose tab has only panes that are not leaders renders `MirroredTabNotice` and not panes. The key window always renders its panes. After that, the first responder is restored through `FocusRestoration.restoreFocusWhenAttached`. It finds the window from the own view of the pane.
- **Closing and quitting**. Only the **last visible** terminal window hides when you close it (`AppDelegate.hidesInsteadOfClosing`). Every other window really closes. A quit freezes the window list (`unregisterWindow` does nothing under `AppTerminationState.isTerminating`). Without this, each window that closes would save a snapshot again with one window fewer. `restoreWindows` gives the first saved entry to the own window of the scene. It opens the others with `applicationOpenUntitledFile`. It fronts the saved key window last.
- **`AppDelegate.isTerminalWindowCandidate` answers "Is this the terminal window?"** Do not use `!(window is NSPanel)`. The function excludes marker subclasses (`QuickTerminalPanel`, `SurfaceIncubatorWindow`). Send any new auxiliary window through it. It is a heuristic. Use it only before `didBecomeMain` has cached the real pointer.
- **Macterm activates the app for a window that opens from the quick terminal while the app is inactive** (`QuickTerminalService.panelDidResignKey` → `AppDelegate.activateForKeyHandoff`). The panel does not activate the app, and it takes keys while another app is frontmost. If you type ⌘, or ⌘N into it, Settings or a new window becomes key in an inactive app. That window is dimmed and you cannot type in it. Macterm watches the handoff for one run-loop turn (the new window becomes key synchronously when the panel resigns). It forces the activation with `ignoringOtherApps: true`. That one activation skips `reopenIfNeeded`. Without this, a terminal window that is hidden comes to the front over the window that the keystroke asked for.
- **A launch that does not front the app builds no window (#241)**. This is how macOS opens apps again at login. `AppDelegate.repairMissingWindow` polls for about 3 seconds. Only if no candidate window exists, it calls `applicationOpenUntitledFile` (activation alone does nothing). The condition is "no window at all". `requestInitialWindow` debounces the call. Without these, one launch opens two windows.
- `AppDelegate.reopenIfNeeded` (the Dock click that brings the app to the front again) uses an `NSWorkspace.didActivateApplicationNotification` observer. `applicationShouldHandleReopen` is not reliable through `@NSApplicationDelegateAdaptor`. Observers that you install in `didFinishLaunching` miss window notifications at launch. On launches from the Dock or Finder, `didBecomeMain` can fire before `didFinishLaunching`.
- **Full screen is native, and fn+F belongs to AppKit**. The `toggle_fullscreen` action of ghostty (⌃⌘F and ⌘↩ by default) toggles the own window of the pane through `toggleFullScreen(_:)` (`GhosttyCallbacks`). This is the same path as the automatic Enter Full Screen menu item of AppKit. That item carries fn+F of macOS. Leave that item alone. Do not set `NSFullScreenMenuItemEverywhere` to false. Do not change its shortcut. Ghostty.app lost fn+F when it rewrote the shortcut of its full-screen item (ghostty-org/ghostty#1389). Macterm does not honor `macos-non-native-fullscreen`. The panel of the quick terminal cannot go full screen.

### Hotkeys

`HotkeyAction` and `HotkeyRegistry` hold the bindings. The defaults are in `Hotkeys.swift`. Overrides are at `macterm.hotkey.<action_id>`. `KeyRouter` installs one `NSEvent.addLocalMonitorForEvents`. It dispatches through the ordered `KeyResponder` chain in `Responders.swift`. `isAppShortcut` in `GhosttyTerminalNSView` lets registered shortcuts pass the terminal.

**Passthrough (#209)**. An action can opt in with the suffix `.passthrough`. Then Macterm gives the chord to the program in the focused pane when the name of that program is in `Preferences.passthroughPrograms`. `KeybindPassthrough` owns the policy. Both key paths (the responders *and* `isAppShortcut`) read it. Remote panes never yield. We tried two times to infer the condition (tty raw mode, "not a shell"), and both failed. Read the doc comment of the type before you try again.

**Global keybinds**. An action can opt in with the suffix `.global`. It is an item in the menu of its row in Settings → Keymaps, next to passthrough. Macterm then registers the chord as a Carbon `RegisterEventHotKey`, so it fires while another app is frontmost. This is the `global:` prefix of Ghostty. `GlobalHotkeys` owns every registration in the process, including the registration of the quick terminal (`HotkeyAction.isAlwaysGlobal`). `sync` reconciles the registrations after each rebind and each change of a flag. It leaves a chord that did not change alone. We use Carbon and not a CGEvent tap, because Carbon needs no Accessibility grant. The system also reports a chord that it will not give us (`eventHotKeyExistsErr`). The row then says so. Otherwise, a chord would do nothing anywhere, in silence.
**One owner:** Carbon consumes a registered hot key, so the local monitor never sees that keyDown. `KeyRouter` yields exactly the chords that Carbon *holds* (`yieldsToCarbon`). This states the rule that nothing fires two times. It also lets a chord that Carbon *refused* work as a plain local keybind. Two results are deliberate. A global chord always runs its app-level `AppCommand`, so it no longer reaches the own splits of the responder of the quick terminal. And Macterm refuses global together with passthrough on one action, so that it does not defeat passthrough in silence. A chord that fires brings a window to the front first (`AppDelegate.showWindow`). The exception is the toggle of the quick terminal, because its panel does not activate the app.

**Non-Latin layouts**. Some keys type no ASCII (Cyrillic, Greek, Hebrew, Arabic and others). A ⌘ chord on such a key gets its name from the Command key map of the layout: `HotkeyRegistry.commandKeyCharacter`. This is the QWERTY Latin letter that those layouts type under ⌘. That one name serves all three matchers:

1. The bindings of Macterm (`eventToken`).
2. The carve-out of `isAppShortcut` for system keys (⌘Q, ⌘H, ⌘M and ⌘,).
3. libghostty. `performKeyEquivalent` gives it the name as the text of the key.

libghostty resolves a unicode binding such as `super+c` from the text before it uses the unshifted codepoint. Under a Cyrillic layout that codepoint is `с`. Without the text, ⌘C and ⌘V matched nothing. The three matchers must agree. If they do not, the raw default bindings of ghostty (`super+q=quit`, `super+w=close_surface`) take chords that Macterm or the menu bar owns. A key that types ASCII keeps its own character. Dvorak, AZERTY and every other Latin layout are unchanged.

### Tab naming and activity

- The automatic title of a tab is the name of the foreground process (`ProcessInspector.runningProcessName`, the kernel `comm`). If there is none, it is the login shell (from `getpwuid`). `customTitle` overrides it. There is no switch for this (`macterm.tabs.autoName` is a retired key). The polling also serves busy-close and execution tracking.
- `AppState` polls in an adaptive way (`PollCadence` and `refreshAllForegroundProcesses`). It polls every 250 ms in a burst after any `.terminalPollEvent`. It polls every 1 s when the app is active and idle. It polls every 2 s when the app is inactive. It stops when nothing is on the screen.
- **Execution tracking runs whatever the "Show tab status indicator" setting is** (#705). `pane list` reports the state, and agents wait on it. The setting only chooses what the tab row draws (`TabIcon`).
- **The `GHOSTTY_ACTION_OUTPUT_ACTIVITY` heartbeat is the only source of activity**. It fires also while the pane is occluded. The scrollbar action in the render path does not. Completion edges (OSC 133;D and foreground transitions) rebase the row baseline. Then the late heartbeat of a fast command never starts it again as activity. `TerminalExecutionTracker` has the rules for when output that does not grow counts as work (foregrounds of AI agents after a real Return).
- **An OSC 9;4 progress ERROR ends the run as a failure**. The done dot of the tab turns red (`MactermTheme.failure`, palette 1, tooltip "Failed"). The outcome is `Pane.completionFailed`. This flag has a meaning only while the state is `.done`.
  - `executionState`'s `didSet` clears the flag each time that the state leaves `.done`. Every path that acknowledges a run therefore clears red in the same way as it clears green.
  - The code sets the flag *before* `.done` publishes. The poll that the publish wakes can save or acknowledge at once, in the same call.
  - Never add a fourth `TerminalExecutionState`. The guards of the tracker compare against `.done`.
  - REMOVE and PAUSE end a run as a success. Macterm drops a report that finds the pane not `.running`. For this reason SET → ERROR → REMOVE stays red.
  - Within a tab, running wins over failed, and failed wins over done.
  - It persists as `PaneSnapshot.completionFailed` next to `needsAttention`. It never replaces `needsAttention`.
  - The `state` of the CLI stays `done`. The percentage is never shown.
- OSC 0 and OSC 2 titles are **gated by provenance** (`Pane.receiveReportedTitle`). Macterm adopts one as `programTitle` only while the foreground is a real program. It pins the title to that pid. The title expires when the program loses the foreground. Macterm discards titles that a prompt sets (nushell, Starship). It never persists titles.
- **Macterm throttles a title report before it costs anything** (`TitleReportThrottle`, one for each pane, pure and tested).
  - The lookup of provenance and the refresh of the foreground that a title triggers cost about 100 µs of syscalls. These are `KERN_PROCARGS2` three times, and `open` and `tcgetattr` on the tty.
  - A zmx session that replays scrollback with many prompts at launch reports one title for each prompt. 150k of them froze the main thread for 14 seconds. The control socket did not answer.
  - Macterm evaluates the first title after a quiet window (`PollCadence.fastInterval`, 250 ms) at once. It holds the other titles of the window. The newest title wins. It flushes once at the end of the window. Nothing is dropped. A title is at most 250 ms late. Macterm judges it against the foreground that holds the pane at that time, which the next tick of the poll would have seen anyway.
  - `receiveReportedTitle(_:programPID:)` is the core with no throttle. The tests drive it. `destroySurface` cancels a flush that waits, and it resets the window.
- **Remote panes** have no local pid. Their name comes from OSC titles (`Pane.receiveRemoteReportedTitle`) and from the host's foreground reports. Nothing else names them: Macterm makes no background ssh for a remote project (0058).
  - **The host's session pushes the foreground (#695).** The pane attaches with `foreground: true`. The session reads the pty's foreground process group before it forwards each chunk of output, and every 500 ms, and sends a `foreground` message on the pane's channel, in order with the output. `PaneSession` gives it to the surface host (`SurfaceChannelHost.paneForeground`), which turns it into a `RemoteForeground` for the pane (`Pane.applyRemoteForeground`).
  - The report carries the host's verdicts about idle and about the shell (`/etc/shells`), and the foreground command line. The command line is the fallback of argv for the agent logo, as `KERN_PROCARGS2` is on the local Mac. It also gives the name of a `comm` that a version names. The sample's origin is `.remoteEvent`.
  - **The order is the point.** A report that the shell is back lands before the shell's prompt, and a report that a program started lands before its first output. A title outside a run is therefore judged against the latest report at once: shown when a program holds the pty, dropped when the shell does or when no report came. A title that arrives while the pane is running (OSC 133, activity, progress) is shown at once. A title that arrives at a prompt that OSC 133;D announced is discarded. A run that ends keeps its title only while the latest report says a program holds the pty. This is how an agent that is idle between turns keeps its title.
  - **A title in the replay of an attach never names the tab.** The session replays its last title with its screen, maybe a prompt's from before the program in front started. The session sends `snapshot.start` and `snapshot.end` messages around each snapshot, and `Pane.receiveReportedTitle` drops every title between them (`Pane.receiveRemoteSnapshot`), before the throttle. The pushed foreground names the tab.
  - The session reports only on macOS and Linux (`proc_pidpath`, `/proc`). A pane with no server on its host (a plain shell) gets no report: it keeps the host name and the titles of its runs, and closing it always asks (the surface's reading of the ssh client: never silently kill an unknown foreground).
  - Both pipelines publish one value, `Pane.foregroundSample`. Policies such as `ForegroundPolicy.needsConfirmClose` are pure functions over it. Every busy-close guard reads `Pane.needsConfirmClose`. It never reads `needsConfirmQuit` of libghostty directly, because for a remote pane that only sees the `ssh` client.
- **`bell-features = attention` has two halves.**
  - `GHOSTTY_ACTION_RING_BELL` handles the app-level parts in `GhosttyCallbacks.ringBell`: the beep, `bell-audio-path` and `NSApp.requestUserAttention`. It also flags the pane that rings (`Pane.ringBell`). `title` and `border` are UI for each tab that Macterm does not implement.
  - The Dock badge is the second half. `BellBadge.label` is the pure rule from the count to the label (nil without `attention` or with nothing that rings, capped at `99+`). `BellBadge.apply` is the one AppKit write. `AppState.syncDockBadge` joins the two.
  - The badge counts **tabs**, not the windows of ghostty, because the user goes to a tab and looks at it.
  - The badge is DERIVED. Code never writes it from the ring. For this reason, a config reload that drops `attention` clears a badge that is already up, and no code path needs to know about clearing.
  - Acknowledgment follows the existing verdict of Macterm, "looking at the active tab". It does not follow the rule of ghostty about the next keypress. The badge therefore cannot disagree with the sidebar. A bell in the active tab of the active app is seen the moment that it rings. Everything else clears in the same way as the completion dot: tab selection, pane focus or interaction, the app that comes forward, and surface teardown.
  - Each change of the flag posts `.terminalBellStateDidChange`, so clearing is derived again with no extra work.

### Password prompts (Settings → Password Manager)

A pane that asks for a password gets a native `NSPopover` at the cursor (`PasswordBubble`). The bubble shows **Autofill** when Macterm saved a password for that prompt. It shows **Save Password?** after a password that the user typed worked. `PasswordPromptMonitor` (`Macterm/App/`) does all of this. The pure rules are in `Macterm/Model/PasswordPrompt.swift`.

- **Detection uses the tty, not the screen**. The rule is canonical mode with echo off (`ProcessInspector.terminalIsReadingPassword`). Ghostty and iTerm2 use the same rule.
  - Macterm reads the tty of the **session** (`ZmxForegroundResolver.daemonTTYPath`, the `pty` of `session.list`). A manual surface has no pty of its own, so libghostty sees none. Under a session, `GHOSTTY_ACTION_SECURE_INPUT` never fires.
  - The same reading also drives `macos-auto-secure-input` (`GhosttyTerminalNSView.detectedPasswordInput`, combined with OR with `passwordInput` of libghostty). The lock badge for each pane is off by default (`macos-secure-input-indication = false` in the defaults layer), because the bubble marks the prompt.
  - Macterm reads the tty in three cases:
    1. On the output heartbeat of the pane (`viewDidOutput`), because a prompt is output.
    2. On every key that the user types into the pane (`viewDidType`). `keyDown` reports it **at the send point, as the text that the tty receives**. This is the committed text of the IME. Nothing is reported during a composition. Nothing legible is reported for an option-as-alt chord. A chord that `isAppShortcut` or the ⌃\ swallow ate is never reported. A program on the own pty of the surface has therefore already ended its read when Macterm reports the Return. An example is the ssh of a remote project. A line end belongs to the prompt that was up when the line went out.
    3. On a timer: every 1 s, with tolerance, for the focused pane while it is idle. Every 150 ms only while some pane is in a *timed* phase (`sighted`, `verifying`), or for `outputWatchWindow` (750 ms) after a heartbeat. A pane that is parked at a prompt or at an offer that nobody answered costs only the slow cadence.
  - **The heartbeat alone cannot sight a prompt**. It is leading-edge with drops: the first output after 500 ms of quiet fires at once, and every chunk in the 500 ms after it is dropped. The echo of the command fires it before the tty changes. The prompt that the program prints after that is in a dropped chunk. Without the watch, the sighting waited for the idle timer. The bubble then came up about 2 s after the prompt. With the watch, the sighting lands within one fast tick of the tty change. A sighting also schedules one look at the end of its hold (`scheduleConfirm`), so the confirmation does not wait for the tick after it. What remains is the hold of 200 ms and the animation of the popover. Measured in a hermetic instance with `pane password`: the prompt was confirmed about 0.93 s after the command went in before, and about 0.37 s after.
  - `pane run` and `pane key` feed the same capture (`viewDidSendText` and `viewDidSendKey`). This is how the e2e suite answers prompts. The monitor fences off its own autofill typing (`isInjecting`).
  - Everything that the monitor reads or drives goes through `PasswordPromptMonitor.Probes`. `PasswordPromptMonitorStateTests` therefore runs the whole machine without a surface.
  - A sighting must hold for 200 ms, unless the user types at it. A script that drops echo to read a reply of the terminal is not a prompt.
  - Prompts of a host's session (`sudo` on a host) are seen through `tty_mode` (see "Prompts on a host"). Prompts inside an `ssh` that you typed by hand stay invisible, because the local ssh client is raw. The own ssh login of a remote project asks in a sheet (`SSHLoginPrompts`), not in the pane.
- **The identity is the command and the prompt line** (`PasswordEntryID`). The command is the foreground command, named by the **real path of its executable** (`ProcessInspector.passwordAsker`: `proc_pidpath` and argv without argv[0]). The prompt line is the last viewport line that is not empty.
  - Never use argv[0]. A process sets it for itself. `exec -a ssh ./fake prod` would collect the password that Macterm saved for the real ssh.
  - `runningCommand` (the capture of `run:` for a layout) still uses argv. Do not change it.
  - The prompt line separates the two passwords of `ssh -J bastion prod`.
  - There are three exceptions. `sudo …` is filed under `sudo` (one login password). Key passphrases are filed under the prompt alone. The login of a remote project is filed under `ssh user@host` (the login sheet offers it).
  - **Those two shared entries answer only a program that the user cannot have replaced** (`PasswordAsker.isProtected` and `ProcessInspector.isProtectedExecutable`). The executable and every directory above it must belong to root, and we must not be able to write them. This is true of `/usr/bin`. It is false of Homebrew and `~`.
  - Anything else with the name `sudo` is filed under its own full command. A passphrase that a program asks for, and that someone can replace, is filed under the path of that program. Without this rule, a `~/bin/sudo` earlier in PATH that prints `Password:` would get the autofill of the login password.
  - A shell that *runs a script* is a program for `passwordAsker` (`isIdleShellInvocation`). A prompt inside `./deploy.sh` is therefore filed under `/bin/sh ./deploy.sh`.
  - The idle shell itself (`read -s`) is `.shell`. It is filed by the prompt alone.
  - A foreground that Macterm cannot read is `.unknown`. It is never `.shell`. The prompt stays `sighted` and Macterm tries again. A key that the user types in the meantime taints the capture (`confirmTyping`).
  - When Macterm shows an entry, it shortens a resolved program path to its name. It drops the options that the ssh wrapper of Macterm injected (`SSHWrapper.userArguments`). The exception is a program that is named `sudo`. It keeps its path, so that it cannot pass for the real one. Matching never shortens.
  - The Details editor files through `declaredEntryID`. It trusts what the user typed.
  - **`Preferences.passwordManagerEnabled` is the master switch**. Macterm stores it under the old key "Offer to save", so an old "off" stays off. When it is off, `step` drops the pane to idle with its offers at every observation. Nothing is captured, offered or autofilled. `detectedPasswordInput` still follows the tty.
- **Macterm offers to save only on evidence** (`PasswordSubmissionJudge`).
  - These events mean failure: a failure line within `failureWindow` (3) lines of the prompt.
  - These events mean success. One is a prompt that is up again after the settle window. Another is an OSC 133 exit with **any** code. Another is output that is not a failure. The last is a tty that leaves line mode (`ICANON` off). A remote project login shows only the last event. zmx then draws the screen again from the top, and nothing is drawn below the prompt.
  - Silence for more than 12 s saves nothing.
  - Two things are deliberately not rejections. One is the exit code, because it judges the command (`sudo grep -q` exits with 1 when it accepted the password). The other is the identical prompt again with no failure line (git over HTTPS asks one time for each connection).
  - Typed keys go through `PasswordLineCapture` (DEL and ⌃H, ⌃U and ⌃W edit the line, and arrows and escape taint it). It gets them from `keyDown` before libghostty, and from `surfaceDidPasteText`.
  - Offers queue (`ssh -J` gives two). Macterm shows one at a time when no prompt is up. An offer expires after `offerLifetime` (15 minutes). Only a command that *the own shell of the pane* runs drops an offer (`foregroundProcessIsShell`). A bare Return keeps the offers. Anything that the user types into the remote shell of ssh keeps them too.
  - If a keychain write fails, the offer stays up with the error (`Offer.problem`). Macterm does not lose the secret.
  - A keystroke at a prompt while a submission is still `verifying` settles the verdict at once (`settle`). A fast retype after a rejection is therefore not captured without its first characters.
  - Failure lines count only within `failureWindow` (3) lines of the prompt. A MOTD that says "denied" is a successful login.
  - Macterm never offers prompts for one-time codes (`isOneTimeCode`).
- **Storage is the login keychain** (`KeychainPasswordStore`, service `<bundle id>.passwords`, metadata as JSON in `kSecAttrGeneric`).
  - The data-protection keychain needs an entitlement for a provisioning profile. A self-signed app cannot have it. Touch ID is therefore the gate of the app (`PasswordAuthenticator`, `.deviceOwnerAuthentication`). The default is once for each app launch. A screen lock, sleep or a switch of user also ends it. Macterm never persists it, because a lock while Macterm is quit leaves no reliable trace. The other option is every time.
  - A debug build with an ad-hoc signature gets a keychain dialog on a read. A debug build with a stable identity (`Configs/Local.xcconfig`, see Build & Run) gets it one time, until you click Always Allow.
  - Tests, `MACTERM_BENCHMARK=1` and any launch with `MACTERM_BENCHMARK_DATA_DIR` use `InMemoryPasswordStore` (`PasswordVault.isHermetic`). A **debug** build under that condition skips Touch ID. The only passwords that such a run holds are passwords that it captured itself. The e2e suite autofills with nobody at the keyboard.
- **Autofill types and never pastes** (`GhosttyTerminalNSView.sendSecret`: the text path without the evidence of a command submission, then Return). It checks the tty again after authentication. It clears a line that the user half typed with ⌃U first.
  - A refused autofill turns the next sighting into "Saved Password Did Not Work". A typed password that then works is offered as an update.
- **The bubble never keeps the key**. It has the behavior `.applicationDefined`. Every button gives the key back to the window of the terminal (`PasswordBubble.returnKey`). It does this only when the popover or nothing holds the key. It never takes the key from another window of ours.
  - The anchor is `cursorCellRect()` (the IME point of libghostty).
  - **Return is the primary button, and Escape dismisses**. Both go through the key path of the terminal (`viewWillSendKey` consumes them). They work only while the user typed nothing since the bubble appeared (`Tracker.typedSinceBubble`). `PasswordBubble.show` resets it when it reports new *content*. A new anchor after the cursor scrolled away and back does not reset it. The first character gives both keys back. A password or a command that the user types under the bubble therefore submits as usual.
  - The bubble draws no key hints.
  - A parked AeroSpace window (off screen) makes AppKit push the popover onto the visible screen. This is not an error of the anchor.
- **On demand** (`PasswordPaletteScope`, the Password Manager of the palette) types any saved entry that the user selects. It types into the focused pane of the active tab (`PasswordPromptMonitor.fillOnDemand`). It needs no prompt match and **no confirmation**. The selection is the authorization. Touch ID still gates the read.
  - The tty decides only Return (`OnDemandPasswordFill` over `TerminalLineMode`).
  - At a verified read (canonical, echo off), Macterm presses ⌃U first, then types the password, then presses Return. It judges the result as an autofill. Its `Submission.id` is the entry that the user *selected*. A rejection therefore marks that entry, and Macterm offers nothing that was typed for saving.
  - At any other place, Macterm types the password with no Return. Examples: ssh or tmux that relays a remote prompt, the line editor of a shell, and a line that echoes. Remote `sudo` is the reason that this feature exists. A wrong selection then never runs, and it never reaches a history. The user submits it or clears it.
  - If a verified read is gone after authentication, Macterm types nothing.
  - **An entry with an empty prompt is only for on-demand use** (`PasswordEntryID.isOnDemandOnly`). Detection never reads an empty prompt line, so nothing ever autofills it. Its keychain account is `<command> — on demand`.
  - The screen is also an action that you can bind (`HotkeyAction.passwordManager`). It has no keybind by default, because ⌥⌘F belongs to Autofill. It is in the View menu. It toggles the palette on that screen (`AppState.toggleCommandPalette(scope:)`). While the palette is up, the app responder stands aside, so `PaletteResponder` answers that chord itself.
  - You add entries from the `+` of Settings, or from the Add rows of the palette. Both use `PasswordEditorSheet`, which Details… shares. `MainWindow` presents the copy of the palette from `WindowState.passwordEditor`. The sheet **requires a command**. Only detection creates entries with only a prompt (key passphrases, `read -s`). You can edit them as they are. You never create them, and you never make them by hand.
- **`pane password` (DEBUG only)** reads the phase, prompt, command and bubble of a pane. It never reads a secret. `--answer accept|dismiss|autofill` presses the buttons of the bubble. `scripts/e2e/test_passwords.py` drives the whole flow with it against a `stty -echo; read` script.
- **Never** add a CLI verb, an App Intent or a log line that carries a secret. Any process in a pane can call `macterm`.
  - Autofill Password is an `AppCommand` (default ⌥⌘F). Its action is nil unless the focused pane is at a saved prompt. As for every chord with a nil action, `isAppShortcut` then swallows it in `keyDown`. It does nothing, and it does not reach libghostty (which has no default on `super+alt+f`).

**Prompts on a host** (design/006 section 6, Ethan: B). A remote pane attaches with `tty: true`. The host's session reads the pty's `ICANON` and `ECHO` and sends `tty_mode` when they change and to a client that connects (`Session.checkTty`). The app keeps the mode in `Pane.remoteLineMode`, and the monitor's probes read it for a remote pane. Line capture and the judge stay in the app: no secret goes to a host.

- **A host entry has a scope** (`PasswordEntryID.host`): the ssh destination as `ssh -G` resolves it (`RemotePasswordScope`, read again after 60 s). With no scope yet, or after a failure, the asker is `.unknown`: nothing is filled or offered.
- **Nothing a host reports is protected.** There is no shared `sudo` entry and no shared key passphrase entry on a host: each is filed under the host's command line. A process on a host can print any prompt and rewrite its own argv, so the host's word is a hint only.

### Copy mode (fork patches 0013 to 0018)

Copy mode is a keyboard cursor over the scrollback, with the keys of Vim by default and the keys of Helix as a setting, over the selection model of Helix. The grammar for users is in `docs/42-copy-mode.md`. The **terminal's selection is the cursor**: its end is the head that the motions move, its start is the anchor.

- **The primitives are fork patch 0013** (`.github/downstream/0013-selection-motions.patch` in macterm/ghostty): the binding actions `start_selection`, `move_selection:<motion>`, `extend_selection:<motion>`, `collapse_selection`, `flip_selection`, `select_line` and `clear_selection`. The arithmetic is `Selection.move` and `Selection.expandToLines`, with tests in `Selection.zig`. The fork's `Test` workflow is off, so `build-ghosttykit.yml` runs `zig build test -Dtest-filter=Selection -Dtest-filter="parse:"` before each build. `adjust_selection` of upstream cannot serve: it needs a selection that the mouse made, it only grows it, and it skips blank cells.
- **The drawn cursor is fork patch 0014** (`0014-selection-cursor.patch`): the binding action `selection_cursor:on|off` sets `Terminal.flags.selection_cursor`, and the render state (`render.zig`) then takes the head of the selection as the cursor cell instead of the program's cursor. That cursor is a steady block, shown even while the program hides its own, and a one-cell selection draws as that cursor alone, as in Helix. The program's cursor does not move, and hit tests and the IME point stay on it. `CopyModeController.enter` sends `on` after `start_selection`; `exit` sends `off` before `clear_selection`. `smooth-cursor` glides it between motions. The build's filter `"selection head"` runs its test.
- **The keys live in Macterm, not in a ghostty key table** (`HelixKeymap` and `VimKeymap` in `Macterm/Model/CopyMode.swift`, pure, `CopyModeTests` and `VimKeymapTests`). This is so the keymap is a Settings choice (`Preferences.copyModeKeymap`, Settings → Keymaps → Copy Mode, read at `CopyModeController.enter`; the default is Vim, because more users know it), and so counts (`5j`) and `g` sequences work. `CopyModeController` (`Macterm/Views/Terminal/`) owns the mode of one view. It resolves each key through the keymap and runs the actions with `sendBindingAction` (`ghostty_surface_binding_action`). The pill's title comes from `CopyModeKeymap.label(for:)`.
- **The Vim keymap needs fork patch 0015** (`0015-selection-vim.patch`): `move_selection:next_word_start` (Vim `w` lands on the next word, Helix's `word_next` before it), `select_line_bounds` (Vim `V`, Helix `X`: whole rows with the direction kept and no growth, so `Vk` keeps moving the head up; `select_line` is Helix `x`, which normalizes the direction and grows by a row) and `selection_rectangle:on|off` (Vim `⌃v`, the `rectangle` flag of the selection). Vim normal mode moves with the anchor on the head; `v`, `V` and `⌃v` are `CopyModeState.visual`; visual line mode sends `select_line_bounds` after every motion; leaving a visual mode collapses to the head, and leaving block mode turns the rectangle off first.
- **`keyDown` and `sendKey` give the controller every key first** while the mode is on. A ⌘ chord is not the keymap's (`resolve` answers nil), so ⌘C, ⌘W and every app shortcut work as before. Any other key that is not in the table is swallowed, so nothing types into the shell. `sendKey` has the same gate so that `pane key` drives the mode in the e2e suite.
- The mode keeps no position. Its state is `selectMode` and a pending prefix (`g`, a count). A mouse drag while the mode is on moves the selection, and the next motion continues from it. `destroySurface` resets the mode without touching the surface.
- The pill is `Pane.copyModeLabel` (`Copy Mode`, `Select Mode`, never persisted), drawn by `ModePill` in `TerminalPane` — the Zoomed pill's chrome, shared through `ModePill` in `MainWindow.swift`. A click on it leaves the mode.
- **Every badge of a pane is one row in its trailing corner** (`TerminalPane`, the `topTrailing` overlay): from the left, Read-Only, Copy Mode, Zoomed, then the secure-input lock. The Zoomed pill moved there from the tab's own overlay in `WorkspaceView`: a zoomed pane is the only pane on screen, so the corner is the same, and one row cannot overlap itself. The quick terminal's zoomed pane got the pill with the move.
- **Copy Mode** is an `AppCommand` (`HotkeyAction.copyMode`, default ⌘⇧Space, `MactermKeybind.copyMode`). Its action is nil without a focused pane with a view.
- **`pane copy-mode enter|exit|status` is DEBUG only**, like `pane password`. `status` returns the selection text, so `scripts/e2e/test_copy_mode.py` reads no clipboard. `enter --keymap helix|vim` names the keymap, so the suite drives both without a change of the setting.
- **A click moves the cursor: fork patch 0016** (`0016-selection-click.patch`). While `flags.selection_cursor` is on, a plain left click puts a one-cell selection at the cell under the pointer instead of clearing the selection, which sent the drawn cursor back to the prompt. Shift-click, double click and triple click are unchanged, the rectangle flag of a block selection stays, and copy-on-select skips that one-cell cursor on release. Nothing on the Macterm side: the keymap state does not hold a position.
- **The Helix word motions are fork patch 0017** (`0017-selection-helix-words.patch`): `select_word:next|end|prev` is the `range_to_target` of Helix (`helix-core/src/movement.rs`) over cells, and the word motions of `move_selection` and `extend_selection` take their head from the same walk. `HelixKeymap` sends it for `w`, `e` and `b` in normal mode (`CopyModeMotion.helixSelectAction`); select mode still extends. Before it, the keymap sent `collapse_selection` then `extend_selection`, which kept the old head cell in the new selection: a `b` from the start of a word took one cell too many, and a `w` on the last word of a row ran to the end of the row. The cells after the last text of a row that does not wrap are a line end (`CellClass.eol`), the newline of Helix: a motion skips them and leaves them out, and a cursor that a click put there walks on from the next row. Zed's Helix mode (`crates/vim/src/helix.rs`) agrees with every case in the tests. The e2e `test_a_repeated_w_moves_word_by_word` replays `w w w b b`.
- **A page motion eases the viewport: fork patch 0018** (`0018-selection-scroll-ease.patch`). `scrollToSelectionHead` records its move through `rowScrollOffset` and flags the offset as a move to ease (`Screen.viewport_offset_eases`), and the renderer decays a flagged offset in the plain `smooth-scroll` mode too, on the curve of a region scroll. Helix scrolls its own region for the same key (DECSTBM and SU), which patch 0005 eases, so the two look the same. A wheel event, a row-level scroll and a landed ease clear the flag, so a gesture remainder is never decayed. The ghostty page-scroll keybinds still jump.
- Not yet: prompt motions.

### Explain Output (Apple Intelligence)

**Explain Output** explains the selection of a pane or, with none, the output of the last command, in a popover. Apple's on-device model writes it (FoundationModels). Nothing leaves the Mac. The grammar for users is in `docs/43-explain-output.md`.

- **`OnDeviceModel` is the only file that imports FoundationModels.** The model needs macOS 26, a Mac that supports Apple Intelligence, and Apple Intelligence turned on. `availability` is `.unsupported` (the command, the palette row and the menu item are not there), `.notReady` (the palette mutes the row and a keybind shows a toast, through `unavailableNotice`) or `.available`.
  - Each request has a new `LanguageModelSession`. A session keeps its transcript, and a transcript that grows fills the context window for good.
  - `stream` yields the whole reply so far. A consumer whose task is cancelled sees the loop end with no error, so it must check `Task.isCancelled` before it treats the end as "done".
- **The input** (`OutputExplanation`, pure, with tests).
  - The context window is for the instructions, the prompt and the reply together. **Read it from the model** (`OnDeviceModel.contextSize`): it is 8,192 tokens on macOS 27 and 4,096 before. A long text is cut to its start (`headShare`) and its end, with a line that counts the lines not shown.
  - **The model's own count decides the cut** (`OutputExplanation.fit`, through `OnDeviceModel.tokenCounter`, macOS 26.4 and later). `fit` counts the prompt, then cuts again with the budget scaled by how far the estimate was off, and keeps the largest excerpt that fits. A text that the estimate cut, and that has space left, grows. A count is a request to `modelmanagerd`: about 0.1 s, and about 0.9 s for the first one (measured). A whole text that takes at most half of the budget by the estimate is therefore not counted, and the count of the instructions is kept for the run. That shortcut trusts the estimate, so very dense text (hex, base64, at about 1.5 to 2 characters to a token) can still overshoot there; the model then reports the text as too long.
  - **More text is a longer wait.** The model reads the prompt at about 300 tokens a second. Measured on macOS 27 in a Debug build: about 3,000 tokens of text gave the first word in 10 s, and about 7,000 tokens (the full 8,192 window) in 23 s, plus 1.2 to 2.0 s of counts.
  - `estimatedTokens` is the fallback for macOS 26.0 to 26.3, and the first cut. It counts 2.5 ASCII characters to a token and each non-ASCII scalar as one. The model counted 2.57 characters to a token in a Python traceback and about 4 in prose. The old rule of 3 counted a traceback 15% low. Text that is denser (hex, base64) can still count low there.
  - **Not Private Cloud Compute.** `PrivateCloudComputeLanguageModel` (macOS 27) has a context window of 32,768 tokens, but a request needs the managed entitlement `com.apple.developer.private-cloud-compute` (`modelmanagerd` logs `alwaysAllowUnentitled: false` and `blockSideloadedApps: true` for its asset). A self-signed app cannot have it: the request fails with `ModelManagerError 1046`. It would also break "Nothing leaves the Mac".
  - The terminal text is untrusted. The instructions say that it is data. The worst result is a wrong explanation in a popover that the user asked for.
  - The reply is in the app language (`OnDeviceModel.replyLanguage`). The instructions stay English.
- **With no selection, Explain selects the last command and its output first** (`GhosttyTerminalNSView+Explain.swift`). The user sees what it explains, and the popover does not repeat the command.
  - The selection is ghostty's own gesture: a ⌘-triple-click on a line of output selects that command's whole output from the OSC 133 marks (`Screen.selectOutput`). On macOS it is ⌘, not ⌃ (`Mods.ctrlOrSuper`). The C API has no call that sets a selection.
  - **A ⌘-click also opens a link.** libghostty decides "over a link" only on a pointer move, with that move's modifiers. The move before the presses carries no modifiers, only the presses carry ⌘, and a last move with no modifiers resets them.
  - The click goes to the last line of output, which `OutputExplanation.lastCommand(in:)` finds from the prompt text (`linesBelowOutput`). nushell marks its prompt rows as output, so a click on a prompt row selects that row. With no guess, the rows above the cursor are tried.
  - The IME point (`ghostty_surface_ime_point`) and `ghostty_text_s.tl_px_y` are both the **bottom** edge of the cell, from the top of the view.
  - Without shell integration a triple-click selects one line, and Explain falls back to the text guess with no selection. The guess finds the last two prompt lines by their prompt mark, and drops the first line of a two-line prompt when it is the same above both marks.
  - **The gesture selects output only, so Explain then grows the selection up to the command** (`extendSelectionToCommand`): `flip_selection`, then `extend_selection:up` a row at a time, until the selection starts on the command's prompt line (`OutputExplanation.selection(_:startsAtCommand:mark:)`). It checks the text, not a count of rows, so a command on more rows, or a long row that wraps, is all included. After `maximumCommandRows` it goes back to the output alone.
  - The model still gets the output as the text, and the command beside it.
  - The popover's close clears the selection, if it is still the one that Explain made.
  - **The command goes to the model, not to the popover.** With the selection known, the command is every line from the prompt mark down to the line before the output (`OutputExplanation.command(in:before:)`), so a `\` continuation, a heredoc or a multiline nu block arrives whole. It reads the scrollback when a long output pushed the command off the active screen. Without a selection, only the guess of `lastCommand(in:)` is left, and a continuation line counts as output.
- **The popover** (`ExplainPopover`) is an `NSPopover` with `.transient` behavior. **It does not take key**: the pane keeps typing, and the pane's `keyDown` closes it on a bare Escape (`closesOnEscape`, before the password bubble and copy mode). A `makeKey` right after `show` did not take, because the popover's window was still opening, and Escape went to the shell. A click in its text makes it key; then its own `cancelOperation` closes it on Escape. Its close gives key back to the terminal only when the popover held it.
  - **A new popover waits for the old one to close** (`pending`). When the old window gave key back after the new one took it, AppKit closed the new transient popover at once.
  - Explain Output goes below the prompt, so it does not cover the output. A selection's popover asks for the space above its first row.
  - It has no disclaimer line.
- The command is `AppCommand.explainOutput` (Panes, default ⌘⇧E) with a `MactermKeybind` case. Not ⌘E: ghostty binds it to `search_selection` (Macterm's search bar for the selected text), and a Macterm chord whose command cannot run swallows the key, so ⌘E would do nothing on a Mac without Apple Intelligence. The right-click menu shows **Explain Output** or **Explain Selection**, only while the model is available.

### Project Insights (Settings → Intelligence)

The user-facing name is **Project Insights** (the Settings section, the command Toggle Project Insights, the docs page `/docs/project-insights`, with a 301 from the old `/docs/project-memory` in the Caddyfile of macterm/website). The code, the preference keys (`macterm.memory.*`), the hotkey id `toggle_project_memory`, the `MactermKeybind` case, the storage folder `Memory/` and the DEBUG verb `project memory` keep the old name on purpose: each is stored or wired, and a rename would drop a user's keybind, a saved shortcut or their records. Each project keeps a log of the commands that finish in it. A floating glass panel on the trailing side of the window shows where the user left off, the project's Git state and the next commands to run. The code is in `Macterm/Memory/` and `Macterm/Views/ProjectMemoryPanel.swift`. The grammar for users is in `docs/43b-project-insights.md`.

- **macOS 26 and later only** (`ProjectMemory.isSupported`). Below it, nothing records, the command has no action, the menu item and the toolbar button are not there, and Settings lists no Intelligence pane (`SettingsPane.visible`). There is no fallback UI.
- **It needs Apple Intelligence** (`ProjectMemory.modelAvailability`, `OnDeviceModel.availability`). While the model is `.notReady` or `.unsupported`, `ProjectMemory.isEnabled` is false, so nothing records and the command, the toolbar button, the panel and the intent are off. `Preferences.projectMemory` keeps the user's value, so the feature comes back when Apple Intelligence does. Settings → Intelligence disables the switch, dims it, shows it off, and adds the reason after its description in the same caption, with the text of the On-device model row. The value is observable and read again only when the app becomes active (`refreshModelAvailability`, observer in `attach`) and when Settings → Intelligence opens, because the user turns Apple Intelligence on in System Settings. A model download that finishes while Macterm is in front shows at the next activation. There is no summary toggle (`macterm.memory.summary` is a retired key).
- **One switch, off until the user turns it on** (Settings → Intelligence → Enable Project Insights, `Preferences.projectMemory`, `macterm.memory.enabled`, `ProjectMemory.isEnabled`). A log of commands is the user's to start, never a surprise. While it is off, nothing records, `AppCommand.toggleProjectMemory` has no action (it is not in the palette or the View menu, and ⌘I is swallowed; Keymaps still lists it), and the toolbar button and the panel are not there (`ProjectMemory.showsPanel`). There is no switch for each project, and the panel has no off state. The View menu item is `ProjectInsightsMenuItem`.
- **Never store the scrollback.** An entry (`MemoryEntry`) is the command, its folder, its exit code, its time and duration, and for a failure only the last 20 lines (2 KB) of output. Every text field goes through `MemoryRedaction` first. A command that starts with a space is not recorded (`HISTCONTROL=ignorespace`).
- **The command text comes from libghostty, or else from the screen at two moments.** Fork patch 0019 (`0019-command-text.patch`) puts the command as typed on `COMMAND_FINISHED` (`ghostty_action_command_finished_s.command`): `Screen.commandInputString` reads the input cells of the prompt at OSC 133;C, before any output, so a `clear` or a screen of output cannot take it away, and the first command of a bash or zsh pane is recorded too. The text keeps its spaces, so a leading space still means private (`ProjectMemory.reportedCommand`). It wins over the submission and the screen (`makeEntry(reported:)`). The screen reads below stay for a NULL field, when the shell marked no input. Before the patch, libghostty gave `COMMAND_FINISHED` (OSC 133;D) with the exit code and duration, but no command text and no start mark.
  - At submission (`ProjectMemory.commandSubmitted`, from `onCommandSubmitted`, before the tracker leaves the prompt), only while `Pane.isShellAtPrompt`: a typed Return reads the prompt line under the cursor (`ScreenCommandExtractor.typedCommand`), **cut at the cursor**. A right prompt (zsh `RPROMPT`, nushell's time) and an autosuggestion (fish, zsh-autosuggestions) are drawn after the cursor and are not the command. The column comes from the IME point (`GhosttyTerminalNSView.cursorColumn`): libghostty puts it at the middle of the cursor's cell, after the left `window-padding-x`, which `WindowPadding` reads from the raw config as `MouseScrollMultiplier` does; the cell width is the surface size's, because the point's own width is the preedit's. libghostty unwraps a wrapped line and the cursor is on its last row, so the column is offset by the rows above. A `sendText` line (`pane run`) is read from `GhosttyTerminalNSView.submittedText`, because its echo may not be on the screen yet. This is the only moment that `clear`, or a command with more than a screen of output, is still on the screen. A Return inside a program is not at the prompt and is ignored. bash and zsh send no 133;D for a pane's first prompt, so the first command of a pane has no submission and is read at its end only.
  - A submission names the command that finishes only when the command started within `submissionTolerance` (2 s) of it. A submission whose end mark never came (an ssh that dropped, `exec zsh`) must not name the next command.
  - At the end: the shell sends 133;D BEFORE it prints its next prompt, so `commandFinished` reads `GHOSTTY_POINT_ACTIVE` after `screenReadDelay` (400 ms), with `OutputExplanation.lastCommand(in:)`.
  - The submitted line wins. When the screen's command continues it with no gap, the cursor cut the command in the middle (a Return pressed mid-line) and the screen has the whole of it (`screenCommand(_:extends:)`). The end read gives the output tail only when it shows the same command, with or without a right prompt past a gap (`screenCommand(_:shows:)`). With neither, nothing is recorded: a row with no command is noise. Never guess.
  - **A mirror records nothing** (`Pane.isMirror`, set by `init(mirroring:)`). A shadow pane is a second zmx client on the session and parses the same OSC 133;D, so without the gate every command in a tab that two windows show was recorded twice. `CommandTextSource` reads the screen; the reported command bypasses it.
- **What it covers** (`ProjectMemory.covers`): projects only. The pinned and scratch workspaces, the quick terminal and desktop widgets are not recorded. A pane with a password prompt up records no text.
- **Storage** (`ProjectMemoryStore`): `<App Support>/Memory/<project id>.json`, 500 entries, oldest first, debounced atomic writes, flushed at quit. A file that does not decode is never written over. A view reads `loadedEntries` only, after `prepare` in `.task`: a lazy load in a body would mutate observable state during the update. `AppState.removeProjectWithoutSaving` deletes a removed project's file (every removal path goes through it). `attach` prunes the files of projects removed while Macterm was not running, **never when `ProjectStore.loadFailed`**: a `projects.json` that does not decode leaves an empty list that is not the user's, and a prune against it deleted every project's memory.
- **Git** (`ProjectGit`, `GitStatusParser`): local and remote projects. Six reads: `status --porcelain=v2 --branch --show-stash` (also the changed paths), `log`, `for-each-ref refs/heads --sort=-committerdate` (the `recentBranchCount` branches with the latest commits), `worktree list --porcelain` (the worktree of each branch), the branch log (`ProjectGit.branchLogScript`, one POSIX sh script for local and remote: the main refs that exist, `origin/HEAD` resolved, then the commits of the current branch that none of them has), and the diff (`ProjectGit.diffArguments`: `git diff HEAD -U1`, staged and unstaged, in the whole repository, with no external diff and no textconv, which run programs that the repository's config names). **The diff is read only when a tracked file has changes** (`GitStatus.hasTrackedChanges`, also on the host), and never for a commit, whose subject is in the digest already. git never sends the files of `GitStatusParser.leftOutNames` (lockfiles, `.env*`, `*.env`, key files, names with `secret` or `credential`) and the files in `leftOutFolders` (folders with those words), which it gets as exclude pathspecs with `top` (a project in a subfolder reads the whole repository), and `head -c` cuts the output at `diffByteLimit` (64 KB), locally and on the host, so a large diff costs no time and no memory. `GitStatusParser.parseDiff` leaves out the same names again, binary files, a file with `PRIVATE KEY`, a file with a line longer than `diffLineLimit` (500 characters: minified or encoded text), and the last file of a cut read. It gives a deleted file one line (`deletedFileLine`) and keeps at most `diffCharacterLimit` characters of whole files. **The diff lines are not redacted** (Ethan, 2026-11-10): the diff goes only to the on-device model and is never stored, and the mask turned code such as `token: String` into noise. The secret files stay out, and the summary is redacted instead (below). It splits at each `\n` scalar, because a CRLF line end is one Swift `Character`. Untracked files are paths only. The branch log is unknown (nil), never empty, without a branch, a main ref or a finished read (its `end` line). Every git run has `core.quotePath=false`. The current branch is in the list as a row like the others, highlighted by the row alone: the accent as its fill and a bold name, with the same glyph in the same color as the other rows (no check); one style for every row keeps the ages in line, where a prominent button style padded differently. A branch row is a card row like the Suggested rows (`cardRow`: a flat fill in `MactermTheme.surface` at the failure card's 12 pt corner, dimmed while pressed by `RowButtonStyle`; the rows were glass buttons first, whose `.glass` style ignores `buttonBorderShape`), with the name and the age only, and goes to the branch in the CURRENT pane (`ProjectMemoryActions.type`): `cd "<worktree>"` typed for a branch that a worktree has checked out, or `git switch <name>` for a branch with none, so the switch is on the screen and in the shell's history, local and remote alike. The pane must have a live terminal that is not `.running`; a toast says so otherwise. A worktree path with a quote or a newline is refused with a toast. The rows opened a tab in the worktree before, which put the branch in another shell than the one the user was in. The card is the branch rows alone: no commit list, no branch line and no counts line; `recentCommits`, the counts and ahead/behind feed the digest only. The panel reads it when it shows a project; **for a local project, on every change in its git dir** (`GitDirectoryWatcher`: a directory watch on the git dir, and the common dir of a linked worktree, so a `git switch` anywhere, in a pane, an IDE or another terminal, moves the highlight within `gitReadAfterDirectoryChange`, 250 ms; the panel's own reads write nothing there, `GIT_OPTIONAL_LOCKS=0`); `gitReadAfterCommand` (300 ms) after ANY command finishes in the project while a window shows the panel for it (`ProjectMemory.panelShows`, never for every command in every project), recorded or not, because a private command or an unread one moves the branch as well; 1 s after a branch row is clicked, for a remote shell that reports no command end; on app activation; and every 15 s while it is up and Macterm is active (`ProjectMemoryPanel.gitRefreshInterval`). **Only a Git state that changed restarts the summary's quiet wait**: with no summary on record every read counts as unseen, and a read of the same state restarted the 10-minute wait, so with the panel up the background summary never came. It never fetches. The panel has no refresh button and no close button. `ProjectGit.run` reads git's output through the pipe's readability handler up to its EOF, bounded by `drainTimeout`, so the tail of `git log` is never lost to a read that raced the last write. **Never run the `/usr/bin/git` shim on a Mac without the Command Line Tools**, because it opens the install dialog. `ProjectGit.executable` takes Homebrew's git, or the git in the developer directory of `xcode-select -p`, which never opens a dialog. Each run has a 5 s timeout, `GIT_OPTIONAL_LOCKS=0` and `core.fsmonitor=false` (a daemon could hold the output pipe open). Git's output pipe is read as data arrives, never with `readDataToEndOfFile`.
  - **A remote project runs the same six reads on the host through its server** (`RemoteSpawn.gitProbeScript`, `ProjectGit.remoteStatus`): one `command.run` request over the host's one connection (`RemoteHosts.run`, 0058), with the outputs separated by `ProjectGit.recordSeparator`. It never asks for a login and opens no connection of its own: with no connection or no server up, nothing is read. The script exits 2, 3 or 4 for no directory, no git and no repository, which read as "no git state", and 0 in all other cases (the branch log fails on a detached HEAD). An unreachable host keeps the last state: a flaky link must not blank the panel. A branch with a worktree on the host is reached with `cd` typed into the current pane, because the shell is the host's.
- **Suggested** (`ProjectMemorySuggestions`, pure): with the model, the rows are its suggestions, from `OnDeviceModel.suggestCommands` (guided generation, a `@Generable` list of command and reason, in `OnDeviceModel.swift` with the rest of FoundationModels), requested right after the summary's text in the same run and stored with it. **The model chooses and orders; it never invents a command the panel will run**: a suggestion is kept only when it is a command that ran in the project (`candidates`: the latest 30, normalized, nothing trivial or masked) or one of `safeGitCommands`. **There is no fallback.** Without the model, before its first summary, or when nothing it suggested survives these checks, the section is hidden, as the summary is: a command is never suggested only because it ran recently or often. The instructions (`ProjectMemoryDigest.suggestionInstructions`) ask for a cause that the log or the Git state shows, and an empty list when there is none. `ProjectMemory.suggestedActions` is the one place that decides.
- **A Suggested row** (`QuickAction`) TYPES the command into a new split (`ProjectMemoryActions`), not into the environment as a palette `run:` does: the command was recorded from the user's shell, so it is in that shell's language. **A command with a masked secret is never offered or run** (`MemoryCommand.isMasked`): the mask would be typed in place of the secret.
- **The panel shows each window's own project, and one toggle shows it in every window.** It shows `WindowState.activeProjectID`, never the app-wide mirror. Its header shows the sidebar's project icon (`Preferences.projectIconSymbol` through `TabRowIcon`, with the color tag). Its visibility is `Preferences.projectMemoryPanelVisible` (`macterm.memory.panelVisible`), one value for the app. The command `AppCommand.toggleProjectMemory` (default ⌘I, for the toolbar's (i) button; ghostty's own inspector is `super+alt+i`) flips it through `AppState.projectMemoryPanelVisible`. Before this toggle each window kept its own copy in `WindowSnapshot.projectMemoryPanelVisible`; the restore reads that field once, so a window that showed the panel turns the toggle on, and never writes it again. The panel floats over the panes and never resizes them.
- **The toolbar button can be hidden** (`Preferences.showProjectInsightsButton`, on by default; Settings → Appearance → Toolbar and the toolbar's right-click menu, both shown only while `ProjectMemory.isEnabled`). It hides only the button: the command and the panel still work.
- **The summary paragraph** (`ProjectMemorySummarizer`, `ProjectMemoryDigest`) is Apple's on-device model (`OnDeviceModel.stream`) over a digest of the git state and the log, never the scrollback. **It summarizes what the user has been working on, from Git first**: the digest puts the branch's own commits (on a branch with none, only that it has none; on the main branch or with an unknown branch log, the latest commits), the first `changedPathLimit` changed paths and the diff of the uncommitted work, within `textTokenBudget` (1,500 tokens). **The summary gets the commands only when Git shows no work** (`ProjectMemoryDigest.summaryText`, `gitShowsWork`: no commits and no changed files). The Recent list shows them, and with them in the prompt the model retold them whatever the instructions said. The suggestions get the latest 12 commands with outcome, age and the redacted failure tail. **The diff gets only the budget that the rest leaves** (`ProjectMemoryDigest.diffLines`): a whole file at a time, a file that does not fit is left out, never cut in a hunk, and a last line counts the files left out. The other branches and a clean tree are not in the digest. The instructions tell the model not to state a goal, not to describe a failure, not to suggest a next step, to name a file only when the digest lists it as changed, to say what the diff does but never call it commits (without that sentence, on a branch with no commits, the model called the diff "the latest commits"), and never to write a secret value. **The model's text and each suggestion's reason go through `MemoryRedaction.redact` before they are shown or stored** (`ProjectMemorySummarizer.redacted`), because the diff in the prompts is not redacted. While the reply streams, the panel shows it up to its last whitespace (`completeWords`), because a key that streams in a token at a time matches no rule until it is whole. **Measure a change of the wording on the real model**: a rule that names a thing to leave out can make the model write about that thing. The instructions say that the text is data. It shows only where `ProjectMemorySummarizer.isEnabled`: memory on and the model `.available`. One summary for each project, keyed by `ProjectMemoryDigest.key` (the records' ids and outcomes, the git line, the branch's own commits, the named changed paths, and `diffHash`, a hash of all of the parsed diff and not only the part that fits, because that part changes with the length of the command lines; so a newly changed file or an edit to a changed file also restarts the quiet wait below, **with no time in it**: the prompt says how long ago each command ran, so the prompt text changes as time passes and cannot be the key), so the same log never runs the model twice. A finished summary is stored in the memory file (`MemoryFile.summary`, `StoredSummary`) and seeds the summarizer at the next launch. A new digest cancels the run in flight and starts another after `debounce` (1.5 s), with the old text up until the new one streams in. **Two things write a summary, and nothing else**: `ProjectMemory.scheduleBackgroundSummary`, after a project has been quiet for `summaryQuietPeriod` (10 min after its last command, panel or no panel, so that a panel opened after a break shows the summary at once; a new command restarts the wait, and so does a Git read whose state the summary on record has not seen, `gitStateIsNews`, which is how a commit from another terminal reaches it; **a project with no summary yet gets its first one with no wait**, at the first Git read that finds a state (`ProjectMemorySummarizer.hasSummary`), because the Git state says most of it and a new project must not wait for commands; the summarizer's `debounce` still makes two reads in a row one run), and the reload button in the Summary header (`ProjectMemory.writeSummary(force:)`, which runs again for the same key). The panel never writes one itself: it `prepare`s the stored summary in its `.task` and shows it. The instructions tell the model not to say how long ago things happened, because a stored summary is read later. A failed run leaves the button; the facts below say the same.
- **The failure card shows a failure only while it is still the thing to fix** (`ProjectMemorySummary.unresolvedFailure`): the latest failed command with no later success of the same program and subcommand (`MemoryCommand.retryKey`: the words before the first option, when there are two or more, else the whole command), and with no pause of `stretchBreak` (1 hour) between two commands after it (`openFailures`). A failure that is the latest command always shows. The digest and the suggestion candidates leave out every failure that is not open (`withoutSettledFailures`), and the answer of Where Did I Leave Off names only the card's failure.
- **`project memory <project> [--set on|off|forget] [--panel show|hide]` is DEBUG only.** `--set on` records without Apple Intelligence (`modelReader` answers `.available`, and `--set off` gives it back), because no CI runner has it; the summary still asks the real model. It reads the redacted entries, the unresolved failure, the suggested rows and the summary's phase and text, shows or hides the key window's panel, and `--summary write` writes the summary now. `scripts/e2e/test_project_memory.py` prints OSC 133;D from a script, because CI's bash 3.2 has no shell integration.
- **The App Intent "Where Did I Leave Off"** (`GetMactermProjectMemoryIntent`) returns the answer as text and as a dialog, so Siri says it. `ProjectMemoryAnswer` (pure) composes it: the stored summary with its backticks dropped, then the latest command when it finished after the summary was written; without a summary, the latest command with its result and the unresolved failure. **It never writes a summary**: the background summary (after the quiet period, or at once for a project's first summary) and the panel's button stay the only writers, so the intent answers at once. It refuses with `MactermIntentError.unavailable` below macOS 26, without Apple Intelligence (with the reason), while memory is off, and for the pinned and scratch workspaces. It reads the memory through `MactermIntentHost.projectMemory`, so a test hands in a memory on a temporary store.

### Read-only panes

Read-only is a mode of libghostty. The control is the **Read-Only Mode** `AppCommand` (`HotkeyAction.readOnlyMode`, no default chord). It only sends `toggle_readonly` to the focused pane, so the state stays in libghostty. Every pane mode (Zoom Pane, Copy Mode, Read-Only Mode) is a Macterm command, so it is in the palette and in Keymaps.

- **One trigger for each action.** A ghostty `toggle_readonly` keybind still works, because libghostty handles it before Macterm hears of it. It has no default, so nothing fires two times unless the user binds both. For the same reason, Macterm deliberately ignores ghostty's split actions (`toggle_split_zoom`, `new_split` and the others). libghostty binds some of them by default (`super+shift+enter`). If Macterm answered them, a user who rebinds Zoom Pane would still zoom on the old chord.
- **libghostty enforces it**. While it is on, the surface drops every key, text and paste to the pty, and tells nobody. Keybinds still run. We verified this live for `pane run`, `pane key` and password autofill.
- **The CLI refuses what libghostty would drop** (`read_only`, `ControlHandler.paneReadOnly`). Without this, both verbs said ok for text that the program never got. `pane run` always refuses. `pane key` refuses only a key that `GhosttyTerminalNSView.keyReachesProgram` says would go to the program: not a keybind (`ghostty_surface_key_is_binding`) and not a copy-mode key. `pane inspect` reports `readOnly`, optional on the wire so that a newer CLI reads an older app. `pane read-only` (DEBUG only) sends the binding action, because the e2e suite has no keyboard (`test_read_only.py`).

- **The pill is the first `ModePill` in the trailing badge row of `TerminalPane`** (Read-Only, Copy Mode, Zoomed, then the lock). A click sends `toggle_readonly` to the surface.

### Search (`Macterm/Search/`)

**Every search in the app goes through one engine**. This covers the palette and its screens. It covers the lists in Settings (Keymaps, saved passwords). It also covers the path mode of the palette. The path mode completes and does not search, but it uses the engine in the same way. Do not add a matcher of your own. The palette of a plugin must use the engine too.

- **The ranking is the ranking of fzf** (`SearchScoring`, its `FuzzyMatchV2` and its constants).
  - The letters of a query must be a subsequence. The score has bonuses for word starts, path components and camelCase humps (Macterm reads them from the unfolded text). Consecutive runs carry the bonus of their first character. Gaps have penalties.
  - Whitespace splits the query into terms. All terms must match, in any field of a record (`split right` is the same as `right split`). A later field costs `SearchIndex.fieldPenalty` for each position. A match in a title therefore beats the same match in a subtitle.
  - Ties go to the shorter title, then to the order of the list. `SearchIndex.rank`, `Search.rank` and every palette list through `rankedByScore()` sort in the same way.
  - There is one deliberate difference from fzf: no clamp at zero. A score stays a true maximum across a long gap.
- **Lists in Settings rank too** (`Search.rank`). They never only filter. Fuzzy matching admits letters that are spread across words. In a list that stays in its own order, such a row looks the same as a strong match.
- **Macterm prepares text one time** (`SearchText`).
  - It folds case and diacritics for scalars. For ASCII it does not use Foundation. A combining mark, as in a decomposed `é`, folds away. It neither breaks a run nor starts a word.
  - It stores a bonus for each scalar and a 64-bit character mask. It also stores offsets back to the original string for highlighting (`PaletteItem.highlights`, which the row draws in semibold).
- **The engine is built for long lists** (`SearchIndex`).
  - The mask rejects with one AND. A forward scan rejects the rest before any scoring.
  - The DP runs only over the window that a match can occupy. It uses two rows at a time in buffers that Macterm uses again (`SearchScratch`).
  - Preparation and matching split across cores above `parallelThreshold`.
  - `search(limit:)` keeps only the best K, in order.
  - `SearchSession` searches only the last matches when a keystroke only narrows the query (`SearchQuery.narrows`). Files and the listing of an extension search through it. Each one prepares the text one time, when its rows arrive.
  - We measured 100k paths in an optimized build: about 45 ms to prepare and 2 to 5 ms for each search.
  - `Search` is the shortcut for a short list that you build at the moment of use.
- `SearchEngineTests` pins the ranking on the own command titles of the app. It also makes sure that top-K, the parallel path and session narrowing give the same answers as the plain path. Change the scoring only when you mean to change those tests.

### Tab switcher previews (#344)

When you hold the Recent Tab chord, `TabSwitcherOverlay` shows one card for each tab in the cycle (`AppState.tabCycleOrder`, limited by `Preferences.recentTabCandidates`). Each card is a mosaic of `PanePreview`s.

- The cards are **live**. `beginLivePreviews` sets `GhosttyTerminalNSView.rendersForPreview`. `syncOcclusion` then reports the pane as visible, and libghostty wakes its renderer. ### Remote Projects (#104)

A remote project is a project whose `path` is an scp-style `[user@]host:dir` (`ProjectPath` parses it). Each pane is a session of the host's server (v2, 0057), reached over the host's one ssh connection (below). The grammar for users is in `docs/70-remote-projects.md`.

- **A remote pane is a manual surface, driven by `RemotePaneDriver`.** The surface runs no process on this Mac (libghostty's manual surface, fork patch 0022): no command, no local `Last login` line. The driver asks `RemoteHosts.answer` what to do (`wait`, `attach`, `plain`, `ended`, `close`) and runs the answer. `RemoteHosts` takes the host and the folder from the panes that show the session (`RemoteHosts.panes`, set from `AppState.remotePanes`), never from anything else, so only the user's own remote panes make Macterm connect to a host. A pane that restores before the app state is installed waits. In the unit-test host (`ZmxBypass.unitTestHost`) the surface keeps the fixed line `noRemoteClientCommand`.
- **Each pane is one channel on the host's link.** `attach` answers with the host's `RemoteServers.Link` (one connection to the host's server over the one ssh login), and the driver starts a `PaneSession` on it: `channel.open`, `attach`, output into `ghostty_surface_feed`, input, size and claim back as messages. One login serves every pane. A session never logs in by itself: a lost link is a `lost` report. A mirror is a second channel to the same session.
- **A decision is short.** A login or an install can wait minutes for the user. So `RemoteHosts.answer` never waits for them: it starts the work and says `wait`. When the work ends, the app posts the session's Darwin notification (`RemoteHosts.wakeName`), and the driver, which registered for it, asks again.
- **One link to the host's server for each host** (`RemoteServers.Link`), for `session.list` and `session.kill`. A pane close ends its session over it, or over a link that it opens with `login: false` and `install: false`: a close never asks for a login, and with no connection up the session stays.
- **An attach never makes a session.** A running session attaches (`channel.open`), and the screen is cleared first, because the session replays its own. A missing session is made (`session.create` over the link, in the folder, with the user's login shell and the host's environment from `RemoteSpawn.createProbeScript`, run by `command.run`: it settles `TERM`, `COLORTERM` and `TERM_PROGRAM` on the host and resolves a `~`) only for a pane that never had a session on the host: a new pane, or one from before v2. A pane whose session ran there (`Pane.hostSessionDirectory`, persisted as `PaneSnapshot.hostSessionDirectory`, the shell's own OSC 7 folder at save time) and is gone (a host restart) prints that the session ended and waits for Return; then a new shell starts in that folder. A server is never started empty in silence for a pane that expects a session (`RemoteHosts.step`). A session that the app made in the last 30 s (`Configuration.creationGrace`) counts as made, not as ended: a mirror can ask before the host lists it, and a channel can drop before it starts. A folder that is not there prints a `macterm:` line and the session starts in the home folder.
- **A shell that exits ends the pane**, with no question (`AppState.handleProcessExit`, from the channel's `exit` message), and the close ends the exited session on the host. A lost link never ends the pane: the driver reports `lost` and waits.
- **Input before the first attach stays for the shell.** A layout's `run:` is written through `manual_write` at the start (`initial_input`). `PaneSession` holds it (at most 1 MiB) and sends it after the first attach. A key in a pane that waits asks again (`retry`); Return in a pane that asks about an ended session makes the new shell (`create`).
- **No local shell for a remote project.** In the unit-test host, a remote pane prints one line and waits (`GhosttyTerminalNSView.noRemoteClientCommand`): never a local shell in a remote project, and never an exit.
- **No server** (the user chose Continue Without Server, or the host has no build, exit 4): each pane is a plain ssh login shell over the master (`RemoteSpawn.plainShellCommand`) that the app runs on a pty of its own and feeds into the surface (`PlainShell`), with one line that says it stops with the connection. It has no persistence, no pushed foreground and no dot. ssh's exit 255 is a lost connection. The decline is kept (`Preferences.remoteServerDeclines`, `RemoteHosts.declined`), so the next panes do not ask; **Install Server on Host…** in the row menu of Settings → Projects shows only then, and asks again.
- **A line of Macterm's starts on a line of its own, and the next attach or new session clears it** (`RemotePaneDriver.paneText`). The lines of failed tries stack until then. A failed connect says why in the pane (`RemotePaneText`): Macterm's sentence for ssh's three common errors (`No host is named x.`, `x does not answer.`, `x refuses the connection.`), else ssh's last line, cleaned, and `Press a key to try again.` These lines stay English, as all text that Macterm writes into a pane.
- When you quit, the channels end and the sessions stay. When you start Macterm again, each pane attaches to its session by the `sessionName` that Macterm persisted.
- v1 zmx sessions on a host keep running: nothing ends one. The remote owner-stamp reaper of v1 is gone with them.

These rules for the pane scripts come from tests against a real host:

- **Depend only on inputs that Macterm controls**. Never source `/etc/profile` or `~/.profile`, in any form. A `~/.profile` that ends in `exec zsh` took over the pane in three different ways. The environment of the user takes effect inside the session, where their login shell starts in the normal way. `remote_scripts_never_source_profiles` enforces this.
- The probe script runs as `argv` of `command.run`, never through the login shell of the user. It names no binary of the server. A folder that is not there gives the home folder and a `macterm:` line in the pane.
- **The host settles TERM, and the script never touches a TERM that resolves**. This includes a TERM that the user pinned to a simpler value with `SetEnv`. The probe replaces only a TERM that does not resolve, and a `dumb` or empty one (a shell may set `dumb` with no export, and the server has no ssh pty to take it from). It uses `xterm-ghostty` if the host has it. If not, it uses `xterm-256color`. The result goes into the new session's environment.
  - The probe exports `COLORTERM=truecolor`, `TERM_PROGRAM=ghostty` and the `TERM_PROGRAM_VERSION` of libghostty itself, and the session gets them. Programs depend on these variables. Claude Code sends OSC 9;4 progress (the status dot of an agent) only to Ghostty 1.2.0 or later.
- `RemoteTerminfo` installs our bundled `xterm-ghostty` entry (`infocmp -x`, then `tic -x -o ~/.terminfo -` on the host through its server's `command.run`, then `infocmp` checks the entry, as the `+ssh` of ghostty does). It starts when the host's link is ready (`RemoteHosts.Configuration.linkReady`), off the critical path. It depends on the own ghostty flag `ssh-terminfo` of the user (off by default upstream). It never caches to disk. It logs stderr only on a failure.

**Dropped connections heal by themselves (#281).**

- **A pane survives a lost connection.** Its channel ends with no exit (`PaneSession` with no reconnect of its own), or its plain ssh exits 255; the driver reports `lost`, and the pane keeps its last screen, blurred and dimmed as a mirror that does not lead (`Pane.isRemoteLinkLost`, `SplitLeafView.isObscured`), with no text, so a frozen program does not look live. A pane that shows a line of Macterm's only dims, so the line stays legible (`Pane.showsRemoteLinkMessage`). Its input is ignored, except the key that asks to connect again.
- Only triggers connect again (wake, a network change from `NWPathMonitor`, activation, project selection), with the backoff of `RemoteReconnectPolicy` (`AppState.reconnectDroppedRemotePanes` → `RemoteHosts.reconnect`, which posts the pane's wake). There is no timer. A key in a lost pane connects at once. A login, when the master died, comes then: the user is at the Mac. A login that brings a host's link back is a trigger too (`.remoteHostDidConnect`, `ReconnectTrigger.hostConnected`): the sweep lets the other lost panes of that host attach with no key, under the same backoff and setting. The attach after it draws the session's snapshot over a cleared screen.
- `Pane.ensureNSView` passes `command` only on the first surface build. A new start therefore never types a `run:` of a layout again.

### One ssh connection for each host (v2, design/005 step 1)

`SSHConnections` (`Macterm/System/SSHConnections.swift`) gives each host one ssh connection. Every pane of a remote project is a channel over it (above). The debug-only `macterm host connect <host>` opens one.

- **The user's own ControlMaster first.** If `ssh -G` names a ControlPath and `ssh -O check` finds a master there, Macterm uses it and opens nothing. Otherwise it runs `ssh -M -N` with its own ControlPath, `<App Support>/cm/<hash>` (mode 0700, `SSHControlPath`). The path is a hash, because a socket path holds 104 bytes. The master gets the path with `-S`, never `-o ControlPath=`: ssh splits an `-o` value at spaces, and `Macterm Debug` has one.
- **A command over the connection never logs in by itself** (`run`, `ttyArguments`; `connect(login: false)` uses only a connection that is up): `BatchMode=yes` refuses a prompt, and `ProxyCommand=/usr/bin/false` stops the direct connection that ssh tries when the control socket does not answer. `RemoteCommand=none` is there because a `RemoteCommand` in the user's config makes ssh refuse a command line.
- **Macterm's master stays after quit, until the link drops** (issue 0084, the type's doc comment has the rules). `ControlPersist=yes` moves it into the background after the login, so only the ssh of a login that has not finished is a child of Macterm (`loggingIn`), and only its askpass gets an answer. The next launch uses a live master on its own path. The askpass variables go only to the master's own process, never to the app's environment, so a pane's ssh never gets them.
- **A changed config logs in again.** The own path is a hash of where `ssh -G` sends the host (`SSHControlPath.endpointKeys`), and each connect reads `ssh -G` again, also while Macterm runs.
- **Macterm ends its own master when the config no longer gives its path.** `<App Support>/cm/connections.json` records the path of each master that Macterm started, because the hosts of an ssh config cannot be listed. The check runs at the next connect for that host, and at launch for each record (`endStaleConnections`). A config that `ssh -G` refuses (exit 255) also ends it. A time-out does not. A master that two destinations record ends only with the last record (`release`). `ssh -O` reads no config (`-F /dev/null`), so a broken config cannot keep an old master.
- **The login asks the GUI** (`SSHLoginPrompts`): the master has `SSH_ASKPASS` set to `Contents/Resources/ssh-bridge/macterm-askpass` (`scripts/askpass-shim.sh`, which execs `macterm askpass`) and `SSH_ASKPASS_REQUIRE=force`. The askpass sends ssh's prompt to the app named in `MACTERM_ASKPASS_SOCKET` (`ssh.askpass`). The app shows an `NSAlert` sheet on a terminal window: a secure field, or Connect and Cancel for a host key or a confirmation.
- **The sheet says less than ssh** (`SSHLoginPrompts.Question`). Macterm knows a question only by the exact text that OpenSSH writes, and shows its own text for it: a password (`bob@box's password:`, or `(bob@box) Password:` of keyboard-interactive), a key passphrase (`Enter passphrase for key '…':`), and a new host key (Macterm's sentence, then the host that ssh names, with `ProxyJump` possibly the jump host, and the key's type and fingerprint in a monospaced label, `hostKey(in:)`; OpenSSH 10.5 writes `is:` before the fingerprint). Any other question shows only ssh's last prompt line, cleaned (`promptLine`), never ssh's other text. The exception is a yes or no question that Macterm does not know: it is about the host's key, so it fails closed and shows ssh's lines above the question. A form that a later OpenSSH changes becomes unknown until a test adds it. The same secret prompt again from the same ssh (`isRetry`: the master, or a jump host's ssh under it) means that ssh refused the answer. The sheet then says that the password, the passphrase or the answer is incorrect (`Question.refusal`).
- **The sheet's field lines up with its text and buttons** (`SSHLoginPrompts.columns`). NSAlert puts an accessory at the left edge of its buttons, and its text a few points in (measured on macOS 27). The password field is as wide as the buttons, and the host key lines move in to the text.
- **A login that asks nothing shows ssh's last line** (`SSHLoginNotice`, `onLoginNotice`). A host can write text and wait with no question, for example a link to log in from the browser. When the last line that ssh wrote since the last question stays the same for `SSHLoginNotice.delay` (2 s), a notice sheet shows it with Cancel, and Open Link (`NSWorkspace.open`) when the line holds an https link. The link starts its own line of the text (`noticeText`), so that it does not wrap after `https://`. The rule is the same for every host: it matches no vendor's text. ssh's own warnings (`Warning:` and `** ` lines) do not count. Open Link keeps the sheet up. A new line changes the text in place. The notices of all logins wait behind any question, and the sheet shows the first one. A notice goes away when its master listens or exits. With no terminal window, no notice shows: a modal alert would hold the wait that closes it. Connect errors show in the pane (`RemotePaneText`).
- **One Cancel ends the login** (`cancelLogin(connectionPID:)`): ssh would ask again, for the next try and then the next method. The connection fails with `Failure.cancelled`. Only the master gets the signal: a jump host's ssh under it can ask once more, gets `denied`, and exits.
- **The answer goes only to an askpass of Macterm's own ssh** (design/006 §4). `ControlSocketServer` reads the peer's pid (`LOCAL_PEERPID`). `askpassOwner(forPeer:)` requires two things. The peer runs the bundled `macterm` (a pid alone can be reused). A running master of Macterm is its parent, or an ancestor at most `askpassAncestry` steps up. ssh execs its askpass directly, and the shim execs too, so for the host's own login the parent is the master. A `ProxyJump` host's login comes from an ssh that the master starts through `sh -c`, lower down. Any other process gets `denied`.
- **A saved password fills the login only after a click** on Use Saved Password, and then `PasswordAuthenticator`. The entry is v1's: `ssh <destination>` and the prompt line.
- **Each new login writes a log line**, `ssh login: host=<host> logins=<n>`, so the logins of a day can be counted from the log (design/005, the question of a link that roams).
- A quit ends only a login that has not finished (`endLogins`). `disconnect` ends Macterm's master with `ssh -O exit`. A user's master is never ended.

### A host's server (v2, design/005 steps 3 to 5)

`RemoteServers` (`Macterm/Server/RemoteServers.swift`) reaches the server on a host over that host's connection. It installs the server first when it is not there. `RemoteHosts` keeps one link for each host. The debug-only `macterm host server <host>` connects, and prints the server's build and the ssh commands that the connect ran.

- **Every background read of a host goes through its server** (`command.run`, `RemoteHosts.run`, 0058): Project Insights' Git state and the terminfo install. The server runs the command to its end in a process group of its own, with no pty, stdin and stderr on `/dev/null` and its own environment, and returns at most 512 KiB of stdout and the exit status. At the time limit (at most 60 s) the group gets SIGKILL and the request fails with `timeout`. `RemoteHosts.run` uses only a link that is up, or one that it opens with `login: false` and `install: false`, as a close does: a background read never asks for a login, and no ssh of its own connects to a host. A client that may create a session may run a command in one, so the method gives no new access.

- **The host scripts are files** (`server/host/attach.sh`, `install.sh`, in the bundle at `Contents/Resources/host`), so that `server/test/host_install.bats` runs the same text over a real sshd on Linux and macOS. **The app sends each one as one line** (`HostScripts.oneLine`: no comment lines, the lines joined with spaces) in `sh -c '<script>' macterm <arguments>`. sshd gives that command to the user's login shell, and csh refuses a newline in single quotes. So every line of a host script ends where a join is valid (each command ends with `;`), it has no single quote, and no `!` that csh reads as history. Each argument is one plain word. `HostScripts.command` refuses anything else, and `RemoteServersTests` checks the bundled scripts with `sh -n` and `csh`.
- **One command checks and attaches.** `attach.sh` prints `macterm-host proxy` and execs `~/.local/share/macterm/bin/macterm-<build key> proxy`. Its stdio is one end of a socket pair. The app drops every byte up to that line (`skipToProxy`: a shell rc file of the user can write to stdout first), then `ServerConnection.handshake(fd:)` does the handshake. A current host costs this one command after the login. With no file of this build, it exits 3 and writes `macterm-host missing <system> <machine> <host id or -> <host keys>` on stderr. Exit 4 is no writable home or an OS with no build. The check writes nothing on the host. Text from the host goes into a log or an error only with its control characters removed (`HostCheck.clean`).
- **The first install asks** (`RemoteServerConsent`, on a terminal window: Install, or Continue Without Server, which Escape presses). The answer is kept in `Preferences.remoteServerConsents`: the destination as `ssh -G` resolves it (`user@hostname:port`) → the host id and the host keys. When `ssh -G` fails, it asks and keeps nothing.
  - **The host id is a file that the first install writes** (`~/.local/share/macterm/host-id`, a UUID that the app makes), not `/etc/machine-id`: a container or a minimal host has none. An install never changes the file.
  - **The host keys are a `cksum` of `/etc/ssh/ssh_host_*_key.pub`** (type and key, sorted), so a host key change asks again. Where the files cannot be read, the value is the same for every host, and only the host id counts.
  - A host with no id file, another id or other host keys asks again. Later builds install with no question. Continue Without Server installs nothing (`Failure.declined`).
- **The install** (`install.sh`) streams the bundled gzip build for the host's `uname` (`ServerBuilds`, `Contents/Resources/server/macterm-<key>-<target>.gz`) on stdin into `bin/.macterm-<key>.<pid>.<time>`, checks the SHA-256 of the binary (`sha256sum`, else `shasum`, else the binary's own `version` must name the build), `chmod 700`, and `mv`s it to `bin/macterm-<key>`. A trap removes the temp file on exit and on a signal (a lost link). Then a symlink to the new build replaces `~/.local/bin/macterm` with the same temp-name-and-`mv` step. A file or a folder of the user there stays. The app reads each build's checksum once for each run (`gzip -dc`).
- **The newest install wins** (`shouldReplace`). A proxy of this build can reach a server that another build started. The app sends that server `server.exit`, once for each connect, and connects again; the sessions keep running and keep their build (design/002). It does this for a lower level, and at the same level only right after this connect installed its own build: builds of one level have no order. A server of a higher level stays: an app never downgrades a host. So two apps of one level on one host (a Debug and a Release build) share the server of the later install, and do not take turns replacing it.
- **The server removes old builds** (`pruneBuilds` in `server.zig`): the files `macterm-<key>` in its own folder whose key no session reports, never its own, and none of the last minute (`fresh_build_ms`: an install whose proxy has not started yet). It does this when every session settled at start and after each session ends. It fails closed: only a server that runs from a `macterm-<own key>` file does it (not the Mac's bundle, not a file that an install replaced under it), and nothing while a session's build has no key. A temp file of an install is not a build.

### Session daemons and macOS attribution (#419)

macOS attributes work that needs privacy permission (Local Network, TCC) to the *responsible process* of a process. The value is fixed when the process starts, and the process inherits it from its parent.

- Because of this, the whole tree of a pane belonged to the Macterm that created its session. It belonged to nothing after that Macterm quit. Every process that survives becomes responsible for itself. A new start of Macterm that connects again over the zmx socket never attributes it again, because a connect is not a fork.
- From then on, macOS judged each pane program by its own identity. For anything that Apple did not sign, this meant `EHOSTUNREACH` on the local subnet, with no prompt.
- The fix is in the zmx fork (change 0004, `daemonize.zig`). On macOS, the session daemon starts itself again with `POSIX_SPAWN_SETEXEC` and `responsibility_spawnattrs_setdisclaim`. It is its own responsible process from the first instant. Every program in the session belongs to **it** for the whole life of the session, whatever happens to the app.

- **The daemon has the signature of the app itself** (`scripts/embed-zmx.sh`). It uses the certificate of the app *and* the bundle identifier of the app. The certificate is the release certificate in CI, and it is ad-hoc on your Mac.
  - macOS identifies a responsible process by the identifier in its code signature. With the identifier of Macterm, the daemon resolves to the name of Macterm, its usage descriptions and its existing grants for Local Network and TCC. One grant covers the app and every pane.
  - Any other identifier names a second thing and needs a second grant. Examples: the `zmx` of the release download, which the linker signed, and a separate "Macterm Sessions". We tried the second one. The prompt only said "zmx", because a bare binary has no LaunchServices record that gives it a name.
  - Xcode never signs a Mach-O again when it copies it into `Resources/`. An ad-hoc daemon would be a new identity at every update.
  - `build.sh` refuses a release bundle whose zmx is ad-hoc or is not `com.thdxg.macterm`. `BundledResourcesTests` pins the identifier on the zmx of the built bundle. A change in a build phase therefore cannot turn every pane prompt into a prompt for "zmx" in silence.
- Full Disk Access follows the same attribution. The programs of the daemon satisfy the own TCC requirement of the app (identifier and certificate). They inherit its FDA grant, and this stays true after the first new start.
- You cannot change responsibility afterwards (`responsibility_set_*` needs a private entitlement). The disclaim exists only as a spawn attribute. This is why the daemon starts itself again in place, and why the fork has no flag for it. The responsible root must *stay* a zmx process. A trampoline that ran the shell with exec would keep the pid, but the identity that macOS evaluates would become the identity of the shell.
- A session that an older build created keeps its old attribution until you create it again. The fix takes effect for each session.
- To measure, use `responsibility_get_pid_responsible_for_pid` (a probe in C of ten lines). A Local Network prompt that nobody *answered* denies everything under that responsible process, also platform binaries. A subnet that looks dead can be a dialog that waits.

### Pinned Tabs

Pinned tabs belong to no project. The sidebar shows them above the projects. They are a **sentinel workspace** (`workspaces[PinnedTabs.projectID]`). Its ID is a fixed UUID that is not a `ProjectStore` row, so the iteration over projects never sees it. Each pinned tab is a `PinnedTabRecord`: a durable declaration (`LayoutTab`) and, while it is loaded, a live `TerminalTab`. All the logic is in `AppState+PinnedTabs.swift`.

- Pin and Unpin are `moveTab`s. They never kill anything. `syncPinnedRecordsWithWorkspace` pins a tab that was born in the pinned workspace.
- **Closing a pinned tab is an unload. It is never a removal**. The sessions end. The record stays as a dimmed row. When Macterm starts again, it starts the tab again at once. Unpin is the path for removal.
  - The same unload happens when the own sessions of a tab die (`paneProcessExited`).
  - The code calls this state "unloaded" (`unloadPinnedTab`). The GUI never does: the dimmed row's tooltip says "Not running".
- The persistence has two layers.
  - The live state is in the `pinned` section of `workspaces_v3.json`.
  - The declaration is in `~/.config/macterm/pinned.yaml`. It is next to `widgets.yaml`. The location comes from `ProjectFileStore.configDirectoryURL`, and the custom store of a test keeps it inside its own directory.
  - The file is a `ProjectFile` whose reserved `path: <pinned>` is the marker. It has no IDs for entries. Macterm matches entries back by name, then by the exact layout, then by position (`PinnedLayoutMatcher`).
  - `AppState` tracks its own last write. It absorbs external edits before each write. A file that does not parse suspends the auto-writes with an alert.
  - A file that is absent or empty means "no input". It never means "remove everything".
- **`pinned.yaml` lived in `projects/` before 1.31. That location is retired (#446)**. Macterm reads and writes only the new place. The 1.31 releases moved an existing file up at launch. A file that is still in `projects/` is ignored. The listing of projects still skips the reserved name there. A leftover file is therefore never offered as a project, and no project can take the name.
- At launch, every record materializes. `materializeRestoredPinnedTabs` asks the server which sessions survived. A session that is dead starts again from the declaration. The declaration refreshes at pin time, when the pinned foreground changes (debounced), and at quit. It never refreshes at unload.
- Sidebar drag: the pinned rows and the tab lists share one `.dropDestination` at the level of the ForEach. It drives the native insertion line. Rows have no destinations of their own. A target on a row kills the line and swallows clicks. `PinTabDropZone` above the List makes the first pin possible by drag. `--project pinned` addresses the workspace over the CLI.
- **No project may have the name `Pinned`** (any case, padding ignored). `ControlHandler.resolveProject` reads it as this workspace before any project, so such a project cannot be reached by name.
  - `PinnedTabs.reservesName` is the one test that every naming path applies. A typed name is refused where the user typed it. These paths are CLI `project create --name` and `project rename`, the notice of the sidebar rename, the New Project intent, and the remote sheet.
  - A name that nobody chose (the own name of a folder) becomes `Pinned 2` in `ProjectStore.create`. `ProjectStore.rename` refuses it outright.
  - Projects that got their names before the rule keep their names.

### Desktop widgets

Desktop widgets are terminals on the desktop (`DesktopWidget`, `AppState+DesktopWidgets.swift`, `DesktopWidgetWindows`, Settings → Widgets). Each one is one pane. Its zmx session persists in the same way as the session of a pinned tab. A panel of our own draws it, in the shape of a system widget. The grammar for users is in `docs/44-desktop-widgets.md`.

- **A widget is not WidgetKit, and it cannot be.**
  - A WidgetKit widget is an archived SwiftUI snapshot that another process renders. It has no NSView and no text input. Its budget of refreshes is minutes.
  - chronod also purges the descriptors of any widget extension that has no Apple team in its signature. It logs `Requested to add extension, but purging instead because we shouldn't cache it`. We measured this with ad-hoc builds and self-signed builds, against a control with a Team ID.
  - Widgets therefore never appear in the Edit Widgets gallery of the desktop. You create them from Macterm (File menu, palette, `+` of Settings, `widget new`).
- **The metrics are measured, not guessed** (`DesktopWidgetMetrics`, `DesktopWidgetGrid`).
  - chronod logs the `CHSWidgetMetricsSpecification` of the host (`log show --predicate 'process == "chronod"'`, the entries with `cornerRadius`). The edges are 164, 344 and 704 pt. The continuous corner is 27.88 pt.
  - These edges are all spans of one module (164 pt cells, 16 pt gaps, a pitch of 180 pt). The size of a widget is therefore a `DesktopWidgetSpan`. There are no presets.
  - A new widget is `DesktopWidgetSpan.initial` (3×3). Macterm puts it at the exact middle of the screen (`DesktopWidgetGrid.centered`). It is off the lattice until its first move or resize. The lattice cell that is nearest to the middle can be half a pitch away. When the middle is taken, Macterm uses the nearest free cell of the default lattice.
  - **There is no grid for the whole screen**. Notification Center stores its widgets as groups, each with its own origin. It logs `Writing desktop widget placement storage to disk: … groups: [{origin: (18.0, 25.0), items: [<col, row, size>…]}]`.
  - Every move and resize therefore ends in `DesktopWidgetGrid.snap`. It snaps onto the lattice of the nearest widget within one pitch. This includes the system widgets. Macterm reads them from the window list (`NativeDesktopWidgets`). The window of a widget is the widget plus 8 pt of shadow. The placement file itself is in a protected container.
  - Read EVERY window, not only the windows on the screen. Notification Center reports its widgets as off screen when windows cover the desktop.
  - Accept only real widget windows. They are windows of the host, at the level of the desktop icons plus 2. They have a visible alpha and whole cells in each direction.
  - Notification Center also keeps a window with no title and alpha 0, one level below. We saw it at 464×824 after we dragged widgets around. When we read it as a widget, it blocked empty cells and pulled the widgets of Macterm onto its lattice.
  - If no widget is near, Macterm uses the default lattice of the screen at the corner inset that macOS uses (26, 33).
  - The result is the nearest cell and span, kept on the screen. If it overlaps, Macterm moves it to the nearest free cell. System widgets count as occupied.
  - `column` and `row` in `widgets.yaml` are on the default lattice. The snap after Macterm applies them pulls a widget back onto the lattice of its neighbor.
  - Measure again when a macOS release looks different.
- **Locked by default. One widget is edited at a time**. `AppState.editingDesktopWidgetID` is the single edit slot. It is only in memory, so every launch comes up locked.
  - A locked widget behaves like a system widget. `canBecomeKey` is false. `DesktopWidgetShieldView` takes every mouse event and turns a press into a widget drag. The wheel is included. Over mouse reporting or alternate scroll, the wheel is input.
  - The terminal gets no focused pane (`focusedPaneID: nil`). The one pane of a widget is always the focused pane of its tab. When we passed that through, every locked widget showed a solid cursor.
  - Editing has four parts. The first is the own edge resize of the widget. The second is the outline in the accent color. The third is a Done button. The fourth is a drag from the margin only. `DesktopWidgetResize` does the resize. It uses the outer 7 pt band of the margin and 20 pt corners. The cursors come from a tracking area with `.activeAlways`. Inside the terminal, a drag selects.
  - We do not use `.resizable` of AppKit. Its resize area for a borderless window is a sliver, and its hover cursor never showed.
  - Every drag waits for a threshold of 4 pt before `performDrag`. A jitter of a click must not move a widget. Then the code polls for the release and snaps the widget.
  - The CLI can still type into a locked widget.
- **An edited widget has no shadow**. The shadow and the rim of a KEY window come from the rectangle of the window, not from its alpha. That put a dark square behind the rounded corners. In an A/B test, the square was gone with `hasShadow = false`. The style mask and `invalidateShadow` did not change it.
- **The panel lives where system widgets live.**
  - Its level is `desktopIconWindow + 1`. It has `.canJoinAllSpaces`, `.stationary` and `.ignoresCycle`. It is borderless and `.nonactivatingPanel`. When you type into a widget, the frontmost app stays in front.
  - The quick terminal shares the key handoff through `panelDidResignKey`.
  - It is an `NSPanel`, so `isTerminalWindowCandidate` already excludes it. AeroSpace does not manage it.
  - A modal that a widget raises (`DesktopWidgetRemoval`) must activate the app first (`AppDelegate.activateWithoutReopen`). In an app that is inactive, the modal never comes forward and blocks, and nobody sees it.
- **The appearance is `WindowAppearance.syncDesktopWidget`**. The window is never opaque, because the rounded backdrop is the shape. Glass and tint are at the corner of the widget.
  - **The shape of the window is the `_cornerMask` of `DesktopWidgetPanel`**. It is the continuous corner of the widget as an image of nine parts. When we left the window server to derive the shape from the alpha, it made a coarse, jagged region with wider corners. With glass off, the CGS blur filled that region. The result was a blurred desktop around every corner, and the radius was visibly lost. Glass hid this, because it draws its material inside the curve. In an A/B test against a flat backdrop, the halo and the rim were gone with the mask.
- **There are two layers of persistence, as for pinned tabs.**
  - The snapshot (`WorkspacesFile.desktopWidgets`, schema v7) carries the session identity.
  - `~/.config/macterm/widgets.yaml` is the declaration (`WidgetLayoutStore`, schema `assets/widgets.schema.json`: keep them in sync). It has `name`, `size`, the grid `column` and `row`, and `display`. `display` is the name of the screen. Macterm always writes it, because the primary display changes with what the user plugs in. In an entry that someone wrote by hand, no `display` means the primary one. It also has the recipe for a new start, `cwd` and `run`. Macterm captures it from the live pane with the pinned rule that an idle capture never clears `run:`.
  - The file follows the rules of `pinned.yaml`:
    - Macterm writes it again after every change and at quit.
    - It absorbs external edits first (baseline of the exact text).
    - It has no IDs (`WidgetLayoutMatcher`: name, then content, then position).
    - It is authoritative for membership at launch.
    - An absent file is no input.
    - A file that does not parse suspends the writes behind an alert.
    - Macterm honors the removal of a running widget at launch only. The entry of that widget stays out of every write from then on (`unlistedDesktopWidgetIDs`). Macterm judges it against the widgets that our last write listed, so that a widget created since then is not taken for a removal. If it did not do this, the next write put the entry straight back.
  - The reconcile at launch adopts the size and the cell of an entry only where they DIFFER from the own declaration of the widget. The cell in the file is on the default lattice, and it cannot express a widget that joined the lattice of a neighbor. When Macterm derived an unchanged entry again, it moved the widget off its neighbor at every launch.
  - The reconcile also saves no snapshot. It runs before any window registers, and `windows` would be written as absent.
  - The capture of the recipe (`refreshDesktopWidgetRecipes`) drops a foreground that it saw while `Pane.isShellAtPrompt`. That is a prompt hook, and Macterm was typing it into the next new shell.
  - Macterm draws restored widgets only after `materializeRestoredDesktopWidgets` asks zmx which sessions survived. A widget that is dead starts again from its recipe. If a surface attached first, it would get the empty shell that zmx upserts.
- **Widgets follow the displays in the way of Notification Center** (`DesktopWidgetPlacement`). We measured this from its logs when we went from a 3008×1692 display to a 1920×1243 display.
  - Notification Center keeps the layout of the system widgets for each display *and* for each resolution. On a display for which it has no layout, it PROJECTS the latest layout, with the same offsets from the visible top-left. It saves nothing.
  - The `placements` of a widget therefore record where the user put it (creation, a settle, a declaration). The key is the display name plus the resolution of the whole frame, so that the Dock does not make a new key. `topLeft` is where the widget is now. Macterm never records a projection.
  - `desktopScreensDidChange` and the restore at launch both go through `placeForCurrentScreens`. `DesktopWidgetWindows` calls `desktopScreensDidChange` 1 second after the notification for the screen parameters stops firing. A connect posts it several times, and Notification Center moves its own widgets in the meantime.
  - `placeForCurrentScreens` uses the display that the widget was last put on, or else the primary display. It uses exact placements first. Then it uses projections, clamped onto the screen. A projection that would land on another widget moves to a free cell.
  - Macterm never shrinks the span to fit. That would lose its size for the large display.
  - `widgets.yaml` declares the latest *placement*, not `topLeft`. If it declared `topLeft`, a quit on the laptop would write the cell of the laptop. The next launch on the external display would adopt it.
  - Not verified live: what Notification Center does with widgets that do not fit, and if it anchors any of them to the right edge. Ours clamp.
- **Widget panes live outside every workspace**, like the panes of the quick terminal.
  - Their sessions are claims (`desktopWidgetSessionNames`). They are bound in `session list`. They are rows in the quit prompt for the case with no persistence. The pane verbs address them through a bare `--session` (`ControlHandler.widgetTarget`).
  - When the shell of a widget exits, the widget starts again in a new session (`desktopWidgetShellExited`). It does not close.

### First-run seed

`FirstRunSeed` (pure) and `AppState.seedFirstRunIfNeeded` seed a fresh install with one project (the home directory) and one pinned "Welcome" tab. Each one runs `macterm tutor <topic>` as its `run:`.

- It runs after `restoreSelection`.
- `Preferences.hasSeededFirstRun` is written on the first launch that can answer, seeded or not. The exception is `.postpone` on `WorkspaceStore.loadFailed`.
- It is off (postponed, not skipped) under `MACTERM_BENCHMARK=1`. The harnesses look like fresh installs, and they do not isolate the defaults domain.
- The seeded `run:` is bare words, so that it tokenizes in the same way in every login shell.

### Project color tags

`Project.colorName` tints glyphs that the row already draws (the project icon, the icons of the tab rows, including agent logos and status glyphs).

- **No stripes. No glyph means no tag. No indicator in the titlebar**. We tried each alternative and rejected it.
- The colors are fixed system colors (`MactermTheme.color(for:)`). They are deliberately not derived from the ghostty palette.
- The picker is `.pickerStyle(.palette)` (`ProjectColorMenu`). It is the only menu form that renders.
- Macterm stores the color as a String, so that an unknown value becomes untagged.
- `iconStyle` wraps both arms in `AnyShapeStyle`. Without it, `tagColor ?? .secondary` coerces to `Color.secondary` in silence and restyles every untagged row.
- `Preferences.autoAssignProjectColors` (default off) is read only at creation, through a closure that you can inject on `ProjectStore`.

### Finder Services

**Services → New Macterm Project Here** is an `NSServices` entry in the plist plus `FinderServiceProvider` (`Macterm/App/FinderServices.swift`). The `NSMessage` in the plist and the `@objc` selector are a contract at run time that nothing checks. `FinderServicesTests` reads the plist back. A request can arrive before the app restores its state. The provider therefore queues requests until `attach`, and then defers through `AppState.performWhenRestored`. Use that hook for any external request at launch.

**Opening a folder or a file WITH Macterm** arrives at `AppDelegate.application(_:open:)`. The ways are Open With in Finder, a drop on the Dock icon, and `open -a Macterm <path>`. `DocumentOpenRequest` (`Macterm/App/OpenFolder.swift`) splits the request.

- Folders go to `FinderServiceProvider.open(paths:)`. This always makes a **new** project, never a tab.
- Files go to `FinderServiceProvider.openTextFiles` (see Text files below).
- A cold launch therefore uses the queue and defer from above for both.

`CFBundleDocumentTypes` has three entries. **All have `LSHandlerRank: Alternate`**, so Macterm is never a default opener until the user selects it with Get Info → Change All.

1. `public.directory` (the entry of Ghostty).
2. `public.text`.
3. A list of extensions for text that macOS does not type as text (`go`, `rs`, `ts`, which it takes for video). The Info.plist of Zed makes the same split.

Unlike Ghostty, Macterm does not declare scripts and executables. A script that you open with Macterm is edited and not run. `OpenFolderTests` reads the plist back for this contract.

**The two file entries name `Document.icns` (`CFBundleTypeIconFile`)**. Finder shows it for a file that Macterm opens by default, as Zed does. Without it, macOS draws its generic white page with the app icon in the middle. The icon is the app icon's screen in the shape of a page: one glass pane over the app icon's characters. It is plainer than the app icon on purpose: it has no cross and no gap. `scripts/document-icon.sh` draws it from `AppIcon.icon` (`scripts/document-icon/render.swift`). After a change to the app icon, run the script and commit the new `Macterm/Document.icns`. The Folders entry names no icon: a folder that opens with Macterm still looks like a folder.
- **The page is real Liquid Glass from `macterm-icon-renderer`**. The script builds Debug and runs the helper, so it needs macOS 26 or later on Apple silicon. The app never draws this icon at run time.
- **The script compiles its own copy of `AppIcon.icon`** (`actool`, into a temporary catalog). In it, the pane and the characters are drawn again for the page, in a region of the canvas with the page's shape, inside the frames, so no ring shows. The copy leaves out the cross, its shade and the screen's gradient (`leftOut`), and each group takes the fill of the first layer it keeps. The pane covers the whole page and more, so its edges are outside the page and it bends nothing in it. The helper renders the copy on the page's own background, and the script lays that region over the page.
- **The page has the app icon's characters**: the same ramp, density gradient, dither, spacing and seed as `scripts/app-icon/characters.swift`, in 96 pt cells, turned 8° as the app icon's are. The page is the app icon's lid, the color of the top of its screen. Never hide a group of the copy: a hidden group drops out of the compiled icon, and the helper refuses a request whose count of groups differs. Hiding a group's only layer, or setting its opacity to 0, also drops the group.

**Text files (Settings → General → Opening Text Files)** open in the terminal editor of the user (`AppState+TextFiles.swift`).

**Set Macterm as Default App… sets Macterm as the default app of every text file type in one click** (`TextFileDefaults`, Settings → General → Opening Text Files). It is Get Info → Change All, for each type.

- Launch Services keeps a default for each content type. A default for `public.text` does not reach `public.python-script`, so the button sets each concrete type.
- A type is in the list because an extension has it: `TextFileDefaults.commonExtensions` and the extensions of the third plist entry. It keeps a type that conforms to `public.text` or that is dynamic (an extension that macOS does not know). It drops HTML, RTF and images (`excludedTypes`). The filter is why `.ts` stays out: macOS types it as MPEG-2 video.
- `NSWorkspace.setDefaultApplication(at:toOpen:)` runs one type at a time, because Launch Services can ask the user to agree to a change.
- The section compares the default app of each type by bundle identifier and reads it again on activation. When every type opens with Macterm, the button is gone and the caption says so.
- The docs list every extension that the button changes (`docs/20-configuration.md`, "Text file types"). `TextFileDefaultsTests` compares that table with `TextFileDefaults.extensions()`. A new extension in the plist or in `commonExtensions` therefore fails a test until the docs list it. Ghostty has no equivalent. Upstream declined the detection of `file:line` and a link that you can configure (discussions #11378 and #9546). This feature is therefore our own.

- **A ⌘-click goes to the pane first** (`GhosttyTerminalNSView.onOpenLink`). This is only for the `.unknown` kind of the link regex. It is never for OSC 8 or for opens by a keybind.
  - `FileLink` splits `:line[:col]` off. The regex of libghostty keeps it, and `foo.swift:42` even parses as a URL scheme. `FileLink` resolves the path against the cwd of the real pane.
  - Anything that is not an existing local file goes to the system opener, unchanged. So does every remote pane.
  - An existing file goes to its **default app, and Macterm drops the line**, because you cannot tell another app a line. The exception is that the default app is Macterm (`TextFileOpening.isDefaultApp`, by bundle id). Then the editor opens directly and keeps the line.
  - A click in a mirror acts on the real pane (`editorAnchor`). A click in the quick terminal splits the panel. A click in a desktop widget goes the Finder way.
- **The editor is `$VISUAL`, if not `$EDITOR`, if not `vi`**. This is the order of git. Macterm has no setting of its own, deliberately. The variable is where a user already names their editor.
  - **Macterm types the command. It does not start the editor with a spawn** (`TextFileEditor`). The variable and the PATH of the editor are in the shell rc of the user, and no process outside the shell can read them.
  - The typed line is a fixed ` exec sh -c '…'`. It parses in the same way in nu, fish, zsh and bash (no `'` or `\` inside). The file and the line go in the environment of the new pane (`MACTERM_EDITOR_FILE` and `MACTERM_EDITOR_LINE`). No path is ever escaped into shell grammar.
  - `exec` makes the pane close when the user quits the editor. If the editor is missing, the line waits for Return instead.
  - Macterm passes the line as `+N`. This is the one syntax that every terminal editor shares.
- **The placement** is `Preferences.textFilePlacement`. It is a split (automatic axis, `SplitDirection.auto`) next to the pane that was clicked or the focused pane of the project. It can also be a new tab.
  - The exception is the pinned workspace. It always splits. A tab that is born there would be pinned, and when you quit the editor, it would leave a dimmed row.
  - A file from Finder goes to `TextFileProject.project`. This is the deepest local project that contains it. If there is none, it is the active local project. If there is none, it is the first local project. If there is none, it is a new project for its folder. It never goes to a remote project.

**A folder that you drop on the sidebar** opens in the same way (`SidebarFolderDropTarget`, `Macterm/Views/SidebarFolderDrop.swift`, through `AppState.openProjects`, which the Finder service shares). Macterm selects it in the window where you dropped it.

- It is an AppKit view over the whole sidebar. It is registered only for `.fileURL`, and it is transparent to `hitTest`.
- AppKit picks a drag destination by the registered type. It does not ask `hitTest`. Clicks and scrolls therefore still reach the outline below it. So do the drags of tabs, projects and panes in the app, because none of them carries a file URL. No SwiftUI destination could have caught a drag from Finder there.
- The feedback is the `+` of the cursor alone.
- A drop on a pane is still the paste of a path by `GhosttyTerminalNSView`.

**SwiftUI answers that same event by opening a second window. The `handlesExternalEvents(matching:)` of the scene stops it.**

- If you leave it alone, an event for open documents gets a new `WindowGroup` window on top of the project that the delegate just selected. Then there are two windows on one tab, a dimmed mirror in front and `MirroredTabNotice` behind. It also happens when we remove our delegate method, so this is the handling of SwiftUI and not ours.
- Macterm emits no external events of its own (no URL scheme, no Handoff). The group therefore declares a condition that nothing ever matches.
- The set must be **non-empty**. `[]` means "handles no external events at all". It also silences `applicationOpenUntitledFile`. That is the only call that reliably builds a `WindowGroup` window. We measured New Window, `window new` and the repair of #241 as dead under `[]` and alive under a condition that never matches.

### Dock menu

When you right-click the Dock tile, you see **New Window**, **New Tab**, **New Project…** and **Toggle Quick Terminal**. This is the set of Ghostty. `AppDelegate.applicationDockMenu` builds it (`Macterm/App/DockMenu.swift`). `@NSApplicationDelegateAdaptor` does forward this one, and we verified it live.

- The items are `AppCommand`s. They run through `AppCommand.action(in:)`. The Dock is therefore a fourth renderer of that list, and not a second set of handlers.
- Macterm builds the menu again at each right-click with `autoenablesItems` off (enabled means that the action is not nil). The menu is nil until `MainWindow` gives the delegate its state objects.
- `DockMenu.Preparation` is what the Dock adds. A selection arrives from outside the app, and it does not activate the app.
  - New Tab and New Project… call `showWindow()` first (the last window, which is hidden, or the state with no window of #241).
  - New Window activates the app and lets the command make its own window.
  - Toggle Quick Terminal prepares **nothing**. The panel does not activate the app, by design.
- Macterm resolves the action *after* the preparation, because fronting a window is what makes `activeProjectID` the right project.
- `DockMenu.Preparation` is now the shared table for **"invoked from outside the app"**. App Intents run through the same `AppDelegate.performExternalCommand`, and they do not decide again. For this reason the table has `.toggleCommandPalette`, which you cannot reach from the Dock menu itself.

### Adaptive icon

On macOS 26 and later, the Dock icon and the app-switcher icon are `AppIcon.icon` repainted in the colors of the terminal theme, with real Liquid Glass (`Preferences.adaptiveIcon`, on by default, Settings → Appearance → App Icon). The grammar for users is in `docs/46-finder-and-dock.md`. Four parts do the work: `AdaptiveIcon` (the pure rules), `AdaptiveIconController` (the triggers), `AdaptiveIconRenderer` (runs the helper) and `AppIconPresenter` (the one write).

- **Only `macterm-icon-renderer` touches the private API, and it runs in a process of its own** (`IconRenderer/main.swift`, target `MactermIconRenderer`, `Contents/Helpers`). It calls Apple's private IconRendering and CoreUI frameworks, which draw every `.icon`.
  - CoreUI reads the icon's layer stack out of the app's own `Assets.car`. IconRendering's `makeIcon()` turns it into its `Icon` model. The helper replaces the fills and renders the icon.
  - A symbol that a macOS update removes makes dyld abort the helper (SIGABRT), and a trap in the framework kills only the helper. The app gets a `Failure`, shows the bundled icon, and turns the adaptive icon off for the rest of the run. We measured both: a helper that segfaults, and a helper that links a symbol that does not exist.
  - **Never call the private frameworks from the app process**, also not through `dlopen`. A trap there stops the app.
  - The request is the helper's only argument, not stdin. The app does not ignore SIGPIPE, so a write to a pipe that a dead helper closed would stop the app.
  - A run that takes longer than `AdaptiveIconRenderer.timeout` is killed. A render takes about 0.25 s. The helper's memory (about 180 MB at peak, mostly GPU setup) is gone when it exits.
  - **Nothing in a run waits without a bound.** The helper gets SIGTERM at the timeout, and SIGKILL `killGrace` (1 s) later. A run ends when the helper exits, not when its pipes close, because a child of the helper can keep a pipe open. The pipes are read as data arrives, for at most `drainTimeout` (1 s) after the exit. Never go back to `readDataToEndOfFile`: a `sleep` child of a stand-in helper held a utility thread for 30 s after the kill.
  - **One helper runs at a time** (`AdaptiveIconRenderer.Queue`, owned by the controller). A request that arrives during a render waits, and a newer request replaces it (`.superseded`). `.superseded` says nothing about the helper, so it does not turn the adaptive icon off.
  - `scripts/build.sh` refuses an ad-hoc signature on the helper when `MACTERM_CODESIGN_IDENTITY` is set, as it does for the app and zmx.
- **The helper compiles against hand-written declarations** (`IconRenderer/PrivateInterfaces`). Do not link a copy from Xcode.
  - IconRendering is a Swift module built with library evolution. A client therefore needs only the declarations, not the layouts of the types. Each declaration must mangle exactly as the framework exports it: the kind (struct or enum), the names, the labels and the types. `.swiftinterface` holds them.
  - `IconRendering.tbd` and `CoreUI.tbd` are link stubs. The frameworks exist on disk only in the dyld shared cache. To add a call, add its declaration, link the helper once against the copy in `Xcode.app/…/Icon Composer.app/Contents/Frameworks`, and copy the `nm -um` symbols "from IconRendering" into the `.tbd`.
  - The helper is arm64 only. An Intel Mac cannot run it and keeps the bundled icon.
- **The catalog lookup has fixed values.** `iconLayerStackWithName:` finds a macOS icon only with scale 1, idiom 0 and an appearance name of `NSAppearanceNameAqua` or `NSAppearanceNameDarkAqua`. A dark render must use the DarkAqua stack. The Aqua stack rendered in the dark style replaces the background with the system's dark one.
- **IconRendering keeps the layer groups bottom to top**, the reverse of `groups` in `icon.json`. `AdaptiveIconRequest.layers` follows that order. The helper refuses a request whose count of layers is different (exit `structureChanged`). An icon redesign that adds or removes a group therefore shows the bundled icon until `AdaptiveIcon.paint(for:)` follows. `AdaptiveIconTests` reads `icon.json` and fails first.
- **The icon has four groups, top to bottom: Silver Frame, Dark Ring, Glass Pane (the four panes and the cross), Characters.** `actool` refuses more than four visible groups, and an empty group, or one whose layers are all hidden, drops out of the compiled icon. The helper paints each group in one color, or leaves its bundled fills when the request names none (`nil` in `AdaptiveIconRequest.layers`): the frames keep their gradients so. A layer that needs a color of its own in the same group takes an accent (`AdaptiveIconRequest.accents`): the cross is one in the glass pane's group. Glass refracts only what is behind its own group, so the characters have the bottom group. Each layer of a group still bends light at its own edges: the panes bend the characters along the cross.
- **The masks are drawn by scripts** (`scripts/app-icon/frame.swift` for the rings, the panes and the cross, and `scripts/app-icon/characters.swift`). Change a shape or the characters there, run the script, and commit the PNG.
  - Both rings follow the macOS icon shape: continuous corners whose radius is 26.15% of the side, measured from the system's render of the icon. Every edge is that shape, inset, with the radius less the inset, so the edges are concentric. Their widths are Ghostty's icon's, measured the same way: the silver bezel ends 52 pt in on the 1024 pt canvas, and the dark ring 108 pt in.
  - The cross is the gap between four quadrants of the screen, drawn as one shape: the gap that the v1.32.1 icon's glyph left between its four panes. Its arms cross 60% of the way across and down, as in that glyph, and the gap is 52 pt, as wide as the silver frame (the glyph's is 66 pt). The cross, its panes and its shade turn 8° clockwise about its middle (`crossAngle`), and the characters' grids turn with them, so their rows stay parallel to the arms. Each quadrant rounds the corner that faces the middle with the dark ring's inner radius, so the cross opens up where its arms meet. The glass pane is the four quadrants. Its mask covers 1.5 times the canvas, so its only edges in the icon are along the cross: an edge at the frame bent the characters there too.
  - The characters are a monospace grid in each pane (120 pt rows, columns 1.6 characters wide), as a terminal pane has its own. Each grid starts 40 pt from the cross and runs outward past the icon's edge, so the characters run on under the frames. Every cell is drawn, clipped to its pane, so the characters reach the rounded corners where the arms meet. The margin keeps them out of the band where the panes' glass bends them: the glass pulls squeezed copies of nearby characters into that band, and a character that crossed it lost its place in the grid. The density is the icon's gradient: heavy characters at the top thin out to dots at the bottom, on a flat background. Each step of the ramp holds Mac key symbols and ASCII of about the same ink (`⌃ + =`, `⇧ ⏎ ⇥`, `# ⌫ ⎋`, `⌘` at the top), measured as rendered. A seeded offset of up to three steps mixes the rows, so no bands show. Each character's ink is centered in its cell: a period on the baseline and a caret at the cap height made the light rows at the bottom look scattered. ⎇ is not in the ramp: CoreText's fallback for it is twice as wide as a cell.
  - The cross casts a shade on the characters (`cross-shade.png`, drawn by `frame.swift`): the cross, blurred by 24 pt and moved 20 pt down, as if lit from above. It is the top layer of the characters' group, flat, black in every theme (`crossShade`, an accent), at opacity 0.9. Icon Composer's own shadow on the cross's group barely shows on the dark screen, also at its highest.
- **The glass settings are in `icon.json`.** Both rings are Ghostty's colors: the silver frame is the gradient of Ghostty's background (88% to 40% gray, top to bottom), and the dark ring a gradient from 28% to 4.5% gray, fitted to Ghostty's inner bevel. They are glass with no translucency and full opacity, so they render as Ghostty's frames do: measured from `ictool`, the silver frame matches Ghostty's at the top, the sides and the bottom, and the dark ring at the top and the bottom, with its sides about 10 levels lighter. Translucent rings were darker, and the characters showed through them. The dark ring has no refraction: its glass bent the image of the cross out to its outer rim, so the arms showed again next to the silver frame. The panes have opacity 0.15, so they are clear glass in the screen's color. The group of the panes and the cross has a neutral shadow at opacity 2, the most that shows: 3 looked the same. The panes' refraction has depth 0.06, half of what it was, so the band where they bend the characters stays narrower than the margin. The characters are glass too, with no translucency: translucent characters showed the dark screen through them and lost their colors. They have opacity 0.5, so they stay behind the panes and the cross.
- **The helper lights the icon from the top-right** (`IconCanvas.lightAngle`, 2.6 radians, through `GlobalConfiguration(lightAngle:)`). IconRendering's default, 0, lights the top rims. The angle is not a key of `icon.json`, so the bundled icon (Finder, Launchpad, a Dock icon while Macterm is not running) has the system's light.
- **The frames keep fixed colors. The cross, the characters and the screen follow the theme** (`AdaptiveIcon.paint(for:)`). The silver frame and the dark ring keep their bundled gradients in every theme: `paint` names no fill for their groups. The characters are one color, the theme's palette 4 (blue, `characterBase`). A mesh of five ANSI colors over them looked busy, and it is gone. The cross is the theme's white, palette 7 (`crossEntry`): it follows the theme and stays light, as the silver frame is. It shares its group with the panes, which take the lid, so it takes its color as an accent. The screen is a gradient from the theme's "lid" at the top to its background at the bottom, turned with the cross. The icon's background is the theme's background, and over it a flat layer at the bottom of the characters' group (`screen-gradient.png`, drawn by `frame.swift`, `screenGradientElement`) lays the lid at the top and fades it out. `ictool` ignores a direction on the icon's own background gradient, so a layer turns it. The lid, which also fills the panes, is the theme's next gray past the background, itself, with no mix: the nearest gray (palette 15, 7, 8 or 0) at least `lidMinimumStep` (0.05) from the background toward the gray that stands out most. Distances are OKLab lightness, signed by the side of that gray, so a light theme gets a lid darker than its white. In eyesclosed the lid is its palette 0 (`#383B4A`). In Gruvbox, whose palette 0 is the background, it is palette 8, which is much lighter. A theme with no gray apart from the background gets nil from `paint`, and the bundled icon shows.
- **`AppIcon.icon` needs Xcode 27 to compile** (`.github/actions/select-xcode` pins 27.1, on GitHub's `xcode-27` image, which runs macOS 27). It uses Icon Composer 27 keys: `features`, `refractivity`, `"specular" : "inside"` and `"blur-material" : null`. The `actool` of Xcode 26 stops on them with `attempt to insert nil object`, so a build with Xcode 26 fails before any code compiles. The panes' refraction needs those keys. The unit tests therefore run on macOS 27 only. `Test / Smoke` on `macos-26` is the one test of the helper there (`older-macos-smoke.sh`): `GlobalConfiguration.init()`, the translucent frame and the 1.33.0 grid error were all found on macOS 26.
- **The bundled icon is the rule's output for eyesclosed**, the theme it is drawn in and Macterm's default: characters eyesclosed's blue, the cross eyesclosed's palette 7, the two frames in their fixed gradients, the screen from eyesclosed's lid (`#383B4A`) to its background (`#111214`), and the panes the lid. eyesclosed still renders like any other theme: a render costs about 0.25 s, and one code path is simpler than a special case. If you change a fill in `AppIcon.icon` or the rule, keep the two in step: `AdaptiveIconTests` compares them.
- **What IconRendering draws differs by macOS, so the helper measures the render and places the body itself** (`opaqueBody` in `IconRenderer/main.swift`). On macOS 27 `renderedIcon` draws the body alone, full-bleed. On macOS 26 it draws the body on the icon grid of its canvas. Neither draws a shadow. The body must fill 824 of 1024 px, centered, under a black shadow (blur 32 px, offset 8 px down, alpha 0.25). These values are measured from `NSWorkspace.icon(forFile:)` of system apps. The shadow is fitted against the system's render of this same icon (0.11 RMSE outside the body). The body is the opaque span of the render's middle row and column, and it must be square and mostly opaque. The macOS version picks the size at which the body draws 1:1 (the body's size on macOS 27, the canvas size on macOS 26), so each macOS renders one time. The measurement checks the pick, and a macOS that draws the other way gets a second render at the other size. 1.33.0 took every render for full-bleed, and on macOS 26 its Dock icon was 664 px of 1024. The unit test pins the grid on macOS 27, and `older-macos-smoke.sh` pins it on macOS 26. Measure again when a macOS release looks different.
- **The system's icon style decides if the adaptive icon shows** (`AppleIconAppearanceTheme` in the global domain: `Regular`, `Clear` or `Tinted`, alone or with `Light`, `Dark` or `Automatic`). Regular follows the system appearance, or its own side. Clear, Tinted and any value that we do not know show the bundled icon, which macOS styles itself. System Settings posts no notice when the style changes. The controller therefore refreshes when the app becomes active.
- **A `macos-icon = custom` image wins** over the adaptive icon (`AdaptiveIcon.decide`).
- **Triggers.** `GhosttyApp.applyAppIcon` gives the config's choice to `AdaptiveIconController.configuredIconDidChange` on each load and reload. The controller refreshes one main-queue turn later, because the first call comes from inside `GhosttyApp.init`, and a synchronous read of `GhosttyApp.shared` there deadlocks its dispatch_once. It also refreshes on `.mactermConfigDidChange`, on app activation and on the preference. A refresh whose request did not change does nothing. `AdaptiveIcon.decide` reads the system scheme (from `GhosttyApp.shared`) only after the setting, the support and the configured icon allow the adaptive icon, so a unit test that flips `Preferences.adaptiveIcon` never starts libghostty.
- **The last icon of each appearance is on disk** (`AdaptiveIconCache`, `<App Support>/AdaptiveIcon/`). A launch therefore shows it at once. The stamp of an entry names the build and the size and date of the catalog, so an update renders again.
- Tests and `MACTERM_BENCHMARK=1` never start the helper (`AdaptiveIcon.isSupported`). `AdaptiveIconRendererTests` runs stand-in helpers for each failure, and the real helper of the test host.
- A runtime icon is a fixed image. It shows only in the Dock and the app switcher, only while Macterm runs, and only in the style that we rendered. Finder, Launchpad and a Dock icon of a quit app show the bundled `.icon`.

### App Intents (Shortcuts, Spotlight)

`Macterm/Intents/` has fourteen intents, plus the hidden Open Project below. They mirror the surface of Ghostty (`macos/Sources/Features/App Intents/`) in the model of Macterm. The intents for projects and tabs are **New Project**, **New Tab**, **Focus Project/Tab/Pane**, **Close Tab** and **Where Did I Leave Off** (Project Insights, see that section). The intents for panes are **Run Command in Pane**, **Send Key**, **Get Pane Contents** and **Get Pane Details**. The other intents are **Toggle Quick Terminal**, **Open Command Palette** and **Invoke Keybind**. The grammar for users is in `docs/85-shortcuts.md`. `AppIntents.framework` is an SDK dependency in `project.yml`. The `appintentsmetadataprocessor` of the build writes `Contents/Resources/Metadata.appintents/extract.actionsdata`.

- **Translate and delegate only**, as `ControlHandler` does. Resolve what an entity names. Then call the same `AppState` and `ProjectStore` methods that the UI calls. The own resolution of `ControlHandler` is deliberately *not* shared. It speaks selector strings (name, index from 1, UUID), but the identity of an entity is exact. `IntentTargets` therefore does lookups by UUID and by session, and the CLI is untouched.
- **`MactermIntentHost`** is the only way for an intent to reach the app. The system makes the instances of intents, so you cannot hand anything in. `AppDelegate.installResponders` attaches it. The readiness waits on `AppState.performWhenRestored`. Running a shortcut *starts* the app, so `perform()` can arrive before the restore. The wait is a bounded sleep-poll (`readinessTimeout`). A launch that does not front a window may never install responders (#241), and a hang would wedge the shortcut with no error.
- **Entities are tokens, not handles**. `MactermPaneEntity.id` is the zmx **session name**. It is not `Pane.id`. Pane UUIDs are new at every restore. A saved shortcut that used one would break at the first new start, *in silence*, while the pane that it names is visibly still there. Tab IDs and project IDs are persisted, so they are fine. Every lookup can answer `.notFound`.
- **The ghostty key `macos-shortcuts` of the user** (`ask`, `allow` or `deny`, default `ask`) controls every `perform()`. `IntentPermissionGate` does this, in front of the readiness wait.
  - Macterm reads the key live from the loaded config (`GhosttyApp.shortcutsAccess` → `ShortcutsAccess.resolve`, in the shape of `MacosHidden`). The raw values are the tag names of ghostty. The key has no Settings UI.
  - `ask` remembers the answer only for the run. `.allow` is the grant that stays. Ghostty instead persists an Allow for ever under one UserDefaults key, and it does not remember a Deny at all.
  - Under `MACTERM_BENCHMARK=1`, it resolves to allow with no modal. The harnesses drive the app with nobody at the keyboard. This is also the reason why Macterm skips the notification prompt. An explicit `deny` still denies.
- **`MactermKeybind` repeats the cases and titles of `HotkeyAction`, because it must**. `appintentsmetadataprocessor` reads `caseDisplayRepresentations` from the source, and it rejects a computed dictionary ("must be a dictionary"). `MactermIntentsTests` pins the set of cases against `HotkeyAction.allCases`. It pins every label against its `AppCommand.title`. A new keybind therefore fails a test. It does not go missing from the picker in silence. The same constraint applies to any future `AppEnum`.
- **Statics must be `let`** under `SWIFT_STRICT_CONCURRENCY: complete` (`title`, `description`, `defaultQuery`, `supportedModes`). `supportedModes` is behind `#if compiler(>=6.2)`, like Ghostty. `supportedContentTypes:` of `IntentFile` exists only on macOS 15. Use `supportedTypeIdentifiers:`. Do not gate an intent away from the floor of macOS 14.
- **Projects are in Spotlight** (`ProjectSpotlightIndex`, macOS 15 and later). `MactermProjectEntity` is an `IndexedEntity`. After each save of `projects.json` (`ProjectStore.onSave`), the index writes the whole list again, debounced, so a removed project leaves no item. Tests and both harnesses never write the index (`ProjectSpotlightIndex.isHermetic`), because the Debug app's index belongs to the developer. A click on a result runs `OpenMactermProjectIntent`, the `OpenIntent` of the entity. It is hidden (`isDiscoverable = false`) and separate from Focus Project, because `OpenIntent` requires a parameter with the name `target`, and a saved shortcut stores its parameters by name.
- **Each pane's view names its pane entity** (`MactermPaneEntity.annotate`, from `Pane.ensureNSView`, `NSView.appEntityIdentifier`, macOS 15.4 and later). Siri and Apple Intelligence can then resolve "this pane". **Never make the pane entity `Transferable`.** The system would read the pane's text without the `macos-shortcuts` gate, and terminal text can hold secrets. Panes of the quick terminal and of desktop widgets get no identifier (`IntentTargets.isAddressablePane`), because `allPanes` walks only the workspaces. Apple's docs say that schema conformance is a prerequisite for on-screen cues, and no schema domain fits a terminal. Siri may therefore ignore the identifier. We have not verified it live.
- **`linkd` indexes the intents of an app only after the app was started from a stable location.**
  - A bundle in `/private/tmp` fails registration outright (`Could not create application record … -10814`).
  - A bundle that you copied to `~/Applications` but never started logs `is not trusted for binding, skipping`.
  - Start it one time, and the audit proceeds (`Checking … extract.actionsdata` → `Collating specified bundles`).
  - This is not a problem of the signature. We reproduced it in the same way with an ad-hoc signature and with a self-signed certificate that has the shape of a release certificate.
  - To see this, run `log show --predicate 'process == "linkd"'`.

### Control CLI (`macterm`)

A bundled CLI controls the app over `<App Support>/control.sock` (target `MactermCLI`, and `PRODUCT_MODULE_NAME` must stay `MactermCLI`). Xcode copies it to `Contents/Resources/bin/macterm`. Every pane gets it in `PATH`, together with `MACTERM_SOCKET` and `MACTERM_SESSION`. The full grammar is in `docs/80-cli.md`.

The verbs:

- `status`
- `project list/create/select/rename/remove`
- `tab list/new/select/move/rename/close/merge`
- `pane list/inspect/dump/split/focus/close/run/key/zoom/resize-split/mirror`
- `grid RxC`
- `session list/info/kill`
- `window list/new/focus/close`
- `widget list/new/set/edit/done/remove`
- `layout apply/save`
- `palette list` (the palette files of the extensions, read again each time, with the error of each one). The hidden `palette exec` is the runner of a `run:` action (`CustomPaletteLaunch`).
- `tutor`
- `ssh` (offline, the `+ssh` of ghostty natively through `SSHWrapper`)
- `skills` (offline, the agent skills below)

Rules:

- **Wire protocol** (`ControlProtocol.swift`, compiled into both targets). One request is one JSON line that ends with a newline, for each connection: `{v, id, command, args}`, with `noun.verb` commands. The responses are `{ok, data}` or `{ok:false, error:{code, message, action?}}`. The codes are in snake_case (`not_found`, `busy`, `no_surface`, `starting`, `ambiguous`).
  - The `v` of a request is the minimum version of the server that it needs. Ordinary requests stay at v1. `focus` needs v2. The handler rejects newer versions before dispatch.
  - Apps of v1 that shipped earlier ignore `v`. The CLI must therefore check newer requests against the version in the response of the server before it sends any mutation. A new version number alone cannot stop an older app from ignoring `--no-focus` in silence.
- **Server** (`ControlSocketServer`). A dedicated thread polls a non-blocking listen fd. The dispatch of each connection hops to `@MainActor`. The server starts in `applicationDidFinishLaunching`. The handler attaches in `installResponders` (early requests get `starting`). The socket has mode 0600 in a directory with mode 0700, for the same user only.
- **Handler** (`ControlHandler`). It translates and delegates only. It resolves selectors (name, UUID, index from 1). It calls the same `AppState`, `ProjectStore` and `ZmxClient` methods that the UI uses. Close verbs return a typed `busy` error, and they do not stage dialogs. A session selector with no `--project` resolves in the project that holds the session (`MACTERM_SESSION` arrives in the same way). A pane in the background can therefore still reach itself while the user looks at another project.
- **Client.**
  - Discovery order: `--socket`, then `MACTERM_SOCKET` (a hint, and the client falls through when it is stale), then the paths in App Support for each flavor.
  - stdout has output only on success. The exit code is 0 for ok, 1 for an error of the app, 2 for not reachable.
  - **Targeting trap:** a `--socket` that is not pinned, from a debug harness, can hit the live app of the developer. An untargeted `pane run` then types into their focused pane.
  - `pane run` therefore types as given only what follows `--`. Before `--`, its own flags parse at any place, and plain words are typed. Any other word with a leading dash fails validation, and Macterm sends nothing.
  - Its text is one `.allUnrecognized` array that Macterm splits at the `--` by hand. A second array with `.postTerminator` fails the validation of ArgumentParser in debug builds.
  - `ssh` keeps `.captureForPassthrough`. It mirrors the own argv of ssh. It answers a leading `-h` or `--help` itself (`startsWithHelpFlag`).
- **Agent skills** (`macterm skills`). There are four Agent Skills (panes, workspace, sub-agents, palettes). They are `SKILL.md` files in the format of agentskills.io. They teach coding agents this CLI.
  - They are compiled into the binary from `Macterm/Control/AgentSkills/` (shared with the CLI target, like `ControlProtocol`). The CLI prints them offline: every skill after a header about the install, or one skill as it is. Agents install them themselves.
  - Agents load one skill at a time, so each skill embeds `AgentSkills.groundRules`.
  - We ran every example against a hermetic instance before it shipped. Keep it that way.
  - `AgentSkillsTests` runs every `macterm …` line in them against the tree of `--experimental-dump-help` of the bundled CLI. If you rename a verb or a flag, a test fails until the skills follow.
- **`tab new --no-focus` and `pane split --no-focus`** send the optional `ControlArgs.focus = false` (absent means true).
  - Creation skips the selection at the mutation of the model. It never selects and then restores. The history of tabs and panes and the selections of windows stay untouched. A split with no focus keeps the zoom. An empty workspace adopts its first tab with no history, because there is no selection to keep.
  - `AppState.createTab` and `splitPane` incubate only children that no window renders (this includes panes that zoom hides). Visible splits then start at their real size.
  - Every warm goes through `warmPane`: project selection, the restore of pinned tabs and the creation by the CLI. The `incubatePane` that you can inject supplies the surface. One exit closure reads `pane.projectID` at the time of the exit, so that moving a tab cannot strand it.
  - A background split starts only the new pane. The other panes of a project that no window showed yet start when the project is selected.
  - The view slot is not observed, so the warm stays synchronous with the structural redraw. A window that is ordered out still mounts new children (E2E pins this). Children that zoom hides do need incubation.
  - Remote tabs get `project.zmxPath` before the warm. A split stamps the whole target tab, so the new sibling inherits the path of the source.
  - The start is asynchronous. It is not a promise that the shell prompt is ready when the CLI returns.
- `pane run` types through the paste path (`sendText`). `--no-submit` withholds the newline and keeps the evidence of a submission armed. `pane key <chord>` uses the key-encoding path (`sendKey`) and **bypasses `keyDown`**, so the interceptions of `keyDown` do not apply. A bare printable key must carry `.text`, or it encodes to nothing. `pane resize` exists only under `#if DEBUG`.

### The v2 protocol (`Macterm/Protocol/`)

The frames and messages between the app, the server and the session processes (design/003). The app speaks it on `ServerConnection` (channel 0) and on every pane's channel (`PaneChannel`, `PaneSession`).

- **The Zig messages are the one source** (`server/src/protocol/messages.zig`). The server binary's hidden `__schema` command writes the Swift types (`Macterm/Protocol/MactermProtocol.generated.swift`), the metadata (`server/schema/protocol.json`) and frames that Zig encoded (`server/schema/frames.json`). `mise run protocol` writes all three. Never edit them by hand.
- `MessagePack.swift` and `ProtocolFrame.swift` follow the Zig codec byte for byte. The cap on array memory differs: Swift counts its stride. `ProtocolFixtureTests` decodes each Zig frame and encodes it again to the same bytes.
- **CI checks the schema** (`scripts/protocol.sh --check` in the Server workflow; `mise run protocol --check` locally):
  - The generated files are current.
  - Against the metadata on main: no message, method, type, field or enum case is removed; no type, default or `since` changes; each addition has the current level; a new enum case needs an `unknown` case in the enum.
  - No method result and no event holds a `secret`.
- The base is main, not the last release, until v2 has a release. A new field in an older type names its level in `field_since`.
- Field names and enum tags are snake_case ASCII (`checkName`), so the Swift String compare is the Zig byte compare.
- `scripts/protocol.sh` needs Zig 0.17 on PATH or in `$ZIG`.
- **Resume (protocol level 2, design/003 §7).**
  - A session counts its output bytes and keeps the last 256 KiB in `ring.zig`. The ring grows only with output, to 320 KiB at most.
  - `snapshot.start` carries the `offset` that its screen shows.
  - `attach` can carry `resume_epoch` (the epoch in the session's `hello`) and `resume_offset`. The session answers `resumed` and the missing bytes, with no snapshot and no repaint. It sends a snapshot when the epoch differs or the ring lost the bytes.
  - The server keeps the last 256 event batches. `control.resume {epoch, seq}` replays the batches after `seq`. Otherwise it answers `replayed: false`, and the client reads `session.list`.
  - `macterm connect` tracks its offset and connects again after a lost link. The app's pane channels do not resume: the relay does not give the client the session's epoch, so a lost link draws a snapshot again.
  - The relay needs no change. It drops queued output and then a snapshot follows, so a client's count is a prefix of the stream until the snapshot resets it.

### The app's client of the local server (`Macterm/Server/`)

`LocalServer` and `ServerConnection` connect the app to `macterm server` (design/001 A, design/002). `LocalSessions` holds the app's one connection, and every local session path goes through it (see "Local panes are v2 sessions" below).

- **The app starts the server.** `LocalServer.connect` connects to `<runtime dir>/.server`. When nothing answers, it runs the bundled `zmx server` with `MACTERM_RUNTIME_DIR` set, so that the app and the server use one directory. `runtimeDirectory(environment:)` finds it as `resolveDir` in `server/src/runtime.zig` does.
- **A newer app replaces an older server** with `server.exit`, then starts its own. The sessions keep running.
  - A lower level is older. A higher level is never replaced.
  - At the same level, another build is replaced only when it runs from this app's own `zmx` path, or from a file that an update removed. `proc_pidpath` of the socket's peer follows a bundle that moved, and gives no path after a delete (measured). A real Sparkle update is not measured yet.
  - A build from another app (Debug next to Release) stays. The order of two builds of one level is not known.
  - One `connect` replaces at most once, so two apps never replace each other's server in a loop.
- `ServerConnection` reads the socket on a thread of its own. A request waits for its response by id. `events` gives one element for each event batch. When the connection ends, each request that waits fails with `ServerClientError.disconnected`. Only the reader thread closes the fd, under the lock that each write holds.
- `LocalServerTests` runs the bundled server in a runtime directory under `/tmp` (a socket path has at most 103 bytes).

### Sessions of an older build (design/002, option A)

A session keeps the build that started it. After an update, `AppState.outdatedSessions` holds the running local sessions whose build key differs from the bundled server's (`SessionBuild`, from `session.list`; refreshed with the zmx cache). A pane whose session is in it shows an **Outdated** pill in its trailing badge row (`TerminalPane`, `AppState.showsOutdatedSessionBadge`; Settings → Appearance → Window → Show outdated session badge, `Preferences.showOutdatedSessionBadge`, on by default). A click on the pill restarts that pane's session (`requestRestartSession(of:)`). **Restart Session** (`AppCommand.restartSession`, no default chord) is available only while the active tab has such a pane, and restarts all of them. A restart swaps each older pane for a new pane in the same folder, ends the old session, and asks first when a program runs (`paneNeedsConfirmClose`). Panes of one tab that show one session restart together. It never runs by itself. Not built: restarting all idle tabs (option C), keeping the old screen, and remote sessions.

### Local panes are v2 sessions

Every local pane (workspace, pinned, quick terminal, widget) is a v2 session of the local server. Remote panes are v2 sessions of the host's server (see Remote Projects).

- **A local pane is a manual surface** (libghostty fork patch 0022, `manual_io`), fed by a `PaneSession` on the app's connection to the server (`LocalSessions.channelConnection`). The app asks libghostty for the pane's launch (`ghostty_launch_resolve`, fork patch 0023: login(1) on macOS, shell integration, `TERM`, `GHOSTTY_*`, the config `env`, a palette's command wrapper), and `session.create` runs it, with the surface's folder and size. A session that exists is attached, and the launch is not run. `manual_write` (keys, pastes, terminal replies, `initial_input`) goes to the channel from a queue of its own, `manual_resize` goes as `resize`, and the claim as `claim` (`GhosttyTerminalNSView+Channel.swift`). With no bundled server, or over the socket-path budget, the pane is a plain, unpersisted shell: a normal surface.
  - `session.create` takes `env` (`NAME=value` entries). The server sets its own `MACTERM_RUNTIME_DIR` in it, so the session listens where the server looks. The surface's env pins `MACTERM_RUNTIME_DIR` to the app's runtime directory.
- **`LocalSessions` is the app's one server connection** (`LocalSessions.shared`). It connects at the first use and again after the connection ends (the server exits when it has no session and no client). `MactermApp` connects at launch, so a server of an older build is replaced early. `ZmxClient.live` sends `killSession`, `listSessions`, `session list/info/kill` and the foreground cache through it.
- **The app ends a session whose shell exited** (`session.kill` takes the status): at its `session.exit` event, and at each connect for one that exited while no app was connected. Its pane already closed from the client's exit. Without this, a session keeps its exit status for ever, and a pane of the same name attaches to an exited session.
- **The foreground and the tty come from `session.list`**: `shell_pid` (the pty's leader) and `pty`. `ZmxForegroundResolver` reads the foreground group of the shell, and `daemonTTYPath` is the session's pty, for the password monitor and secure input. `ProcessInspector` is unchanged.
- **A session keeps each pane's attention flags** (`Attention`: `unseen`, `failed`, `bell`, `events.zig`; design/004 §6). A run that ends and a bell set them. A new run clears `unseen` and `failed`. They live in the session process, so they stay while the app is quit and across a restart of the server: a new server reads them from the session. `session.list` shows them, and the server sends `pane.attention` to every client at each change. `pane.seen` (local clients only) tells the session to clear them, and the reply goes after the event. The GUI does not call it yet: v1's code still derives its own dots until the cut-over.
- **No listing gate.** One server answers every list. `session list` lists only running sessions. `clients` is the session's own count of the clients that sent `attach`: the session sends `state` again to the server each time the count changes.
- **The local orphan sweep runs once at launch** (`AppState.sweepLocalOrphans`, `ZmxReaper.localOrphans`): it ends a running `macterm-` session that no pane claims and no client shows. It is safe because each build flavor has its own runtime folder (`LocalServer.folderName`: `macterm`, `macterm-debug`), so every session there is this flavor's. This also keeps a Release pane's session off the Debug binary. It skips everything when `WorkspaceStore.loadFailed`.
- **`zmx connect <name> --` asks the server first, also when the socket answers.** The server refuses a create for a session whose shell exited (`exited`); the client ends it (`session.kill`) and creates again, as v1's `zmx attach` made a new session for a dead one. A connection that ends before the reply (a server that a newer app replaced) gets one more try.
- **The first v2 launch ends v1's local sessions** that the restored panes name (`AppState.endV1SessionsOnce`, design/008 §4 Q3 A), with the programs in their panes. Each pane already opened a new v2 session of the same name, with a new shell in its saved folder. v1.33.2 ships zmx 0.8.1, and `zmx kill` of 1.0.1 hangs against it, so Macterm uses no zmx IPC here (`V1Sessions`): it finds each daemon by its argv (`zmx __daemon <name>`; a v2 session is `__session`), sends SIGHUP and SIGTERM to every descendant of the daemon and every process in its pane's pty session (of the user's real uid, so setuid programs too), SIGTERM to the daemon, and SIGKILL to what a new scan finds after 2 s. Then it removes the sockets from v1's socket folder (`ZmxSocketBudget.v1SocketDir`). `Preferences.endedV1Sessions` is set only when a full scan finds no daemon of the names. Otherwise, also when a scan fails, the next launch tries again. A hermetic run (`PasswordVault.isHermetic`) neither reads nor writes the flag, because it shares the real defaults domain. v1 sessions that no pane names, and the sessions of remote projects (`localSessionNames`, also for a host that is this Mac), are left alone. Not found: a program that `setsid`'d away from its pane, and a daemon whose re-exec failed (it keeps the argv `zmx attach <name>`).
- The unit-test host starts no server and runs no session (`ZmxBypass.unitTestHost`): every live session call returns nil or does nothing there.
- The server tests are `server/test/connect_create.bats` (the create path of `zmx connect`, which is the CLI's client now) and `server_v2.bats`. The app tests are `PaneChannelTests`, `PaneSessionTests` and `RemoteHostsTests`, against the bundled server and a local sshd.

### Ghostty config pipeline

In automatic mode, Macterm delegates the user layer to `ghostty_config_load_default_files`. Settings can append custom files. `GhosttyApp.loadConfig` loads `macterm-defaults.conf`, then the user files, then `macterm-overrides.conf` (the last one wins). It regenerates both private files (`MactermConfig.regenerate()`) before every load, because the overrides depend on the content of the user. `GhosttyConfigSource` is the seam for raw text, for keys that the C API cannot expose.

**`~/.config/macterm/config.ghostty` is a custom config file of the user that Macterm seeds and lists for them** (`MactermConfigFile`). Ghostty.app never reads it, so a key in it applies to Macterm alone.

- Macterm seeds it at the first launch that finds it missing (`MactermConfig.init`), as a template: every line of `MactermConfig.defaults` commented out, each under its note. A commented line sets nothing. `MactermConfigFileTests` pins that no line of the template is bare. An uncommented default would override the Ghostty config in silence.
- At the same time, one time per install (`Preferences.addMactermConfigFileOnce`, flag `macterm.ghostty.addedMactermConfigFile`), Macterm appends it to the custom config files of Settings → General → Ghostty Config, so it loads last. **It is a row like any other from then on.** The user can move it or remove it. Macterm never puts it back on its own. There is no special layer, no special row and no special path in the loader.
- The defaults layer stays the home of each default. The file lists the defaults. It never holds them. A user who deletes the file, or who installed before a default was added, loses nothing.
- Macterm never writes the file again. An absent file means "no input". A present file belongs to the user. Open Macterm Config (`AppCommand.openMactermConfig`, the command palette and the View menu) seeds it again before it opens the file in the terminal editor, the way a text file from Finder opens. If the file is not in the list, a toast says where to add it.
- The listed path is `MactermConfigFile.listedPath`: `~`-abbreviated under the home directory, absolute elsewhere, because `~` expands through the user record and not through `$HOME`.
- Hermetic runs (`MactermConfig.isHermetic`: tests, `MACTERM_BENCHMARK=1`) neither seed nor list it, as they load no user config.

**Ghostty keys that Macterm applies to its own behavior** have no Settings UI.

- `macos-shortcuts` (App Intents).
- `tab-inherit-working-directory` and `split-inherit-working-directory`. `false` means the project directory. In a project-based terminal, this is the "default working directory" of ghostty. `AppState.newTabInheritsWorkingDirectory` is the read that you can inject.
- `macos-hidden`.
- `macos-icon`.
- `window-theme`, and the `set_window_theme` action, which overrides it until `set_window_theme:config` (`WindowTheme`, the rule of Ghostty.app). They give one light or dark scheme (`GhosttyApp.windowScheme`): the chrome (`MactermTheme.colorScheme`) and the scheme of each surface, which picks the side of a `theme = light:X,dark:Y` split. `auto` follows the terminal background, as before. `system` and `ghostty` follow macOS. The override is in memory only and survives a config reload. The window title (the project name and the path) is drawn over the terminal, so it takes the scheme of the window's terminal background, not this one (`WindowAppearance.titleAppearanceName`). Ghostty.app's transparent titlebar does the same for the whole terminal window. Where AppKit paints its own titlebar background (fullscreen), the title keeps the window's scheme.
- `focus-follows-mouse`. Macterm reads it live on each pointer move. It moves focus only away from another pane.
- `font-family` is for terminal panes only (libghostty reads it). Monospaced UI text (panels, sheets, Settings, keybinds) uses the system monospaced font: `.monospaced()` or `design: .monospaced` in SwiftUI, `NSFont.monospacedSystemFont` in AppKit. Macterm never reads `font-family` for its own UI. `.monospacedDigit()` sets only the digits of the system font.

**When the default of Macterm departs from the default of ghostty, the departure is a line in `macterm-defaults.conf`**. The place is the `MactermConfig.defaults` table: the line, and the note that the template of `config.ghostty` prints above its commented copy. `defaultsBody` is derived from it. `MactermConfigTests` pins it: `tab-inherit-working-directory = false`, `macos-secure-input-indication = false` and `background-opacity-cells = true`. It is never a fallback in `Preferences`. The user can then override it in the same way as any other key.

**Wheel scrolling belongs to libghostty on every path**. `GhosttyTerminalNSView.scrollWheel` forwards events exactly as Ghostty.app does (2× precise deltas, momentum phase). `SurfaceScrollView` only draws the scroller. It turns scroller drags into `scroll_to_row` and, under smooth scrolling, into the sub-row remainder (see Animations). We removed the row accumulator in the style of iTerm2 from #102, with its Scroll speed slider. `mouse-scroll-multiplier` therefore means the same thing here as in Ghostty. Do not bring back a wheel path on the side of Macterm.

Overrides that Macterm must lock. The `smooth-scroll`, `smooth-cursor`, `cursor-morph` and `cursor-trail` lines from `MactermConfig.Animations` come in addition (see Animations).

- `background-default-transparent = true`. This is a fork patch. The renderer skips the default background, so that `WindowAppearance` composites the translucency itself.
- `background-opacity = <Preferences.windowOpacity>`. This is the real value, so that the `background-opacity-cells` of the user works.
- `background-blur = 0`. Macterm calls the CGS blur SPI.
- `env = GHOSTTY_BIN_DIR=<bundle>/Contents/Resources/ssh-bridge`. This folder holds our `ghostty` shim that relays `+ssh` to `macterm ssh`. Keep it out of any folder in the PATH of the pane.
- `shell-integration-features`, emitted again with the flags of the user plus `no-path` (`ShellIntegrationFeatures.overrideValue`, #75). You cannot write the key bare.

The state of the UI of Macterm lives in `Preferences`. It never touches this pipeline.

**Custom app icon**. Macterm honors `macos-icon = custom` and `macos-custom-icon` with the semantics of Ghostty.

- `GhosttyApp.applyAppIcon` runs after every load and reload. It reads both keys from the *loaded* config, so a `config-file` include counts. It uses `configCString`. The C getter of libghostty returns enums as their tag name, and it returns `?[:0]const u8` as a bare C string, not as a `ghostty_string_s`. This is the reason why that getter is different from `configString`.
- It passes the keys to the pure function `GhosttyAppIcon.resolve` (`.bundled` or `.custom(URL)`). With no path, it uses `~/.config/ghostty/Ghostty.icns` of Ghostty. A path that is still relative after the expansion of `~` is invalid, because the cwd of a GUI app is not predictable.
- The one AppKit write is `AppIconPresenter.apply`. It sets `NSApp.applicationIconImage`. For a file that is missing, that it cannot read or that it cannot decode, it assigns nil. This restores the icon of the bundle.
- Every other `macos-icon` value is artwork of the Ghostty brand that we do not ship. We deliberately do not mirror the Dock-tile plugin of Ghostty.
- Hermetic caveat: `loadConfig` disables the user layer under `MACTERM_BENCHMARK=1`. To verify, use a throwaway `HOME`, `XDG_CONFIG_HOME` and `ZMX_DIR` plus `MACTERM_BENCHMARK_DATA_DIR`, and **no** `MACTERM_BENCHMARK`.

**`macos-hidden`**. `never` and `always` of ghostty map to `.regular` and `.accessory` through `MacosHidden`. This is a pure function with tests. The raw values are the own tag names of ghostty, so a rename of a case breaks the wire.

- `AppDelegate.applyActivationPolicy` applies it after `GhosttyApp.shared` at launch, and again on `.mactermConfigDidChange`. It skips AppKit when the policy already agrees. This is what makes the observer safe, although the observer fires too often.
- Read it as an **enum** (`configEnum`, a bare `[*:0]const u8`). Never read it through `configString`. The `ghostty_string_s` of that function leaves `len` at 0. This is the reason why `GhosttyColorSpace` went to raw text.
- Accessory mode is deliberately narrower than that of Ghostty.app, which builds no window. Macterm still builds one, because `MainWindow.onAppear` installs the responders and attaches the control handler.
- Every explicit request for a window (`window new`, `window focus`, `revealProject`) calls `MacosHidden.activateForWindowRequest`. It forces the activation with `ignoringOtherApps: true`. We measured that cooperative activation **refuses**, in silence, a plain `activate()` and an activate from another process.
- An accessory app has no menu bar. Settings, Quit, About and Check for Updates therefore lose their only route. Keybinds are not affected (`KeyRouter` handles them, not the menu bar).

**Process locale (#370)**. `ghostty_init` calls `setlocale(LC_ALL, "")`. Under any locale with a comma as the decimal separator, the rendering of toolbar glyphs in SwiftUI asserts inside CoreUI on macOS 27. The result is SIGTRAP, with nothing on stderr. `ProcessLocale.pinNumericToC()` runs right after `ghostty_init`. It touches only `LC_NUMERIC`. To reproduce, unset `LANG` (a launch from the Dock). `OS_ACTIVITY_DT_MODE=enable ACTIVITY_LOG_STDERR=1` shows the text of the assertion.

### Animations (Settings → Animations)

This is the motion pane. It is directly under Appearance in the sidebar of Settings. It has six toggles. **Smooth scrolling**, **Snap to whole row** and **Animate splits** ship **on**. The three cursor effects are opt-in. The pane was Settings → Experimental until the smooth-scrolling and split toggles graduated. Anything that is still settling in belongs here too, off by default, until it graduates.

- **Smooth scrolling** is fork patch 0005 (`.github/downstream/0005-smooth-scroll.patch`). It is behind the fork key `smooth-scroll`. The toggle writes the key into the overrides through `MactermConfig.Animations` (`Preferences.smoothScrolling`, default on). The default of the ghostty key itself stays off.
  - `scrollCallback` of libghostty already accumulates precise trackpad deltas in pixels, and it commits whole rows. With the key on, the patch does these things:
    1. It keeps the sub-row remainder on `Screen.viewport_pixel_offset`.
    2. It captures the rows that scrolling reveals as the `RenderState` overscan of upstream (ghostty-org/ghostty#14400, the first step of the own smooth scrolling of upstream). The `beginShiftedUpdate` of the fork sets the request: `overscan.above` rows at the top, or one row below (fork PR 16).
    3. It shifts the grid by a `scroll_offset` uniform. It clips to the visible grid, which it sizes from `grid_size × cell_size`. **It never sizes it from the bottom and right of `grid_padding`**. They hold the leftover that Macterm measured at the last resize, and they go stale after the growth from the incubator to the pane.
  - Any move of the viewport by rows goes through `Screen.scroll`, which zeroes the remainder.
  - Macterm has no part in the routing of a *wheel* event. Every event reaches libghostty untouched (#393). This is exactly why the gate is a ghostty key and not a read of `Preferences`.
  - The alternate screen has no scrollback. There, the key animates a program that scrolls a region of its screen by rows. The cases are DECSTBM or DECSLRM with SU or SD, or IND or RI at the margin, which is what `less` does. The renderer draws the new content of the region, shifted by the scrolled distance, and eases it home in about a quarter of a second. The rows that scrolled out slide away as ghost rows (fork PR 11). It is in 0005 since fork PR 14, because a sync dropped it. A program that repaints every row still moves by rows.
  - **A resize moves the viewport by pixels too** (fork PR 9).
    - A grid comes only in whole rows. The leftover height of a viewport grows while you resize a pane, until it is a full row and the viewport takes one. At that instant everything on the screen jumps by one cell, because the new row comes from the scrollback at the top.
    - With the key on, the renderer gives that leftover to the render state (`RenderState.Geometry`). It adds to the remainder that a gesture left. The grid is drawn lower by that distance, with the row above partly revealed.
    - A divider drag and every split animation therefore slide the content and do not step it. The cost is a partial row at the top of any pane whose height is not a whole number of cells. It is a scrollback row. After a clear, it is the old prompt line.
    - That row selects like any other row (`RenderState.Shift.rowsAboveAt`, fork PR 17). Selection resolves the pointer to a pin. A coordinate of the viewport cannot go above the first row of the viewport, and it clamped a press there to the row below.
    - The two offsets add up. This is why more than one row can be revealed above, and why `scroll_offset` carries the leftover in `.z`. The shifted grid draws onto it, so the clip extends by it.
  - **A drag of the scroller is the one exception**. `scroll_to_row` lands on whole rows, and `Screen.scroll` zeroes the remainder on the way. `SurfaceScrollView` sends the row. Then it gives the sub-row leftover to the core as a synthetic precision scroll (`GhosttyTerminalNSView.applySubRowScrollOffset`).
    - It can aim, because `ScrollAccumulator` mirrors `Surface.mouse.pending_scroll_y`. You cannot read that value over the C API. But `scrollCallback` is its only producer, and Macterm is the only caller of `ghostty_surface_mouse_scroll`. If we mirror every delta that we send, we reproduce it.
    - The size of the nudge lands the accumulator exactly on the remainder that we want. That remainder is under one cell, so it commits no row of its own. If the aim is wrong, the cost is at most one row of offset until the next update of the drag.
    - The multiplier that it divides out is the `mouse-scroll-multiplier` of the user. Macterm reads it from raw config text (`MouseScrollMultiplier`), because the key is a Zig struct that has no shape in C.
    - Macterm skips this with the toggle off, and when there is no scrollback to drag through.
  - **The render state enforces two rules. We found each one when we measured frames** (see `RenderState.resolveShift` in the fork).
    1. Macterm validates the remainder of the gesture *on its own* before it adds the resize leftover. A remainder that has no row to reveal is dropped, and the leftover still shifts the grid. If we validated the sum instead, a scroll that is pinned at the bottom made the content bob on every event. The bob was up to the height of the leftover. The remainder cycles through one cell while row after row fails to commit.
    2. The render state measures the leftover *against the row count of the terminal* (`Geometry.terminal_height`). The renderer never measures it against its own grid. The size of the renderer and the rows of the terminal change on different threads. A frame that fell between the two drew the grid one whole cell off. Every divider drag showed this as a slide and then a snap back.
  - **Anything that turns a pixel into a row takes the shift from the render state** (`RenderState.resolveShift`, fork PR 13).
    - This covers the hit test of the surface (selection, clicks, links), mouse reports and the IME point. They subtract exactly the shift that a frame draws, validation included.
    - A copy of the arithmetic in `Surface.posToViewport` skipped those checks. It put the pointer one row off in every place where they drop the shift (#433). The pointer was below the row at the bottom of the scrollback after a scroll. It was above the row in a pane without scrollback, on the alternate screen and at the top of the history.
    - The offsets of an animation of a region scroll are state of the renderer for each region. The renderer therefore publishes them (`RenderState.RegionShifts`, fork PR 15), and the same three consumers undo them. They use the offsets of the frame that the layer shows. Its contents change on the main thread, where hit tests run, so neither the drawing of a frame nor its presentation decides. They add every region scroll that the terminal did since that frame was drawn.
    - A click lands on the row that is drawn under the pointer. This is also true for a click during the ease of a quarter of a second, or in the middle of momentum. A click on a row that the region scrolled out of resolves to the edge row of the region.
  - **The overscan of upstream leaves the cursor out of the rows that it reveals**. `cursor.viewport` is null there, and `renderer/cursor.zig` draws no cursor without it. The cursor of the prompt therefore vanished from the row that a scroll reveals at the bottom, until the fork added `cursor.captured`. The renderer and the style gate read it instead. Links still come back in viewport rows. We found both problems only when we diffed rendered frames against the previous build. The unit tests passed.
- **Snap to whole row** is fork patch 0011 (`.github/downstream/0011-smooth-scroll-rows.patch`). It is behind the fork key `smooth-scroll-rows`. This is a mode of `smooth-scroll`. `MactermConfig.Animations` writes it only together with `smooth-scroll` (`Preferences.snapScrollToRow`, default on). The toggle is indented under Smooth scrolling, and it is disabled without it.
  - Scrolling moves the viewport by whole rows, and each move slides into place. The region scrolls of `less` already animate in this way. The viewport therefore never rests between rows.
  - The input accumulates as it does without smooth scrolling. Macterm never draws its sub-row remainder.
  - Macterm draws each row that the viewport really moves from where it was (`Surface.rowScrollOffset` puts the distance in `Screen.viewport_pixel_offset`). The renderer decays the offset on the time constant of 45 ms of the region animation (`decayViewportScroll`, under the terminal lock on update wakes).
  - The motion is the own offset of the terminal. The hit test, the selection, the cursor and the IME point follow it with no copy.
  - When you scroll back, the content rows are drawn up. `resolveShift` therefore reveals as many rows below as the offset spans (`scroll_offset.w` tells the clip of the shaders).
  - At rest, the leftover height stays padding. The geometry gets no terminal height, so only whole rows show. A resize steps one row at a time, as it does in `less`.
  - It is a feature of the fork, because every wheel event reaches libghostty untouched (#393). We tried a settle in Swift after the gesture first. It missed smooth-wheel input with no phases (Logi Options+ posts precise deltas with no gesture phases).
  - `SurfaceScrollView` sends no sub-row offset for a scroller drag in this mode.
- **Animate splits** (`Preferences.animatedSplits`, default on) swaps the recursive `SplitTreeView` for `AnimatedSplitView`. It renders the tree of the tab **flat**.
  - `SplitLayout` (pure, tested) resolves every pane and divider to an absolute rect. One ZStack that is keyed by the pane ID lays them out. Any change of the tree is then frames that move on stable identities, and SwiftUI animates it. The recursive view cannot do this, because nesting a leaf again changes its structural identity.
  - `SplitRootView` is the switch. Both call sites (`WorkspaceView`, the quick terminal) go through it.
  - We verified each of these rules live:
    - **A platform view moves only by its frame**. `.scaleEffect` and the transitions `.scale` and `.move` leave an NSView where it is. A new pane therefore grows out of the seam of its split from a frame of zero length. It is locked to the edge of the sibling that shrinks.
    - **Nothing crosses another pane**. Backgrounds are transparent, so an overlap is text through text. An empty new pane is invisible anyway.
    - **A closing pane is a ghost**. `Pane.destroySurface` takes a snapshot of the last frame (`Pane.closingSnapshot`, only while the toggle is on) *with no background fill*. An opaque ghost flashed to full opacity in a translucent window. The snapshot is clipped to the strip that the sibling did not yet reclaim.
    - The direction is the **own outer edge** of the pane in the split. The pane at the right or bottom slides right or down. The pane at the left or top slides left or up.
    - **The code reads from the new layout what the strip closes onto. It never reads it from the old tree** (`SplitLayout.closingSeam`). When one sibling reclaims the strip, that is the own edge of the branch. But the rebalance of auto-tiling moves *both* neighbors of a pane in the middle. If the strip collapsed to the edge of the branch, it dragged the dead divider back across the pane above it.
    - **A divider that outlives its branch travels to that same seam** (`AnimatedSplitView.MergingDivider`). It does not blink out. The two dividers on each side of a pane that closed cover the same distance from opposite sides and merge. This is the close read backwards from a split. In a split, the new divider is born on the seam that it peels off.
    - **The dim of the split that is not focused is a value, not a branch** (`SplitLeafView.isSplitDimmed` drives an opacity, always mounted). A view that comes and goes cannot cross-fade with the slide. It also popped one shade darker at the instant that a pane arrived.
    - The animation is keyed to the structure plus the zoom plus `TerminalTab.animatedResizeGeneration`. It is never keyed to ratios. A divider drag and `pane resize-split` of the CLI therefore land at once. Resize Split Left, Right, Up and Down bump the generation together with their ratio change, so they slide.
    - Each animation of an arriving pane or a ghost starts from its own `onAppear`, in the same frame as the sibling. A deferral of one turn made the seam visibly out of sync.
  - Zoom keeps the tiles that are hidden mounted at opacity 0 (`GhosttyTerminalNSView.hiddenInLayout` makes their renderers sleep). It removes the dividers. Their grab bands are NSViews, and they would catch drags through the zoomed pane.
  - Every animation frame resizes the surfaces that move. This is the same path as a divider drag. Reduce Motion disables the animation.
  - **The curve is a spring, which we define by its settling time** (`SplitAnimation.curve`). SwiftUI drives a spring itself, frame by frame, so each frame reaches the surfaces as a resize. A timing curve (`easeOut`) is bridged to Core Animation for the frame of a representable. The view gets its size one time, the layer is stretched, and the program sees two SIGWINCHs for each split.
  - A spring that we named by its perceptual duration (`.smooth`) kept settling for about 250 ms after that duration, one pixel in each frame. Each frame was a pty resize and a full redraw.
  - libghostty applies those resizes behind its own coalesce timer (upstream: a fixed 25 ms, and fork patch 0010 tracks frames). The grid therefore steps at that cadence, not at the cadence of SwiftUI.
- **Smooth cursor** is fork patch 0008 (`.github/downstream/0008-smooth-cursor.patch`). It is behind the fork key `smooth-cursor`. `MactermConfig.Animations` writes it into the overrides (`Preferences.smoothCursor`, default off).
  - The renderer owns the motion (`CursorGlide` in `generic.zig` of the fork).
  - Macterm still adds the sprite of the focused cursor (block, bar or underline), at alpha 0. The uniforms of a custom shader then keep naming its cell.
  - Macterm eases the rect itself into the uniforms of the cell in every frame that it draws. The ease is 140 ms, ease-out cubic. It retargets in the middle of a glide from where the rect is drawn.
  - The **shader for the cell background fills the rect by exact box coverage**, under the text. The **text shader colors each glyph pixel as cursor text by that same coverage** (`cursor_glide_text`). This replaces the recolor of the whole cell by the vertex shader under `cursor_pos`. The code leaves `cursor_pos` unset.
  - This makes a glyph that the cursor is halfway across two-toned. It also lets the own background of a highlighted cell show through the part that is not covered. A custom shader could not do these two things. It sees one composited frame in which ghostty already painted the destination glyph in cursor-text color. It cannot tell a glyph from a cell background.
  - The rect is in grid pixels. It therefore rides a smooth scroll with the rows. It takes the shift of an animation of a region scroll that its cell is in.
  - The draws come from the display link of the vsync. The animation timer of 8 ms is skipped on macOS whenever a display link exists. `animationWake` keeps the display link running while the glide is in flight. It stops the display link when the glide lands. `smooth cursor landed after N frames` in the debug log is the measured frame rate.
  - A reshape of the grid, a change of font or a toggle of the key snaps the cursor to its cell.
  - Programs that paint their own cursor cell still move that paint by cells, under the terminal cursor that glides. Examples are the theme style `ui.cursor` of Helix and its secondary cursors.
  - The previous implementation was a custom shader that glided a block over the composited frame, plus an override `cursor-opacity = 0`. Both are gone.
- **Morph cursor while moving** is fork patch 0021 (`.github/downstream/0021-cursor-morph.patch`). It is behind the fork key `cursor-morph`. This is a mode of `smooth-cursor`. `MactermConfig.Animations` writes it only together with `smooth-cursor` (`Preferences.cursorMorph`, default off). The toggle is indented under Smooth cursor, and it is disabled without it.
  - Only a block cursor changes. A bar, an underline and a hollow block glide as before. While a block glides, it is a comet (`CursorGlide.Comet`): a round head on the glide rect, with the area of the rect, and a body that gets thinner back to a round tail of half the radius of the head. The tail is where the head was 30% of the glide before (`lag`), so the comet is long while the cursor is fast, and it points the way that the cursor really moves, also on a diagonal. The body is at most 2.5 cell heights (`max_length`).
  - The block turns into the comet in the first 10% of the glide and back into the block from 70% (`grow_until`, `settle_from`). A move of one cell height or less has no comet, so typing looks the same. A jump of a few columns or more gets a short comet. A retarget in the middle of a glide carries the comet into the next glide (`Comet.Carry`), so a held key bends it.
  - The background coverage and `cursor_glide_text` fill and color by the coverage of the comet (`Uniforms.cursor_comet`), not by its box.
- **Cursor trail** is fork patch 0009 (`.github/downstream/0009-cursor-trail.patch`). It is behind the fork key `cursor-trail`. `MactermConfig.Animations` writes it (`Preferences.cursorTrail`, default off).
  - It uses the same `CursorGlide` motion. The code tracks the glide whenever either key is on.
  - Under the trail, the streak (`CursorGlide.trail`) goes into the uniforms next to the rect. The streak is an axis-aligned box with the size of the drawn rect. It is swept from a tail to the head, where the cursor is drawn. The tail sets out halfway through the move. The streak fades as the move completes. A move of less than 1.5 cell heights leaves nothing, so typing does not leave a streak.
  - The background shader paints the streak in the cursor color under the text, beneath the own fill of the cursor.
  - With the trail alone, the sprite stays the cursor, and only the streak is drawn.
  - The trail replaced the last bundled custom shader. For this reason `AnimationShaders`, `Resources/shaders/` and the install of the encoding header are gone.
  - libghostty animates any loaded custom shader without a stop while the pane is focused. It wakes a draw every 8 ms. The display link never pauses. At an idle shell prompt, it renders the whole frame again and post-processes it at the refresh rate of the display. The cost of the trail was therefore permanent. The version in the renderer costs about 140 ms after a move, and nothing in any other case. Its head is the drawn rect of the glide, not the cell of the cursor.
  - Macterm ships no custom shader now. The own `custom-shader` lines of the user are untouched.

### Adaptive terminal background

`AdaptiveTerminalBackground` infers the background of a TUI from the BGRA8 IOSurface of libghostty. It fails closed if the format changes. It can also take OSC 11 directly.

- **Macterm presents a report over the inference. It never writes the report into the inference** (`AdaptiveTerminalChrome.reportedCandidate`). libghostty reports an OSC 111 reset as a change *to the configured color*. A report that reset the stabilizer left the stale sampled color as the fallback. The `:theme` of Helix then left a hole of tint over the bare shell after you quit, until the config reload of a new surface.
- The report carries the alpha at which the renderer paints cells (`reportedPaintAlpha`: the window opacity under `background-opacity-cells`, if not opaque). It is never a bare 1.
- The alpha floor derives from the window opacity (`minimumPaintedAlpha`). Painted cells arrive premultiplied at `background-opacity`.
- A color that is translucent gets no fill for the pane. The window tint is **cut out from under its whole pane**. Its margin is **filled again in its own color**. `TintCutout` does this, with a `TerminalPaintRegion` for each pane.
  - The paint, which Macterm walks along the edges by alpha through `paintedUnitBounds`, stays bare.
  - The `window-padding` around it, which nothing painted, gets the color of the pane at the window opacity, on a sibling layer. In a split, the window keeps the configured theme. When Macterm cut out only the paint, it framed every TUI in that theme.
- The tint therefore lives in a view that you can mask. It never lives in `NSWindow.backgroundColor` or `NSGlassEffectView.tintColor`. The tint does not depend on the key status. Colors are read in the color space of the renderer (`GhosttyColorSpace`).
- `AdaptiveTerminalInferenceGate` freezes the inference while `ghostty_surface_has_selection` is true. It protects a confirmed color from repaints that have no output heartbeat within 1.5 s. This is for adoption only, never for clearing.
- The winning color must also span 0.80 of the sampled grid **on each axis** (`minimumBackgroundExtent`). This keeps a slide or an image from tinting the window again.
- **A region follows the visibility of the pane, not its frame** (`AdaptiveTerminalChrome.paintRegion`). A pane that zoom hides keeps its frame, its color and its sampled paint at opacity 0. Its hole showed the bare material inside the zoomed pane. `hiddenInLayout` drops the region at once. It restores the region only after the split animation faded the pane back in (`layoutVisibilityDidChange`).
- The quick terminal is outside the tint of the whole window.

## Tests

### Unit (`MactermTests/`)

There is one `XxxTests.swift` for each production type. It mirrors the source path. The tests use `@testable import Macterm` and `@MainActor`.

- Swift Testing suites run in parallel. Anything that touches shared state (preferences, stores) is injected. Tests that need `AppState` or `WorkspaceStore` inject a file in a temp directory.
- Helpers are in `Support/`: the DSL `TreeBuilder` (`H(pane("a"), V(pane("b"), pane("c")))`), `TreeRenderer` and `LayoutFixture`.
- The coverage targets the model, persistence, palette and hotkey logic, and pure helpers. Nothing unit-tests SwiftUI views and the bindings of libghostty.
- A wait that polls for a condition must sleep. Do not use `Task.yield()` in a loop with a fixed count.

### End-to-end (`scripts/e2e/`)

The suite starts the real Debug app in a hermetic way through `MactermHarness`. It uses a throwaway `$HOME`, `MACTERM_BENCHMARK_DATA_DIR`, `MACTERM_RUNTIME_DIR` and `ZMX_DIR`. The runtime directory of the session server is per user. Without the override, a hermetic instance would use the developer's real server and share its sessions. The suite asserts through the CLI (`pane dump` and others read the live state of libghostty). Darwin notifications open the project and front the window (`BenchmarkControl`, which listens only under `MACTERM_BENCHMARK=1`; that flag also skips the notification prompt, Sparkle and the first-run seed).

Conventions:

- There is one app instance for each session. Keep it the **active app** before every test (`_active_app` in `conftest.py`: `lsappinfo front`, taken again through the `activate` hook of `BenchmarkControl`). That hook forces activation, because the cooperative request is refused once another app holds the front.
  - The password monitor watches only the focused pane of the key window. It runs no timer while the app is inactive.
  - A test that starts an instance of its own (`open -n` fronts it) leaves the shared instance behind Finder when it kills its own. This is what timed out both tests of `test_passwords.py` on CI.
- Use the `fresh_tab` fixture. Never change the initial pane.
- Every wait is a poll with a deadline.
- Type commands as `/bin/sh -c "…"` with no single quotes (the login shell of CI is bash 3.2).
- Target panes explicitly.
- Prove that something ran with markers that you assemble at run time (`printf started-%s <nonce>`). No signal for idle or running is independent of the environment.
- CI runs it as `Test / End-to-end`. A failure uploads `e2e-diagnostics`.

### Release build and older macOS (`scripts/older-macos-smoke.sh`)

`Test / Release Build` builds the universal Release app and its DMG with `.github/actions/build-release`. This is the same recipe that `release.yml` and `release-tip.yml` use. The test build has no secrets: it is ad-hoc signed, has the Sparkle placeholder key, and is never published. A release never reuses it. A release always builds again from its tagged commit, with the certificate and the key.

Every other macOS job runs on `xcode-27` (macOS 27). **Runners are chosen by cost.** Every macOS job runs on GitHub-hosted runners, which are free for this public repository. Blacksmith bills a macOS minute 20 times a 2 vCPU Linux minute and has no macOS runner under 6 vCPU: Unit, End-to-end and Release Build there cost about $900 a month at the volume of 2026-11 (about 300 full Test runs a week), for checks about twice as fast. Linux jobs run on Blacksmith's 2 vCPU runners, except the two Linux server tests (4 vCPU, because Zig uses every core) and Session Layer (Linux) (GitHub, for netem). The ghostty fork runs on GitHub-hosted runners. `Test / Smoke` starts the Release build on `macos-26` and `macos-15`, isolated, and requires these things:

- The control socket answers `status`. A newer SDK or Swift runtime can break the launch on an older system without a compile error.
- The app is a terminal. A new tab and a split each get a shell through the bundled zmx, and a command that the script types there shows its output in `pane dump`.
- On macOS 26, the app paints its adaptive icon by itself, so the private renderer still works there, and the icon's body spans 824 of 1024 px on its middle row, so the body is on the icon grid. This is the only test of either on macOS 26. If the icon is not there, the script runs the helper by hand so that the helper's own error is in the log.
- Before macOS 26, the app does not try.
- No crash report from the app, zmx or the icon helper appears during the run.

`Release Build`, `Smoke (macos-26)` and `Smoke (macos-15)` are required checks on main, next to `Format`, `Lint`, `Unit` and `End-to-end`. **The Smoke checks are two jobs, not a matrix.** A matrix job that its `if:` skips reports its unexpanded name (`Smoke (${{ matrix.runner }})`). A required check with the expanded name then never reports, and a pull request that changes no Swift can never merge. The server checks of `server.yml` (`Test (macOS)`, `Test (Linux x86_64)` and `Test (Linux aarch64)`) are required on main only, in their own ruleset, because `v1` has no `server.yml`. They are a matrix, so they skip at step level: the workflow starts on every pull request, and each step after `Find Server Changes` skips when no server file changed.

The script stops only the process that it started, and it kills its own zmx sessions. On a developer Mac it still reads and writes the real defaults domain of the build, because cfprefsd ignores `HOME`. The CLI takes `--socket` after the subcommand (`macterm status --socket <path>`).

### Session layer benchmark

`scripts/session_bench.py` measures what the session layer adds to typing, to a reattach, to memory and to idle wakeups, for v1's and v2's panes side by side, local and over ssh. It runs no app: a pty driver plays the terminal. CI runs it on a pull request that changes `server/`, `protocol/`, the script, its limits or the server build, and by hand (`.github/workflows/session-bench.yml`). The workflow starts on every pull request, and a `changes` job skips the measuring jobs when no such file changed, so its checks report also where they are required. It writes the report to the job summary. Run it locally with a zmx build (`run`, then `report`); `--ssh-host` adds the remote arms. The report gives p50, p95 and p99, and a table of each v1/v2 pair with the ratio:

- **Local panes**: one binary has both. `v1` is `zmx attach <s> <command>` (a v1 daemon for each pane), `v2` is `zmx connect <s> -- <command>` (a v2 session made through the server). The run sets `MACTERM_RUNTIME_DIR` to its throwaway folder, so v2 never uses the user's server.
- **Each pair runs in one run, alternated**: the echo keys go in rounds to v1 and v2 in turn, the reattaches alternate, and the idle panes of both are measured in the same window. A pair is never compared across runs or runners.
- **Echo**: write one key and time its echo, 500 keys. `bare` is `/bin/cat` on a pty in line mode, so only the kernel echoes (the floor). `v1` and `v2` are `/bin/cat` in a local pane. On Linux, `ssh` is `ssh -tt localhost /bin/cat` (the floor for a remote pane), `remote-v1` is a remote pane of v1 (`ssh … zmx attach`, a login of its own), `remote-v2` is a remote pane of v2 (`ssh -S <master> … zmx connect`, a channel over the run's one connection, as `SSHConnections` does), and `relay` is a channel of `zmx proxy` over that connection (the one stream for each host that the app will use for its panes).
- **New remote pane** (Linux): from the start of the pane's ssh to the first echo after the session prints its ready marker, 5 panes in each layer, alternated. v1 logs in for each pane. v2 opens a channel, and its first pane starts the host's server. The report gives the login of the connection on its own line, and adds it to v2's time to the 5th pane.
- **Relay flood** (Linux): one relay channel prints as fast as it can, 3 times. The run times the keys of a second channel, channel 0's pings, and the interrupt of the flood until its prompt shows, and counts the skips ahead (`relay.skip_ms`). The Linux job limits loopback to 100 Mbit/s. The report gives the rate that the client got: a flood with no skip was not faster than the link.
- **Reattach**: fill a session with 10,000 lines of 199 characters on a 200-column terminal, detach, then time a new client until the echo of a marker line. The marker goes in after the client takes the terminal, and its echo comes after the replay. The report gives the size of the replay.
- **Idle** (macOS): 1 and then 9 panes of `/bin/cat` in each layer. It reads `phys_footprint` and the interrupt wakeups (`proc_pid_rusage`, with no sudo; the kernel counts each package idle wakeup also as an interrupt wakeup) of the session side (v1's daemons; v2's server and sessions) and of the clients, over 60 s. The programs in the panes are not counted. The run ends the sessions of the other arms first, so v2's server holds only the idle sessions. v2's server carries the argv of the client that started it, so the run finds it by the peer pid of its socket.
- A key goes in only after the client turns echo off on its pty and the session prints a ready marker. Before that, the kernel or the remote pty echoes the key, and the time is not the session layer's. An ssh client turns echo off before the remote side runs zmx.
- The JSON records `ssh -V`: OpenSSH 9.5 and later delays keystrokes (`ObscureKeystrokeTiming`).
- The report gives p95 and p99 only for 20 samples or more.
- Not measured here: the GUI part of typing latency (`keyDown`, the render, the compositor), and the app's own memory.
- Every session that a run makes is ended after the run, in a throwaway `ZMX_DIR` and runtime folder. A session with no client drops terminal replies.
- **The gate** (`check`, the step Compare v2 with v1) fails the job when v2 is worse than v1 in the same run. It compares echo p50 and p95 (local and remote), the new remote pane, the reattach and the memory as v2 / v1, and the idle wakeups for each pane as v2 − v1. A limit is no change plus the noise: the largest distance of one run from the median of 20 runs (`limits`, written to `scripts/session_bench_limits.json`, one entry for each system). A v2 that is worse passes also when the difference is under `FLOOR_MS` (1 ms, typing and reopen) or `FLOOR_MB` (2 MB, memory): a user cannot feel it (Ethan, 2026-11-10). Wakeups have no floor. A measurement that the limits name and the run does not have fails. A job whose Server job fails fails too, because a skipped job counts as passing where a check is required. To make the limits again, run the workflow by hand 20 times on one commit (a temporary 20-run matrix works), download the `session-results-*` artifacts, and give `limits` all the JSONs. The gate has no unit test: check it by running `check` on a results JSON against a limits file with a limit of -5.
- No comparison with an earlier run: v2 is compared with v1 only.

### Demo recordings

`scripts/record-demos/record-demos.sh` records the twelve clips that the landing page plays. It drives the **installed** app with synthetic keystrokes. For demos 8, 9 and 12, it also drives the pointer. Whatever runs it therefore needs Accessibility and Screen Recording. It also needs ffmpeg, and podman for demos 5 and 10 (it starts the podman machine itself).

Masters land in `$MACTERM_DEMOS_OUT` (default `~/Desktop/macterm-demos`). Only `record-demos.sh web` writes outside the masters, and it writes into a checkout of `macterm/website` (`MACTERM_WEBSITE_DIR`, default `../website` next to this repository). It encodes the finished clips again to 1400×792 with CRF 26, and a poster of the first frame, in `assets/demo/` of the website. The website build copies them to `public/assets`, so they are served as `/assets/demo/…`. Commit them in the website repository.

The script has these rules. We learned each one with the real app:

- **You place the window. The script refuses to record until the rect matches** (1600×870 at 1330,411, captured with a margin of 40 pt). This place keeps the frame clear of two things. One is the desktop widgets in the columns at the top left. The other is the desktop icons in the corner at the top right. Every clip then lines up. `quick-prefs` places the panel of the quick terminal at the same frame. The frame of the panel is computed again from the prefs at each show, so a move with AX never stays. If you move the window, you must run `quick-prefs` again and start the app again.
- **Wait for a shell prompt. Never wait for a delay**. Every command that the script types polls `pane dump` until the pane shows a prompt. A remote pane starts blank, because the shell printed its prompt before zmx had a client. The wait therefore nudges it with Ctrl-L until a prompt appears. Never nudge a pane that is at a password prompt. The Ctrl-L becomes part of the password.
- **The tab switcher needs a HELD modifier**. The overlay lives exactly as long as the modifier of the recent-tab chord is down (`commitTabCycle` fires on the flags-changed event when the modifier drops). System Events cannot hold a modifier across statements. `hold.js` posts the key events at the level of CGEvent from osascript. The script reads the chord from `macterm.hotkey.recent_tab` at run time. It does not assume it.
- **The script records the quick terminal with the window parked off screen, not closed**. The panel does not activate the app. With no window at all, Macterm cannot be the frontmost app. Every keystroke that is meant for the panel then lands in whatever app is in front. `qt_ready` refuses to type unless the panel is up *and* Macterm is frontmost. Finder renames files with stray keystrokes.
- **`guard_repo` restores only the files that a demo opens** (`AGENTS.md`), in the checkout of the macterm *project* (`shown_repo`). This is the checkout in which its panes open files. It does not have to be the checkout that the script runs from. Helix saves automatically on loss of focus, so a keystroke that lands in an editor pane is written to disk. A blanket list reverts unrelated work as a side effect.
- **Cleanup matches by path, never by name**. Demo 3 opens `~/dev/macterm/docs`. It removes only the project and the layout file that point there. If it removed "the project with the name website", it nearly took a project of the developer.
- **Programs that interrupt themselves get an instruction not to**. opencode (demos 2 and 6) runs with `OPENCODE_DISABLE_AUTOUPDATE=1`. Without it, an update dialog lands over the TUI in the middle of a take.
- **Demos 5 and 10 build their own host.**
  - It is a podman container with sshd, vim and zmx (compiled from source, because the fork ships only binaries for macOS). It is published on 127.0.0.1:2222. A marked `Host demo-box` block is put at the start of `~/.ssh/config` (`HostName localhost`, which is what the password prompt of ssh names).
  - It takes a key and a password. The block decides which one the pane uses. The own checks of the recorder always force the key (`rssh`).
  - It refuses to record unless the alias answers with the own marker of the image. A collision of names can therefore never point a recording at a real machine. The teardown removes the project, the container and the config block.
- **Desktop demos check that the frame is empty** (`region_clear`, over the window list of `windows.swift`). They record the cursor (`CAPTURE_CURSOR=1`, moved by `mouse.js` on an eased arc, because a pointer that jumps looks fake). An EXIT trap restores the state of Finder that they change, however the run ends.
- **Demo 8 drops a dummy `~/Desktop/starfield` on the Dock tile.**
  - `dockdrop` aims for the x of the tile while the Dock that hides automatically is still below the screen. It wiggles on the edge until the Dock slides up. Then it reads the tile again under magnification.
  - A desktop with Stacks or a sort order ignores the position of the folder. The take therefore switches both off in `DesktopViewSettings` of Finder. Finder restarts to read them.
- **Demo 9 records the widgets of the desktop as they are**. Nothing is created or moved for the take. The frame is the full height below the menu bar, with the desktop icons hidden (`CreateDesktop`). The btop widget is reset to a shell, edited from its right-click menu, and dragged out and back. btop needs at least 80×24 cells. At a font of 16 pt, a widget that runs it needs 4×4 grid cells or more.
- **Demo 11 copies the Git extension of this checkout into the real extensions folder.**
  - The installed app reads `~/.config/macterm/extensions/` again at every open of the palette. There is no throwaway config to point it at.
  - The take copies `extensions/git` to `macterm-demo-git`, with a marker in the first line of its `extension.yaml`. It refuses to touch a folder with that name that has no marker. It refuses to record next to another palette with the name Git Branches (when you type `git br`, the selection must land on its row). The EXIT trap removes the folder only when it carries the marker.
  - The take shows the real extension, so the video cannot drift from what users install. It searches two branches of the project (the two shortest names) and runs **Log** in a split. It never runs **Switch to it**, because that changes the branch of the project.
  - The palette has no CLI view, so its steps take beats. The script waits for the Log split through `pane dump`.
- **Demo 12 scrolls copy mode up a long traceback, and explains its cause.**
  - The server is `scripts/record-demos/orbit/`. It runs from `/tmp/orbit` (a mark file, removed by the EXIT trap), so no line wraps and no home folder is in the frame. Its `#!/usr/bin/python3` keeps the frames the same on every take. It starts again on a clean path, because `./server.py` puts `/./` in every frame.
  - The real cause (`KeyError: 'ORBIT_DATABASE_URL'`) is the first of three chained tracebacks, more than a screen above the last line. When the model got the whole first traceback, it named the unset variable. With the error line alone, it blamed `os.py`. A JSON error was rejected: the model blamed unquoted keys for a trailing comma that it could not see.

A right-click inside a selection keeps it (ghostty's `context-menu`), and the popover of a menu click opens below the click point, so it does not cover the selection. The menu item comes from Accessibility, with an offset from the pointer as the fallback.

The answer varies between takes, so read it before you keep one. The release build has no `pane explain`, so the take waits a fixed 8 s for the answer. Three Escapes end it: the popover, Visual Line, then copy mode.

## The website

The site at `macterm.thdxg.dev` (landing page, docs, changelog, and the proxy of the update feed) is the `macterm/website` repository. This repository keeps what the site renders and serves:

- `docs/*.md`, the user docs. A feature and its docs page land in one PR here. `TextFileDefaultsTests`, `CustomPaletteFileTests` and `DocsLinkTests` read the pages.
- `assets/`: the JSON schemas and the icons. The demo clips are in `macterm/website`.

## Releasing

Macterm updates itself with Sparkle. `SUFeedURL` is `https://macterm.thdxg.dev/appcast.xml`. The Caddyfile of the `macterm/website` repository serves it straight from the `main` branch of the `macterm/appcast` repository, which is a store and not a site. `FEED_REPOSITORY` and `FEED_BRANCH` in `scripts/publish-appcast.sh`, the fetch in `release-tip.yml` and the proxy rewrite in the Caddyfile name it. The feed lived on the orphan `appcast` branch of this repository until 2026-11. That branch stays as it was. Remove it only after one tip release has published to the new repository. `UpdaterChannelTests` pins the two files in this repository, and `check-feed.mjs` of macterm/website pins its Caddyfile and `SITE_URL` to them. A build that a pushed tag starts releases through `release.yml`. `release.yml`, `release-tip.yml` and `Test / Release Build` share one build recipe, `.github/actions/build-release`.

Secrets:

- `SPARKLE_ED_PUBLIC_KEY` and `SPARKLE_ED_PRIVATE_KEY`.
- The org secret `MACTERM_APP_PRIVATE_KEY` and the org variable `MACTERM_APP_CLIENT_ID` of the `macterm-ci` GitHub App. The jobs that write to another repository (the cask bump to `macterm/homebrew-tap`, the GhosttyKit bump PR, the website dispatch). The push of `publish-appcast.sh` to `macterm/appcast` uses it too, so the app is the commit author. These jobs take a short-lived token of it from `actions/create-github-app-token`, for the repositories that they write (`macterm` and `appcast` for a publish). No workflow uses a personal access token.
- `MACTERM_SIGNING_CERT_P12` and `MACTERM_SIGNING_CERT_P12_PASSWORD`. This is a stable self-signed certificate. It keeps TCC grants across updates. **Back up the private key and the certificate**. If you lose either one, users are stranded.

The release notes come from the generator of GitHub (`.github/release.yml`). A person chooses the version number. The `/release` skill walks through the ceremony. The recipe for the certificate is in the history of this file.

- **The website's `/changelog` shows the notes of every stable release** (`releases.mjs` of macterm/website, rendered by its `build-docs.mjs`). The GitHub release is the only copy of the notes. An edit there reaches the page at the next site build. `website-dispatch.yml` starts that build for each release that a person publishes, edits or deletes. The page links `#123` and `@user` itself and drops HTML comments, so write the notes in the same Markdown as before.

- **There are three Sparkle channels and one feed**. A prerelease item carries `<sparkle:channel>beta|tip</sparkle:channel>`. Settings → Updates → Channel opts in (`Preferences.updateChannel`, the raw values are the wire names). A channel on an item that is not a prerelease is a hard error in `publish-appcast.sh`. Homebrew stays stable-only.
- **Read the prerelease flag live** (the job `flag`, through `gh release view`). Never read it from `github.event.release.prerelease`. The payload is frozen at dispatch, and an edit does not fire the event again. Job outputs are strings. Compare with `== 'false'`.
- **Version ordering** (`sparkle_comparison_version` in `_lib.sh`):
  - `0.9.0-beta.1` becomes `0.9.0.1`.
  - Stable `1.8.0` becomes `1.8.0.9999`.
  - Tip `1.24.2-tip.7` becomes `1.24.2.9999.7`.
  - `build.sh` and `publish-appcast.sh` must both use it.
  - `macterm_tip_version` filters tags to `^v[0-9]+\.[0-9]+\.[0-9]+$`, because the rolling `tip` tag breaks `git describe`.
- **Tip channel** (`release-tip.yml`).
  - Every commit on main for which CI *passed* (Test success and Checks polled) publishes to ONE permanent prerelease that Macterm edits in place.
  - The rolling `tip` tag moves **last**, as the commit point.
  - The build job is in one concurrency group with `cancel-in-progress: true`. A newer commit that passed the gate replaces an older build. The setting is at job level, so that a commit that is red, or that only changes docs, cannot cancel a good build. The gate skips a commit when a newer commit already passed Test and Checks, because Test runs finish out of order.
  - There is one tip item in the appcast. Macterm keeps the newest 3 DMGs.
  - The check for staleness asks if the `tip` tag is an ancestor of the built commit. It never compares against HEAD of main.
  - **Macterm never builds a version again that is already in the appcast**. A run whose tag push failed has shipped everything else. A re-run for the same commit would `--clobber` the DMG with new bytes, while `publish-appcast.sh` keeps the old signature for the equal version. The build job therefore first reads `appcast.xml` from `macterm/appcast`. If the version is there, it only moves the tag.
  - `build.sh` bakes `MactermUpdateChannel` into `Info.plist`. A tip build that you install by hand therefore uses the tip channel by default. Beta stamps `stable`.
- `release.yml` skips itself for `ref_name == 'tip'`.
- **GitHub Pages is retired, and the `gh-pages` branch with it**. The feed was at `thdxg.github.io/macterm/appcast.xml` before 1.26.0. An install from before that version asks that URL for ever, gets a 404 and reports no update. Such an install updates only by hand.
- **Never delete `macterm/appcast` or its `main` branch**. `publish-appcast.sh` creates a missing `main` again as an empty orphan (it cannot make a missing repository), and the feed then names only the one release that it publishes. Every other channel is empty until its next publish. The 2026-10-29 deletion of `gh-pages` lost every item in this way, and the branch was rebuilt from a local clone.

## Conventions

### Writing style

- **Write all text that you generate in ASD-STE100 style** (Simplified Technical English). This includes documentation, the website, README and CONTRIBUTING, Settings text, CLI output, error messages, code comments, commit messages and PR descriptions.
- Use the `asd-ste100` skill (https://github.com/danyuchn/asd-ste100-skill, MIT, kept in `.claude/skills/asd-ste100/`). Run its linter on the Markdown that you write: `python3 .claude/skills/asd-ste100/scripts/ste-lint.py <file>`.
- Use **Strict** mode for procedures, error messages, CLI output, Settings captions and agent skills. Use **STE-flavored** mode for README, docs prose and PR text.
- Follow `WRITING.md` for Macterm terms and the words to use. It is the project glossary.
- The skill has no copy of the official dictionary of ASD. It checks sentence structure, not approved words. Do not claim that text complies with the dictionary.
- Keep every fact, condition and hedge. Do not change a product term, a command, a key name, a file path or a code identifier to make a sentence simpler.

### Localization

The GUI text is in three String Catalogs: `Macterm/Localizable.xcstrings` (the app), `Macterm/InfoPlist.xcstrings` (the permission prompts of `Info.plist`) and `Macterm/ServicesMenu.xcstrings` (the Finder → Services item, keyed by its title after the build puts the display name in, so it has one entry for each build). The source language is English. The translations are Korean (`ko`) and Simplified Chinese (`zh-Hans`). `TRANSLATING.md` is the guide for translators, with the word table for each language.

- **Write a `String` that the GUI shows as `String(localized: "…")` where the code defines it.** A SwiftUI literal (`Text("…")`, `Button("…")`) is localizable as it is. `Text(someString)` is not: it shows the `String` verbatim. Write a whole sentence in one string, with interpolations. Never join localized fragments into a sentence. Add `comment:` to a short string whose meaning is not clear.
- **A catalog keys an entry by its text, not by its comment.** One English word with two meanings ("Show" as a heading and as a button) is one entry with one translation. Give the second meaning a semantic key with the English as its value: `String(localized: "toolbar.tabSwitcher.show", defaultValue: "Show", comment: …)`. `mise run strings` prints a notice for a key with two different comments.
- **Use `Text(verbatim:)` for text that is not language**: a path, a config key, a number, a symbol.
- **Never compare, persist or parse a localized string.** Split the value: an English or raw value for the logic, and a localized display property. `HotkeyRegistry.isUnbound` replaced a comparison of `displayString` against "None". A raw value is an identifier. `AppCommand.Category.title` is its label.
- **These stay English**: the CLI and the control socket, agent skills, logs, `macterm tutor`, the first-run seed, the YAML validator errors (`macterm palette list` prints them), ghostty config text, and text that Macterm types into a pane or matches against its output.
- **Never send `error.localizedDescription` to the CLI or a log.** The bundle has translations, so Foundation localizes its own errors (Cocoa, POSIX, `DecodingError`). Use `EnglishErrorText.describe(error)`. Our own error with a localized message adopts `EnglishDescribedError` (`LayoutFileError`, `CustomPaletteError`): it defines each message one time as a `LocalizedStringResource`, and resolves it with `String(localized:)` for the GUI and `String(english:)` for the CLI. `BilingualMessage` carries a message in both forms where one value goes to an alert and to the log.
- **The palette and Keymaps also match a command by its English title** (`AppCommand.searchAliases`, through `PaletteItem.searchAliases`), so `split` finds the row in every language. The English titles are resolved one time.
- **xcodebuild does not update the catalog**. `mise run strings` (`scripts/strings.sh`) builds Debug, merges the `.stringsdata` of the compiler into the catalog with `xcstringstool sync`, and removes unused entries. It writes the exact format of Xcode, so a build in the IDE does not rewrite the file. It reads only the `arm64` `.stringsdata` whose source file exists, because xcodebuild keeps the output of a removed Swift file and CI restores DerivedData from older builds. CI runs `mise run strings --check --no-build` after the unit tests.
- `LocalizationTests` requires a translation of every entry in every language of a catalog, with the placeholders of the English string. The test scheme runs in English (`language: en` in `project.yml`), because tests pin English text.
- **Settings → General → Language** (`Preferences.appLanguage`) lists **System** and each translation (`AppLanguage.available`), each in its own name. It is Foundation's `AppleLanguages` key in Macterm's own domain, which **System Settings → General → Language & Region → Applications** also writes, so the two places always agree. Read it from the persistent domain only: the global domain also has `AppleLanguages` (the list of macOS). Foundation reads the key at launch, so a change applies at the next start.

### Code style

- SwiftFormat and SwiftLint are enforced. Run `mise run format`, `lint` and `test` before you commit. swiftformat owns trailing commas. Never write `static weak var` (the two tools fight).
- Use `@MainActor @Observable` on all state classes. Do not use `@Published` or `ObservableObject`. Inject through `@Environment(AppState.self)`.
- Use `os.Logger` only, with one `private let logger = Logger(subsystem: appBundleID, category: "TypeName")` for each file. **Every interpolation is `.public`**. View the logs with `mise run logs`.

### Commits and PRs

- **Never add a `Co-Authored-By: Claude` trailer or any AI sign-off.**
- Subject lines say why. Split independent changes into separate commits.
- **PRs merge by squash only**. The PR title is the squash subject. If there is a conflict, merge `main` into the branch. Never rebase.
- Edit `AGENTS.md`. `CLAUDE.md` is a symlink to it.

### UI principles

- **The GUI never shows the concept of unloading.** Macterm starts the shells of a project when a window selects it, so the user never loads or unloads a project. There is no action that stops a whole project and keeps its layout: no Unload command, menu item or Settings badge. Remove ends the sessions of a project for good. The CLI keeps the `loaded` field of `project list` (`not loaded` means that no workspace exists yet), because scripts read it.
- **Use native SwiftUI and AppKit components only**. Accept a native limitation. Do not mimic the behavior.
- All colors come from `MactermTheme`. Fixed system colors are allowed only for identity labels (`ProjectColor`, `AgentIcon.brandColor`).
- Put APIs that exist only on Tahoe behind `#available(macOS 26.0, *)`. For controls, also use `WindowAppearance.glassSupported`.
- Settings text: section headers are Title Case. Controls are in sentence case. Buttons are Title Case. `AppCommand` titles are Title Case.
- Settings captions are of two kinds, as in System Settings:
  - A **description** explains one control. It is the second `Text` of the control's label (`Toggle(isOn:) { Text("Title"); Text("…").settingsDescription() }`), which a grouped form draws under the title, with no divider. `settingsDescription()` sets the color, so the text dims with a disabled control, and a 2 pt top gap (`SettingsDescription.gap`). A row with no native subtitle (a slider, a custom `HStack` row) puts the text in a `VStack` with `.settingsSecondaryText()`, with the same gap added to the stack spacing.
  - A **footnote** is about the whole section. It is a row of its own, the last row of the section (`.settingsSecondaryText()`, which a status line in a pane also uses).
- **Controls on a row that a hover reveals change values, not the structure of the view. Never use `.onHover`.**
  - The new-tab button of `SidebarProjectHeader` is one `isRevealed` Bool. It drives padding, opacity and hit testing. An `if/else` in the label of a `List` row tears the row down and corrupts the reuse of `NSTableView`.
  - Hover comes from an `NSTrackingArea` (`RowHoverTracker`, `.activeInActiveApp`). We retired `.onHover` three times, because of lag and exits that leaked.
- With stacked `.dropDestination`s, only the first one that you apply wins.
- The closure of `.contextMenu(forSelectionType:)` in the sidebar runs one time for each open of the menu. It never runs on a redraw of a row (we measured it). A cheap read such as `GitWorktrees.list` therefore belongs there. Inside it, `.disabled` on a `Menu` is dropped. The item then renders enabled over an empty submenu. A disabled submenu must therefore be a disabled `Button` (`SidebarContent.worktreesMenu`).
- **Anything that takes mouse input over a pane needs an AppKit view**. `GhosttyTerminalNSView` wins the hit test. SwiftUI gestures over a pane therefore never see the press. `PaneDragSource` and `ResizeDragBand` are `NSViewRepresentable`s. They forward what they do not own to `viewBeneath`. `NSHostingView` swallows hit tests even with `allowsHitTesting(false)`. Override `hitTest`.

### Terminal surface rules

- Never tear down the NSView from a SwiftUI path.
- `pane.destroySurface()` kills the shell. Call it only when a pane is closed for good, or for a remote reconnect, which never kills the session.
- `createSurface()` needs a frame that is not zero, and a window. `TerminalSurface` waits until it is attached. `Pane.command`, `shell` and `env` map to `initial_input`, `command` and `env_vars` of libghostty. Macterm passes them on the first build only.
- The `closeSurface` callback is asynchronous. Guard against a double close.
- The handoff of the first responder goes through `FocusRestoration`. A bare `makeFirstResponder` races with the attachment of the window.
- **A window that has not reported its occlusion yet counts as visible while it is on screen** (`SurfaceVisibility`, `WindowOcclusionReports`). AppKit sends the first `didChangeOcclusionState` of a new window some hundred milliseconds after the window is on screen. If you trust `occlusionState` before that report, every pane of a launching window parks its renderer, and the window shows rows of colored blocks with no text until the next resize. After the first report, the report is the only source.
- Any encoded key counts as typing for libghostty (it clears the selection and scrolls to the bottom). Do not send control sequences on focus.
- **Every resize of a surface goes through `GhosttyTerminalNSView.applySurfaceSize`, gated by `SurfaceSizeGate`**. A grid under 8×2 cells is refused, and the surface keeps its last size. libghostty reflows the scrollback into any grid that you give it. A grid with two columns shreds every line, and it leaves the content above the viewport when the pane grows back. Such a grid can come from the first frame of a split animation. It can come from a window that shrinks to the width of the sidebar. It can also come from a container that collapses in the middle of a tab switch. Ghostty.app never meets this, because its window cannot get that small.
- **A surface opens its pty at the size of its view** (`initial_width_px` and `initial_height_px` on `ghostty_surface_config_s`, fork patch 0012). `createSurface` gates that size with `SurfaceSizeGate` on the cell size of the last push. Without the field, libghostty starts every surface at a placeholder of 800×600 px, and the first size push races the startup of the child. Under launch load the child wins. `zmx attach` then reports the placeholder grid (47×13 cells), and zmx lays the reattach snapshot out for it. A restored pane still attaches in the incubator first (107×35 cells), before it moves into its window. The zmx fork therefore replays the scrollback and the visible screen as logical lines (changes 0007 and 0009), and it scrolls the scrollback off the screen before the clear (0008, now upstream). A snapshot at any size reflows on the next resize, and it keeps the rows above the screen. `test_reattach.py` pins all three.

### Persistence

- Workspaces are in `~/Library/Application Support/<display name>/workspaces_v3.json` (schema v6, written as v7 only while desktop widgets exist). Projects are in `projects.json`. The wrapper configs are next to them. Debug builds use `Macterm Debug/`, and the Debug bundle is `Macterm Debug.app` (`PRODUCT_MODULE_NAME` stays `Macterm`). Write the space wherever you name the bundle by path.
- `Pane` IDs are new at every restore. The session identity (`sessionID` and `sessionName`, stored exactly as given) is what connects a pane to its session again.
  - Only an explicit Apply Layout applies a declared layout (palette, menu, Settings row, `layout apply`). When you select a project or start Macterm again, Macterm never reads it. The snapshot restores, and a project without a snapshot gets the default workspace.
- **A directory is not an identity**. `ProjectStore.create` always appends a new project. `findOrCreate` exists only for callers that must be idempotent (the `open-project` hook of `BenchmarkControl`, and the folder rows of the palette).
- Project declarations are YAML in `~/.config/macterm/projects/`. All build flavors share them. They look at the `$HOME` env first, through `ProjectPath.currentHome`.
  - `name:` is for display only. `path:` is the identity (scp-style, with `~` when Macterm writes it). `tabs:` is optional.
  - The schema is `assets/project.schema.json`. Keep them in sync.
  - Only an explicit Save Layout and the editor of the user write a file. Only Settings → Projects → Layouts → Remove deletes it.
  - Matching is by the canonical `path:`. The slug of the name of the project breaks a tie when one directory backs several projects (`ProjectSlug.owns`). Macterm surfaces duplicates. It never deletes them.
- `save` records `run:` as the live foreground command (`ProcessInspector.runningCommand`, for a remote project through the probe cache). It records `shell:` only for a shell that is not the default. `apply` (`LayoutReconciler`) matches by the same `(run, cwd)`. Files that do not parse surface `LayoutFileError`. An empty `tabs:` is a bare declaration.
- v1.22.0 removed the `.macterm/layout.yaml` in the repo. `LayoutFile` has no form on disk. Do not add helpers to load or serialize it.
- **The tab of the quick terminal persists too** (`WorkspacesFile.quickTerminal`, an optional section with deliberately no change of the schema version, see its doc comment).
  - `AppState` adopts `QuickTerminalService.shared.splitState` one time (`adoptQuickTerminal`, which you can inject at init for tests). It takes a snapshot of it in every `saveWorkspaces`. It hands the tab back in `restoreSelection`. It counts the sessions of the tab as claims. The panes connect only when the panel is shown for the first time, so until then they have zero clients.
  - `QuickTerminalSplitState` reports its own splits and closes through `onStructureChange`, because it owns no `AppState`. Macterm refuses a restore after the panel was shown in this run.
  - Results: a quit kills nothing and confirms nothing while zmx is bundled. The confirmation returns, with the quick terminal included, only when zmx is not available. A close of a pane in the panel is still the one permanent kill.
- Settings → Projects duplicates the alerts for layout and remove. Keep them gated on `AppState.DialogHost`, so that a confirmation that the palette raises does not also open Settings.

### Adding a new feature

**A feature request starts with the question "does ghostty already do this?" The answer goes to the user before you write any code**. The config surface of libghostty is large. An implementation in Macterm of something that a ghostty key already expresses is a second answer. It disagrees with the first, and the user must find it. #393 deleted the scroll-speed slider and the whole wheel path of Macterm after someone tried `mouse-scroll-multiplier`. It also deleted two Settings controls that `tab-inherit-working-directory` and `macos-shortcuts` had answered all along. Read the config reference of ghostty and `ghostty.h` first. Then choose one of these:

- **A ghostty key covers it**. Read the key live from the loaded config (see the config pipeline) and add **no Settings UI**. Where the default of Macterm must be different from the default of ghostty, that departure is a line in `MactermConfig.defaultsBody`. It is never a fallback in `Preferences`. Naming the key can be the whole answer. Say so, and do not build.
- **Ghostty can express it as a custom shader or a fork patch**. Prefer that to a reimplementation in Swift. Land it in Settings → Animations first, off by default.
- **It is a concept of Macterm itself** (projects, tabs for each project, the sidebar, layouts, windows, the CLI, sessions). Build it here and follow *Adding a new setting*.

### Extensions are a compatibility promise

Every build reads the extensions of the repository on `main`, and anyone can have installed any of them. **An app update must therefore never break an extension that worked.**

- The extension format only grows. It includes `extension.yaml` (`ExtensionManifest`), palette files (`CustomPaletteFile`, `assets/palette.schema.json`), the environment that their commands get (`MACTERM_EXTENSION_DIR`, `MACTERM_PROJECT_*`, exports) and how commands run. Add keys and capabilities. Never remove one, never rename one, and never change what an existing one means.
- A key that a build does not know is an error *in that build* (`no such key`). This is how an extension that uses something newer reads as "needs a newer Macterm", and not as something that half works in silence.
- `CustomPaletteFileTests` reads every extension in the repo on every PR. A change that breaks one fails CI.

### Adding a new action

1. Add an `AppCommand` case (a title in Title Case, a category, and a linked `HotkeyAction` if you can rebind it). The palette, the menus and Settings use it.
2. If you can bind it, add the `HotkeyAction` to `Hotkeys.swift` with its default, **and the matching `MactermKeybind` case and label**. The picker of App Intents repeats them, and `MactermIntentsTests` fails until they match.
3. Handle it in the right `KeyResponder` in `Responders.swift`.
4. Add a `HotkeysTests` case for new behavior of parsing or display.

### Adding a new setting

Macterm-side settings go through `Preferences`. Settings that have the shape of ghostty (theme, font, palette) belong in the ghostty config of the user. Do not add UI for them.

1. Add a `Preferences` property with a `didSet` that writes UserDefaults.
2. Only if libghostty must be forced: add `notifyConfigChanged()` in `didSet` and a line in `MactermConfig.regenerate()`.
3. Add UI to the matching pane in `Macterm/Settings/`. A new pane also needs a `SettingsPane` case and a line in `SettingsView.detail`.

### Windows and sidebars, AppKit reach-throughs

- **Settings window**. `PinnedSidebar` locks the sidebar (it sets min and max thickness of the `NSSplitViewItem` to the same value, and `canCollapse = false`). A `DividerShield` over the divider also locks it. SwiftUI resets the column metrics on events that have no hook, so both layers are load-bearing. If you replace the delegate of the split view, the app crashes. The empty `NSToolbar` (`.unified`) gives the window its roomier titlebar. Never set `titlebarAppearsTransparent` on it: a transparent titlebar draws no scroll-edge band, and a scrolled pane runs under its title (`SettingsWindowChrome`).
- **The width of the sidebar of the main window** is persisted for each window (`WindowSnapshot.sidebarWidth`, default `Preferences.defaultSidebarWidth`).
  - `WindowAppearance.restoreSidebarWidth` restores it through `NSSplitView.setPosition`. It tries again across run-loop ticks until the split view exists. The autosave key of SwiftUI has a runtime address in it, which you can never read back, and `navigationSplitViewColumnWidth(ideal:)` is ignored.
  - `pinSidebarAutosaveName` gives the split view a stable name. `pruneChurnedAutosaveKeys` sweeps the old keys (it matches the marker `(unknown context at $`, and it is skipped under tests).
  - A sidebar that is collapsed is left alone. `forgetSidebarWidthRestore` clears the slot of a window that closed.
- **The frame of the main window** is persisted for each window too (`WindowSnapshot.frame`, the `frameDescriptor` string of AppKit). Macterm records it on every move and resize outside full screen. `WindowAppearance.restoreFrame` restores it through `setFrame(from:)` (#496).
  - The frame autosave of the `WindowGroup` of SwiftUI uses the content type of the scene as the key. That prints a private type (`AppColorScheme`) as `(unknown context at $ADDR)`. It therefore wrote a new `NSWindow Frame …` key at every launch and never read one back.
  - A stable name is not the fix. We measured it with `AppColorScheme` made internal: every window of the group writes the one key `AppWindow-1`. SwiftUI therefore keeps one frame for each group (the window that moved last), and the other windows that Macterm restores open at the default size. The key also still changes each time that the modifiers of the scene closure change.
  - `disownFrameAutosave` clears the autosave name of the window at attach (one owner). `pruneChurnedAutosaveKeys` sweeps both families of stale keys.
  - Macterm centers a restored frame on the main screen at its saved size when it has less than 60 pt on any screen. An example is the corner of a hidden workspace of a window manager.
- **Never leave persistent window state to an autosave of SwiftUI**. We measured every one of them (sidebar column, window frame). Each one uses a key with a runtime address, so it resets in silence at every launch and update. A stable key in `WindowSnapshot` is the rule.
- **The overlay sidebar peek is a side panel, the same as the Project Insights panel** (`SidebarOverlayPanel`). It has the same surface (`glassPanel`) and the same corner and inset (`GlassPanelMetrics.sidePanelCornerRadius` and `sidePanelInset`), and it starts below the toolbar. Its hover exit edge counts the inset (`SidebarOverlayMetrics.exitEdge`).

## Known Limitations

- **Local sessions do not keep running after a restart of the Mac. Remote sessions do**. Every pane (workspace, pinned, quick terminal) persists through zmx. It connects again after a quit.
- **Remote sessions need Macterm's server on the host**. Macterm installs it at the first connection, after one consent, for Linux x86_64 and aarch64 and for macOS. Any other host, and a host where the user declined, gets plain ssh shells that end with the connection. **Windows hosts are not supported.** When the attach command ends with no line of the script and not with 255, the app runs one probe (`HostCheck.windowsProbe`, `echo %OS% $env:OS`: `Windows_NT` in cmd.exe and PowerShell). If it answers, the connect fails with `Failure.windowsHost` and the pane says so. That failure gets no plain shells, because the plain-shell command is POSIX. The probe never reads the host's error text, which is in the host's language.
- **A remote session whose pane closed while no connection was up stays on the host.** Nothing reaps remote sessions.
- **A second window on the same tab shows a mirror**. It is dimmed where the pty has the size of the other view. You cannot declare `pane mirror` panes in layouts, so Save Layout and Apply Layout split one into two sessions.
- **Adaptive background inference depends on the private renderer layout of ghostty** (BGRA8 IOSurface). It fails closed. Selections that a program renders (helix, or vim under mouse capture) remain a gap that we have not closed.
- **Developer ID does not sign Macterm**. On first launch, you need `xattr -cr /Applications/Macterm.app`, or Homebrew. The stable self-signed certificate keeps TCC grants across updates.
- **`macos-hidden = always` costs the menu bar**. Settings, Quit, About and Check for Updates have no route while it is on. Set the own preferences of Macterm before you switch it on.
- **Pane IDs are not stable across restarts.**
- **Desktop widgets are not in the widget gallery of the system**. See Desktop widgets. They also do not take the monochrome look of the system while an app is in front.
- **Macterm detects password prompts only where it can read the tty that prompts**. This means local panes, and remote panes whose host session reports its tty (`tty_mode`, protocol level 3). It does not see anything behind an `ssh` that you typed by hand. It does not see prompts in raw mode that draw their own `*` mask either.
