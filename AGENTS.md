# Macterm Codebase Guide

A macOS terminal emulator built with SwiftUI and libghostty. Single-window app with project-based workspace management, split panes, and a quick terminal overlay.

## Build & Run

```bash
mise install          # Install tools (gh, swiftformat, swiftlint, xcodegen, xcbeautify)
mise run setup        # Download pre-built GhosttyKit.xcframework
mise run run          # Build and launch (debug)
mise run logs         # Stream live logs from the debug app (--release for release app)
mise run format       # Auto-fix formatting with swiftformat
mise run lint         # swiftlint
mise run test         # Run the test suite
mise run build        # Release build + DMG
mise run bench        # Release build + window-state resource benchmark
mise run e2e          # Debug build + end-to-end suite against the real app
```

`format`, `lint`, and `test` show a spinner and print output only on failure. **Always pass `--verbose`** (e.g. `mise run test --verbose`) to stream the raw output.

Requires macOS 14+, Swift 6.0+. Liquid glass and a few chrome refinements are macOS 26 (Tahoe) features that degrade gracefully on older systems (gated behind `WindowAppearance.glassSupported` / `#available`). GhosttyKit is a pre-built xcframework from `thdxg/ghostty` (a fork that adds CI builds); no zig toolchain needed.

**"libghostty" throughout these docs means `ghostty-internal`, which upstream does not support for external use.** Worth knowing precisely, because it sets what we're owed. Ghostty builds two C libraries: `libghostty-vt` (public, `include/ghostty/vt.h`) is the VT layer — parser and screen model, no threads, no renderer, and **no surface API at all**; and `ghostty-internal.a`, whose own pkg-config reads `Description: Ghostty internal library (not for external use)`, which is what `GhosttyKit.xcframework` wraps and what we link. Everything Macterm is built on — `ghostty_surface_*`, the Metal layer, key encoding, pty spawn — exists only in the internal one, so `libghostty-vt` is not a fallback: moving would mean writing the renderer, pty, and input stack ourselves on top of the VT layer. Ghostty.app's own Swift frontend links the same archive (`GhosttyXCFramework.zig` builds it from `GhosttyLib`), so we're using it the way it's used upstream — just with no stability promise. That is the standing justification for the fork-patch strategy, the pinned release, and the `GHOSTTY_ACTION_OUTPUT_ACTIVITY` ABI probe: **treat every internal API as able to change without notice, and pin/probe rather than assume.** (Confirmed by a maintainer on ghostty-org/ghostty discussion #13547, where the `sentry-init` crash was reported.)

`GhosttyKit.xcframework` and the `Macterm/Resources/{ghostty,terminfo,…}` contents are gitignored artifacts downloaded by `mise run setup` — **every fresh checkout, including a git worktree, must run `mise run setup`** before it can build. Don't symlink them from another checkout: setup normally uses a presence check rather than a version check, so a symlinked copy silently goes stale. The one capability exception is `GHOSTTY_ACTION_OUTPUT_ACTIVITY`: setup replaces a present framework that lacks this required ABI (probed by globbing the xcframework's slice dirs for the symbol in `Headers/ghostty.h`, never by naming a slice). The replacement is downloaded and validated in a scratch dir and only swapped in once it passes, so a release that also lacks the ABI leaves the existing framework alone rather than stranding the checkout with none. Requiring the ABI is also a **bisect hazard**: a checkout from before the reliable-activity-detection change doesn't need the ABI, so if a release ever regresses the symbol setup refuses to run at all. Bisecting across that commit means extracting a GhosttyKit from a `thdxg/ghostty` release contemporary with the older commit rather than running setup (its error message says so). To refresh any other stale artifact, delete it and re-run setup.

**Both fork artifacts come from one pinned release, not `latest`.** `GHOSTTYKIT_TAG` in `setup.sh` names the `thdxg/ghostty` release supplying the xcframework *and* the resources tarball. It used to track `latest`, and the fork publishes a `build-YYYY-MM-DD` release **every day** — so every build, tagged releases included, silently picked up whatever libghostty landed that morning; two builds of one Macterm commit could ship different terminal cores. Bumping the terminal core is now its own reviewable commit. `GHOSTTYKIT_TAG=latest mise run setup` (or any tag) tries one without committing. Because the presence checks would otherwise keep the old copy through a bump, setup records the installed tag in `.ghosttykit-tag` (gitignored) and refreshes when it disagrees; the two artifacts always move **together**, since a bump must never leave a new libghostty beside the old release's terminfo. Bumping the pin edits `setup.sh`, which changes CI's GhosttyKit cache key, so the next run downloads fresh.

**The stamp describes what a run actually downloaded, so it is written only when that run fetched *both* fork artifacts.** It is one scalar and can only honestly describe a tree where both came from one release. It used to be written whenever the two dirs merely *existed*, which laundered a stale tree as pinned: a run that downloaded neither (only zmx missing, say) or just one of the two stamped the current pin over whatever was already there, and every later run then saw a stamp agreeing with `GHOSTTYKIT_TAG` and never refreshed — staleness became invisible *and* permanent. A real checkout was found in exactly that state, stamped `build-2026-08-02`: terminfo three weeks older than that tag, beside a framework whose `ghostty.h` was 36357 bytes against the release's 36582 — two artifacts from two different releases, the framework at best from an earlier upload of the stamped one (see the next paragraph on mutable tags). Its 24 renumbered `ghostty_action_tag_e` constants are what `scripts/ghosttykit-api-diff.sh` will show you if you ever need to confirm a suspected mismatch locally. So the write gates on the `need_*` flags; a pin bump sets both, so the case the stamp exists for still records itself. **The gate stops new launderings but doesn't unwind one already written** — a tree holding a bogus stamp that agrees with the pin takes the settled no-op path and stays quietly stale, so curing it is a one-time manual `rm -rf GhosttyKit.xcframework Macterm/Resources/terminfo && mise run setup`. The disk checks remain as belt-and-braces for the property that **a partial setup never stamps** (a failure between the two downloads aborts under `set -e` well before the write, and any `exit 1` leaves the old stamp — and its refresh — in place).

**An absent stamp therefore means "provenance unknown", not "matches the pin".** It still forces no re-download — that's what kept introducing the pin from churning every checkout — but it is a dead end for the refresh, because `tag_changed` needs a stamp to disagree with, so an unstamped tree never adopts a bumped pin on its own. Rather than either lie or churn, `warn_unstamped_artifacts` says so on the settled no-op path (and after a one-artifact refresh), with `rm -rf` remediation. A forced re-download was the rejected alternative: CI restores precisely this state from its GhosttyKit cache, so it would re-download on every hit. CI is instead exempt by construction — `.ghosttykit-tag` is now in the cached paths, so a restored tree arrives stamped, and that cache's key hashes `setup.sh` and so already pins which release the artifacts came from.

**A pinned tag is not immutable, and the pin alone does not make a Macterm commit's terminal core reproducible.** GitHub lets a release's assets be replaced under an unchanged tag, and the fork has done it: `build-2026-08-02`'s two assets were re-uploaded at 08:32Z, hours after CI had already cached the earlier bytes under the same tag and the same `setup.sh` hash. Nothing in `setup.sh` notices — the tag stamp matches, the presence checks pass, and the ABI probe passes for both — so two checkouts can sit on one pin holding *different* libghostty. There is no recorded checksum to catch it; the only signal is downstream breakage. It surfaced as a CI build failure no re-run could clear (see the framework-hash comment in `test.yml`'s unit job), and the same swap can equally reach a tagged release build. So treat the pin as "one reviewable decision about which release", not "these exact bytes" — and when a build behaves differently from an identical commit, compare `GhosttyKit.xcframework/*/Headers/ghostty.h` sizes before suspecting your own change.

**CI's build-product caches are keyed on the installed framework, not just on `setup.sh`.** Because a pinned tag can change bytes, the `derived-debug-*` / `derived-release-*` DerivedData caches key on `hashFiles('GhosttyKit.xcframework/*/Headers/ghostty.h')`, so build products can never be restored alongside a framework they weren't compiled against. That requires reading the hash *after* `mise run setup`, which is why those jobs use an `actions/cache/restore` + `actions/cache/save` split with setup moved above the restore, and why the save re-uses the restore step's `cache-primary-key` instead of re-evaluating `hashFiles` (which would hash the build's own output). The save is success-only, so a failed build never hands its products to the next run. Don't collapse this back into one `actions/cache` step, and don't add a framework-agnostic prefix to the `restore-keys` — a fallback that reaches across a framework change is exactly what turned an asset swap into a wedged pipeline.

**Bumping the pin is a weekly auto-PR, not a chore you remember.** `.github/workflows/bump-ghosttykit.yml` runs Mondays (matching `dependabot.yml`'s actions group, with the same `dependencies`/`area:ci` labels and `chore(deps):` prefix), resolves the fork's latest release, and opens a `chore/ghosttykit-<tag>` PR when it differs from the pin — one branch per target tag, so a re-run while that PR is open is a no-op. It uses `GH_PAT`, not `GITHUB_TOKEN`: a PR opened by the default token doesn't trigger workflows, which would deliver the bump **untested** and defeat the point. `GH_PAT` exists for this workflow alone (a fine-grained PAT on this repo, Contents + Pull requests read/write) — nothing else needs one, since the fork is public. Its **absence is silent**: a missing secret interpolates to an empty `GH_TOKEN`, and the first scheduled run died in 8s on gh's generic "set the GH_TOKEN environment variable", which reads as a workflow bug rather than an unset secret. Hence the `Check the bump token` preflight step — keep it first, and if the token strategy ever changes (a GitHub App, say), update its message with it. Only `gh pr create` actually needs the escaping token; the branch push rides the checkout's `GITHUB_TOKEN`, because every CI workflow triggers on `pull_request` and nothing triggers on a push to a non-main branch. That split is also a trap worth knowing: a PAT granted **Contents but not Pull requests** gets all the way through the commit and push and fails only on the last line, as a bare `Resource not accessible by personal access token` — the push succeeding says nothing about the PAT, since the push wasn't using it. **And any failure after that push wedges the workflow**, which is why the push is `--force`: the branch survives on the remote, the next run rebuilds the same one-line change as a new commit (new timestamp, new SHA) on the same base, and a plain push is rejected non-fast-forward forever until someone deletes the branch by hand. Force is safe precisely because the branch is named per target tag, owned only by this workflow, and unreachable once a PR for it is open (the check step returns early). The dedupe guard keys on an **open** PR, so re-dispatching after a *closed* one deliberately opens it again. **CI on that PR is the gate** — editing `setup.sh` changes the cache key, so the run downloads the new pin from scratch and puts it through Unit, End-to-end, and the benchmark, which is the check that would have caught the `sentry-init` crash before it reached a release. Green means it builds and the suites pass, not that no behaviour moved — so the PR body carries an **API review** (`scripts/ghosttykit-api-diff.sh`) that diffs the two releases' `ghostty.h` filtered to the ~156 `ghostty_*`/`GHOSTTY_*` symbols our own Swift actually references, because the header is ~1200 lines and a week of upstream churn touches plenty we never call. It reports: symbols we use that **vanished** (a build break, named here so a red CI run isn't a mystery), enum constants we use whose **numeric value moved** — with the added/removed member that caused it, since the culprit is usually a member we *don't* reference — constants whose value it **couldn't evaluate** (listed, never assumed unchanged), and the changed **hunks** touching our symbols. The renumbering case is the one worth having: Swift imports enum constants by name, so an upstream insert mid-enum shifts values (23 of ours moved by one between `build-2026-07-15` and `build-2026-08-02`) while compiling silently. That is harmless only because the header and archive always ship together from one release; never pair one with the other's. The report is advisory — a failure to generate it opens the PR anyway, since the PR *is* how the new pin gets tested.

**The script's design rule is that a false negative is the only unacceptable outcome**, because a reviewer who reads "no relevant change" and merges is worse off than one who reads noise. An adversarial pass found six ways it lied, all now fixed and each with a regression case: it matched **per changed line**, which misses the two commonest C ABI breaks since neither names the symbol on the line that changed (a struct field's type inside `ghostty_text_s`, a parameter of a multi-line prototype — so it now matches per **hunk, with context**); its enum parser counted only `GHOSTTY_`-prefixed members, so `/* reserved */ GHOSTTY_X,` took a slot invisibly and every later constant kept its old number; the removal verdict used **substring** matching, and 14 of our symbols are prefixes of longer ones (`ghostty_surface_free` inside `ghostty_surface_free_text`), so a real removal reported ✅; `1 << N` was unevaluated, leaving all of `ghostty_input_mods_e` permanently unwatchable; a `}` sharing a member's line broke enum framing badly enough to attribute members to a *union*; and a single-line `typedef enum {…} name;` was dropped whole, which silently disabled the renumber check for it. It also exports `LC_ALL=C` — BSD `sort` collates while BSD `comm` compares bytes, and under a UTF-8 locale that disagreement invented a **phantom removal** on the exact line the prose tells you to read hardest. The enum parser simulates real C values (explicit `= N` continues the count; hex, `1 << N`, `5U`, split and comment-bearing initializers all resolve) and avoids gawk's `strtonum` so it runs on macOS's one-true-awk too. `warn_if_ghosttykit_stale` is the backstop if those runs start failing silently: it now also runs on setup's "already present" path (it used to sit after the downloads, making it dead code on a settled checkout — survivable while the tag was `latest`, useless once nothing pulls current on its own), and its remediation says to bump `GHOSTTYKIT_TAG` rather than the old `rm -rf && setup.sh`, which under a pin just re-downloads the same tag. One caveat on that warning: it infers the upstream base as the fork commit's *parent*, which holds only while the fork's `main` is `upstream + 1 squash commit`. Land a normal PR on the fork (as the `-Dsentry=false` change did) and the parent is a fork commit instead, so the age it reports is meaningless until the next `sync-upstream` run rewrites `main`.

## Releasing & Updates

Auto-updates ship via [Sparkle](https://sparkle-project.org/) — daily background check, manual via **Macterm → Check for Updates…**. Updates verify an EdDSA signature, so no `xattr` workaround after first install. No telemetry.

Tag-pushed builds release via `.github/workflows/release.yml`, which needs repo secrets: `SPARKLE_ED_PUBLIC_KEY` (baked into `Info.plist`), `SPARKLE_ED_PRIVATE_KEY` (signs each DMG — **back it up; losing it means users can't auto-update to any further release**), `HOMEBREW_TAP_PAT` (pushes the cask to the tap repo), and `MACTERM_SIGNING_CERT_P12` + `MACTERM_SIGNING_CERT_PASSWORD` (the stable self-signed code-signing certificate — **back it up too; rotating or losing it resets every user's TCC privacy grants one more time**, because TCC keys grants to the certificate in the app's designated requirement. Ad-hoc signing, the old scheme, keyed grants to the per-build CDHash, which is why every update used to drop Documents/Downloads access. A missing cert secret fails the release loudly rather than silently shipping an ad-hoc build that would reset grants again; local `mise run build`/`bench` stay ad-hoc, which is fine because they're never distributed).

The certificate is a once-a-decade ceremony, so there's no script — the recipe lives here. It deliberately uses `/usr/bin/openssl` (macOS's LibreSSL): its PKCS#12 defaults are the legacy algorithms `security import` is guaranteed to read, where a Homebrew OpenSSL 3 defaults to AES/PBES2 containers it has a history of rejecting. The codeSigning EKU is what makes the identity acceptable to `codesign`; validity only gates *future signing*, not already-shipped apps.

```bash
mkdir -p ~/.config/macterm/signing && cd ~/.config/macterm/signing
/usr/bin/openssl rand -hex 16 > macterm-signing.password
/usr/bin/openssl req -x509 -newkey rsa:2048 -sha256 -nodes -days 3650 \
  -subj "/CN=Macterm Release Signing" \
  -addext "keyUsage=critical,digitalSignature" \
  -addext "extendedKeyUsage=critical,codeSigning" \
  -addext "basicConstraints=critical,CA:FALSE" \
  -keyout macterm-signing.key -out macterm-signing.crt
/usr/bin/openssl pkcs12 -export -inkey macterm-signing.key -in macterm-signing.crt \
  -name "Macterm Release Signing" -passout "pass:$(cat macterm-signing.password)" \
  -out macterm-signing.p12
gh secret set MACTERM_SIGNING_CERT_P12 --repo thdxg/macterm --body "$(base64 -i macterm-signing.p12)"
gh secret set MACTERM_SIGNING_CERT_PASSWORD --repo thdxg/macterm --body "$(cat macterm-signing.password)"
``` GhosttyKit needs no secret: `thdxg/ghostty` is public, so `setup.sh`'s release downloads run under `GITHUB_TOKEN` here as in every other workflow. The workflow appends an `<item>` to `appcast.xml` on `gh-pages` (served at `https://thdxg.github.io/macterm/appcast.xml`, the feed URL in `Info.plist`) along with a per-version notes page rendered from the GitHub Release body (`publish-appcast.sh`).

**Release notes come from GitHub's native generator**, configured by `.github/release.yml` (categories keyed on the `enhancement`/`bug`/`chore`/`dependencies`/`documentation` labels, `skip-changelog` excluded, a trailing `*` catch-all so nothing is silently dropped — GitHub assigns each PR to the first matching category, so that entry must stay last). `release-drafter` used to maintain a rolling draft and derive the next version from PR labels; it was removed as redundant now that the notes are native. The tradeoff is deliberate: **the version number is chosen by hand when cutting a release**, since native notes only ever describe a tag that already exists. That is also what keeps `vX.Y.Z-beta.N` prerelease tags simple — nothing tries to compute them.

### Stable, beta and tip channels

The GitHub Release's `prerelease` flag is the switch between stable and beta, and it drives **one feed with three Sparkle channels** — not an appcast per channel. A prerelease's `<item>` carries `<sparkle:channel>beta</sparkle:channel>`, which Sparkle hides from any updater that hasn't opted into the `beta` channel; a stable item carries no channel element at all (the default channel, visible to everyone). Opt-in is **Settings → Updates → Channel** (a Stable/Beta/Tip picker: `Preferences.updateChannel`, an `UpdateChannel` enum → `UpdaterDelegate.allowedChannels(for:)`, read fresh on every check, so the picker needs no restart). The enum's raw values are both the persisted preference and — for every non-stable case — the wire channel name (`betaUpdateChannel`/`tipUpdateChannel` derive from the `rawValue` rather than restating it), so a case rename is a stored-preference *and* wire-format migration; an unrecognized persisted value falls back to stable. The channel gates *visibility*, so it governs the scheduled check and the manual **Check for Updates…** identically — there is no manual-only escape hatch. Opting back out doesn't downgrade an installed beta; the next stable above it replaces it. The channel literals are a wire contract between Swift and the workflows: `publish-appcast.sh` no longer names a channel at all, it interpolates `$CHANNEL` (unset + `PRERELEASE=true` ⇒ `beta`, preserving release.yml's old behaviour; `release-tip.yml` passes `tip`), and a channel on a non-prerelease is now a hard **error** rather than a silent tag — an item nobody on the default channel can see. `UpdaterChannelTests` pins every side. What stays stable-only is the **Homebrew tap** — `bump-cask` is still gated on `!prerelease`, so betas and tip builds are DMG/auto-update only and `brew` never serves one.

Prerelease tags may carry a `-beta.N` suffix (`v0.9.0-beta.1`), accepted **only** when the release is flagged prerelease so a stable release can't ship a beta version string. `gh release edit` re-asserts `--prerelease` explicitly alongside `--draft=false`, since publishing a draft is otherwise a chance to silently drop the flag and leak a beta into the stable channel.

**Every job reads that flag live, never from `github.event.release.prerelease`.** A single `flag` job resolves it once via `gh release view --json isPrerelease` and the rest consume `needs.flag.outputs.prerelease`. The event payload is a snapshot frozen at dispatch, and *editing a release does not re-fire `published`* — so promoting a prerelease to stable in the same breath as publishing it makes every job read the stale `true`. v1.21.0 shipped exactly that way (run `30699334224`): the release record said `prerelease: false`, the payload said `true`, `bump-cask` skipped, and the appcast got no item, leaving the tap a version behind and auto-update silent until the tag was re-published. The tell at the time was the run's display title reading "Macterm v1.20.11" against tag `v1.21.0` — but **that tell is gone**: the title renders live from the release *name*, so it rewrote itself to `v1.21.0` when the release was retitled, and release names are now just the tag (the `Macterm ` prefix was dropped from all 112 past releases and from `gh release create --title`), so the two can no longer visibly disagree. A repeat is silent — a skipped `bump-cask` and an appcast with no item. Adding `released` to `types:` would only patch the one path we hit (and the docs don't say whether it fires on an edit-to-promote), whereas a live read is correct for any activity type. One footgun to preserve: a job output is always a **string**, so the gate must compare `== 'false'` — `!needs.flag.outputs.prerelease` negates a truthy non-empty string and would skip `bump-cask` on every release.

**Version ordering is not the marketing string.** `SUStandardVersionComparator` treats a `-beta.N` suffix as insignificant — it ranks `0.9.0-beta.1 == 0.9.0 == 0.9.0-beta.2` (measured against the real comparator, not assumed) — so feeding it raw would mean beta→beta updates never appear ("You're up to date") and the eventual stable `0.9.0` never reaches testers. So `sparkle_comparison_version` (`scripts/_lib.sh`) maps the marketing version to the 4-component string Sparkle actually orders by: `0.9.0-beta.1` → `0.9.0.1`, stable `1.8.0` → `1.8.0.9999`. Both emitters must use it — `build.sh` for `CFBundleVersion` and `publish-appcast.sh` for `<sparkle:version>` — because a mismatch between the two silently breaks updates; `<sparkle:shortVersionString>`/`CFBundleShortVersionString` keep the human form for display. The `9999` sentinel is load-bearing: the comparator ranks `0.9.0.0.9 > 0.9.0`, so padding stable with fewer components than a beta inverts the order. One migration caveat: apps installed before this change carry a bare `X.Y.Z` `CFBundleVersion`, which sorts *below* the same version's new `X.Y.Z.9999`, so re-publishing an already-shipped tag would offer those users a spurious update to the identical release (the dedupe guard in `publish-appcast.sh` prevents that path; ordinary version bumps are unaffected).

A **tip** version rides the same sentinel from the other side: `1.24.2-tip.7` → `1.24.2.9999.7`, keeping the stable sentinel and appending the commit count since that stable tag, so it ranks *above* the stable release it is built on top of (it is strictly newer code) and below the next one. Monotonic across a base bump too — the count restarting at 1 under a higher `X.Y.Z` still outranks a large count under the lower one, because `X.Y.Z` is compared first (`a_restarted_tip_count_still_outranks_the_previous_base` asserts exactly this against the real comparator). **Ghostty's scheme is simpler and was deliberately not adopted**: it makes `CFBundleVersion` a bare `git rev-list --count HEAD` integer on *both* channels, which gets cross-channel ordering for free — but every already-installed Macterm carries `X.Y.Z.9999`, and swapping in a bare integer re-orders all of them against a number line the stable and beta channels aren't built or tested on. Extending the sentinel costs one component and changes nothing for installed apps.

### The tip channel

`.github/workflows/release-tip.yml` builds and publishes **every commit on main that passes CI**, modelled on ghostty's `release-tip.yml`: `workflow_run` after `Test`, a force-moved rolling `tip` tag, and ONE permanent GitHub prerelease edited in place (never delete-and-recreate — it keeps its URL and download counts, and `--prerelease` is re-asserted on every edit so it can never silently become "Latest"). Four things diverge from ghostty, each on purpose:

- **We gate on CI having *passed*.** Ghostty's tip fires on `Test` merely *completing* — there is no `conclusion` check anywhere in its workflow, so it ships builds from red commits. Here the `gate` job requires `workflow_run.conclusion == 'success'` **and** polls `checks.yml`'s run for the same SHA (Format/Lint), because Test alone is not "CI passing". `skipped` counts as green: both workflows' paths filters skip their jobs for a change touching no Swift. Test takes 15–30 min against Checks' ~2, so the poll is a race guard, not a real wait.
- **The version scheme** (above) — a sentinel-extended semver, not a bare integer.
- **Artifacts live on the GitHub release, not a per-commit blob store.** Ghostty writes immutable `tip.files.ghostty.org/<sha>/Ghostty.dmg` objects to R2, which is what lets it keep its newest 16 tip items in the appcast. We have one mutable release and no immutable URL, so `publish-appcast.sh`'s `ROLLING=true` keeps **exactly one** tip item (stripping every existing item carrying the channel before inserting) and the workflow prunes all but the newest `KEEP_ASSETS` (3) tip DMGs. Keeping stale items would be worse than untidy — their enclosures would 404 once pruned. The appcast step runs **last**, after the DMG is on the release, so the feed can never name an enclosure that isn't there yet.
- **One feed, one more Sparkle channel** — not a second appcast file. Ghostty explicitly declined channels (`UpdateDelegate.feedURLString` picks `tip.files`/`release.files` per check because it "didn't want to share a single appcast file"); Macterm already shipped the channel-element mechanism for beta, so tip is one more channel rather than a second feed and a second `SUFeedURL` story.

Two guards keep the rolling state consistent. The `concurrency` group is single-flight with **`cancel-in-progress: false`** — publishing is a read-modify-write of `appcast.xml` on `gh-pages` plus a force-moved tag and an asset swap, and two runs interleaving there can leave the feed naming a pruned DMG (ghostty's own comment gives the same reason). And a `Confirm no newer tip is already published` step asks the **ledger** — is the `tip` tag an ancestor of the commit we built? — skipping the publish (cleanly, not as a failure) only when it isn't. **The obvious version of that check is wrong and cost a real build**: comparing against main's current *HEAD* instead, run `33108018478` built `081e1e4` as `1.24.2-tip.2`, #311 merged four minutes in, and the run discarded a finished 20-minute universal build to report a green no-op with no release — which any merge landing during a build would have done. Main moving on does not make a build unpublishable; it just means a newer one is queued behind, and publishing `tip.2` now and `tip.3` twenty minutes later *is* the channel working. The only genuinely stale case is a tip already published from a commit at or ahead of ours, which is exactly what the tag records because it moves last. A git ref is also authoritative in a way the feed is not (Pages serves `appcast.xml` through a CDN, so reading it there can see a stale copy); `publish-appcast.sh` keeps its own version guard against the real `gh-pages` branch as the backstop. `is-ancestor` is exact here only because PRs merge via squash, so main is linear.

The **`tip` tag is the ledger**, and the publish order is built around that: release-update → appcast → **tag move last**. Advancing the tag is the commit point of the whole publish, so a failed asset upload or a failed `gh-pages` push leaves the ledger at the previous commit and the next automatic run simply redoes that commit (if it was the tag push itself that failed, the appcast's equal-version guard makes the redo a no-op). Advancing it any earlier means a mid-publish failure leaves the ledger claiming a build nobody can download, with the gate skipping that commit forever. The gate skips a commit the tag already points at, which makes a re-delivered `workflow_run` free (ghostty gets the same idempotency from a `HEAD` against its per-commit R2 object; a tag needs no extra state) — but a `workflow_dispatch` deliberately **ignores** the ledger, so re-dispatching is always a working recovery path. The gate also skips when nothing shippable changed since the last tip build — `git diff` against the tip tag, filtered against docs/website paths, mirroring ghostty's `paths-filter` with `base: tip`; spending ~20 min of macOS runner so followers can install a byte-identical app with a higher version number is pure waste. That tag is *also* a trap for anything deriving a version from git: it is force-moved onto HEAD, so **`git describe --tags --abbrev=0` always returns `tip`**. `macterm_tip_version` therefore filters `git tag --list 'v*'` to `^v[0-9]+\.[0-9]+\.[0-9]+$`, excluding both `tip` and `vX.Y.Z-beta.N` (`tip_version_ignores_the_tip_tag_and_beta_tags` builds a scratch repo and proves it).

`release.yml` skips itself for `github.ref_name == 'tip'` (on the `flag` job, which everything else `needs`). It should be unreachable — release-tip.yml mutates the release with `secrets.GITHUB_TOKEN`, and events raised by that token don't start new workflow runs — but if `release: published` ever did fire for `tip`, release.yml's version gate would fail on a tag that isn't `vX.Y.Z` and paint main red for a tip build that worked fine.

Tip signs with **the same certificate** as stable and beta — the shared step is now the `.github/actions/import-signing-cert` composite action rather than 60 duplicated lines. Signing tip with a different identity (or ad-hoc) would reset the TCC privacy grants of everyone following tip on *every single build*.

**A hand-installed tip DMG would otherwise dead-end.** A tip version outranks every stable release of the same base, so a tip build sitting on the `stable` channel sees "You're up to date" forever. So `build.sh` bakes `MactermUpdateChannel` into `Info.plist` (from `macterm_update_channel` in `_lib.sh`) and `Preferences.init` uses it as the **default** when the user has never picked a channel — the same trick as ghostty's build-time `release_channel`, minus the config key. Beta deliberately stamps `stable`: a beta sorts *below* its stable release, so the stable release still reaches it and there is nothing to dead-end. That keeps the invariant the tests exist for — no stable or beta build ever defaults to a prerelease channel.

## Benchmarks

`.github/workflows/benchmark.yml` measures resource usage (CPU-time delta, RSS, and — best-effort via `powermetrics` — wakeups/s) across three states: an idle `focused` sanity baseline plus two `workload-*` states — `workload-focused` and `workload-unfocused` — each sampled after `$BENCH_WORKLOAD` (default 2) busy tabs are spawned through the bundled `macterm` CLI (`tab new --run` + `grid 2x2 --run`, a `/bin/sh` date loop per pane), so the workload numbers cover an app doing real terminal work. The state set was cut from six (`focused`/`unfocused`/`minimized`, each idle + workload) to these three: 3 states × 4 metrics = 12 flag-chances instead of 24, and the near-redundant idle `unfocused`/`minimized` states carried almost no signal an idle `focused` baseline doesn't. `STATES` = `IDLE_STATES` (`focused`) + `WORKLOAD_STATES` in `benchmark.py`; a baseline missing the `workload-*` states just shows no deltas for them (called out in the report footnote). Pushes to `main` upload a `benchmark-results` artifact; PR runs pool up to the last 10 main runs' artifacts into a per-metric **median baseline** (`pool_baselines` in `benchmark.py`) and post a comparison table to the job summary and a single updated-in-place PR comment. Runs land on different shared runners, so cross-run deltas are noisy — four layers keep that noise from mislabeling a PR. First, the pooled baseline: a delta against a single main run is one noisy sample vs. another (doubling the noise in every cell), and one unlucky main run then mislabels every PR until the next push replaces it — the median across runs absorbs such an outlier entirely, which is also why it's a median and not a mean. Second, each state is sampled as the median of several short windows (`--samples`×`--seconds`, default 3×10s, same total wall-clock as the old single 30s window) so one co-scheduled CPU spike can't skew a state. Third, a cell is **flagged** (gets a 🔺/🔻 in the table) only when it clears both ±25% _and_ the metric's absolute noise floor, and — for the CPU metrics — only when the _baseline itself_ is above a `min_baseline` (an idle app legitimately wanders 0.6–1.4% CPU on a shared runner, so a big relative swing off a sub-1.5% baseline is noise, not a regression). Fourth — the layer that gates the actual PR **label**, distinct from the per-cell flag — the set of flagged cells must clear a corroboration bar: ≥`MIN_LABEL_CELLS` (2) cells moving the same direction, at least one under a `workload-*` state (`should_label` in `benchmark.py`). A lone noisy cell, or two cells confined to the idle baseline, still print their raw % and arrow in the table but do **not** tag the PR — the idle state's known jitter can corroborate a workload move but can never carry a label alone. All the noise guards live in `METRICS` + `should_label` in `benchmark.py`; a guarded-out delta still prints its raw % in the table. Corroborated deltas add the `benchmark:regression` / `benchmark:improvement` PR label (removed again when a later push clears them) and the comment explains which metrics triggered it. The label + comment writes live in a separate `benchmark-report.yml` workflow triggered via `workflow_run`, not in `benchmark.yml` itself: a `pull_request` run from a fork gets a read-only `GITHUB_TOKEN` (the job's `permissions:` block is capped at read regardless of what it declares), so writing from there 403s. So `benchmark.yml` renders the report and uploads it as a `benchmark-report` artifact (report markdown, verdict JSON, and the PR number — the latter because `workflow_run.pull_requests` is empty for forked PRs), and `benchmark-report.yml` runs on completion in the base repo with a read/write token, downloads that artifact, and does the writes. The reporting workflow never checks out or executes fork code — it treats the artifact as pure data.

The harness (`scripts/benchmark.py`, invoked by `mise run bench`) launches the Release app under a throwaway `$HOME` (hermetic: no user ghostty config, fresh App Support) with `MACTERM_BENCHMARK=1`, which arms `BenchmarkControl` — Darwin-notification remote control (`notifyutil -p com.thdxg.macterm.bench.<cmd>`; commands: `open-project`, `activate`, `minimize`, `restore`). Darwin notifications and `open`-based activation need no TCC grants, which is what lets a headless CI runner script window states at all (AppleScript/synthetic keys would need an Accessibility grant). Benchmark mode also skips the notification-permission prompt (it would steal key focus mid-measurement) and doesn't start the Sparkle updater — a bench-built Release app carries the placeholder EdDSA key, so Sparkle's failed-start alert would otherwise block the launch run loop until someone clicks OK.

The launch/drive/teardown machinery lives in `scripts/_harness.py` (`MactermHarness`), shared with the e2e suite: LaunchServices launch (`open -n --env…`, exact-pid matching that excludes pre-existing instances), the `open-project` readiness loop, control-socket polling, bundled-CLI invocation, a live `log stream` capture (the app logs at `.info`/`.debug`, which never persists to the log datastore — a post-hoc `log show` returns nothing), and failure forensics (screenshot + streamed log + per-pane dumps). Isolation is three env vars: throwaway `$HOME`, `MACTERM_BENCHMARK_DATA_DIR` (App Support resolves via the user record, not `$HOME`), and `ZMX_DIR` — the zmx socket dir is per-*user* (`TMPDIR/zmx-<uid>`), NOT `$HOME`-scoped, so without the override a hermetic instance shares the session namespace with the developer's real Macterm (its `session list` would show their sessions, and its orphan reaper could kill their detached shells). Teardown kills only sessions attached to the instance's own panes (scoped by attachment, never by name), then SIGKILLs the app (SIGTERM hangs on the quit dialog).

## End-to-end tests (`e2e/`)

`mise run e2e` builds the Debug app and runs a pytest suite (`e2e/`, venv-bootstrapped by `scripts/e2e.sh`) that launches the real GUI app hermetically via `MactermHarness` and asserts through the bundled `macterm` CLI — `pane dump`/`pane inspect`/`pane list` read libghostty's own live state, so a passing I/O test proves the whole stack (socket → AppState → libghostty → pty → shell → renderer cells). Debug configuration on purpose: correctness is under test, it shares CI's Debug DerivedData cache with the unit-test job, and the debug-only verbs (`pane resize`) stay available. CI runs it as the `End-to-end` job in `test.yml` (grouped with the unit suite so checks render as "Test / Unit" and "Test / End-to-end"; `checks.yml` keeps the style gates); failures upload a `e2e-diagnostics` artifact (screenshot, streamed unified log, per-pane text — captured by `e2e/conftest.py`'s autouse fixtures).

Suite conventions: ONE app instance per session (launch costs ~15–30s), so tests own their blast radius — take the `fresh_tab` fixture for a disposable tab (an autouse janitor force-closes leftovers), never mutate the initial project pane. Every wait is a deadline poll (`_harness.wait_for`), never a fixed sleep. Commands typed into panes must parse in ANY login shell (CI's runner user logs into bash 3.2; dev machines may run nushell/fish) — write them as `/bin/sh -c "…"` with a single-quote-free script, the same trick as the benchmark workload and `RemoteSpawn`. Target panes explicitly (`--session`/`--pane`); `pane run` goes through `MactermHarness.pane_run`, which places connection flags *before* the command (its passthrough capture would otherwise swallow a trailing `--socket` into the typed text and fall back to discovering a real Macterm's socket).

**No ghostty-side idle/running signal is environment-independent — sync on output markers.** `needsConfirmQuit` (what the busy-close guard reads) is accurate only where shell integration reaches the zmx session shell: the fork's command-wrapper injects it per shell (nushell gets `--execute 'use ghostty *'`), but ghostty has no integration for bash 3.2 — CI's login shell — so there every pane reads perpetually busy, idle or not. The foreground-name poll (`pane list` `.process`) is no better: a fresh session that misses the zmx resolver's registration retries waits on a 30s reconcile TTL. So tests prove execution state with runtime-assembled markers (`printf started-%s <nonce>` — the *typed* line never contains the assembled string, so a dump match proves execution, not echo), and the close-without-force contract is asserted conditionally on the signal the guard actually reads (`test_tab_close_follows_the_running_program_signal`).

## Architecture

```
MactermApp (SwiftUI @main)
  └─ WindowGroup
       └─ MainWindow
            ├─ SidebarContent (List with native selection)
            └─ WorkspaceView
                 └─ SplitTreeView (recursive)
                      └─ TerminalPane
                           └─ TerminalSurface (NSViewRepresentable)
                                └─ GhosttyTerminalNSView (owned by Pane)
```

### Key Design: Pane-Owned NSView

**`GhosttyTerminalNSView` is owned by its `Pane` model, not by SwiftUI.** `TerminalSurface` is an `NSViewRepresentable` whose `makeNSView` returns `pane.ensureNSView()` — a cached instance living for the lifetime of the `Pane`. `dismantleNSView` is a no-op; the NSView dies only via an explicit `pane.destroySurface()`. This exists because ghostty surfaces are tightly coupled to their `NSView` + `CAMetalLayer` — if SwiftUI recreated the NSView on tree reshapes or tab switches, the surface would die.

### State Management

- **`AppState`** — single `@Observable`, passed via `.environment()`. All workspace/tab/pane mutations go through here. `WorkspaceStore` is injectable for tests.
- **`ProjectStore`** — global project list, persists independently.
- **`Workspace`** — per-project tab collection, keyed by project ID in `AppState.workspaces`.
- **`TerminalTab`** — owns a `SplitNode` tree and focused pane ID.
- **`SplitNode`** — recursive enum: `.pane(Pane)` or `.split(SplitBranch)`.

### Single Window Enforcement

The app blocks additional windows. `WindowGroup`'s `.newItem` command is replaced with a "Show Window" item (Cmd+N) that re-fronts the existing window. The close button hides (`orderOut`) instead of closing, preserving surfaces. Dock-icon reopen goes through an `NSWorkspace.didActivateApplicationNotification` observer in `AppDelegate.reopenIfNeeded()` — `applicationShouldHandleReopen` alone isn't reliable through `@NSApplicationDelegateAdaptor`, and AppKit reports `canBecomeMain = false` on ordered-out windows, so the filter walks the window list for any hidden window that could be the terminal one.

**"Could be the terminal window" is `AppDelegate.isTerminalWindowCandidate`, and it is not just "not an `NSPanel`".** That older spelling was true only while the quick terminal was our one auxiliary window; `SurfaceIncubator`'s window is a plain, **permanently invisible** `NSWindow` sitting in `NSApp.windows`, which is the exact shape `reopenIfNeeded` looks for — "hidden, not a panel" matches it on *every* activation once any off-screen pane has been warmed. Ordering it in draws a blank black 1024×768 rectangle, and `reopenIfNeeded` then caches it as `mainWindow` — the pointer every key-window-gated hotkey reads — so the whole keymap goes dead until relaunch. The exclusion is a marker subclass (`SurfaceIncubatorWindow`, mirroring `QuickTerminalPanel`) rather than a question asked of `SurfaceIncubator.shared`, whose `window` is `lazy`: asking would *create* the window from inside a predicate whose job is to ask whether it exists. Every window-identity heuristic — `hasTerminalWindow`, `showWindow`, `reopenIfNeeded`, `BenchmarkControl.mainWindow` — goes through that one predicate, so a future auxiliary window is excluded in one place; route new ones through it rather than re-spelling `!($0 is NSPanel)`. It stays a heuristic, not an identity: the Settings window is also a plain `NSWindow` and still matches, which is why identity remains the pointer `didBecomeMain` cached and this only narrows the fallback used before that pointer exists. (`reopenIfNeeded` reads the injectable `windowLister` for the same reason `repairMissingWindow` does — it is what makes any of this testable.)

**SwiftUI only builds that window during AppKit's launch open-untitled step, and a launch that doesn't front the app skips it (#241).** That is exactly how macOS relaunches apps for "Reopen windows when logging back in", so after a reboot the app ran with a Dock dot and **zero** windows — nothing hidden for `reopenIfNeeded`, "Show Window", or a Dock click to re-front, `MainWindow.onAppear` never running (no responders, control socket stuck answering `starting`), and quit-and-relaunch the only cure. Reproduce it without rebooting: `open -g -n` the app (the unified log shows `BringFrontModifier … dontMakeFrontmost=1`, then the `aevt/oapp` handler running but stopping short of window creation, against a foreground launch where it continues into it). Activating afterwards does **not** make AppKit reconsider — measured: `NSApp.activate(ignoringOtherApps:)` produced nothing, while `applicationOpenUntitledFile` (the call AppKit itself makes on a foreground launch, which SwiftUI's `@NSApplicationDelegateAdaptor` wrapper implements) produced the window. So `AppDelegate.repairMissingWindow` polls for ~3s after launch and, only if there is still no candidate window, asks for one; `reopenIfNeeded` and "Show Window" do the same when they find nothing to front. Two things hold it together: the repair is **gated on there being no window at all** and **debounced** (`requestInitialWindow`), because SwiftUI's window materializes a run-loop turn or two after the request and a second request would open a second window in a single-window app; and the delay is deliberate, since AppKit decides during launch-event handling — a window that hasn't appeared by the deadline is never coming.

### Hotkey System

All keybinds are configurable via `HotkeyAction` + `HotkeyRegistry`. `KeyRouter` installs a single `NSEvent.addLocalMonitorForEvents` at launch and dispatches through the ordered `KeyResponder` chain in `Responders.swift`. `isAppShortcut` in `GhosttyTerminalNSView` lets registered app shortcuts pass through the terminal. Defaults live in `Hotkeys.swift`; user overrides in UserDefaults (`macterm.hotkey.<action_id>`).

**Passthrough (#209)** lets a per-action opt-in (`macterm.hotkey.<action_id>.passthrough`) hand a binding's chord to the program in the focused pane instead of firing — what makes `ctrl+h` bound to Focus Left still reach nvim so it can move its own splits, then hand focus back out via `macterm pane focus --direction`. `KeybindPassthrough` owns the policy, and it yields only when the action is flagged **and** the pane's foreground process is one the user **named** (`Preferences.passthroughPrograms`, a comma/whitespace list matched on lowercased basenames). Matching deliberately uses `ProcessInspector.runningProcessName` — the same function that names the tab — so the contract is "type what the tab shows". Three things not to undo: **both** key paths consult the policy (the responders returning `.passThrough` is not enough — `isAppShortcut` would still swallow the chord in `keyDown`; the real `NSEvent` continues through `keyDown` so encoding and key-repeat stay normal, and `TerminalPane.configure` injects the pane-aware seam because the NSView has no back-reference to its `Pane`); the gate scans only *flagged* actions from a cache (`HotkeyRegistry.passthroughActions`, invalidated on toggle) and an empty program list short-circuits before any syscall, because this runs on every keystroke and each candidate costs an `eventToken` normalization; and **remote panes never yield** (no local process describes them, and `RemoteForegroundResolver`'s ~3s cache that freezes on probe failure is too stale to decide a keystroke). Inferring the condition instead of asking the user was tried twice, and both failures are recorded in `KeybindPassthrough`'s doc comment: raw/cbreak tty mode alone is *wrong*, because interactive shells hold the tty raw to run their own line editors (ZLE, readline, reedline), so an idle prompt was indistinguishable from an editor and every flagged binding yielded everywhere, never firing; adding "foreground is not a shell" fixed that but still swallowed the chord in any raw-mode program that ignores it (`btop`, `less`). Sending the key speculatively and reacting to it being ignored is not available either: no terminal protocol has an "unhandled" reverse channel, the cursor position that would prove nvim moved isn't in the libghostty ABI, and the send can't be taken back.

### Tab Naming

A tab's auto-title is, by default, the pane's live **foreground process name** (`hx`, `btop`) — falling back to the login shell name (from `getpwuid`, not `$SHELL`) when idle, overridden by a user-set `customTitle`. Auto-naming is a preference (`Preferences.autoNameTabs`, Settings → Appearance → Sidebar, default on); off pins tabs to the static fallback (shell/host name) via a display-only gate in `Pane.displayTitle` — polling and probing keep running for busy-close and execution tracking, and `processTitle` stays live for the quit dialog. `ProcessInspector.runningProcessName` reads the foreground pid's kernel `comm`. `AppState` polls panes adaptively (`PollCadence` + `refreshAllForegroundProcesses`, republishing only on change): 250ms during a ~5s burst after any poll event (tab switch, keystroke, OSC title, execution transition — all post `.terminalPollEvent`) or while a command runs frontmost, 1s when active-idle, 2s when inactive with a visible window, stopped when nothing is on screen (events resume it instantly; the quit dialog re-reads names one-shot since the poll may be paused). The throttled `GHOSTTY_ACTION_OUTPUT_ACTIVITY` heartbeat from the pty IO path is the **sole** activity source (the render-path `GHOSTTY_ACTION_SCROLLBAR` feeds only the overlay scrollbar): it keeps firing while occluded and `setup.sh` requires the ABI that emits it, so an activity-sourced run's silence is meaningful on or off screen — the indicator quiet-settles occluded and visible panes identically, with no occlusion exemption. The heartbeat carries the row total, keeping runs alive through in-place redraws and letting the tracker distinguish growth from a redraw. The heartbeat throttle (500ms, leading-edge, drops — never defers) means a fast command's output often surfaces only on a heartbeat emitted *after* its completion, so completion edges (OSC 133;D via `markCommandFinished` — even while idle — and any foreground transition in `refreshForeground`) rebase the row baseline: growth measured across a completion must never restart a finished command as a quiet-settling activity run. Row growth may start activity under the normal interaction guards. Non-growing output can start activity only for a recognized AI-agent foreground, as two heartbeats within 2s of an actually forwarded unmodified Return/newline submission with committed prompt content; a genuinely blank submission briefly suppresses even row-growth redraws. This covers Pi's nested `!` commands without treating Return in ordinary raw TUIs, startup output, typing, IME composition, or one prompt redraw as work. OSC 0/2 titles are **provenance-gated** (`Pane.receiveReportedTitle`): the raw sequence can't distinguish a program naming its session (claude, ssh) from a shell titling its prompt (nushell, Starship emit the cwd), so the title string is adopted as `Pane.programTitle` only while the foreground process is a real program — not a shell — and is pinned to that pid; the poll expires it when the pid loses the foreground (`applyForegroundRefresh`), and prompt-time titles are discarded. `displayTitle` prefers `programTitle` over the process name; the quit dialog keeps the process-derived `processTitle`. Every OSC title arrival also triggers a process refresh (command boundary). Titles aren't persisted — always derived live.

**Remote panes** (#104) leave the local pipeline entirely — the local process table only knows the `ssh` client, so `ProcessInspector.foregroundPID(forPane:)` returns nil for them. Their naming is two-tier: OSC 0/2 titles gated by the OSC 133 execution state instead of a pid (`Pane.receiveRemoteReportedTitle` — adopt while running, discard prompt churn, expire on the running→ended edge), plus `RemoteForegroundResolver`, one BatchMode ssh per host per ~3s (frontmost project only, overlapping probes dropped, transient failures freeze names and retry; an auth-REFUSED probe — classified from ssh's stderr, `RemoteProbeOutcome` — suspends the host's probes for the rest of the run, because BatchMode can't suppress the per-connection system dialog of a Touch ID-gated key (#272), and a never-seen pane on the host clears the gate for one retest, so a since-configured ControlMaster is picked up at the cost of at most one prompt beside the pane's own) running the same session→leader→tpgid→comm pipeline as a portable POSIX script (`RemoteSpawn.foregroundProbeScript`), which also emits the **host's own idle verdict** per session (`1` when the tty's foreground group IS the session leader's — the shell owns its prompt; empty when the pgid read failed, parsed as unknown, never invented). Execution boundaries force a probe NOW: any `executionState` transition and the unconditional OSC 133;D hook set `Pane.remoteProbePending` (the remote mirror of #210's local command-boundary refresh, which is a no-op for remote panes), which bypasses the resolver's per-host interval, rides along from a background project, and probes even while no window is visible — without it a finished program's name lingered until the next scheduled probe or user interaction. Every remote pane also **primes** one such request at init: scheduled probes cover only the frontmost project, so a restored pane in a background project would otherwise never be probed and `needsConfirmClose` would sit on its conservative ssh-is-busy fallback (every plain-shell close warned) until the project was selected once; a probe listing that misses a never-named pane's session (the ~12–14s registration race) re-arms the request, bounded. Idle fallback is the host name. **The whole probe pipeline sits behind `Preferences.backgroundSSHConnections`** (Settings → General → Remote Projects, default on) — the user-facing kill switch for hosts where every background connection raises a Touch ID dialog (#272): off gates the single resolver call site in `refreshAllForegroundProcesses` (so scheduled, boundary, AND priming probes — each is its own connection) plus the `RemoteTerminfo` install, and flips `ForegroundPolicy.needsConfirmClose`'s no-sample fallback from conservative-busy to don't-warn (a positive OSC 133 running state still warns — it rides the pane's own connection and costs nothing; local panes are untouched). The close-time `killRemoteSession` deliberately stays: it's an on-demand one-shot at a user action, and cancelling its prompt merely orphans that session. The probe also carries the foreground's full command line (`ps -o args=`, the tab-tolerant LAST wire field), cached as `Pane.remoteForegroundCommand` — that is what `ProcessInspector.runningCommand`'s remote branch answers with, so layout `save` captures a remote pane's `run:` and reconcile matches it by the same value (both seams read the one function; a shell-NAMED foreground clears the cache so an idle remote prompt still saves a plain leaf). Both pipelines publish into ONE observable value, `Pane.foregroundSample` (`ForegroundSample`: name, shell-ness judged at sampling time, origin, timestamp) — `foregroundProcessName` is a view over it — and the policies that consume it (`ForegroundPolicy.needsConfirmClose` etc.) are pure functions, so the local/remote asymmetry lives in the sources, never at consumer call sites. Shell-ness in a remote sample is the probe's host-side verdict (falling back to the local /etc/shells only when the flag is missing) — the local database is wrong in both directions across hosts: it doesn't list remote-only login shells (idle prompt read busy forever), and it can't see that a NESTED shell inside the session shell is a running child (closing kills it — now warns, matching libghostty's local semantics).

### Remote Projects (#104)

A project whose `path` is an scp-style `[user@]host:dir` spec (parsed by `ProjectPath`; created via the sidebar's New Project → Remote Machine sheet or a central project file). Each pane is a persistent zmx session **on that host**: the surface command is `ssh -t host 'sh -c '\''…cd dir && exec zmx attach <session>'\'''` (`RemoteSpawn.paneCommand`) with **no local zmx wrapper — nested zmx is broken upstream**, the remote daemon owns persistence. Quit kills the ssh clients → sessions detach and keep running (they survive local reboots); relaunch re-runs the same command against the snapshot's persisted `sessionName` and reattaches. The pane's ssh is interactive (no BatchMode) so password/2FA prompts render in the pane, and connection failures surface on ghostty's abnormal-exit screen — ssh's own stderr is the error UI. Background ops (kill, the naming probe) use `BatchMode=yes -o ConnectTimeout=5` so they can never hang on a prompt; teardown routes through `ZmxClient.killRemoteSession` (a local kill of a remote name would silently no-op). Every busy-close guard (pane/tab close, unload/remove, CLI `busy` errors, quit rows) reads `Pane.needsConfirmClose`, not the surface's `needsConfirmQuit` directly — for a remote pane libghostty only sees the local `ssh` client, a perpetually "running program", so an idle remote prompt would always stage the kill-confirmation dialog. The remote verdict comes from the signals we do have (execution state, else the probe-derived foreground name — a shell at its prompt is idle), falling back to the conservative surface reading only while no probe result has ever landed.

**Dropped connections self-heal (#281).** When the network drops (lid close, wifi change), every remote pane's `ssh` dies and libghostty leaves its abnormal-exit overlay up while the remote zmx session lives on — before #281 the only cure was quit-and-relaunch. Now `AppState.reconnectDroppedRemotePanes` respawns a dropped pane's surface in place: `Pane.destroySurface()` (never `killPersistentSession` — the session is the reattach target) then `requestSurfaceReattach()`, which re-runs the same `ssh … exec zmx attach <sessionName>` and zmx replays scrollback into the new surface — per pane, exactly what relaunch does. Detection is `Pane.isDisconnected` (`isRemote && processExited`), read at trigger time; `GHOSTTY_ACTION_SHOW_CHILD_EXITED` is handled log-only and still `return false`s so the core renders its own message/overlay. **How a pane gets to sit in that state is the second half of the fix**: ghostty's overlay only appears for a child that died within `abnormal-command-exit-runtime` (~250ms — spawn failures); a LONG-running ssh that dies requests `close_surface`, which used to close the pane *and kill its session* — so a wake-time ssh death destroyed the remote work the moment the network returned. `AppState.handleProcessExit` (the `onProcessExit` route for the main window) now decides: local panes close as always; a remote pane's exit is classified by asking the HOST (one BatchMode stamp-then-list, reusing `sweepRemoteOrphans`) — session gone → deliberate end (typed `exit`) → close; session alive or host unreachable → drop → keep the pane. **Never by exit code**: measured on macOS it is always 0, even for an ssh that exited 255 (ghostty's own Surface.zig notes Darwin exit-code detection doesn't work). With `backgroundSSHConnections` off, every remote exit keeps the pane (no probe allowed; a kept pane costs a manual close, a wrong close costs the session). Background remote ops also now exec PATH-resolved `ssh` via `/usr/bin/env` — the pane's own ssh is PATH-resolved, so ops must dial the same client (also what lets the e2e harness's ssh shim cover them; OpenSSH resolves `~/.ssh/config` via the user record, not `$HOME`, so a hermetic config is only reachable through PATH). **Triggers only, never a timer**: system wake (a bounded delay burst, because wifi isn't up at wake and a frontmost app never gets an activation), app activation, and project selection — with per-pane escalating backoff and a survival-judged streak reset in `RemoteReconnectPolicy` (a dial can hang in TCP connect ~75s looking alive, so "alive" only clears the streak after `recoveryGrace`). A respawn must not retype the pane's layout `run:` command into a session already running it, so `Pane.ensureNSView` passes `command` only on the FIRST surface build (`hasBuiltSurface`) — the same contract as snapshot restore. The toggle is Settings → General → Remote Projects (`Preferences.reconnectRemotePanes`, default on; off exists for Touch ID-gated hosts, #272 — a wake with N dead panes is N prompts). Local panes are structurally out: no network to lose, and a normal local child exit closes the pane via `close_surface`. There is deliberately **no user-facing or CLI reconnect verb** — reconnect is automatic or nothing; the e2e suite drives the real `.projectSelected` trigger instead (`project select` away and back), against an unreachable-host project everywhere and against a Docker sshd+zmx container where docker is available (`e2e/test_remote_reconnect.py` — the container test also proves the full reattach+replay round trip).

**Remote orphans are reaped with an ownership label (#281).** `killRemoteSession` is best-effort `BatchMode` — closing a pane, unloading/removing a project, or a layout apply while the host is unreachable silently leaves the session running with nobody tracking it. On project selection (throttled per destination, ≥10 min) `AppState.sweepOrphanSessions` runs one stamp-then-list connection (`RemoteSpawn.orphanSweepArgv`): re-assert `macterm.owner=<Preferences.installationID>` on every session our panes claim, then `zmx ls`, and kill only sessions that are `macterm-*`, zero-client, unclaimed by any pane, **and carry OUR stamp** (`ZmxReaper.orphans(in:known:owner:)`). The stamp half only ever names sessions we pass in, which is the whole safety argument on a shared host — another machine's sessions are structurally unreachable. Three traps encoded here: zmx labels are in-memory and settable only on a LIVE session (no `attach --label`), so a session orphaned before it was ever stamped is spared **forever** — the accepted residual gap; `zmx ls --where k=v` is in zmx's help but silently unimplemented (the arg loop parses only `--short`), so it would list *everything* — never filter host-side; and both reapers (this and the local launch reap) infer "unclaimed" from the restored snapshot, so **both skip entirely when `WorkspaceStore.loadFailed`** — an empty claim set would mark every live session an orphan. The remote half also sits behind `backgroundSSHConnections` (#272), and the local reap now reruns on the same throttled trigger instead of launch-only.

**Design rule, earned the hard way: the spawn script may depend only on inputs Macterm controls — its own preamble and the project's config — never on the host's dotfiles.** The user's environment gets full effect in the right place instead: *inside* the zmx session, where their login shell starts normally (an `exec zsh` in `~/.profile` is legitimate user config for managed hosts — it just must never run in our plumbing). Do not reintroduce profile sourcing as an "improvement"; a regression test (`remote_scripts_never_source_profiles`) enforces this.

**Wire format (`RemoteSpawn`, hard-won against a real host):** every remote command ships as `sh -c '<single-quote-free script>'`. `sh -c`, NOT `sh -lc` — the login flag is unportable (older dash, common as `/bin/sh`, rejects `-l` and silently drops to an interactive shell that ignores the command). The single-quote-free script is the one form bash/zsh/fish/nu all tokenize identically before POSIX `sh` takes over. **PATH:** sshd runs commands with a bare non-interactive PATH, so the script appends a fallback dir list (`~/bin`, `~/.local/bin`, `~/.cargo/bin`, `/usr/local/bin`, `/opt/homebrew/bin`). Profiles (`/etc/profile`, `~/.profile`) are **deliberately never sourced, in any form** — they're arbitrary code in the pane's critical path, and every containment attempt leaked a pane-killer, each observed on a real or harness host: inline sourcing let a `~/.profile` ending in `exec zsh` hijack the script (fds→/dev/null: visible prompt via ZLE's /dev/tty, visible keystrokes via kernel pty echo, invisible output, no attach); a subshell harvest let the exec'd shell inherit the pane's tty stdin and block forever reading keystrokes; adding `</dev/null` still spun forever on a profile exec'ing a login shell that re-reads the same profile. The dir list covers where zmx actually lives; `zmxPath` covers everything else. **`zmxPath` escape hatch:** PATH resolution still can't cover every host (network-mounted home, exotic `/bin/sh`, PATH set only in a non-POSIX shell config), so a `Project.zmxPath` (optional, in the sheet + `projects.json` + `ProjectFile`) is used verbatim, bypassing PATH entirely and skipping the presence guard. **Failure visibility:** when zmx isn't found (PATH mode) or the `cd` fails, the script prints a `macterm:` diagnostic and drops to `${SHELL:-/bin/sh}` instead of exiting — a bare exit would fire `closeSurface` and vanish the pane with no clue why. **TERM is settled against the terminfo DB the remote actually has**, host-side, by the pane script — and **a TERM the host can already resolve is never touched**, including a coarser one the user pinned themselves. Only an unusable arriving TERM is replaced: `xterm-ghostty` when the host has that entry, else `xterm-256color`, because a TERM with no entry makes TUIs refuse to start. That precedence is load-bearing and inverting it is a regression that looks like its opposite: an earlier revision *preferred* `xterm-ghostty` whenever the host had it, overriding a `SetEnv TERM=xterm-256color` pin in `~/.ssh/config`, and a stock Debian host's prompt went **monochrome** — its default `~/.bashrc` gates color on `case "$TERM" in xterm-color|*-256color)`, which `xterm-ghostty` matches neither of, so the *more* capable terminal (that entry adds `Tc`; both report 256 colors) drew the *plainer* prompt. Capability and dotfile heuristics are different things, and a pinned TERM is a decision the user already made about both. `RemoteTerminfo` still unlocks full capabilities, the honest way: with the entry installed, the TERM ssh forwards *naturally* becomes resolvable, so it is kept rather than downgraded — no override needed. Deciding it host-side at all is the deliberate divergence from `ghostty +ssh`, which forces `-o SetEnv=TERM=xterm-ghostty` from the client because its wrapper has no remote-side script to work with: reading the remote DB directly needs no guess about the host, no cache that can disagree with reality, and it works where env requests are dropped. (Verified un-confounded on a real host: zmx renders fine under `TERM=xterm-ghostty` — an earlier contrary finding was an artifact of the profile-hijack bug above.) **`COLORTERM=truecolor` is exported by the script itself**, because that fallback only ever *downgrades* TERM and nothing else carries the signal: libghostty sets `COLORTERM=truecolor` in every pane's pty env, but **`TERM` is the only variable ssh carries by a channel a server can't refuse** — it rides the *pty request* (and OpenSSH ≥8.7 lets `SetEnv` override the value put there), while every other variable is an `env` channel request the server filters. Don't read that as "`SetEnv` works": the same flag succeeds or vanishes depending only on which variable it names. Measured on a real host behind **Tailscale SSH** — `tailscaled be-child ssh` serves the session, so the host's `AcceptEnv COLORTERM` is a red herring it never consults — `-o SetEnv=TERM=xterm-ghostty` arrived while `-o SetEnv=COLORTERM=truecolor`, `-o SendEnv=COLORTERM`, and a control `-o SetEnv=FOO=bar` all arrived empty. So a host lacking the ghostty terminfo entry — or one whose `~/.ssh/config` pins `SetEnv TERM=xterm-256color`, which beats our forwarded TERM — had no truecolor signal at all, and helix refused truecolor themes outright ("Unsupported theme: theme requires true color support"). Ghostty.app never hits this by a route we structurally can't take: its shell-integration `ssh` wrapper hands the connection to `ghostty +ssh`, which installs `xterm-ghostty` on the host and forces `-o SetEnv=TERM=xterm-ghostty` (that entry declares `Tc`), whereas a Macterm pane command **is** the surface command, spawned with no shell in front of it, so no wrapper can run. Only newly created sessions pick the variable up — `zmx attach` hands its env to the shell it *creates*, so pre-existing sessions keep the old environment until killed.

**`RemoteTerminfo` installs our own `xterm-ghostty` entry on a host, natively — no ghostty binary.** This is the piece of `ghostty +ssh` worth having, reimplemented rather than delegated: Macterm ships no `ghostty` CLI, so calling `+ssh` would make remote projects work only where Ghostty.app is also installed *and* new enough, and would put a foreign auto-updating binary in the pane's spawn path where a failed init fires `closeSurface`. All three pieces were already to hand — our bundled compiled entry, macOS's own `/usr/bin/infocmp`, and `tic` on the far side — so it is `infocmp -x xterm-ghostty` piped to a remote `sh -c 'tic -x -'`. Rules worth keeping: the source is **our** bundled DB (`GhosttyApp.bundledTerminfoDirectory`, derived the same way libghostty derives `TERMINFO` so both move together), never an installed Ghostty.app's, because `TERM=xterm-ghostty` on the remote is a promise about what *our* pinned libghostty supports; `RemoteTerminfo.entryName` is shared with the preamble so the installed entry and the one the script looks for can't drift (a test pins this). Three divergences from ghostty's implementation, all following from remote panes having no shell wrapper in front of the command: the install runs **off the critical path** as a fire-and-forget `BatchMode` op instead of synchronously inside the wrapper on the pane's own `ControlMaster` connection — so no `tic`, an unwritable terminfo dir, or interactive-only auth (a `BatchMode` op cannot answer a prompt) costs the pane nothing, since `COLORTERM` already guarantees truecolor without it; the result is **never cached to disk**, because the preamble asks the host what it has at attach time, so the in-memory `attempted` set exists only to stop one app run re-writing a host's terminfo on every pane spawn (a failure stays recorded — retrying would mean an ssh connection per pane to a host that already said no; next launch tries again); and stderr is **captured and logged on failure only**, since it is the sole account of why an install failed and nobody is watching (a *successful* `tic` still chatters about the description field). Gated on the user's own `ssh-terminfo` flag via `ShellIntegrationFeatures.isEnabled`, which reads their **raw** ghostty config, not the effective post-override value: the overrides re-emit that key to force plumbing flags (`no-path`), and an intent flag like `ssh-terminfo` must never be coupled to whatever plumbing Macterm forces alongside it. ghostty ships that flag **off** (`ghostty +show-config --default` → `cursor,no-sudo,title,no-ssh-env,no-ssh-terminfo,path`, which is why `featureDefaults` is a per-flag table and not a blanket `false`) — writing files onto someone's server is not a thing to start doing unasked, and reusing their existing flag keeps a ghostty-shaped setting out of Macterm's own preferences.

Constraints, all deliberate: zmx must be preinstalled on the host (set `zmxPath` if it's not on the non-interactive PATH); port/identity/ControlMaster/IPv6 come from `~/.ssh/config` aliases, never Macterm flags; the remote orphan sweep only ever kills sessions carrying our own ownership stamp (zero-client `macterm-*` sessions on a shared host legitimately belong to other machines — see the sweep paragraph above); local-cwd features (Replace Project Path with Current Dir, live cwd and `shell:` capture on Save Layout) are disabled for remote panes — live `run:` capture works, answered from the foreground probe's ~3s cache rather than a fresh ssh; declared layout `cwd`/`~` resolve remote-side as pure strings (`LayoutBuilder.resolveCwd`). Tested against loopback, a Docker Linux harness (nushell login shell, dash `/bin/sh`, zmx in `~/bin`, exec-ing `~/.profile` — Dockerfile preserved in PR #138's appendix), and a real CMU AFS host, which found four bugs the green environments couldn't.

### Pinned Tabs

Tabs that belong to no project, shown as flat top-level sidebar rows above the projects (pin icon). Under the hood they are a **sentinel workspace** — `workspaces[PinnedTabs.projectID]`, a fixed UUID that is deliberately NOT a `ProjectStore` row, so everything that iterates real projects (Settings → Projects, palette project source, CLI `project list`, layout save/apply) never sees it by construction; the narrower `activeProjectID → Project` call sites render it through the synthetic `PinnedTabs.project`. Each pinned tab is a `PinnedTabRecord` (`AppState.pinnedRecords`, ordered): a durable **declaration** (`LayoutTab` — splits + per-pane cwd/run/shell, every leaf cwd self-contained: absolute/`~`/scp-spec, so one pinned set can mix local and remote panes) plus, while loaded, an ordinary live `TerminalTab` in the sentinel workspace. All pinned logic lives in `AppState+PinnedTabs.swift`.

The rules: **Pin/Unpin are moves, never kills** — pin = `moveTab` into the sentinel (declaration captured via `LayoutSerializer.pinnedDeclaration`, origin project stamped), unpin = `moveTab` back to the origin (`moveTab` itself routes a pinned destination through `pinTab` and drops the record on the way out, so every drag/menu path is a plain `moveTab`). A tab created *inside* the pinned workspace (CLI `tab new`, separated pane, merge) is pinned from birth — `saveWorkspaces` runs `syncPinnedRecordsWithWorkspace`, which records any live tab it doesn't know. **Closing a pinned tab is an UNLOAD, never a removal** (`closeTab` routes pinned to `unloadPinnedTab`; last-pane `closePane`, bulk deletes, and CLI `tab close` all land there): sessions end, the record — and its `pinned.yaml` entry — stays as a dimmed row, and the next launch eager-starts it again; Unpin is the removal path. The pinned workspace stays guarded out of `unloadProject`/`removeProject`. The same unload happens when a tab's own sessions die — `paneProcessExited` (the surface's process-exit callback, now distinct from the user's close request: `WorkspaceView` wires `onClosePane` to it) **unloads** the last-dead-pane tab: surfaces torn down, record kept as a dimmed sidebar row. Selecting an unloaded row rebuilds the tab from its declaration via a pure-spawn `LayoutReconciler.plan`, re-running its `run:` commands — the whole point of pinning. **The dimmed row is a shared treatment, not a pinned-only one**: `unloadProject` marks the project in `AppState.unloadedProjectIDs` and the sidebar dims its tab rows the same way, since they are equally a layout with no shells behind them. That mark is in-memory on purpose (after a relaunch every project is lazy again unless `Preferences.restoreAllProjectsOnLaunch` is enabled, so a persisted mark would dim rows whose sessions are merely detached), and it clears in `activeProjectID`'s `didSet` rather than in `selectProject` — becoming active IS the reload in the default lazy mode, since `warmFocusedProject` only ever spawns the focused project's shells; the launch preference instead warms every restored workspace without changing selection, while `SidebarPresentationState.restoreExpansionOnce` reveals every restored project without reopening groups the user later collapses. The declaration is deliberately NOT refreshed at unload (a dead pane reads idle, which would erase the `run:`); it refreshes at pin time, whenever the poll sees a pinned pane's foreground change — a command starting or ending re-captures the declaration and persists both layers, debounced ~2s (`notePinnedForegroundChangesIfNeeded`) — and once more at quit (`persistForTermination`).

Persistence is two layers. **Live state**: a `pinned` section in `workspaces_v3.json` (schema v5 — the bump is what makes a downgrade refuse-to-save instead of silently dropping pinned tabs), each record with its declaration plus, when loaded, a normal `TabSnapshot` whose session names reattach. At launch, **every record materializes into a running tab** (pinned tabs are eager — they exist to keep things running; ordinary projects stay lazy by default, while `Preferences.restoreAllProjectsOnLaunch` opts them into one globally staggered warm batch): `zmx attach` is an upsert, so `materializeRestoredPinnedTabs` first asks `zmx ls` which sessions actually survived — survivors reattach their snapshots, dead ones (and declaration-only records, including hand-added file entries) respawn from the declaration, re-running their `run:`; tabs with any remote pane, and a failed listing, reattach conservatively (fail toward reattach, never toward respawning over sessions that may be alive); the launch orphan reaper's `known` set includes the still-pending session names, and surfaces warm through the injectable `warmPane` seam (incubator), staggered like `warmFocusedProject`. The unloaded (dimmed) row state therefore arises only mid-session, when a tab's own sessions die — deliberately lazy there (eager respawn at the moment of death is a crash loop for a `run:` that exits immediately); selection restores it. Keyboard navigation treats the pinned rows as a project: in-project next/previous cycles the RECORDS (restoring an unloaded row on landing, `cyclePinnedTab`), and global next/previous walks pinned records first, then every project's tabs. **Declaration**: `pinned.yaml` in the layouts directory — the one auto-written file there (a deliberate divergence from "files are written only on explicit Save Layout"), rewritten on membership changes and refreshed at quit, a real `ProjectFile` whose reserved `path: <pinned>` is the marker (safe by construction — angle brackets are illegal in hostnames, a local path starts `/` or `~`, and `ProjectPath.parse` rejects the literal, so it can never match a project), with NO per-entry ids — a UUID on every entry was hostile to the hand-editing the file exists for, so entries match back to records by name → exact layout → position (`PinnedLayoutMatcher`, mirroring `LayoutReconciler.matchTab`; the positional pass refuses name-contradicting pairs, or a remove+add would silently convert into an "edit" that keeps a session the user meant to unpin — and a mismatch is non-destructive by construction anyway, since a live tab is at worst unpinned, never killed; a `name:` makes heavy hand-edits unambiguous). It is the ONLY two-writer file in the app, so `AppState` tracks the exact text of its own last write and **absorbs external edits before every write, never clobbers**: additions become unloaded records, edits update declarations (they take effect at the next restore), removals of unloaded records are honored; removals of LIVE tabs are honored at launch only (`reconcilePinnedLayoutAtLaunch`, where a project list exists to move them into — as an unpin, not a kill). An absent or empty file reads as "no external input", never "remove everything" (editor truncate-then-write saves); an unparseable file (or one missing the marker) **suspends auto-writes** with an alert so a mid-edit typo can't be overwritten. The filename is reserved: `ProjectFileStore.write` never binds or realign-deletes it and a project named "Pinned" collides into `pinned_2.yaml`; `listAll` hides it from Settings → Layouts. Because the layouts dir is shared user config, the pinned SET is user-level (both build flavors converge on it via the launch reconcile) while live sessions stay per-flavor.

Sidebar drag mechanics: pinned rows and project tab lists share the SAME native mechanism — a ForEach-level `.dropDestination` whose insertion offset drives the native insertion line; a drop pins/reorders/moves/separates at that slot, and rows carry NO destinations of their own (a row-level target claims the drag before the ForEach's mechanism sees it and kills the line — and a row-level `.onDrop` additionally swallows left clicks, measured live). The pinned ForEach is wrapped in a headerless `Section` so it sits inside a container like the tab ForEach (a `.dropDestination` on a BARE top-level ForEach crashes the outline accept, per the notes in `SidebarContent.body`). Dragging a pinned row into a project section unpins it. The always-available target is `PinTabDropZone` — a thin strip in a `safeAreaInset` ABOVE the List (outside the outline machinery entirely, so none of its drop hazards apply) that pins at the first slot; it keeps a nonzero idle height because `isTargeted` can't fire on a zero-height view. It expands into a labeled "Pin Tab" band while a drag hovers it ONLY when there are no pinned rows yet: with a row present the List's native insertion line already marks that slot, so the band merely doubled it — the strip is silent there and the line is the affordance. It is what makes the FIRST pin possible by drag; the tab context menu / palette / `Pin Tab` command (`AppCommand.pinTab`/`.unpinTab`, unbound by default) are the pointer-free paths. Global tab cycling includes pinned tabs first; `--project pinned` (or the sentinel UUID) addresses the workspace over the control CLI.

### Control CLI (`macterm`)

A bundled CLI (issue #107) controls the running app over a Unix socket at `<App Support>/control.sock` (per build flavor; `MACTERM_BENCHMARK_DATA_DIR` relocates it with the rest of app data). Full grammar + protocol reference in the docs site (`website/docs/pages/80-cli.md` → published at `/docs/cli`). Built as the `MactermCLI` tool target — `PRODUCT_NAME` is `macterm` but `PRODUCT_MODULE_NAME` must stay `MactermCLI` (a `macterm` module would collide case-insensitively with the app's `Macterm.swiftmodule` in the shared products dir). A post-build script copies it to `Contents/Resources/bin/macterm`; the app prepends that dir to `PATH` and exports `MACTERM_SOCKET` before any shell spawns, so `macterm` works inside every pane. Verbs: `status`; `project list/create/select`; `tab list/new/select/move/rename/close`; `pane list/inspect/dump/split/focus/close/run/key/zoom/resize-split`; `grid RxC`; `session list/info/kill`; `layout apply/save`; `ssh` (the one **offline** verb — no socket, no app needed: ghostty's `+ssh` natively, see `SSHWrapper`). New panes/tabs take `--run CMD` (spawn-time `initial_input`, the layout `run:` path); `pane run` types into an *existing* live shell via `GhosttyTerminalNSView.sendText` (the paste path — `ghostty_surface_key` with `.text`). `pane key <chord>` sends a single encoded keypress via `GhosttyTerminalNSView.sendKey` (`ghostty_surface_key` with a keycode+mods), reusing `HotkeyRegistry.parseShortcut`'s chord grammar. **A printable character comes only from the event's `.text`** — libghostty's encoder derives control bytes (`ctrl+c`) and named keys (`escape`, `up`) from keycode+mods, but a keycode-only event for a bare letter encodes to *nothing* and vanishes with the verb still reporting success, which is what `pane key a` did until `sendKey` started attaching text. That text is resolved from the chord's own token via `HotkeyRegistry.printableText` (US-ANSI, matching the `keyCodes` table the grammar already assumes) rather than from the active keyboard layout, so `pane key a` types `a` on any layout; it rides the PRESS only (a release carrying it would double-type under a protocol that reports releases), consumes Shift the way `keyDown` consumes its translation mods, and records command-submission evidence so a following `pane key return` reads as a real submission. Ctrl/Cmd/**Option** chords stay text-free: ctrl encodes from `unshifted_codepoint`, cmd is never forwarded, and Option's character is a layout translation with no NSEvent to read it from — `pane run` is the answer when the literal text is what's wanted. **This bypasses `keyDown` entirely** (that's how it emits raw control bytes), so any interception living in `keyDown` — e.g. the Ctrl-\ swallow guard — does *not* apply to `pane key`; the two key-input paths don't share a gate. `pane inspect`/`dump` are read-only introspection over libghostty's own state (`ghostty_surface_size`, the scrollbar snapshot, `ghostty_surface_read_text`) for debugging reflow/scrollback (#165); `zoom`/`resize-split` expose the zoom keybind + an absolute split-ratio setter as verbs (#166). `pane resize --cols --rows` is a **debug-only** in-place `set_size` for isolated reflow repro (#167) — gated `#if DEBUG` in both `ControlHandler`'s dispatch and the CLI, so a release app answers `unknown_command`. `project create` accepts remote specs (stored verbatim, no existence check — the pane is the error UI, #281 unlocked this for the reconnect e2e). Every pane's env carries `MACTERM_SESSION` (its restart-stable session name) so a bare `macterm pane split` inside a pane self-targets; close verbs demand explicit targets and return a typed `busy` error instead of staging UI confirmation dialogs (headless callers can't click).

- **Wire protocol** (`ControlProtocol.swift`, compiled into both targets so the codec can't drift): one request per connection; newline-terminated JSON both ways; client half-closes after sending. Requests are `{v, id, command, args}` with `command` namespaced `noun.verb` (`pane.list`); responses echo `id` with `{ok, data}` or `{ok:false, error:{code, message, action?}}` — `action` is a human recovery hint. Errors use snake_case codes (`not_found`, `busy`, `no_surface`, `starting`…).
- **Server** (`ControlSocketServer`): dedicated thread polling a non-blocking listen fd (20ms) — never a blocking `accept()` on a queue shared with `stop()`, which would starve shutdown. Per-connection dispatch hops to `@MainActor`. Starts in `applicationDidFinishLaunching` (skipped under xctest); the handler attaches later in `installResponders` when AppState exists — early requests get a `starting` error. `FD_CLOEXEC` on the listen fd so spawned shells can't hold the socket past quit.
- **Handler** (`ControlHandler`): translate-and-delegate only — resolves selectors (name/UUID/1-based index for projects and tabs; conflicts and dupes are typed `ambiguous` errors) and calls the same `AppState`/`ProjectStore`/`ZmxClient` methods the UI uses. Reads zmx through `appState.zmx` so tests stub one seam.
- **CLI client**: discovery order `--socket` (hard pin) → `MACTERM_SOCKET` (hint only — falls through to the well-known release/debug paths when stale, avoiding cmux's pinned-env trap) → per-flavor App Support paths. Refuses sockets not owned by the current user; non-blocking connect with a 250ms poll so a dead socket never hangs. Safe-fail contract: stdout only on success; exit 0 ok / 1 app error / 2 unreachable.
- Security posture: same-user only, enforced by filesystem permissions (0600 socket, 0700 dir) — the same boundary zmx itself uses. No token auth by design; the request envelope leaves room for an `auth` field if that ever changes.

### Ghostty Config Pipeline

Automatic mode delegates the default user layer to `ghostty_config_load_default_files`, so the pinned libghostty owns the filesystem rules: XDG loads before macOS Application Support, and legacy `config` loads before current `config.ghostty` within a directory, so later files win. Ghostty also owns duplicate warnings, non-empty-file preference for the edit target, and first-run template creation at `~/Library/Application Support/com.mitchellh.ghostty/config.ghostty`. Settings shows detected default files under an opt-out toggle, including the resolved target when a location is symlinked, and can append zero or more custom files. Loading retains the checked path and lets file opening follow the symlink, matching Ghostty and preserving the checked directory as the base for relative `config-file` paths. The custom files load in their displayed order after the defaults. The user is the source of truth for every ghostty setting. `MactermConfig.regenerate()` writes two private files in App Support, and `GhosttyApp.loadConfig` loads `defaults → user's config files → overrides` (libghostty does last-wins merge):

`GhosttyConfigSource` is the matching raw-text seam for features whose values the C API cannot expose or whose user-stated value matters. It concatenates readable default root files in Ghostty order (XDG `config`, XDG `config.ghostty`, Application Support `config`, Application Support `config.ghostty`), followed by the custom files in Settings order. Recursive `config-file` includes are loaded by libghostty at runtime but remain outside those raw-text scans.

- **`macterm-defaults.conf`** — first-launch tasteful defaults; anything in the user's config overrides them.
- **`macterm-overrides.conf`** — keys Macterm must lock: `background-default-transparent = true` (fork patch 0004 — the renderer never paints the *default* background, so `WindowAppearance` composites translucency itself without double-tinting; the same renderer mechanism ghostty's macOS glass styles use, exposed as a config key), `background-opacity = <Preferences.windowOpacity>` (the REAL opacity, not a pinned 0 — that's what lets the user's own `background-opacity-cells` flag work as ghostty documents it, making TUI-painted cell backgrounds translucent at the window opacity; under the old `background-opacity = 0` pin that flag multiplied every painted cell to invisible. `Preferences.windowOpacity` keeps it current via a debounced regenerate+reload — the instant window resync stays on the cheap no-reload path), `background-blur = 0` (Macterm calls the CGS blur SPI itself), plus `env = GHOSTTY_BIN_DIR=<bundle>/Contents/Resources/ssh-bridge` and a `shell-integration-features` line forcing `no-path`. The shell-integration `ssh` wrapper execs `"$GHOSTTY_BIN_DIR/ghostty" +ssh`, and that dir holds Macterm's own `ghostty` shim (`scripts/ghostty-shim.sh`, installed by the "Bundle macterm CLI" post-build step), which relays to `macterm ssh` — so `ssh-env`/`ssh-terminfo` work with **no Ghostty.app installed** and are never forced off (only if the shim is missing from the bundle — a broken build — are they, so the wrapper falls through to plain `ssh` instead of dying on a bad exec). The shim lives in its own dir, NOT `Resources/bin` or `Contents/MacOS`, because both land on pane PATHs (`EnvironmentSetup` prepends bin; libghostty unconditionally appends the exe dir) and a `ghostty` that only answers `+ssh` must never be reachable by name — which is also why `no-path` is always forced (that feature's only effect is putting `GHOSTTY_BIN_DIR` on PATH). The features key can't be written bare — libghostty re-parses it from defaults on every occurrence, wiping the user's own flags — so `ShellIntegrationFeatures.overrideValue` re-emits the user's effective value with our `no-*` flags appended (#75). Because the override depends on the user's config content, `loadConfig` calls `regenerate()` before every load.

Macterm-specific UI state (window opacity/blur, quick terminal, hotkeys, auto-tile) lives in `Preferences` and never touches the ghostty config pipeline.

### Bundled Ghostty Resources (standalone operation)

Macterm bundles ghostty's runtime resources so it runs without a Ghostty.app install, **mirroring a real Ghostty.app layout**: `Contents/Resources/ghostty/{themes,shell-integration}` with the compiled terminfo DB at the _sibling_ `Contents/Resources/terminfo/`. `setup.sh` downloads the tarball from the `thdxg/ghostty` release; `project.yml` folder-references it into the bundle. `GhosttyApp.resolveResources()` points `GHOSTTY_RESOURCES_DIR` at `Contents/Resources/ghostty`, always resolving from our own candidates and ignoring any inherited env value (a stale one would shadow our complete bundle). Selection logic is the pure, tested `GhosttyResourceResolver`.

Two non-obvious terminfo facts (the regression behind #39/#40 — broken `TERM=xterm-ghostty` and key input):

- **Never set TERMINFO ourselves.** At shell spawn libghostty _unconditionally overwrites_ `TERMINFO` with `dirname(GHOSTTY_RESOURCES_DIR)/terminfo`, so the bundle layout must make that derivation land on the dir we ship — terminfo MUST be a sibling of `ghostty/`, never inside it. `BundledResourcesTests` asserts this invariant.
- **The terminfo tree uses the macOS hashed layout** — `terminfo/78/xterm-ghostty` (`x` = 0x78), not `terminfo/x/...`. It's a `tic -x` compiled tree shipped verbatim.

### Tests (`MactermTests/`)

One `XxxTests.swift` per production type, mirroring the source path. `@testable import Macterm` + `@MainActor` on test classes.

- Shared helpers in `MactermTests/Support/`: `TreeBuilder` DSL (`H(pane("a"), V(pane("b"), pane("c")))` → tree + name map) and `TreeRenderer` (inverse, for readable assertions).
- Tests needing `AppState`/`WorkspaceStore` inject a tempdir file — never touch `~/Library/Application Support/`.
- Tests run hosted inside the debug app, so `UserDefaults.standard` there is the developer's real debug-app domain. `Preferences.defaults` detects a test run (XCTest env vars) and resolves to a wiped `.tests` side suite instead, and everything that persists defaults (`Preferences.shared`, project recency, hotkey overrides) goes through it — so writes, including indirect ones like `AppState.activeProjectID`'s write-through, never leak out of the run (`PreferencesTests` guards this). Never use `UserDefaults.standard` directly in app code.
- UI (SwiftUI views, AppKit surfaces, libghostty bindings) is not unit-tested; coverage targets model + persistence + palette/hotkey logic and pure helpers.
- `BundledResourcesTests` is an artifact check: it asserts `Macterm/Resources/` ships what libghostty needs (#39/#40 guard) and `#require`-skips on a fresh checkout before setup has run.

## Conventions

### Code Style

- **SwiftFormat** + **SwiftLint** enforced. Run `mise run format`, `lint`, and `test` before committing.
- `@MainActor @Observable` on all state classes. No `@Published`/`ObservableObject`; inject via `@Environment(AppState.self)`, not `@EnvironmentObject`.

### Commit Conventions

- **Never add a `Co-Authored-By: Claude` trailer or any AI sign-off.** Commits are authored by the human committer only.
- Subject line focuses on the "why". Split logically independent changes into separate commits.
- **PRs merge via squash only** — make the PR title a good squash subject. When a PR conflicts, merge `main` into the branch; never rebase the branch onto `main`.

### UI Principles

- **Always use native SwiftUI/AppKit components.** Never mimic native behavior with custom implementations. If a native component has a limitation, accept it rather than building a workaround.
- All colors come from `MactermTheme` (derived from the ghostty theme config). No hardcoded colors.
- Minimum target is macOS 14; the liquid glass appearance is a macOS 26 (Tahoe) enhancement, gated so older systems fall back to native materials/blur. Gate any new Tahoe-only API behind `#available(macOS 26.0, *)` and, for user-facing controls, `WindowAppearance.glassSupported`.
- **Overlay-sidebar spacing and blur are separate layers.** The transparent top `safeAreaBar` reserves titlebar space; `SidebarTopBlurBar` must stay above scrolling rows and remain non-interactive. `scrollEdgeEffectStyle` alone does not create visible top blur outside the native split-view sidebar.

### Terminal Surface Rules

- Never tear down the NSView from a SwiftUI path (`dismantleNSView` is a no-op by design).
- `pane.destroySurface()` kills the shell process — only call when a pane is permanently closed (AppState handles this after the pane leaves the tree).
- `createSurface()` needs a non-zero frame and a window; `TerminalSurface` defers creation until attached. A `Pane`'s `command`/`shell`/`env` (from a declarative layout) map to libghostty's `initial_input`/`command`/`env_vars`.
- The `closeSurface` callback fires asynchronously — guard against double-close.
- First-responder handoff after reshapes/tab switches must go through `FocusRestoration.restoreFocus(...)` — a bare `makeFirstResponder` races the NSView's window attachment.
- **Anything that must take mouse input over a pane needs an AppKit view of its own.** `GhosttyTerminalNSView` handles `mouseDown` itself and wins AppKit hit testing, so a SwiftUI gesture layered over a pane never sees the press — which is why the pane grab handle (`PaneDragSource`) and the split divider's grab band (`SplitResizeBand`, #260) are both `NSViewRepresentable`s. Before that band, the divider's SwiftUI `DragGesture` was reachable only in the 1pt gap *between* the two panes, which is exactly how "you have to be very precise to resize" got reported. A SwiftUI overlay is fine only where it takes no clicks (the unfocused-pane dim, which is `allowsHitTesting(false)`). Such a view sits ON a pane, so it must hand back what it doesn't own: the band claims the left button and forwards scroll/right/middle events to `viewBeneath`, because the responder chain runs up through its ancestors and never across to the sibling it covers.

### Persistence

- Workspaces → `~/Library/Application Support/Macterm/workspaces_v3.json`; projects → `projects.json`; wrapper configs (`macterm-defaults.conf`, `macterm-overrides.conf`) in the same directory. The directory name comes from `appDisplayName` (`CFBundleDisplayName`), so debug builds use `Macterm Debug/` — fully separate data per build, mirroring the bundle-ID split.
- `Pane` IDs are not preserved across restarts — restore creates fresh UUIDs. Session identity is separate: `Pane.sessionID`/`sessionName` persist in the snapshot (the name VERBATIM, never re-derived — its slug reflects the project at creation), so a restored pane reattaches its still-running zmx session.
- **A directory is not an identity — a path can back several projects.** `ProjectStore.create` always appends a fresh `Project` (its own `id`), so the folder picker, the New Remote Project sheet, and `macterm project create` add a distinct project even when one already backs that directory. `ProjectStore.findOrCreate` is the create-*or-select* variant kept only for idempotent callers (the benchmark's `open-project`); the CLI `project create` verb is deliberately **not** idempotent. Two same-path projects stay fully isolated: workspaces key on `Project.id`, and zmx session names carry per-*pane* hex (`macterm-<slug>-<hex>`) so their sessions never collide. The one shared resource is the layout file — see the matching bullet below.
- **Settings → Projects manages both lists without a terminal.** Projects: add (local folder / remote machine), and per row Apply Layout, Save Layout, Move Up/Down, Unload, Remove — all delegating to the same `AppState`/`ProjectStore` calls the sidebar uses, including the `request*` confirmations, so a busy pane still prompts. Both lists put their rows **directly in the `Form` section**, so each grows with its content and the Form's own scroll view carries the overflow. They used to be nested `List`s with a fixed `maxHeight`, which capped the pane at about six rows and stranded the rest: the Form's scroll view swallows an inner one's wheel events, so the inner list never scrolled. That's also why reordering is menu items rather than a drag — `.onMove` exists only on `List`. Layouts: **every** `*.yaml` in the directory (`ProjectFileStore.listAll`), not just the ones a project backs — surfacing an orphan declaration is the point, since it's invisible everywhere else; per row Create Project (adds a project for the file's `path:` and selects it, so first-open auto-applies) and Remove. The pane is the reason the `Settings` scene carries `.environment(appState)`/`.environment(projectStore)` and its own copies of the layout/unload/remove alerts — the originals hang off `MainWindow` and would fire on a window the user isn't looking at. **Those duplicated alerts must stay gated on `AppState.DialogHost`**: both scenes bind to the *same* pending value, and an ungated `isPresented` presents in both — SwiftUI materializes and fronts the settings window purely to show its copy, so an Apply Layout confirmation raised from the palette opened Settings with a second identical dialog stacked inside it. Every staging call therefore records the window that asked (`host:`, defaulting to `.mainWindow`; `.settings` only from the Projects pane) and each scene's binding reads only its own — thread the host through any new shared confirmation.
- Project declarations are _authorable_ YAML files in `~/.config/macterm/projects/` (`ProjectFile`/`ProjectFileStore`), normally one per project — two projects on one directory that also share a name-slug deliberately share a file (see below): top-level `name:` (display only), `path:` (required — the identity), optional `tabs:` layout. Applied/saved on demand via `applyLayout`/`saveLayout`. JSON schema at `assets/project.schema.json` — keep it in sync when layout types change.
  - **Files and the runtime project list are decoupled.** `projects.json` stays the source of truth for which projects exist; a file matters only when a project with a matching path is added, first-opened, or has Apply/Save Layout invoked. Files are written on exactly two events — explicit "Save Layout" (creates/rewrites, realigning the filename to the current name slug) and the user's own editor. Nothing else (add/remove/rename/reorder/setPath) touches them. The **one** path that deletes a file is Settings → Projects → Layouts → Remove (`ProjectFileStore.delete`, confirmed first, guarded to the projects directory) — `write`'s realign-delete only drops a file it has just superseded, so removing a project still never removes its declaration. No file watching: hand-edits made while running surface on next use (every read re-scans).
  - **Matching is by canonicalized `path:` inside the file** (`ProjectPath.matches`); a single declaration loads regardless of filename, so a hand-rename survives. When one directory backs several projects — all declaring the same `path:` — the project's name-slug is the tiebreaker that identifies its *own* file (`ProjectSlug.owns`; collisions get `_2` suffixes case-insensitively). So lookup, save realignment, and conflict detection key on path **and** slug: the slug is a per-project layout identity, not a cosmetic name. A save binds to the path-match its *own* slug owns before falling back to the first path-match no sibling owns, so an unowned stray declaring the same path is never realign-deleted. `path:` is scp-style: absolute/`~` = local, `[user@]host:dir` = remote (parsed by `ProjectPath`, groundwork for remote projects #104 — not yet openable). Canonicalization expands `~` and normalizes `.`/`..` but resolves neither symlinks nor case; writes contract the home prefix back to `~` (`ProjectPath.homeContracted`) so files survive a dotfiles sync across usernames. Genuine duplicates (two files the *same* project owns, e.g. a hand-authored copy or a failed realign-delete): first in filename order wins; the rest are surfaced (palette subtitle via `paletteSubtitle`, post-save conflict alert), never deleted. Two projects on one directory with the **same** name-slug do resolve to the same file — last Save Layout wins, and `AppState.presentSharedPathConflictIfNeeded` warns on exactly that pair. **Distinct** names get distinct slug files that each load independently, and a save leaves a sibling's file untouched (`write`'s `reservedSlugs`) instead of realign-deleting it.
  - The directory is shared across debug/release builds (user config, like the ghostty config — unlike App Support) and resolves `$HOME`-env-first (`ProjectPath.currentHome`) so the benchmark's throwaway `$HOME` isolates it — `NSHomeDirectory()`/`expandingTildeInPath` resolve via the user record and silently ignore the env var.
  - On relaunch the workspace snapshot always wins — it carries live session identity, and force-applying a declared layout would destroy reattachable shells. A file only seeds a genuine first open (no snapshot; pure-spawn, never destructive) via `autoApplyLayoutOnFirstOpen`.
  - An unparseable file surfaces `LayoutFileError` in an alert (`AppState.pendingLayoutError`) and is never applied; the lenient `ProjectFileHeader` decode keeps a file with a broken `tabs:` matched to its project so the error shows on apply instead of the file silently unmatching. A file with no/empty `tabs:` is a bare declaration: nothing to apply, and the palette shows "Apply Layout" muted (`PaletteItem.isEnabled`) with the reason; an invalid file keeps the command enabled so invoking it surfaces the dialog.
  - `save` records a pane's `run:` as its **live** foreground command (`ghostty_surface_foreground_pid` → `ProcessInspector` argv via `KERN_PROCARGS2`) — an idle prompt saves no `run`. `shell:` is recorded only when the pane sits in a _non-default_ shell. `run` and `shell` are mutually exclusive on a leaf.
  - `apply` (`LayoutReconciler`) matches live panes to declared ones by that same live `(run, cwd)`; a pane that quit its declared command is respawned. A plain-shell leaf matches an idle pane positionally, but a declared `shell:` only reuses an idle pane running that shell (basename compare). The live-command/live-shell lookups are injected closures (default `ProcessInspector`), so the logic is unit-testable. There is no name-mismatch prompt: `name:` drift after a project rename is expected (only Save Layout rewrites it).
  - **Removed (v1.22.0):** the in-repo `.macterm/layout.yaml` and its `assets/layout.schema.json`. It was deprecated in v1.20.0 when #137 centralized layouts, and until removal a committed file was imported into the central directory on first open *and* on an explicit Apply Layout. `LayoutFile` survives as the in-memory layout type only — it is reached exclusively through `ProjectFile.layoutFile` and has **no on-disk form of its own**, so don't reintroduce load/parse/serialize helpers on it (tests parse fixtures through `ProjectFile` via `MactermTests/Support/LayoutFixture`). Users with a stale in-repo file get no import and no warning — Save Layout recreates the declaration centrally.

### Adding a New Setting

Macterm-side settings flow through `Preferences` (UserDefaults); ghostty-shaped settings (theme, font, palette…) belong in the user's Ghostty config — don't add UI for them.

1. Add a property to `Preferences` with a `didSet` that writes to UserDefaults.

3. Add UI to the matching pane in `Macterm/Settings/`, binding to `Preferences.shared.x`. A whole new pane also needs a `SettingsPane` case (title + SF Symbol) and a line in `SettingsView.detail`.

Descriptions use the shared `.settingsCaption()` modifier — never restyle them inline, which is how one had already drifted to `.footnote`.

### Settings window

Sidebar-style (`NavigationSplitView`), matching the macOS System Settings shape. Two things about it are hard-won and easy to undo:

- **The sidebar is fixed-width and non-collapsible, and that needs AppKit.** `navigationSplitViewColumnWidth` and `columnVisibility` are documented *preferences* ("SwiftUI may use a different width for your column"), so `PinnedSidebar` reaches the `NSSplitViewItem` SwiftUI builds and sets `minimumThickness == maximumThickness`, `canCollapse = false`, `holdingPriority = .required`. That genuinely locks the column — but **not durably**: SwiftUI restores its own column metrics on events with no hook to answer (a window move fires neither `didResizeNotification` nor `updateNSView`), and until the next re-assert the drag affordance is back and the column can collapse. So a `DividerShield` sibling view sits over the divider and takes the mouse before AppKit sees it; that survives any reset. Both layers are load-bearing — dropping either brings the handle back. Two alternatives are already ruled out: the split view's delegate owns the divider's effective rect but AppKit **raises** rather than let a controller-managed delegate be replaced (this crashes the app), and a plain non-`.sidebar` item drops the affordance but moves the pane title off the detail column, which `NSTrackingSeparatorToolbarItem` does not restore.
- **The window carries an empty `NSToolbar`.** Not decoration — having a toolbar at all is what makes AppKit lay out the roomier titlebar and inset the traffic lights to match the main window (~23pt vs ~16pt without). `.unified`, not `.unifiedCompact`, which shrinks it back.

### Main-window sidebar width

**Macterm persists it (`Preferences.sidebarWidth`) and restores it through AppKit, because both SwiftUI mechanisms for this are broken.** SwiftUI *does* autosave the column width — but under a name it can never read back: the name is `String(describing:)` of the `WindowGroup`'s entire modifier-chain type, in which private types print as `(unknown context at $ADDR)`, a **runtime address**. ASLR moves it every launch, so each drag is written under a brand-new key and nothing ever reads one (a real defaults domain held 49 such keys, 49 distinct addresses, carrying the user's stranded 225/213.5/144… widths — they also accumulate forever). The documented fallback, `navigationSplitViewColumnWidth`'s `ideal:`, is a *preference* and was measured to be ignored outright: with the autosave keys cleared and `ideal: 250`, the column still came up at 144, its content-derived width. So `MainWindow`'s `onGeometryChange` records the width and `WindowAppearance.restoreSidebarWidth` reopens it with `NSSplitView.setPosition(_:ofDividerAt:)` — the same reach-through `PinnedSidebar` makes above, for the same reason.

**The same broken name also made those keys accumulate without bound**, since AppKit's key is literally `NSSplitView Subview Frames <autosaveName>` — a fresh name per launch means a fresh key per launch, forever (9 in one release domain, 65 in a debug one). So `pinSidebarAutosaveName` gives the split view our own stable `autosaveName` and AppKit rewrites one key in place, and `pruneChurnedSidebarAutosaveKeys` sweeps what earlier launches left. The sweep matches on the `(unknown context at $` marker, never on the `NSSplitView Subview Frames ` prefix alone, so stable names — ours and the Settings window's `com_apple_SwiftUI_Settings_window…` — are spared (verified by seeding both kinds and launching: the churned one went, the Settings one stayed). It reads `UserDefaults.standard` against the usual rule because that is the only domain AppKit wrote them to, and is skipped under a test run so a hosted suite can't reach the developer's live domain. Pinning is hygiene only — it does **not** make AppKit's own autosave the restore path, because when AppKit consults it relative to SwiftUI's layout pass is exactly what isn't dependable.

Three things hold the restore together. It reads **`Preferences.launchSidebarWidth`, a frozen copy**, never the live property: the column lays out (and the geometry callback writes its 144 over the stored value) *before* the window is styled, so the live property already says 144 by restore time — the first cut of this fix restored 144 over 144 and looked like a no-op. The one-shot is **consumed as soon as the split view exists, collapsed or not**, because `sync` also runs on every window-became-main and an arm left standing would later snap a width the user had since dragged. And a **collapsed sidebar is left alone** — moving divider 0 on it pops it open on every launch — so a sidebar hidden at launch and shown mid-session gets SwiftUI's own width, and the next launch with it visible restores properly.

## Known Limitations

- **Adaptive TUI background inference depends on Ghostty's current macOS renderer layout** — explicit OSC 11 color changes use the supported callback path, but painted-cell fallback detection reads the surface currently exposed through Ghostty's layer as a BGRA8 IOSurface. Macterm validates that format and fails closed; if Ghostty changes this private renderer detail, OSC 11 continues to work while painted-cell inference remains disabled until updated. That surface is **premultiplied**, and how a painted cell arrives in it depends on the user's `background-opacity-cells`: without it a painted cell is alpha 255, with it `@intFromFloat(255 * background-opacity)` — which Macterm forces to the Settings window opacity. So the detector's alpha floor is derived from that opacity (`minimumPaintedAlpha`) rather than fixed near 255, and the sampled color is un-premultiplied before it means anything. A fixed 230 floor is what made "Adaptive background" silently do nothing for anyone running `background-opacity-cells` below ~0.94: every TUI-painted pixel (opencode's 96%-coverage background, say) landed one or two counts under it and the frame looked empty. Unpainted cells stay exactly alpha 0 in either mode — that is the `background-default-transparent` contract — so the two never blur together no matter where the floor sits. A color detected as translucent also gets **no pane fill**: the renderer already painted it at the window opacity, and backing it with a solid slab would make the pane the one opaque thing in a translucent window. It also gets the window's tinted backdrop **cut out from under it** (`TintCutout`, fed by `AdaptiveTerminalChrome` → `WindowAppearance.updateTerminalPaintRegions`), because the tint and the TUI's cells are then two layers of the same color at the same opacity: the pane composites to `1-(1-opacity)²` — 0.99 against chrome at 0.90, i.e. ten times less wallpaper through the pane than through the sidebar — which is what "the opacity is different between the TUI and the app" looks like. Only the *tint* is cut, never the material or blur behind it, so both surfaces keep one tinted layer over the same backdrop. The inactive-glass overlay is **not** cut and sits *below* the tint, inside the backdrop both surfaces composite over: above the tint it is a layer only the chrome shows at full strength (the terminal's paint covers it), which made an unfocused window's app area read more opaque than its terminal — measured chrome (48,38,76) against grid (52,42,76) — and cutting it instead made that worse. Sampled pixels and OSC 11 colors are also interpreted in the renderer's own color space (`GhosttyColorSpace`, resolved from the user's raw `window-colorspace` text — `ghostty_config_get` returns empty for that enum, the surface layer is an `IOSurfaceLayer` with no `colorspace` property, and its only hint is an undocumented numeric attachment). Reading Display P3 numbers as sRGB shifts the tint by about (-2, +0.5, -2), which is visible exactly where the pane's paint meets the padding; the tint's alpha is likewise quantized the way the renderer truncates it. With all of that, a flat TUI paint and the chrome measure identical. Two consequences shape the implementation. The tint can no longer be `NSWindow.backgroundColor` (AppKit draws it under the whole window and no view can subtract from it) nor `NSGlassEffectView.tintColor` (baked into the material), so both translucency paths now put the tint in a maskable view — `MactermTintBackdropView` for the plain path, a tint layer over *untinted* glass in `MactermGlassView` — and the inactive-glass overlay is cut alongside it, or the mismatch returns the moment the window loses key focus. And the cut has to follow the paint's real edge: the color sampler insets 5% to keep edge artifacts out of the color vote, and cutting to those coarse bounds leaves a ring where cells and tint both paint — a solid frame around the TUI, reported as "the padding area is solid" and independent of `window-padding-color`. So `paintedUnitBounds` judges by **alpha, not color** (any painted cell already carries the opacity, whatever its color) and walks each edge outward pixel by pixel. That also keeps `window-padding-color` meaningful: measured, `background` leaves the padding to the tint while `extend` has ghostty paint it and the cut follows, both single-layer. **The window-wide tint belongs to the window it was sampled from, and the quick terminal is deliberately outside it**: its panes still get their own adaptive fills (`Pane.adaptiveBackgroundColor`), but `refreshPresentation` skips `adoptAdaptiveBackgroundColor` whenever the monitored window is an `NSPanel`, and `WindowAppearance.syncPanel` reads `MactermTheme.nsConfiguredBg` rather than `nsBg`. Without both halves the panel came up wearing the focused tab's TUI background for the frame between order-front and the next sample — which, now monitoring the panel's plain shell, took it away again: the reported flash. The skip is also what freezes the window underneath (tint *and* its paint-region holes, which have to move together) for as long as the panel is up, instead of having it untint the moment the panel takes key. **The sampled frame is a composite, and only provenance separates a TUI's paint from an overlay the *viewer* drew on top of it** — a selection highlight arrives as an ordinary cell background at the same opacity, over the same cells, so no statistic on the pixels (coverage, alpha, geometry) can tell the two apart, which is why dragging across most of a pane used to retint the whole window in the selection color. `AdaptiveTerminalInferenceGate` answers it from outside the frame, with two signals that cover each other's gaps. The **overlay predicate** is exact: `ghostty_surface_has_selection` (via `GhosttyTerminalNSView.hasViewerOverlay`) reports the very state that dirtied the frame, and a frame carrying an overlay is inferred from not at all — the pane *freezes* on its last confirmed presentation rather than clearing, because the screen model behind the highlight did not change, and no verification retry is requested, so a selection held for a minute does not drive a 4 Hz timer for a minute. Any future viewer-drawn overlay belongs beside selection in that predicate rather than as a new filter in the sampler. **Output causality** is the backstop for an overlay with no such predicate: a terminal background only ever changes because the program wrote to the pty, so a confirmed color is protected from any repaint with no output heartbeat within `outputRecencyWindow` (1.5s — a whole 0.12s-plus-retries burst with slack for Metal, and far shorter than any drag a hand can hold). Two asymmetries in that second gate are load-bearing, and both were found by walking the cases rather than by testing: it guards **adoption only, never clearing**, because falling back to the configured theme is always a valid presentation while adopting a color the terminal never painted is not — and gating the clear direction would strand a TUI that exits inside an occluded tab on its dead color, since that exit is only ever observed on the way back, long after its last output; and it never blocks a pane's **first** adoption, since a quiet TUI already on screen when the preference is switched on has no output to point at, which is precisely the opening the exact overlay predicate is there to keep safe. OSC 11 bypasses the gate entirely — it is terminal-native evidence, not an inference from pixels. **Which selection you get depends on the modifier, and only one kind is a viewer overlay at all**: a program holding the mouse (helix, vim, tmux) receives a plain drag as *input* and paints its own selection as ordinary cells — genuinely its output, no terminal selection, `has_selection` false — whereas **shift**+drag is the standard escape hatch from that capture, so it produces a ghostty-native selection and is the case the predicate covers. That is the reported bug (measured under helix: shift+drag, `has_selection` true, candidate `63,61,80` — the selection color the detector was about to adopt — rejected, chrome unmoved). A program-rendered selection is a real residual gap, deliberately left open: closing it needs a pointer-manipulation signal (a drag is a viewer gesture whether the terminal renders it or round-trips it through the program), and the version of that tried here froze inference for a grace period after *every* click — which has to exceed `outputRecencyWindow` to interlock, and therefore also suppresses a background change a user triggers *by* clicking. That cost was not worth paying for a case that could not be shown to change the chrome: helix leaves its background unpainted by default, so there is nothing for the sampler to adopt, and its own selection is bounded by the text rather than filling the frame. If it ever does surface, the frame-intrinsic alternative is worth weighing first — a true background reaches the grid's edges while a program's selection is bounded by content, so requiring the winning color to hold some share of the painted region's border ring would separate them with no timing, no ABI, and no mouse state.
- **Quick-terminal sessions are ephemeral** — they die on quit (workspace panes persist via zmx and reattach on relaunch; local sessions don't survive reboot — the zmx daemon dies with the OS; remote sessions do, theirs doesn't).
- **Remote projects require zmx preinstalled on the host** — auto-detected via PATH (profiles + a fallback dir list); if that fails (network-mounted home, exotic `/bin/sh`, non-POSIX shell config), set the project's `zmxPath` to an absolute path. A missing binary surfaces a `macterm: zmx not found` diagnostic in the pane (not a silent close). No upload/install flow yet.
- **Remote orphan reaping only reaches sessions this installation has stamped** — the sweep kills only zero-client `macterm-*` sessions carrying our own `macterm.owner` label (see Remote Projects), so a session orphaned before it was ever stamped (created and lost between two sweeps, or by a pre-#281 build) is spared forever and stays the user's to `zmx kill`.
- **Single window only** — multi-window would require a tmux-like daemon; out of scope.
- **Not code-signed with a Developer ID** — first launch needs `xattr -cr /Applications/Macterm.app` (or Homebrew install); Sparkle updates verify EdDSA after that. Releases are signed with a stable self-signed certificate, so TCC privacy grants (Documents, Downloads, Full Disk Access, …) persist across updates — under the old ad-hoc signing they reset on every update.
- **Pane IDs not stable across restarts** — fresh views are created on restore.
